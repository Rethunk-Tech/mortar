# Lethal Company: research for the second game

Research for the second `Game` implementation. Sources: Gale (`Kesomannen/gale`), r2modmanPlus (`ebkr/r2modmanPlus`), the Thunderstore server source (`thunderstore-io/Thunderstore`), and BepInEx 5.4.23.5's release zip.

- **Discovery:** Steam app `1966720`. On Linux it runs through Proton.
- **Mod index:** the chunked listing index at `https://thunderstore.io/c/lethal-company/api/v1/package-listing-index/`, fetched in parallel and cached. Never the full v1 package list.
- **Downloads:** `https://thunderstore.io/package/download/{namespace}/{name}/{version}/`, no auth. Dependencies are `Namespace-Name-Version` strings.
- **Loader:** the `BepInEx-BepInExPack` package. Doorstop's `winhttp.dll` and `doorstop_config.ini` must sit next to the game executable, so, as Gale does (`Kesomannen/gale` `src-tauri/src/profile/launch/mod.rs`, `copy_required_files`), launch copies those two files from the profile into the game folder and removes them after. Everything else, the core, plugins, patchers and config, stays in the profile, and packages are copied into the profile, never into the game folder.
- **Launch arguments** depend on the Doorstop version, read from the profile's `.doorstop_version` (default 3): `--doorstop-enable true --doorstop-target <preloader>` for 3.x, `--doorstop-enabled true --doorstop-target-assembly <preloader>` for 4.x.
- **Saves:** `{localLow}/ZeekerssRBLX/Lethal Company/` (inside `compatdata/1966720/pfx` under Proton) holds one file per slot, `LCSaveFile1` to `LCSaveFile3`, and `LCChallengeFile` for the weekly challenge moon, beside `LCGeneralSaveData` (settings), `Player.log` and mods' folders. The save files are encrypted Easy Save 3 data with no mod list, so the Saves tab lists them by slot with an unknown fit.
- **Proton:** the Wine override `winhttp=n,b` is written into `compatdata/1966720/pfx/user.reg`, backed up first, as Gale and r2modman both do. Paths passed to Doorstop use the `Z:` form.
- **Package layout:** follows r2modman's walk (`ebkr/r2modmanPlus` `src/installers/InstallRulePluginInstaller.ts`, `buildInstallForRuleSubtype`), which mod authors build against. The first folder on a file's path named `plugins`, `patchers`, `monomod`, `core` or `config`, at any depth, decides its place and keeps the structure below it: `BepInEx/<dir>/<Namespace-Name>/`, with `config/` flat. A file under no such folder goes by its name alone, a `.mm.dll` to `BepInEx/monomod/<Namespace-Name>/` and anything else to `BepInEx/plugins/<Namespace-Name>/`, so the folders above it are flattened (MirageCore ships `FSharp.Core/FSharp.Core.dll` and Mirage loads it from beside its plugin); when two files land in one place the later in a folder-files-first walk wins, ignoring case. An archive holding two names that differ only in case is refused, where r2modman keeps the later on Windows and both on Linux, for Wine to load either. An archive from another site (Nexus, a file on disk) with no manifest but a DLL or a `BepInEx/` folder installs by the same rules under its store key, as the component `bepinex:<first DLL's name>`, so another file of the same mod replaces it.
- **r2modman profile codes:** import and export them, since that is how Lethal Company players already share. A code is `#r2modman\n` followed by base64 of an `.r2z` zip, which holds `export.r2x` (YAML: `profileName`, `mods[]` with `name`, `version {major,minor,patch}` and `enabled`) and the `config/` folder. Codes are stored with `POST https://thunderstore.io/api/experimental/legacyprofile/create/` and read with `GET .../legacyprofile/get/{key}/`. The endpoint is marked experimental; Gale uses it too.

- **Mod identity:** a Thunderstore package (`Namespace-Name`) is the identity; its `[BepInPlugin]` GUIDs are a per-version secondary key, used to attribute log lines and `BepInEx/config/<guid>.cfg` files. Of 50 Lethal Company packages (the 30 most downloaded plus 20 random, latest versions), 39 hold exactly one plugin, 1 holds three and 10 hold none (asset packs, libraries, patchers); 3 of 24 compared packages changed their GUID between their first and latest version.
- **BepInEx root:** BepInEx 5 takes its root from the preloader it was started with, the grandparent of `BepInEx/core/BepInEx.Preloader.dll` (`BepInEx.Preloader/Entrypoint.cs:61`, `BepInEx/Paths.cs:11-30`, v5-lts `f4c1b110`), so `plugins/`, `config/`, `patchers/`, `cache/` and the log all live in the profile; only the game's `<exe>_Data/Managed` comes from the game folder. Mortar never writes `doorstop_config.ini`: it copies the pack's own file beside `winhttp.dll` and passes the target as launch arguments (`--doorstop-enable true --doorstop-target <preloader>` for Doorstop 3, `--doorstop-enabled true --doorstop-target-assembly <preloader>` for 4, read from `.doorstop_version`; a launch without mods passes `false`). The `winhttp.dll` proxy reads `doorstop_config.ini` from the working directory and the `--doorstop-*` arguments override it; under Proton the target path takes the `Z:` form. The game folder gets only `winhttp.dll` and `doorstop_config.ini`, as Gale copies them (`Kesomannen/gale` `src-tauri/src/profile/launch/mod.rs:183-224`).
- **BepInEx.cfg:** both packs the matrix runs, `BepInEx-BepInExPack` 5.4.2100 and 5.4.2305, ship `HideManagerGameObject = false` (the BepInEx default); Mortar keeps the pack's file on pin and reinstall and only edits `[Logging.Console] Enabled` and `LogLevels` (`internal/loader/bepinex5/logging.go`). Chainloader makes `BepInEx_Manager` with `DontDestroyOnLoad` in 5.4.21 and 5.4.23.5 alike (`BepInEx/Bootstrap/Chainloader.cs` 296-300 and 302-306) and hides it only when that setting is true, so the setting does not tell the two loaders apart.
- **Load order:** the Load order tab lists plugins, not packages, in chainloader order (`internal/dotnet/order.go`). BepInEx 5.4.23 keeps the newest copy of each GUID, puts the GUIDs in a `SortedDictionary` with `StringComparer.InvariantCultureIgnoreCase`, and runs `Utility.TopologicalSort` over them: a depth-first walk that places each plugin's hard and soft dependencies first, in attribute order (`BepInEx/Bootstrap/Chainloader.cs` 312-366, `BepInEx/Utility.cs` 135-180). So the tie-break is the caseless GUID order, never the plugin name or the package; a cycle makes the sort throw and no plugin loads. The prediction matched all 77 `Loading [` lines of a 79-plugin matrix run (`TestRealBepInExRun`). Where the profile's last `LogOutput.log` loaded plugins in another order, the tab shows that order for them and marks the rows that moved.
- **Game version:** the menu shows `v{GameNetworkManager.Instance.gameVersionNum}` (`MenuManager`; the field's default is 1, the prefab sets the real number, which is also the network protocol version and the lobby's `vers`). Unity's `Application.version` is the project's unset `bundleVersion`, `0.1` in `globalgamemanagers`, so the BepInEx bridge reports `gameVersionNum` in that form instead (`mortar-bepinex-bridge` `GameVersion.cs`). A mod may append to the menu text, as `v81 (MC)` does. MoreCompany's `GameNetworkManager.Awake` postfix adds 9950 to the field (without LC_API) to keep its lobbies apart, so the bridge takes the value in an `Awake` prefix, before any postfix, and reports `v81`, not `v10031`.
- **Startup and intro** (read from the game's `Assembly-CSharp`): the first scene, `InitSceneLaunchOptions` (`PreInitSceneScript`), waits for a click on Online or LAN on every start; `IngamePlayerSettings` loads its settings half a second in and, once `PlayerFinishedSetup` is saved in `LCGeneralSaveData`, skips the first-run panels straight to that choice. `InitScene` or `InitSceneLANMode` (`InitializeGame`) then plays a boot animation of about 3.4 s before `MainMenu`, or instead a cold-open cinematic: `ColdOpen1` when the last version played is before v50 (a first start included) or on the seventh start, and `ColdOpen2` once, after the 25th start or when the last version played is before v60. The game reads no command-line argument but Doorstop's, and the choice and the cinematics live in Easy Save 3's encrypted `LCGeneralSaveData`, so no launch option or registry key skips them. A sandbox or regress launch has `MORTAR_SKIP_INTRO=1` in the game's environment, set by the sandbox's launch guard (`scripts/launch-guard.sh`), which only direct launches pass through; the BepInEx bridge then picks LAN after 2 s, clears `InitializeGame`'s boot and cold-open flags between its `Awake` and `Start`, and the game reaches `MainMenu` with no input. Without the variable the bridge changes nothing (`mortar-bepinex-bridge` `IntroSkip.cs`).
- **Unmeasured:** a real Windows run confirming the command-line target wins over a stale ini, and profile paths with spaces or non-ASCII characters (BepInEx flags `Assembly.LoadFile` issues on some Mono builds, `Entrypoint.cs:94,142`).
