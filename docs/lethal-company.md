# Lethal Company: research

Sources: Gale (`Kesomannen/gale`), r2modmanPlus (`ebkr/r2modmanPlus`), the Thunderstore server source (`thunderstore-io/Thunderstore`), BepInEx 5.4.23.5's release zip. The catalog (`internal/components/components.json`) holds the game's wiring; this file holds what it rests on.

- **Discovery:** Steam app `1966720`; Proton on Linux.
- **Mod index:** the chunked listing index `https://thunderstore.io/c/lethal-company/api/v1/package-listing-index/`, fetched in parallel and cached; never the full v1 package list.
- **Downloads:** `https://thunderstore.io/package/download/{namespace}/{name}/{version}/`, no auth. Dependencies are `Namespace-Name-Version` strings.
- **Loader:** the `BepInEx-BepInExPack` package. Doorstop's `winhttp.dll` and `doorstop_config.ini` must sit next to the game executable, so launch copies those two files from the profile into the game folder and removes them after, as Gale does (`Kesomannen/gale` `src-tauri/src/profile/launch/mod.rs:183-224`, `copy_required_files`). Everything else (core, plugins, patchers, config) stays in the profile; packages are copied into the profile, never the game folder.
- **BepInEx root:** BepInEx 5 takes its root from the preloader it started with, the grandparent of `BepInEx/core/BepInEx.Preloader.dll` (`BepInEx.Preloader/Entrypoint.cs:61`, `BepInEx/Paths.cs:11-30`, v5-lts `f4c1b110`), so `plugins/`, `config/`, `patchers/`, `cache/` and the log live in the profile; only `<exe>_Data/Managed` comes from the game folder.
- **Launch arguments** by Doorstop version, read from the profile's `.doorstop_version` (default 3): `--doorstop-enable true --doorstop-target <preloader>` for 3.x, `--doorstop-enabled true --doorstop-target-assembly <preloader>` for 4.x (`false` for a launch without mods). Mortar never writes `doorstop_config.ini`: it copies the pack's own file, and the `--doorstop-*` arguments override what the `winhttp.dll` proxy reads from the working directory. Under Proton the target path takes the `Z:` form.
- **Proton:** the Wine override `winhttp=n,b` is written into `compatdata/1966720/pfx/user.reg`, backed up first, as Gale and r2modman do.
- **Saves:** `{localLow}/ZeekerssRBLX/Lethal Company/` (under `compatdata/1966720/pfx` on Proton) holds `LCSaveFile1` to `LCSaveFile3`, `LCChallengeFile` (weekly challenge moon), `LCGeneralSaveData` (settings), `Player.log` and mods' folders. Saves are encrypted Easy Save 3 data with no mod list, so the Saves tab lists them by slot with an unknown fit. Easy Save 3 (`Assembly-CSharp-firstpass.dll`) writes `.bac`, `.tmp` and `.tmp.bak` companions beside a slot; the catalog keeps them out of the list. A slot above 3 comes from a save-slot mod.
- **Package layout** follows r2modman's walk (`ebkr/r2modmanPlus` `src/installers/InstallRulePluginInstaller.ts`, `buildInstallForRuleSubtype`), which mod authors build against:
  - The first folder on a file's path named `plugins`, `patchers`, `monomod`, `core` or `config`, at any depth, decides its place and keeps the structure below it: `BepInEx/<dir>/<Namespace-Name>/`, `config/` flat.
  - A file under no such folder goes by its name alone: `.mm.dll` to `BepInEx/monomod/<Namespace-Name>/`, anything else to `BepInEx/plugins/<Namespace-Name>/`. The folders above it are flattened (MirageCore ships `FSharp.Core/FSharp.Core.dll` and Mirage loads it from beside its plugin).
  - Two files landing in one place: the later in a folder-files-first walk wins, ignoring case. An archive with two names differing only in case is refused (r2modman keeps the later on Windows and both on Linux).
  - An archive from another site with no manifest but a DLL or `BepInEx/` folder installs by the same rules under its store key as component `bepinex:<first DLL's name>`, so another file of the same mod replaces it.
- **r2modman profile codes** are imported and exported, since that is how players share. A code is `#r2modman\n` plus base64 of an `.r2z` zip holding `export.r2x` (YAML: `profileName`, `mods[]` with `name`, `version {major,minor,patch}`, `enabled`) and `config/`. Stored with `POST https://thunderstore.io/api/experimental/legacyprofile/create/`, read with `GET .../legacyprofile/get/{key}/`; the endpoint is experimental and Gale uses it too.
- **Mod identity:** the Thunderstore package (`Namespace-Name`); its `[BepInPlugin]` GUIDs are a per-version secondary key that attributes log lines and `BepInEx/config/<guid>.cfg` files. A package can hold one plugin, several or none (asset packs, libraries, patchers), and a plugin's GUID can change between versions.
- **BepInEx.cfg:** the matrix's packs, `BepInEx-BepInExPack` 5.4.2100 and 5.4.2305, ship `HideManagerGameObject = false`. Mortar keeps the pack's file on pin and reinstall and edits only `[Logging.Console] Enabled` and `LogLevels` (`internal/loader/bepinex5/logging.go`). Chainloader makes `BepInEx_Manager` with `DontDestroyOnLoad` in 5.4.21 and 5.4.23.5 alike (`BepInEx/Bootstrap/Chainloader.cs` 296-306) and hides it only when that setting is true, so the setting does not distinguish the two loaders.
- **Load order:** the Load order tab lists plugins in chainloader order (`internal/dotnet/order.go`). BepInEx 5.4.23 keeps the newest copy of each GUID, sorts GUIDs in a `SortedDictionary` with `StringComparer.InvariantCultureIgnoreCase`, then `Utility.TopologicalSort` (depth-first, hard and soft dependencies first, in attribute order; `BepInEx/Bootstrap/Chainloader.cs` 312-366, `BepInEx/Utility.cs` 135-180). The tie-break is the caseless GUID order, never plugin name or package; a cycle makes the sort throw and no plugin loads. `TestRealBepInExRun` checks the prediction against a real run's `Loading [` lines; when the last `LogOutput.log` differs, the tab shows the logged order and marks moved rows.
- **Game version:** the menu shows `v{GameNetworkManager.Instance.gameVersionNum}` (`MenuManager`; the prefab sets the number, which is also the network protocol version and the lobby's `vers`). Unity's `Application.version` is the unset `bundleVersion`, `0.1`, so the bridge reports `gameVersionNum` (`mortar-bepinex-bridge` `GameVersion.cs`). MoreCompany's `GameNetworkManager.Awake` postfix adds 9950 to keep its lobbies apart, so the bridge reads the value in an `Awake` prefix and reports `v81`, not `v10031`.
- **Startup and intro** (from the game's `Assembly-CSharp`): `InitSceneLaunchOptions` waits for a click on Online or LAN on every start (`IngamePlayerSettings` skips the first-run panels once `PlayerFinishedSetup` is saved in `LCGeneralSaveData`). `InitializeGame` then plays a boot animation of about 3.4 s before `MainMenu`, or a cold-open cinematic: `ColdOpen1` when the last version played is before v50 (a first start included) or on the seventh start, `ColdOpen2` once, after the 25th start or when the last version played is before v60. The game reads no command-line argument but Doorstop's, and the choice and cinematics live in encrypted `LCGeneralSaveData`, so no launch option or registry key skips them. With `MORTAR_SKIP_INTRO=1` (set by `scripts/launch-guard.sh`, direct launches only) the bridge picks LAN after 2 s and clears the boot and cold-open flags between `InitializeGame`'s `Awake` and `Start` (`mortar-bepinex-bridge` `IntroSkip.cs`); without it the bridge changes nothing.
- **Unmeasured:** a real Windows run confirming the command-line target beats a stale ini, and profile paths with spaces or non-ASCII characters (BepInEx flags `Assembly.LoadFile` issues on some Mono builds, `Entrypoint.cs:94,142`).
