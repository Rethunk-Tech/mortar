# Mortar architecture

How Mortar works: storage, profile semantics, the game catalog and its registries, and the Nexus and wire-format facts that settle questions. Per-game facts (Stardew Valley, SMAPI, Content Patcher) are in [games.md](games.md). Decided work not yet built is in [design.md](design.md), screens in [gui-design.md](gui-design.md), standing rules in [AGENTS.md](../AGENTS.md), threat model and guards in [security.md](security.md), packaging in [release.md](release.md). Behaviour the code and its tests state is named here by owning symbol, not narrated.

## Product

Mortar finds a game, installs its mod loader, keeps each set of mods in its own profile, and launches the game with the chosen profile. Windows and Linux only (fleet CI has no macOS runners, and Wails does not cross-compile to it). Licence: AGPL-3.0-only. The signed catalog lists every game ([Games and the catalog](#games-and-the-catalog)); a game's `enabled` flag makes it selectable.

**External profile import** (Profiles › Import…) reads r2modman, Gale, Stardrop (Stardew Valley only), Vortex and Mod Organizer 2 from their default data (`packsvc.LocalProfiles`, `migrate.Detect`). Vortex and MO2 take the game's names from its catalog `importIds`. Present folders are copied into the store; missing Nexus mods go through the share-import resolver and download queue.

## Stack

- **Wails v3**, pinned in `go.mod` ([AGENTS.md](../AGENTS.md)). React, TypeScript, MUI and Lingui on Vite; typed bindings from `wails3 generate bindings` into `frontend/bindings`; client state in zustand.
- **Go services:** each backend area the UI calls is one Wails service whose exported methods are bound to TypeScript. Methods only Go calls carry a `//wails:ignore` doc directive.
- **Window:** solid and frameless with the app's own title bar unless `systemTitleBar` is on. Trap: dragging works only once the Wails runtime is loaded (`@wailsio/runtime` or `/wails/runtime.js`).
- **Session-only state:** the toast history and the Console's command history live in memory; a toast's Undo, Redo, Show or Retry works only while that change is still the latest for the same mods.

## Storage

Everything lives in the user data folder, `%LOCALAPPDATA%\Mortar` or `$XDG_DATA_HOME/mortar`, never under the Windows install folder (the uninstaller deletes that recursively). State is JSON written through a temp file and rename (`safefs.WriteFileAtomic`/`WriteStreamAtomic` from [go-safefs](https://github.com/Rethunk-Tech/go-safefs), and `datadir.WriteJSON`; `TestFilesAreCreatedOnlyThroughDatadirOrSafefs`); no database. The Nexus key is in the OS keyring.

- **Move** (Settings › Storage): `datasvc.Measure` probes free space with a real clone or link because FAT, exFAT and SMB count every name. It never follows symlinked folders, junctions or mount points, and is refused while the game runs.
- **Portable mode:** a `portable` file beside the executable (symlinks resolved) puts data at `<exe dir>/data`, ignores `data-location` and refuses Move. The marker is ignored inside a Flatpak and an AppImage mount; one beside an executable in an unwritable folder stops the start with `datadir.PortableError`. A portable copy has its own single-instance id (hash of its data folder).
- **Missing data folder:** a `data-location` naming a missing folder (unplugged drive) is never created; on Windows a message box offers the default location, a folder picker or quit. Every startup failure is appended to `startup.log` in the default folder.

Layout (shapes: the named package):

- `store/`: each downloaded archive extracted once, content-addressed. `blobs/<sha256>/` holds the extracted files (`.complete` marks a finished extract, written to a temp folder and renamed; `mortar-root` names the subfolder that is the mod), `loaders/<game>/<loader>/<version>/` a loader's bundle, and `index.json` maps (game, key) to the blob plus source, package, version and last use. Keys: `nexus-<mod id>-<file id>` (a Nexus file can hold several SMAPI mods, so the key is the file), `github-<owner>-<repo>-<tag>-<asset>-<hash>`, `pkg-<hash of name and version>` (Thunderstore), `local-<sha256 of the archive>`, `<loader id>-<version>`, `bridge-<version>-<hash>`.
- `profiles/<game>/<profile id>/`: `profile.json` and `mods/` (the folder SMAPI is pointed at). Each entry is copied to `mods/<store key>/`, or only its `mortar-root` subtree; further files from the same Nexus page join as `extraStoreKeys` under `mods/<entry key>/<extra store key>/`, and Update, Roll back and Remove cover every store item on the entry. `runs/` keeps the newest `runsKept` launches; `saves/` is the profile's own Saves folder when `separateSaves` is on.
  - **Mod-folder picker:** an archive with a `manifest.json` SMAPI would not find, or one UniqueID in several folders, asks the user for the folder that is the mod; an update reuses the same-named variant.
  - **FOMOD** detection runs first. The resolved files are copied instead of the raw extraction and the chosen plugin names stored on the entry as `fomod`; Update and Roll back replay them (`internal/profile/fomod.go`) and ask again when a choice no longer exists or an update adds an unanswered group (`internal/fomod/resolve.go` `Unanswered`).
- `backups/<game>/`: zips of the Saves folder, never listed or restored for another game. Kinds, rotation (`saveBackupsKept`, `saveBackupKeep`) and the sibling `<stamp>.json` record are in `internal/backup`. A save is a folder holding a file of its own name or, with catalog `saveFiles` patterns, matching files plus `saveCompanions` sharing their stem (`saveUserFolders`: inside each subfolder).
- `downloads/<item id>.<ext>` with a `.resume.json` sidecar; `<game>/last-played.json`; `tools/<game>.json` (`arguments` is a JSON array, never a shell string, launched through `os/exec` without a shell); `queue.json` holds no `nxm://` keys.

### Optional files

`internal/profile/overlay.go`, `overlayset.go`. A Nexus file with no `manifest.json` and no installer (an "Optional" file that swaps some files of the main one) is an overlay of the profile's entry from the same mod: its own store item and `profile.json` entry with `overlayOf` naming the main entry's key. Without a main entry it is refused (`NoBaseError`). Placement, first match wins: a single top folder named like one of the main entry's mod folders; else the layout under which most files already exist in the main entry; else Mortar asks (`RemapAsk.overlay`) and stores `overlayFrom`/`overlayTo`.

Invariant: overlays are laid over the main folder in entry order (later wins) through `datadir.MaterializeFile`, so no store item is ever written. Switching one off restores the main entry's own file for every path it covered and deletes paths only it brought. Updating or rolling back the main entry takes overlays off first (so carry-over never sees them as user edits) and lays them over the new folder.

### `profile.json`

Fields and caps: `internal/profile` (`Profile`, `Entry`). Rules not obvious from the structs:

- `overrides` holds profile-overridable game prefs; `settings.ResolveAt` uses the profile value, else the key's own scope, else the registry default.
- `install` and `loader` name the game install and loader the profile runs (empty means the game's selected install and primary loader). `launchEnv` and `launchPrefix` apply to direct launches only.
- `groups` are named sets of entry keys that enable and disable together. A name is a `/` path, so nesting is only in the name: a share's `grp` and a saved group see a plain group of that name, and a parent needs no group of its own.
- `intentSince`, `intentOffered`: install reasons and whether the player answered the one-time offer to classify older entries (a content pack stays explicit even when required: `InferImplicit`).
- `key` is the store item in use; for an entry cut from a folder game's archive `<item>#<path>` with `item` and `file`. Mods in an entry are components with `id` `<format>:<local>` (e.g. `smapi:Pathoschild.ContentPatcher`).
- `previousKey`/`previousSource`/`previousExtraStoreKeys` are the Roll back copy.
- `implicit`: Mortar brought the entry in for another mod; absent means the player asked. Set at creation, copied by every path that copies an entry, changed only by Mark explicit/implicit; loader and bridge entries are always implicit. In an entry with several mods the main mod is the base the others build on.

The store keeps every item a profile names as `key` or `previousKey` and deletes the rest 30 days after last use. `ProfilesWithMod` reads `profile.json` files, not the store. The hero cover is `internal/profile/cover.go`.

## Settings file

`settings.json` has a `formatVersion` and three blocks: `global`, `sources` (per mod source id) and `games` (per game id). A key is read at the most specific scope that sets it (source, game, install, loader, profile), then broader ones, then its default (`internal/settings/scope.go`). A missing or unparseable file gives the defaults; an invalid value is replaced by the default on load and refused on write.

Each key's meaning, scope, type, default and allowed values are defined once, in code: field comments on `Settings` (`internal/settings/settings.go`) and the registry (`internal/settings/registry.go`). `mortar settings get` lists every key with its value.

**Export and import:** Settings › General › Settings file writes the fields in `portableFields` (`internal/settings/portable.go`); import (`internal/settings/import.go`) refuses any other version and applies only after a preview. Account and machine state is never exported (`TestPortableFieldsNameNoAccountOrMachineState`); the keyring is never read.

**Clean-up** (`internal/datasvc`): Clean up… previews, then deletes exactly the listed items; its keep set is `datasvc.KeepSet`, the set the startup 30-day sweep also builds.

### Store integrity

Installing an item records the SHA-256 and size of every file beside the store (`.manifests/<game>/<key>.json`), so hashes are never copied into a profile. `store.Verify` reports files missing, changed or extra. An item with no record is baselined by its first verification, which cannot see earlier damage; for a signed-in Nexus item, verification first looks in the downloads folder for an archive whose MD5 equals Nexus's, and that becomes the baseline. `storecheck.Run` verifies items not checked in 7 days, only while idle (no game, download or install). Repair sets a damaged item aside and re-obtains it from its recorded source; the damaged copy is put back if the queue refuses.

## Profile operations

**Materialising store items into a profile** (install, duplicate, rebuild, update) is per file, in order, falling through on `EXDEV`/`EOPNOTSUPP`/`EINVAL`/`ERROR_INVALID_FUNCTION`: copy-on-write clone, hardlink, symlink, copy (go-safefs's `Materializer`). Which files may share an inode is Mortar's policy (`internal/datadir/materialize.go`): files a mod may write (`config.json`, `data/` and saves-like folders, `*.mortar-old`, editor-openable text files) use clone or copy only: SMAPI's `helper.Data.WriteJsonFile` truncates in place, so a link would leak one profile's write into the store and every other profile (`TestConfigJSONNeverHardlinkedOrSymlinked`). Drift ignores those paths. Duplicate never hardlinks or symlinks `mods/`. Deleting a profile unlinks its names and never removes store files.

Each operation is a method of `internal/profile` `Store` or a named service; the tests state the edge cases. Traps:

- **Toggle** renames the mod's folder with a leading dot (SMAPI skips it) and records it in `disabled`. **Dot-hidden mods:** a dot-prefixed folder inside an entry that Mortar did not add hides every mod under it from SMAPI (`showDotHiddenMods`, `UnhideMod`).
- **Profile folder** (`folder.go`): `MoveToFolder` replaces the profile's usual folder with a symlink (a junction on Windows), so every path built from the profile id still resolves. `Purge` and `PurgeTrash` refuse a symlink.
- **Damaged profile:** an unreadable `profile.json` is listed by `ListDamaged` and skipped by `List`; `StoreKeys` fails while one exists, so no store collection runs. `mortar profile repair` rebuilds it from the latest readable history snapshot and renames the broken file to `profile.json.damaged-<timestamp>`.
- **Import and Move from the game's Mods folder** (`import.go`, `gamemods.go`) exists only for a loader with `loader.ManifestMods` (SMAPI's). A symlink-deploying manager (Vortex) imports as the files the links point to (`datadir.CopyTreeResolvingLinks`), while the store otherwise refuses links that leave a folder. Move deletes by renaming aside first and is refused while any game process is up.
- **Extra mods folders** (`extraModsFolder`) are listed by the game's loader (`installer.TakesPackages` for Thunderstore games). `InstallExtraFolderMod` never writes the folder; the entry's `Source.Folder` makes the next install from it replace that entry even when the mod's id changed.
- **Outside edits** (`drift.go`): `mods-snapshot.json` fingerprints each entry folder; a first scan with no snapshot records the tree and reports nothing.
- **Compare:** Match versions runs through `UpdateEntries` as one atomic change.
- **Saved groups and templates** (`internal/savedgroups`, `internal/templates/apply.go`): `ApplyTemplate` never removes the profile's own mods, takes `profile.Store.Baseline` first and returns an `Undo`.
- **Back up and restore a file** (`internal/packsvc/backup.go`): restore makes a new profile via `UniqueName`, never overwriting, and takes a store item only when its hash matches `backup.json`.
- **Typed config editing** (`internal/configsvc`): `.cfg` `Set` rewrites only that entry's line; `config.json` keeps key order, types and unknown fields and refuses a path that leaves the mod folder. Every write fails while the profile's game launches or runs.
- **Pin and skip:** a pinned entry is offered no update; `skipVersion` hides that exact newer version until a later one appears.
- **Update checks** (`internal/control/updates_apply.go`, `internal/profile/service_update.go`): SMAPI's API is asked 100 mods per request; Nexus GraphQL v2 gives file lists for the mods it flags (signed in only). An update is real when a newer non-archived file with the same display name exists or the installed file's version is below SMAPI's; an unbumped manifest inside the newest file is not offered.
- **Change history** (`internal/profile/history.go`): name, notes, colour, cover and profile order are not history. Revert rolls `config.json` back only when every event since the target is a config edit. Invariant: every profile mutation records an event and undoes exactly (`TestEveryProfileChangeRecordsAnEventAndUndoesExactly`).
- **Update or roll back** (`internal/profile/update.go`): the target is copied into a fresh folder, then what the mod or user wrote is carried over by three-way comparison of each file (profile, store copy of the current version, target). A file the profile changed that the target also changed: the target wins and the profile's copy is kept as `<name>.mortar-old`. A file the target drops follows `oldFilesOnUpdate`. The Saves folder is zipped into `backups/` first.
- **Update channel:** an entry's `updateChannel` (main files only, `optional`, `beta`) filters offers; GitHub reads `beta` as prereleases (`github.Select`), CurseForge and Modrinth read the three as release, release and beta, and release, beta and alpha (`source.Stability`).

## Command line

Mortar is GUI-first: the CLI exposes only what the window can already do, and a new capability lands in the window first. Verbs: [HUMANS.md](../HUMANS.md#command-line).

- `mortar <verb>` (`internal/cli`) is decided in `main` before `application.New`, so it never takes the single-instance lock or opens a window; any other first argument, a link, a file path or `--play=<game>/<profile>` is a window launch. Under `--json` a failure is `{error, kind, code}` on stderr plus `detail` when the app sent one.
- **Play mode** (`--play=<game>/<profile> --steam-session`: an Add to Steam shortcut while Mortar is closed): the window starts hidden and renders only the launch layer; a blocking pre-Play check shows the window holding only that dialog. `main` quits once the played game has been Running and is Idle again, so Steam counts playtime from Mortar's own process. If a Mortar already answers on the control channel, the start sends `play.request` over it and `shortcut.Follow` waits for the game.
- **Control channel** (`internal/control`; the CLI is a client of the running app): loopback on an OS-chosen port, with `control.json` (`port`, random `token`, `pid`, `version`, `protocol`; 0600) in the data folder, removed on exit only while still that instance's file. Methods run on the app's own services, so window and CLI never write the data folder at once. The CLI calls `hello` first and fails on a `controlwire.Protocol` mismatch; a start finding another Mortar answering `hello` waits five seconds for it to exit, then stops before it touches data. A server build refuses to start on the account's own data unless `MORTAR_SERVER_REAL_DATA=1`; the desktop app opens no HTTP port.

## Failure behaviour

Once mods are installed, nothing external is needed to open, edit or launch a profile. Failures reaching the user are classified in `internal/usererr`. Go wraps the cause as `[kind] message`; the window (`errorMessage` in `frontend/src/toasts/report.ts`) and the CLI (`Sentence` in `internal/cli`) map the kind to the same English sentence (`TestSentenceMatchesGUIForEveryKind`), with the cause in a Details tooltip or under `--json`/`-v`.

- **A mod source unreachable:** `internal/netstate` records per source whether its last real request hit a network error; a bad answer leaves state alone. A banner names each unreachable source and disables network actions needing one. Trap: SMAPI's API or the dataset unreachable degrades and never blocks: update checks show "unknown", dependencies are checked after download.
- **Archive formats** (`internal/archive`, a thin face on the [go-archive](https://github.com/Rethunk-Tech/go-archive) module, which holds every reader and its caps): found by magic bytes, never extension (the module's `Extensions` are only what pickers, drop and the downloads watcher accept). A compressed stream whose payload has a `ustar` header is read as a tar; any other is one file named from the archive's name minus its suffix, queued as `<id>~~<original name>` (`archive.SavedName`), and the facade cuts the `<id>~~` off before the module names the file. Mortar adds the file opening and the preview and manifest reading the UI needs; packs and `.mortar` files are read in memory through `archive.ZipFunc` (the module's `ExtractFunc`, zips only), and LAN store items through the module's `ExtractReader`; the Windows name check is the module's own `WindowsSegment`, which `winname.Valid` also delegates to.
- **Lenient JSON** (SMAPI manifests, Content Patcher content and config files, mod `config.json`): read through the [go-lenientjson](https://github.com/Rethunk-Tech/go-lenientjson) module's `Clean`, which rewrites what Json.NET accepts into strict JSON for `encoding/json` and keeps every newline, so a parse error's line is the file's.
- **Versions** (mod updates, dependency checks, BepInEx load order): ordered by the [go-semverish](https://github.com/Rethunk-Tech/go-semverish) module, SMAPI's rules for mod versions and .NET `System.Version`'s for BepInEx plugins; Mortar keeps only `Newer` and `NewerFile` (`meta/version.go`) and the Thunderstore `d.d.d` check (`deps/scheme.go`).
- **Caches** (GitHub releases and notes, Nexus mod pages, SMAPI, the catalog): JSON files through go-safefs's `diskcache`. A cache whose shape changes takes a new file name (`-v2`) and a `meta.Retired` rule that Clean up applies, rather than migrating on read: an older build reading a reshaped file under its old name would trust it, and a cache costs only a refetch, so caches sit outside the Brownfield rule.
- **HTTP** (every client): [go-httpkit](https://github.com/Rethunk-Tech/go-httpkit). A capped 200 fetch goes through `httpkit.DoCapped`, whose non-2xx answer is a `*httpkit.StatusError` that `usererr.classify` kinds by status: 404 NotFound, 429 and any `*httpkit.RateLimitError` RateLimited, 5xx Network (which the queue retries), any other status Unknown, because a refusal is never retried. Source drivers keep `source.DoJSON` and `source.StatusError`, whose message names the site. `github.RateLimitError` and `nexus.RateLimitError` keep Mortar's wording and unwrap to `*httpkit.RateLimitError`; the queue holds the item's own `sourceKey` for either. `main.go` wraps `http.DefaultTransport` in `httpkit.Transport` for the User-Agent before any client is built, so code that clones the default transport unwraps `Base` first (`queue.downloadTransport`).
- **Credentials** (`internal/secret`, a facade on [go-keyring](https://github.com/Rethunk-Tech/go-keyring)): the facade fixes the service, seal info and folder that every 0.3.8+ build wrote, and maps the module's errors onto `usererr` kinds.
- **Assemblies** (`internal/dotnet`, a facade on [go-dotnet](https://github.com/Rethunk-Tech/go-dotnet)): the module reads metadata, IL and PDBs; BepInEx load order and `Loadable` (`dir.go`, `order.go`) stay in Mortar.
- **A download cut off or corrupt:** extraction goes to a temp folder on the store's volume and moves in only when every entry passed its checksum; failure deletes the temp folder and the item can be retried. Disk full fails the same way and says how much space the item needs.
- **Mortar quits mid-operation:** every write is temp-then-rename and startup removes leftover temp folders; a deleted `mods/` folder is rebuilt from the store. What startup repaired itself is collected by `internal/tidy` and shown as one info notification.

## Resource limits and tests

Go's soft memory limit (`memlimit.go`; `GOMEMLIMIT` wins) is a collector target, not a cap: a lower limit costs far more GC CPU on large installs. Installs run one at a time. The budget is `scripts/mem-budget.sh`.

Go tests replay recorded Nexus, SMAPI API and dataset responses from local HTTP servers ([testing.md](testing.md)); recordings are scrubbed of account fields before commit. Tests must set `XDG_DATA_HOME` (or `LOCALAPPDATA`) under `os.TempDir()`; `datadir.Dir` refuses any other location while `testing.Testing()` is true.

## Games and the catalog

Everything that can be data is catalog data; code exists only where behaviour differs, as a driver found through a registry. Adding to each registry: [HUMANS.md](../HUMANS.md#adding-a-game). Each registry below is a package under `internal/`; its driver list, capability interfaces and per-driver tests are in the package.

- **Catalog:** `internal/components` holds `GameInfo` entries in the signed component manifest (`GameInfo.Validate` guards the shape; `TestEveryCatalogReferenceResolves` checks every reference resolves). `game.Catalog()` returns the verified manifest's games when it lists any, else the bundled ones. Optional blocks an older Mortar ignores: `graphics` and `knownBroken`.
- **Custom games** (`internal/customgame`, `components.SetUserGames`): Add a game… saves a name, the executable and one of five loaders (`BepInEx5`, `BepInEx6`, `MelonLoader`, `Shimloader`, `Folder`) in `custom-games.json`. Each becomes a `GameInfo` shaped like a shipped game of that loader (`ValidateUser`), id `custom-<slug>`, answered after the signed catalog's and never shadowing it. The entry is never uploaded or synced and adds no setting: every per-game setting applies as for a shipped game on the same loader.
- **Stores** (`internal/gamestore`): one driver per store key in the catalog's `stores`, run only for games naming its key. A user-chosen folder wins over discovery; a `manualFolder` game names no store.
- **Installs and runtime** (`internal/game/install.go`, `internal/runtime`): an install is a store and a folder with a stable id, a platform (an `.exe` marker is a Windows build) and a runtime:

  | Runtime | Claims | Path template resolves in | Start |
  | --- | --- | --- | --- |
  | `native` | native builds | the host's folders | direct |
  | `proton` | a Steam Windows build on Linux | its `compatdata` prefix | Steam |
  | `wine-prefix` | a Windows build in a Bottles bottle | the bottle's `drive_c/users/<user>` | `bottles-cli run` |
  | `launcher-prefix` | a Windows build in the prefix its own launcher (Heroic, Lutris) keeps | that prefix | `heroic://launch` or `lutris lutris:rungame/<slug>` when the plan needs only DLL overrides, else direct |
  | `mortar-proton` | any other Windows build on Linux | a prefix Mortar keeps per game, `<data>/prefixes/<game>/pfx` | `<proton>/proton waitforexitandrun <exe>` with `STEAM_COMPAT_DATA_PATH` and `STEAM_COMPAT_CLIENT_INSTALL_PATH`, as Heroic and Lutris start Proton outside Steam |

  `runtime.FindProton` picks the build; Flatpak Steam's builds need its runtime and are excluded. A plan's `dll-override` requirements reach the prefix as `WINEDLLOVERRIDES` for a direct start and as a `user.reg` edit (`wineoverride.Ensure`) for a start a launcher relays, so the first start, before the prefix exists, loads them.
- **Sources** (`internal/source`): a driver registers itself (`source/all`) and implements `Source` plus optional capabilities by type assertion (`Searcher`, `Categorizer`, `Gated`, `Sorter`, `ItemLister`). A `Gated` source says through `Unavailable()` what the user must set up first; an `all` search leaves it out.
- **Browse** (`internal/browse`): `all` sorted by downloads or update date is one ranked list across sources; a source that cannot sort that way is left out and named in `Unsorted`; best match interleaves each source's page, since scores do not compare across sites. Only all sources failing is an error. Hits of one mod from different sources fold into one card on package identity, an explicit link, or the same name by the same author (`mergeSame`; the catalog's `authors` aliases count). A name alone never merges: a hit sharing its name with a better-downloaded hit by another author is marked `reuploadOf` instead.
- **Thunderstore** (`internal/source/thunderstore`): `Closure` treats a pinned dependency version as a minimum and installs the newest, as r2modman does, unless a root names an exact version or per-game `dependencyVersions` asks for the author's pin, as Gale does. Deprecated packages are not searchable but still resolve as dependencies; managers a community lists as packages (r2modman, Gale) never install as dependencies.
- **Gated sources** (`modrinth`, `curseforge`, `itch`) install through the queue's direct path (`queue.ResolveDirect`): each project resolves once, at most 16 deep; a `sha512:` digest is verified after download. CurseForge: Mortar's own API key goes in `x-api-key` (`-X .../internal/source/curseforge.apiKey=...` at release build, else `MORTAR_CURSEFORGE_KEY`), never in an address or log; a file's version is its display name; the `sha1:` digest is not verified because the lint bans weak hashes; an author who forbids distribution gives `NotDistributableError` and the queue opens the mod's page. itch.io: the player's own key goes in `Authorization`, is kept in the OS keyring under `itch`, and settings keep only the account name.
- **Handoff sources** (Patreon, itch.io page): no search, download or update check; the player saves the file from the site and the Downloads watcher adds it (`archivesvc.InstallHandoffDownload`). Patreon has no API for a post's files and its terms bar automated access.
- **Loaders** (`internal/loader`): a driver registers by id and implements `Loader` (`Status`, `Install`, `Contribute`) plus optional capabilities. A launch is a `launchplan.Plan` the loader adds to; `game.Starter` runs it through the install's store: Steam through `steam -applaunch`, every other store by running the game's executable.
  - **Pipeline** (`internal/launchsvc/pipeline.go`): one install runs one launch at a time (the preparing claim is the lock). Order: loader contributes; packages are laid out (`SyncPackages`); the deployer places install-side files (journaled first); profile game settings apply and the changed-launch save backup is taken; the profile's Saves folder, options file and mod config folder (`modConfig`) are swapped in; the runtime is prepared; the store starts the game. When the game exits or the start fails, placed files are purged, swaps undone, settings restored. `RecoverDeploys` finishes what a crash left at startup, skipping an install whose game still runs.
- **Installers** (`internal/installer`): an archive's shape picks a driver in `detectionOrder`; every laid-out path is validated to stay inside its target and be storable on Windows. **Frameworks** (`internal/framework`): a driver keyed by a framework mod's id adds conflicts, hints and findings to Problems; Content Patcher is the only one. **Hosts** (`internal/host`): `host.Direct` fetches any HTTPS address (GitHub release assets resume through `github.Download`, which uses the user's `gh` login when present).
- **Pack formats** (`internal/pack`): `Format` readers turn another manager's list into a `Draft` and write nothing; `packsvc.ExportModpack` and `ExportR2z` write files their own readers read back.
- **Known-broken lists** (`internal/components/knownbroken.go`): kept apart from the catalog in `Rethunk-Tech/mortar-known-broken` (`lists/<game>.json`, signed with the catalog's key, published to the rolling release `lists`); no copy ships in the build. `KnownBrokenFor` (`components/signedlist.go`) verifies and refuses a lower serial than the cached one. An entry flags versions up to `through`, may limit itself to `gameVersions`, and is `broken`, `superseded` or `notRecommended`. It reaches Problems, Browse, import previews, the update review and the patch-day sweep (`launchsvc.sweepKnownBroken`).
- **Mod development** (`internal/devsvc`, `frontend/src/develop/`): a loader entry's `devTemplate` names a GitHub template repo and tag; the template is a .NET template with `.template.config/mortar.host.json` marking the parameters Mortar remembers or fills itself. Mortar runs `dotnet new` in its own hive, so nothing is installed for the player's own `dotnet new`. A project added from a folder or cloned is `untrusted` and builds nothing until `Trust`. Build output becomes an extra mods folder bound to the development profile. An asset project (a loader's `assetKinds` entry) is not built: once trusted, its own folder becomes the extra mods folder, installed without `.git`, `.mortar` and `artifacts`. New mod offers a kind only when its `dependency` package is on Thunderstore or is one of the player's projects (`frontend/src/develop/assetKinds.ts`). `MORTAR_DEV_TEMPLATE` replaces the catalog's template in any build.

### Folder games

`internal/loader/folder`: a game with no mod loader names the loader `folder`, a `mods` path role (where the game reads mods, possibly outside the install) and a `mods` target whose root is a profile subfolder (`{profile}/Mods`).

- **Entries:** an added archive lays out below the target as packed and becomes one entry per laid-out file (key `<store item>#<slash path>`, `Entry.Item`, `Entry.File`), unless it lays out a file whose extension is in the target's `keepWhole` list: then one entry holds every file. Trap: everything reading the store (backups, listings, keep set, sizes) uses `Entry.StoreKey()`, never the key, so an archive counts once.
- **Replacement:** an install replaces an earlier archive only as its update (`Source.WithReplacing`, or a GitHub asset of the same repository and shape); every entry of the superseded archive is replaced together, each keeping its on/off state, and the first new entry records them so Roll back restores all.
- **Launch:** the loader plans one file per file below the target with `launchplan.PlanFile.Root` `mods`; the deployer places them under `deploy.View.Roots["mods"]` with the same journal and crash recovery as install-side files. `SyncPackages` records each file in `.mortar-packages.json` and never overwrites a copy changed since.
- **Install-side mods folder:** a `mods` path of `{install}` or below needs no deployer of its own. With `{install}` itself an archive is laid out as packed from the install root, so the folder's top folders are what a profile owns for write-back, and Import from the game's Mods folder offers nothing. Not covered: an archive packed without its folders (Cyberpunk's loose `.reds`), and Witcher 3's `mods.settings` load order.
- **Settings:** `gameSettingsMode` decides whether Mortar writes the catalog's `requiredSettings` into the profile's own copy of the `options` file before a launch (`launchsvc.swapOptions`) or only reports them. `scripts/selftest.sh regress --game sims4` checks the player's files are identical afterwards.

### Deploy methods

`internal/deploy`, `GameInfo.Deploy`.

- **`redirect`:** the loader points the game at the profile's folder; nothing is placed (SMAPI's `--mods-path`).
- **`profile`:** the profile holds the loader and mods (the r2modman and Gale model): `SyncPackages` copies each enabled package's files into the profile (a package's config file only seeds it) and removes files of packages no longer enabled; the deployer copies only the loader's install-side files into the install (BepInEx's Doorstop pair, its config pointing at the profile's absolute preloader path) as real files, never links (the game and its anti-cheat may write to them), journals every move first and restores what they displaced when the game exits. A plan path leaving the install is refused.
- **Journal** (`deploy.go`, `oplog.go`; `crash_test.go` crashes after every step): `Apply` persists `deploy.json` in `<data>/journal/<install id>` before the first file moves and refuses with `ErrUnrecovered` while an earlier journal exists.
- **Purge invariants** (`deploy_test.go`, `writeback_test.go`): a displaced file goes back over its destination; with nothing displaced a destination is removed only while its hash is the recorded one, so a player's own file is never deleted. A crash between any two steps leaves the bytes in the profile, the shared folder or both, never neither.
- **Write-back:** the profile owns what a launch changes in files it placed; the shared folder is scratch. After the game exits, a changed file placed into a path role's folder is copied over the profile's copy before removal, and a file created during play inside a folder an entry owns is adopted (never through a link). The target is the profile's copy, never a store item. When the profile's folder is gone, bytes are never removed without a copy: a changed file over a displaced one is renamed `<name>.mortar-rescued` before the player's file returns.
  - **A mod's BepInEx config** (`modconfigs.go`): switching the mod off moves it to `<profile>/config-aside/`; removing the mod deletes it.
  - **`changed/<path>`** is the one rule for update, roll back, uninstall and a switched-off package: a changed copy is moved under `<profile>/changed/`, never deleted, and comes back when an archive ships it again or the entry is reinstalled. It travels in a `.mortar` payload like config files (`Include.ConfigFiles`, `profile.WriteChangedFiles`).
- **Files an update drops:** follow `oldFilesOnUpdate`; one whose entry was switched off or removed is held under `changed/` whatever the setting (`.mortar-held.json`) and deleted at the next sync once held longer than `trashRetentionDays`. A dropped file nobody changed is removed in every mode.

### Loader notes

Each loader names a hidden companion mod (the SMAPI bridge, the BepInEx bridge) that lets Mortar query the running game ([Companion bridges](#companion-bridges)). Launch arguments and file routes per loader are in the driver (`internal/loader/*`, `internal/loader/thunderpack/specs.go`); the facts below are the ones it cannot say.

- **BepInEx 5** (`profile`): keeps core, plugins, patchers, config and log in the profile, where Doorstop's `--doorstop-target` points. A native Linux build (an install holding `linuxMarker`) gets no files: it starts directly with the pack's `libdoorstop_x64.so` in `LD_PRELOAD`. Settings walked: `bepinex5Pin` is read through the loader service; `skipIntro` through the BepInEx bridge (`ArmIntroSkip`); the Console page and the stream overlay through the driver's log and `ArmOverlay`; `enableRequirements`, `missingRequirements` and `dependencyVersions` from the packages' Thunderstore dependencies; `extraModsFolder` takes packages and build output folders; `graphicsApi`, `gameSettingsMode` and `cacheClearing` where the game's catalog entry has their block; game-scoped pipeline settings apply as they are; `cosmeticConflicts`, `conflictScanDepth`, `showDotHiddenMods` and the SMAPI settings are not read (no asset index, no dot-folder rule).
- **Folder** (`internal/loader/folder`, built in): its mods are files the deployer places in the folder the game reads for the length of a launch. Settings walked: no pin and no Loader page; `skipIntro` is not read (no companion mod); requirements are not read (loose files declare none); `extraModsFolder` takes loose mod folders; the Console page shows only where a log reader exists (`vslog` for Vintage Story); `cosmeticConflicts` and `conflictScanDepth` only where the game's mod formats index asset edits (`framework.IndexesAssets`); game-scoped pipeline settings apply as they are; the SMAPI and BepInEx settings are not read.
- **MelonLoader** (`profile`, `internal/loader/melonloader`): one catalog component shared by every MelonLoader game; only `version.dll` is placed beside the executable. A game with no catalog `routes` runs MelonLoader 0.7's recursive layout; one that lists `routes` takes the classic layout. Only Windows x64 builds are covered. `UserData/MelonPreferences.cfg` names no types, so an entry's type is read off its value (`internal/configsvc/melon.go`). Settings walked: `melonloaderPin` is read through the loader service; the game-scoped settings the pipeline applies to any loader apply as they are; `skipIntro` is not read (it needs a companion mod and MelonLoader has none); the SMAPI loader settings are not read.
- **ReturnOfModding, GDWeave, Lovely, Northstar, Rivet, Unity Mod Manager and Shimloader** (`profile`, `internal/loader/thunderpack`: one driver, a `Spec` per loader in `specs.go`, from r2modman's ecosystem schema): the loader is the game's Thunderstore package, so a mod's dependency on it is the loader's own. An update removes the previous release's placed files and replaces only the folders the release owns. Only a library or launcher that must sit beside the executable is placed for a launch, with `dll-override` `native,builtin` for each top-level library under Proton. Traps: Northstar's `NorthstarLauncher.exe` starts in place of the game (`Plan.OverrideExe`, a direct start), so a Steam install under Steam's own Proton is refused; Unity Mod Manager passes both the Doorstop 3 and the Doorstop 4 spelling of the target and switch, since each ignores the other's. None writes a log Mortar reads, so a launch is up when the game process is. Settings walked: each loader's pin (`returnofmoddingPin`, `gdweavePin`, `lovelyPin`, `northstarPin`, `rivetPin`, `ummPin`, `shimloaderPin`) is read through the loader service; game-scoped pipeline settings apply as they are; the console filters have no log to filter; `skipIntro` is not read (no companion mod); `graphicsApi`, `gameSettingsMode` and `cacheClearing` read catalog blocks these games lack; `nxmDefaultProfile` needs a Nexus source, which they lack; the SMAPI and BepInEx settings, `showDotHiddenMods` and `extraModsFolder` are for those loaders' folders.

### Components

`components.source.json` names each loader or companion mod by game, kind, GitHub source, release asset pattern and version policy; its `games` section holds each game's identity and `authors` the people known by different names on different mod sites. `cmd/components` resolves releases, downloads the assets and writes the signed `components.json`, embedded at `internal/components/components.json` for offline and first-run fallback.

- **Signature:** Ed25519 with the update key (`build/updater/public.key` is the embedded public half); the detached signature is published beside the manifest. Each signed manifest is its own immutable `components-v2-<serial>` release; `v2` is the manifest schema, and a schema change takes a new prefix.
- **Client** (`internal/components`): fetches the newest non-draft `components-v2-*` manifest at startup, verifies before parsing, rejects a lower serial and falls back to the cached or bundled manifest. Source hosts are limited to `github.com` and `thunderstore.io`. Every asset is checked against its manifest SHA-256 before extraction.

### Companion bridges

Mortar has no access to SMAPI's stdin, so a small mod in the game (`Rethunk-Tech/mortar-smapi-bridge`, `Rethunk.MortarSmapiBridge`; the BepInEx one is `Rethunk.MortarBepInExBridge`) accepts commands on a loopback port. Each is installed hidden in every profile as a `bridge-<version>-<hash>` store entry with source kind `mortar`.

- **Channel** (`internal/bridge`): the mod writes `mortar-smapi-bridge.json` (`{port, token}`, user-only) in its folder (the BepInEx one in `BepInEx/config`); Mortar sends `<token>\n<command>\n`. Commands run on the game's next tick and their output arrives in the log. Both read `startup/skip-intro` in the profile folder (`loader.WriteIntroSkip`).
- **Log sources:** the BepInEx bridge prefixes each managed message with `⟦src=Type::Method;obj=<hierarchy path>⟧`; `launch.parseBepInEx` lifts it into `Entry.Source`/`Object`. Hidden sources are per game: the signed defaults from `Rethunk-Tech/mortar-log-suppressions` (fetched like the known-broken lists, `components/signedlist.go`) less those the player showed again (`shownLogSources`), plus the player's own (`hiddenLogSources`), merged by `settings.HiddenLogSources`. Before each launch `launchsvc.writeHiddenLogSources` writes them to `startup/hidden-log-sources` for the bridge to drop. A list entry `mod:<Mod>` with masked `text` names a message by its log column: `launch.SetHiddenMessages` drops those for every reader.
- **Running state:** while a game Mortar started runs, `launchsvc` asks `status` periodically (`loader.RunningState`); each enabled package whose DLLs declare plugins gets a loaded badge. Trap: BepInEx keeps the newest version of a GUID and, between equal versions, the first file its folder walk meets (`Chainloader.cs`), which only the bridge's `location` tells.
- **Stream overlay:** the bundled OBS page is written to `<data>/overlay/index.html`; at launch the bridge gets `OverlayEnabled`, `OverlayPort` and `OverlayToken` (0600, atomic; `startup/overlay.json` for a loader whose bridge keeps settings in the profile).
- **Startup timings:** the bridge writes `<profile>/startup/<process start UTC>.json` (schema in its README; times are exclusive). **Measure next launch** also times every other mod's Entry, event handlers and asset edits and samples stacks through an EventPipe session. BepInEx times only a measured launch: `LogOutput.log` has no timestamps, so the bridge's preloader patcher wraps Harmony's `Patch` entry points instead (`launchsvc.MeasureInGame`); Unity's Mono has no diagnostics port, so there is no stack sampling.

### Launch

The pipeline is under [Games and the catalog](#games-and-the-catalog) (Loaders); Stardew's launch facts are in [games.md](games.md#launch).

- **Launch options:** `--mods-path`, `--no-terminal` and `--skip-terminal` are refused in a profile's `launchOptions` since Mortar sets them; `launchPrefix` (Linux only) and `launchEnv` apply to Direct launches only, since Steam `-applaunch` receives neither; an unknown preset name refuses the launch before anything starts. Changing any of these never touches `mods/`, so a running game does not block it.
- **Before Play:** gathers missing required dependencies, unresolved non-cosmetic conflicts, pending updates, mods flagged broken or obsolete, a changed game version and the newest save's gap into one dialog; `skipPlayCheck` skips it. With `updateModsBeforePlayDefault` on, Play queues every installable, non-pinned update first, records a history restore point and rolls back entries whose update fails. A failed backup zip does not block Play.
- **Likely cause:** `launchsvc.CrashHint` explains the latest `crashed` run; the first hit wins: the run's recorded cause; the loader's log analyzers; a .NET stack blame (`dotnetstack.Blames`; two equal matches blame neither); a crash dump or the Windows Application event log (`internal/crashdump`), blaming a mod only when the faulting module is its `EntryDll` or a same-named file within three folders of its folder. A run's Summary is `crashed` when a Unity player log written since the run began holds `Crash!!!` or `Fatal error` and the loader reported no crash itself.
- **Bisect** (`internal/bisect`): halves enabled mods (keeping required dependencies) on a scratch profile (`profile.ScratchCopy`, removed when the check ends and, after a crash, at the next start).

### Saves

`internal/savesiso`: a `separateSaves` profile plays on `<profile>/saves` for the length of a launch with mods. `Apply` persists a `Manifest` before the shared folder moves, renames the shared folder to `<Saves>.mortar-shared` (a rename, never a copy) and points the save path at the profile's folder with a symlink, or a working copy (`Live`) where symlinks are refused. `Purge` checks the disk at every step so it can run again after a crash; an incomplete copy is never written back. `Apply` refuses with `ErrUnrecovered` while an earlier swap's record exists. The same package swaps a single file (the game's options file) and a mod config folder.

**Backups** (`internal/backup`, `internal/savessvc`): Restore first zips the current Saves folder, extracts beside Saves and swaps each save folder in by rename, so a failure leaves the old one; it is refused while the game is launching or running. `RunScheduledBackups` waits while a game runs (including one Mortar did not start). `savessvc.SaveGap` compares the mods a save was last played with (`last-played.json`) against the profile.

### Problems

Problems warn and never block. The checks are in `internal/problems` (one file per family, each with a `_test.go`). Rules not obvious from the code:

- **Minimum game version** is compared against the loader's game version or, where it knows none, the version the game's last run logged.
- **Broken, obsolete, abandoned** come from SMAPI's API, with a one-click replacement when its `compatibilitySummary` names a target Mortar can install. A mod whose replacement is enabled too is superseded and loses its Broken and Compatibility rows.
- **Source flags** (`source_flags.go`): Nexus pages whose cached status is not `published` (read from the page cache, never fetched) and, through `source.StandingChecker`, archived, deleted or unavailable projects on Modrinth, CurseForge and GitHub (bounded per pass, stopping on a rate limit, each answer cached a day). Thunderstore deprecations are `DeprecatedPackage` rows.
- **Plugin clash** (`pluginclash.go`): a `[BepInPlugin]` GUID declared by more than one enabled package (BepInEx loads only one).
- **Paths too long** (`longpath.go`, Windows only): a file the game would read at a full path of 260 UTF-16 characters or more. `LongPathsEnabled` is not read, since it lifts the limit only for `longPathAware` programs; Wine opens such a path, so Linux never checks. The walk is slow, so it starts after the rest and is kept per mods fingerprint: window loads (`ProblemsNoWait`) answer without it and `problems:changed` brings the rows.
- **Nexus-listed requirements** come from batched page data (`nexussvc.Prime`). Trap: Nexus lists a page-wide outside requirement for every file of the page, sub-packs included, so it is only Optional for a file whose own manifest declares dependencies and names none like it.

## Nexus Mods

Client `internal/nexus` (REST v1, GraphQL v2), service `internal/nexussvc`; endpoint shapes and caching are in their tests. Registration with Nexus: [nexus-application.md](nexus-application.md).

- **Sign-in:** the build picks the flow. By default Settings takes a personal API key, kept in the OS keyring and never sent to a server of ours (`internal/nexussvc/apikey.go`); `GET /v1/users/validate.json` gives the account's `user_id` and `is_premium`. Setting `-X github.com/Rethunk-Tech/mortar/internal/nexussso.ClientID=<id>` at build time selects browser sign-in with OAuth PKCE instead (one fixed loopback redirect, `nexussso.RedirectURI`, since Nexus registers a non-dynamic callback; tokens in the keyring as `nexus-oauth`; a pasted key is refused), and `-X .../nexussso.Slug=<slug>` selects legacy SSO; with neither set the key box is the only sign-in. Every request carries a truthful `Application-Name` and `Application-Version`.
- **Browse:** search uses the public v2 GraphQL endpoint, which needs no key. Trap: a category list is an AND in Nexus's filter, so included categories become one OR branch each, every branch also excluding the excluded ones; category names come from the game's category list, which Nexus serves only to a signed-in account.
- **GitHub search** falls back cache, then GraphQL when the user's `gh` login lends a token, then REST `search/repositories` with the game's topics (one search per topic, merged by the chosen sort), then github.com's own search page (`Accept: application/json`, ten rows a page, one request at a time, half a second apart, under Mortar's User-Agent). Each way waits out its own refusal (Retry-After, else `X-Ratelimit-Reset`, else a minute) without asking again.
- **Downloads need the user** ([AGENTS.md](../AGENTS.md)): update checks (including the background check, which only notifies) are allowed, but a Nexus file is never downloaded or installed without a user action, and a queue restored from a previous session is held paused at startup when it holds a Nexus file.
- **Update path:** a Nexus mod's update comes from SMAPI's API through the mod's `UpdateKeys` (`Nexus:<id>`), and the Nexus file lists then decide the file. Trap: Mortar never searches Nexus once per installed mod (`problems` skips `nexus` and `github` sources in its per-source update search): that would spend hundreds of the hourly quota to repeat SMAPI's answer. Page data for many mods is one GraphQL `legacyModsByDomain` request per 50 mods (`nexus.Client.ModsByDomain`), cached by `nexussvc.PrimeDetails`.
- **Manual downloads:** per-game `offerNewDownloads` offers archives landing in the Downloads folders; nothing installs on its own (`internal/dlwatch`). A Nexus file name `<name>-<modId>-<version>-<timestamp>.<ext>` supplies the mod id, otherwise `dlwatch.Identify` peeks `manifest.json` in a zip.
- **Mod page details** (`nexussvc.Details`): cached in `cache/nexus/`, never in `profile.json`; signed out, rate-limited or offline, the cached copy is served however old. `available` false marks Hidden on Nexus, `status` other than `published` Removed from Nexus; those pages are not offered as updates.
- **Files:** an update takes the `MAIN` file matching SMAPI's `suggestedUpdate`, else the `is_primary` one, and never an `OPTIONAL` file unless the profile already uses it. A file whose GraphQL v2 `scannedV2` is `QUARANTINED` is omitted, and a request for it fails the queue item.
- **Download links:** premium accounts get links directly; they expire, so Mortar asks just before downloading and again on a restart. A free account gets HTTP 403 and needs the `key` and `expires` from the `nxm://` link of the site's Mod Manager Download, one click per mod. Endorse and track happen only on the user's click.

### `nxm://` links

`nxm://<domain>/mods/<mod id>/files/<file id>?key=<key>&expires=<unix>&user_id=<id>`; Mortar takes this form only for a Nexus domain a catalog game maps to, unexpired and for the signed-in account's `user_id` (`internal/nxm/link.go` `Parse`; guards: [security.md](security.md#network-and-links)). A link Mortar was not waiting for asks which profile it is for before anything downloads.

- **Registration:** only one app can own the scheme, and Wails' NSIS macro would delete and rewrite its key at install time without asking (`build/windows/nsis/wails_tools.nsh`), taking it from Vortex or Mod Organizer 2. So `nxm` is not in `build/config.yml`: Mortar registers it at runtime after the user agrees, records the previous handler in `settings.json` (`nxmPreviousHandlers`) and restores it when turned off or when uninstall runs `mortar.exe --release-links`.
- **Bursts:** each `nxm://` launch is a second instance whose arguments the running one queues at once; a link that arrives again before its own `expires` is taken once.
- **Browser limit:** Chromium browsers launch at most one external protocol per user gesture, so Nexus Slow Download countdowns that end with no click in between are blocked.

### Browser extension host

The extension lives in Rethunk-Tech/mortar-browser-extension (UI: [gui-design.md](gui-design.md#browser-extension)). To avoid the gesture gate it reads each `nxm://` anchor on `www.nexusmods.com` and sends it with `sendNativeMessage` to the host `tech.rethunk.mortar`, which is Mortar itself (`internal/nativehost`); that process starts `mortar <link>`, so the link takes the same second-instance path.

- **Protocol:** every message and reply carries `protocol`; Mortar answers `MinProtocol`..`MaxProtocol` and records a refusal in `extension-contact.json` as `mismatch`. A change to a message's shape bumps both sides (shapes: `internal/nativehost/nativehost.go`); refusal rules: [security.md](security.md#network-and-links).
- **Data requests** are read-only and start no download. Every reply carries `games` so the extension maps a page's key to the Mortar game id and opens `mortar://<game id>/mod/<id>`. The extension follows the Download link of Nexus's requirements dialog only when it points at the page's own mod, because Mortar resolves requirements itself.
- **Project requests** (`installedProjects`, `installProject`): CurseForge `curseforge://install` and Mod DB `vintagestorymodinstall://` clicks are handed over as `link`, which `source.IsLink` accepts like `nxm://`.
- **Host manifest:** on Linux, turning nxm handling on (and every start while on) writes the host manifest into each installed browser's `NativeMessagingHosts/` folder; turning it off removes them. A Flatpak build writes none.

### Download queue

An import or a profile's missing files run one queue (`internal/queue`), persisted in `<datadir>/queue.json` without `nxm://` keys. Mod files and Nexus data stay on the user's machine; a share link holds IDs only. Invariants a change must keep:

- Items store as `nexus-<mod id>-<file id>`; the entry's source kind (`profile.Kind*`) records mod id, file id and version; a `github` source holds `repo`, `tag`, `asset`.
- **`latest`:** installs started from a save's missing mods, a missing dependency or a Problems fix follow Nexus `file_updates` to the newest listed file. Share imports leave it off to reproduce the shared files.
- **Which file an update downloads** (`nexus.Supersedes`, `internal/nexus/choose.go`): a page's version is the main file's, so the page's version never decides. When none supersedes the installed file but a current file of another download exists, the update is marked `pickFile` and nothing queues it.
- A free account's head item waits for its click and a matching `nxm://` link is routed to it. A Nexus file the game's store already holds installs from the store with no download and no click, unless the profile has an entry from the same mod page. A reached rate limit, Nexus's or GitHub's, pauses the whole queue until its reset.
- **Free space** (`internal/queue/size.go`): before the first byte the archive plus twice its size for extraction plus a margin must fit on the downloads and data volumes, or the item fails with `NoSpaceError` with no override; a download over `LargeDownloadBytes` parks in `StateConfirmLarge`.
- **Resume** (`github.Download`, the one path every queue download takes, over [go-httpkit](https://github.com/Rethunk-Tech/go-httpkit)'s `download.File`, which also owns the sidecar, the idle limit and the checksum checks): a retry, restart or unpause sends `Range` with `If-Range`, accepts 206 only when `Content-Range` starts at the offset and its total equals the recorded size, and starts over otherwise. A network error, stall or pause keeps the partial; a failed check, Cancel and Skip delete it.
- **Pause** is a user pause of one item and survives a restart; `HoldForPlay` pauses running downloads while a game runs when `pauseDownloadsWhilePlaying` resolves true for its profile. Order is the order of `queue.json`'s `items`.

## GitHub releases

`internal/github` reads `/repos/<owner>/<repo>/releases`, with the gh token when gh is signed in. Answers are cached on disk and served stale when GitHub is unreachable; the unauthenticated limit is per IP.

- **Trust** (`internal/github/verify.go`): a GitHub-sourced install counts as verified only when SMAPI's update API maps the manifest's `UniqueID` to the same repo. A known mismatch parks the item in `needs-confirm`; an unknown answer installs and marks it "could not verify"; nothing here blocks.
- **Asset picker** (`internal/github/pick.go`): the first rule that leaves one archive wins; several left park the item in `needs-choice` (last choice kept in `github-choices.json`).
- **GitHub vs Nexus for updates:** a free Nexus account must click for every file, so a Nexus update carries a GitHub fallback repo (`GitHubFallback`): the queue downloads a GitHub release at the same version with exactly one archive whose staged contents hold the mod's UniqueID (`FallbackID`), else the item goes back to Nexus.

## Sharing

- **Form:** Discord makes only `http://`, `https://` and `discord://` links clickable, so a link is `https://mortar.rethunk.tech/<game id>/p#<payload>`, handed to the app as `mortar://<game id>/p/<payload>`. Browsers never send the part after `#`, so no profile data reaches any server. The app accepts either form, or a bare payload. Each playable game's share page is built from `web/src/pages/[game]/p/index.astro` and runs `web/public/share/app.js`.
- **Payload** (`internal/share/share.go`): compact JSON `[3, "<profile name>", "<game id>", {"<source id>": "<that source's game key>"}, [<entry>, ...], "<game version>"]`, Brotli, base64url without padding. The leading number is the format version (only 3 is read). The link holds no `UniqueID`s, which barely compress. `web/test/testdata/go-link.txt` is the link the app's encoder made, read by both the Go and site tests.
  - **Entry** names its source (`s`) so a link names the exact file (`share.Ref`). A new source leaves the format version unchanged: an older Mortar rejects an unknown source as a bad entry.
  - **Extras** (`imp`, `grp`, `overlay`, `fomod`, `pin`, ...): past the cap `kb` and `min` go first, then the extras except `imp`. A share with no `imp` entry may predate install reasons, so the receiver infers them (a package another listed package requires is implicit); profile codes, `.r2z` files and modpacks are inferred the same way.
  - **What is shared:** only enabled entries with a source; local archives and switched-off entries are listed at Share as left out. Every entry cut from one store item is one ref keyed by `Entry.StoreKey()`. SMAPI's bundled mods and the bridge are never shared. CurseForge downloads with the receiver's own key; itch.io and Patreon entries travel as the page alone.
- **One import engine** (`sharesvc/pack.go`): `sharesvc` reads every format (`PreviewLink`, `PreviewFile`, `PreviewLocalProfile`) and previews it through the same resolver. A pack becomes `share.Ref` packages plus config and loose files written below the loader's import folders (`pack.ProfileFiles`; executable types are listed in `SkippedPrograms`). A mod the other manager added from disk (`pack.LocalMod`) installs as a local entry through `profile.Store.InstallLocalFolder`, so the store's antivirus scan applies. A package the community index cannot resolve is an unavailable row with `ReasonNotInIndex`, so the rest still imports.
- **Import preview** (`internal/sharesvc`, `preview.go`) resolves every entry and creates nothing (a Nexus file that is gone or `ARCHIVED` is replaced by the `MAIN` file with the same version, else the primary file, marked "different file"); nothing downloads before the user's click.
- **`.mortar` file:** a zip holding `profile.json` (same format version and entries as a link, plus name, notes and the shared mods' ids `ids`, which bound the config files it may carry), `configs/<format>/<local id>/<relative path>.json`, and `loader/<path in the profile>` for text config files under the loader's config folders (`loader.WithConfig`). Files over the size cap, with unusual names or past the totals are skipped and listed at Save. The profile's favourite star travels only in this file; colour and icon travel in neither.
  - `share.Apply` writes config files once their mods are installed, only under a folder an installed mod of that import already has, never over mods the profile already had; waiting ones are kept in `<datadir>/pending-configs.json`.
  - **Problem choices** (`problems` in `profile.json`; File and LAN only): `dismissed` tokens and `wins` (`Component.LoadAfter`), bounded; a file past them is refused whole. The receiver only adds (`sharesvc.applySharedChoices`) and skips a win when the profile decided the pair the other way.
- **Routing:** `mortar://` is in `protocols:` in `build/config.yml` and `.mortar` in `fileAssociations:`. A link reaches the app as an argument: a cold start reads `os.Args` and a running instance gets a second-instance handoff (`sharesvc.Receive`); it opens the Import dialog filled in, never importing by itself. `mortar://<game>/mod/<id>` selects the Nexus mod on the Mods tab (`route.go`).
- **LAN sharing** (`internal/lan`): with Settings › General Share profiles on the local network on, Mortar advertises `_mortar._tcp` and serves HTTP on `lanPort`; sends are refused while sharing is off and incoming shares are rate-limited per peer. To a paired computer every option applies and archives added from disk travel as store items; to an unpaired one config files are dropped (they can hold keys) and local archives left out. Pairing makes two of the user's own computers trust each other: a single-use code shown on one and typed on the other leaves a 32-byte key in `<data>/lan/peers.json` (0600); construction and limits: [security.md](security.md#network-and-links).
  - **Store transfer** (`transfer.go`): the receiver installs through `Store.AddDir` only when the hash of what arrived (`store.HashDir`) equals the one the sender vouched for, and refuses an entry with no vouched hash. A paired receiver gets the files whatever the source or licence.
- **Windows firewall:** the per-user installer adds no firewall rule. Settings › General Fix relaunches Mortar elevated (`--firewall-allow`), which writes the rules through `INetFwPolicy2` (`internal/lan/firewall_windows.go`), removing every inbound block rule for the executable first (Windows names the ones it creates after the file description, not `Mortar`). When every connected network is Public and the allow-any-address setting is off, Mortar does not listen and LAN use returns a Permission error (`errPublicNetwork`).
- **Nexus collection draft** (`sharesvc.ExportCollection`): a `collection.zip` holding `collection.json` in Vortex's `ICollection` shape. Nexus takes a collection as a 7z and no 7z-writing Go library is in go.mod, so the export is a zip and the toast gives a repack command.

## Sync folder

`internal/syncsvc` keeps each profile's `.mortar` export (never mod files) in step between computers through a folder another tool (Syncthing, Dropbox, a NAS) carries; the folder is `Settings.SyncFolderFor`. Layout and version vectors: `syncsvc.go`. Invariant: the payload is written first and the version file last, so a computer that sees a version finds the payload it names. A version file whose vector holds a revision this machine lacks becomes an offer, never merged; `Resolve(game, remote, "theirs")` replaces the profile, `"mine"` writes a revision on top of both vectors.
