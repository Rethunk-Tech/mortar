# Mortar architecture

How Mortar works: storage, profile semantics, the game catalog and its registries, trust boundaries, and the Stardew, Nexus and wire-format facts that settle questions so they are not re-litigated. Decided work not yet built is in [design.md](design.md), screens in [gui-design.md](gui-design.md), standing rules in [AGENTS.md](../AGENTS.md).

## Product

Mortar finds a game, installs its mod loader, keeps each set of mods in its own profile, and launches the game with the chosen profile.

External profile import is available for r2modman, Gale, Stardrop (Stardew Valley only), Vortex and Mod Organizer 2 when their default data is present.

Vortex and MO2 take the game's names from its catalog entry (`importIds`: `vortex` is the game extension's `GAME_ID`, `mo2` the game plugin's `GameName`); a game with no `importIds`, such as Lethal Company, which neither manager ships support for, has neither:

- **Stardrop:** profiles from the platform application-data `Stardrop/Data/Profiles` folder; `EnabledModIds` match manifests in the configured game `Mods` folder. A profile that keeps configs per profile (`PreservedModConfigs`) writes its own copy over the folder's, or onto a downloaded mod once it installs, under the same caps as a `.mortar` file's configs; oversize ones are listed in the import preview.
- **Vortex:** profiles from its `state.v2` persistent JSON; each profile's `modState` is matched to the extracted staging folder. Configs live only in that staging folder.
- Present folders are copied into Mortar's store (each keeps its `config.json`); missing Nexus mods enter the same share-import resolver and download queue. Enabled UniqueIDs with no matching folder on disk are listed in the import preview as **Not found in the Mods folder**.

The Profiles page's **Import…** wizard lists every detected profile with its manager and mod count: `packsvc.LocalProfiles` reads r2modman's profile folders and Gale's `data.sqlite3` (read-only, through the pure-Go `modernc.org/sqlite` driver, for the profiles whose game slug is the game's Thunderstore community), and `migrate.Detect` the Vortex, Mod Organizer 2 and Stardrop installs. A pack profile opens the pack import preview; any other kind opens the Import dialog on `migrate.Preview`.

- **What matters:** Mortar working for personal use with a personal Nexus API key. Registering the app with Nexus is not a v1 goal.
- **Licence:** AGPL-3.0: the same as GPL-3.0 for the desktop app, and it covers a hosted share service.
- **Games:** the signed catalog lists every game ([Games and the catalog](#games-and-the-catalog)). A game's `enabled` flag makes it selectable; Stardew Valley and Lethal Company are catalog entries. Mortar runs on Windows and Linux and finds installs from Steam (including Flatpak Steam on Linux), GOG Galaxy / the GOG offline installer, Heroic's GOG library on Linux, Minigalaxy, Lutris and Bottles on Linux. macOS is out (fleet CI has no macOS runners, and Wails does not cross-compile to it).

## Stack

- **Wails v3**, upgraded one beta at a time on purpose; the pin and its Go floor are in `go.mod`. Betas are small fixes; there is no date for a stable v3.0.
- **Frontend:** React, TypeScript and MUI on Vite, from Wails' `react` template. Typed bindings from `wails3 generate bindings` into `frontend/bindings`. Client state in zustand. Lingui 6 for every string; English only.
- **Go services:** each backend area the UI calls is one Wails service (`application.NewService`), so its exported methods are bound to TypeScript. Methods only Go calls (quit, tray, control server, CLI, other services) carry a `//wails:ignore` doc directive, so the bindings expose only what the GUI calls.
- **Solid window:** `BackgroundTypeSolid` (`main.go`); the base, tint and surfaces are in [gui-design.md](gui-design.md#surfaces-and-colour). The wallpaper endpoint is `/background`; it honours `?mode=` (`image`, `desktop` or `solid`) and answers `Cache-Control: no-store`.
- **Frameless, with a themed title bar:** `Frameless: true`, and the app draws its own title bar marked `--wails-draggable: drag`. Measured on GNOME and on KDE Plasma 6.6 (Wayland, Fedora 44): drag, edge and corner resizing, the 768x432 minimum, double-click maximise and the window buttons work; neither compositor draws a drop shadow, so the app draws a 1px border and rounded corners. Trap: dragging works only once the Wails runtime is loaded (`@wailsio/runtime`, or `/wails/runtime.js`).
- **Credits:** Settings › About lists bundled licences from `frontend/src/settings/generated/credits.json`, which `scripts/gen-credits.ts` writes at every frontend build from `frontend/package.json`'s runtime dependencies and `go.mod`'s direct requires (licence read from each package's own metadata), plus Mortar (AGPL-3.0 from the repo `LICENSE`) and the default wallpaper. SMAPI, BepInEx and the two bridges are downloaded into a profile, never bundled, so they are not listed.
- **Session-only state:** the toast history (the last 200 toasts, newest first) and the Console's command history live in memory and are written nowhere; a toast's Undo, Redo, Show or Retry in the history works only while that change is still the latest for the same mods. The Notifications panel lists the toasts it has not shown as read under **New** and, under **Earlier**, the open profile's durable change history (`history.json`, [Profile operations](#profile-operations)), each event with **Show diff** and an Undo that reverts to the snapshot before it.
- **Packages worth knowing:** `internal/components` (the catalog and signed manifest), `internal/game` (the `Game` interface and the catalog-driven install, path and launch-option lookups; every game is the catalog-driven `catalogOnly` implementation, and `game.Starter` starts a launch plan the way the install's store requires), `internal/loader` (the loader registry and its drivers: `smapi`, `bepinex5`) with `internal/launchplan`, `internal/gamestore`, `internal/runtime`, `internal/source` with `internal/browse`, `internal/metadata`, `internal/host` and `internal/pack` ([Games and the catalog](#games-and-the-catalog)); `internal/archive` extracts zip, RAR and 7z; `internal/configsvc` (typed config editing), `internal/savesiso` (a profile's own saves for a launch) and `internal/syncsvc` (the sync folder) are described under [Profile operations](#profile-operations), [Saves](#saves) and [Sync folder](#sync-folder).

## Storage

Everything lives in the user data folder, `%LOCALAPPDATA%\Mortar` or `$XDG_DATA_HOME/mortar`, never under the Windows install folder (the uninstaller deletes that one recursively).

- **Move:** Settings › Storage can **Move…** the data folder to a chosen empty folder with enough free space, not inside the current folder and not while the game is running: Mortar copies everything, verifies the copy, writes `data-location` in the default folder so the next start finds it, removes the old copy, and restarts.
- **Portable mode:** a file named `portable` beside the executable (symlinks resolved) puts the data folder at `<exe dir>/data` and ignores `data-location`; it is decided once at start, Move is refused while it holds, and `datasvc.DataLocation` reports `dir` and `portable` for Settings › Storage. The marker is ignored inside a Flatpak (`FLATPAK_ID`, or the executable under the read-only `/app`) and an AppImage's read-only mount; a marker beside an executable in an unwritable folder stops the start with an explanatory error (`datadir.PortableError`) instead of quietly keeping data on the host, and a portable copy has its own single-instance id (a hash of its data folder) so it runs beside the installed one; a portable copy belongs in a user-owned folder, never the Windows install folder the uninstaller deletes.
- **State:** WebView2's user data is `webview/` in that folder (`Options.Windows.WebviewUserDataPath`). Mortar's own state is JSON, each file written through a temp file and rename; no database. The Nexus key is in the OS keyring. The uninstaller also deletes `%APPDATA%\mortar.exe` if that leftover WebView2 path exists.
- **Move keeps sharing:** The store is copied first. On the same clone-capable filesystem (btrfs, XFS with reflink, ReFS) every file is cloned, so files that shared extents still do. Across filesystems, a profile file under `mods/<key>/` whose bytes equal its `store/<game>/<key>/` file is cloned from the already copied store file, so profiles stay shared on a reflink target; anything else is copied while its SHA-256 is taken, and the verify pass reads only the target. Further names of a hard-linked inode are re-linked. The free-space estimate is `datasvc.Measure`'s extent-aware total when the target can clone (probed with a real clone); otherwise it counts each linked inode once when the target accepts hard links (probed with a real link; FAT, exFAT and SMB targets count every name). Windows keys links on the 128-bit file id (ReFS), falling back to the 64-bit index. Symlinked folders, junctions and mount points are not followed or copied, and a move logs the ones it left behind.
- **Missing data folder:** A `data-location` that names a missing folder (an unplugged drive) is never created: on Windows a message box offers the default location, a folder picker or quit before the window exists, and every startup failure is also appended to `startup.log` in the default folder.

Files in the data folder:

- `settings.json`: Mortar's preferences and small pieces of state, field by field under [Settings file](#settings-file).
- `store/<game>/<key>/`: each downloaded archive, extracted once.
  - A `.complete` file marks a finished extract (items extract into a temp folder and are renamed into place); an item without it is incomplete, and an install reports it instead of copying a half-extracted folder.
  - A `mortar-root` file in that folder, when present, names the relative subfolder that is the mod (reused for the same Nexus file id; Mortar asks again if that path is gone).
  - Keys: `nexus-<mod id>-<file id>`, `github-<owner>-<repo>-<tag>-<asset>-<sha256 prefix>` (the hash of the exact names tells apart names the folding makes equal), `local-<sha256 of the archive>`, `smapi-<version>` for SMAPI's bundled mods, and `bridge-<version>-<sha256 prefix>` for the Mortar SMAPI Bridge.
  - One Nexus file can hold several SMAPI mods, so the key is the file.
- `store/index.json`: each store item's last use, meaning the last time any `profile.json` named it.
- `store/.manifests/<game>/<key>.json` and `store/verify.json`: integrity records (see [Store integrity](#store-integrity)).
- `profiles/<game>/<profile id>/`:
  - `profile.json`, and beside it `mods/`, the folder SMAPI is pointed at.
  - Each entry is copied to `mods/<store key>/` as extracted, or only the `mortar-root` subtree when one is set.
  - Further files from the same Nexus page can join that entry (`extraStoreKeys`), each copied to `mods/<entry key>/<extra store key>/`. Update, Roll back and Remove cover every store item on the entry.
  - **Optional files** (`internal/profile/overlay.go`): a Nexus file with no `manifest.json` anywhere and no installer (Nexus "Optional" files that swap some files of the main one) is an overlay of the profile's entry from the same Nexus mod that holds a manifest. It goes into the store as its own item like any archive (no manifest is made up) and into `profile.json` as its own entry with no mods, `overlayOf` naming the main entry's key, and no folder of its own. Without such an entry in the profile it is refused: "<archive> has no manifest. Install the main file of <mod> first, then this optional file goes on top of it." (`NoBaseError`, `usererr` not found; the queue row's toast opens the mod's Nexus files page). An archive with no Nexus mod ID and no manifest anywhere is refused as "No SMAPI mod was found in this archive".
    - Where it goes: a single top folder named like one of the main entry's mod folders (case-insensitive) is laid into that folder; otherwise the layout (with or without a single top folder, at the entry root or a mod folder) under which most of its files already exist in the main entry wins; otherwise a single top folder whose children match names in a mod folder goes there; otherwise Mortar asks, with the file's folders and the main entry's folders (`RemapAsk.overlay`, answered by `InstallOverlay` or the queue's `AnswerOverlay`). The answer is recorded as `overlayFrom` (the folder of the store item) and `overlayTo` (where inside the main entry's folder).
    - Laying over: after the main entry's folder is in place, its optional files are laid over it in entry order, so a later one wins. Each replaced file is removed and a new name is linked or cloned from the optional file's store item (`datadir.MaterializeFile`), so neither store item is ever written. Enablinge off (`overlayOff`) or removing it puts back the main entry's own file for every path any of its optional files covered, deletes the paths only optional files brought (and folders left empty), and lays the others again. Switched-off mod folders keep their dots: paths follow them.
    - Alternatives: two optional files of one main entry that replace any of the same main-entry files are alternatives (`OverlayFiles` lists, per optional file, the main-entry paths it replaces, the paths it adds, and its alternatives). Adding one, or enablinge on (`SetOverlayEnabled`, or a mod enable its key), switches its alternatives off in the same write, so only one of them is laid at a time.
    - New versions: an install whose source names the file it replaces (`Source.WithReplacing`, set by the queue from a request's `currentKey`) takes the old optional file's entry in place (same position and switch, `overlayOf` unchanged), keeping the old `overlayFrom` and `overlayTo` when the new file still has that folder.
    - The main entry carries its optional files: removing it removes them, switching its mods off leaves them inside its dotted folder, and updating or rolling it back takes them off first (so carry-over never sees them as the user's edits), swaps the version, renames their `overlayOf` to the new key, and lays them over the new folder. A rebuild that re-places the main folder, Restore and Revert from outside-edit drift, history Revert and Undo all lay them again. Mods, problems, load order and update checks see only entries with mods, so optional files never show as mods of their own. Drift snapshots are taken after the optional files are laid, so their files are expected, not user edits.
    - A profile export zip carries the main folder as installed, with its optional files taken back off, and each optional file's store item under `overlays/<entry key>/`; restoring it adds each optional file back over its restored main entry with its `overlayFrom`, `overlayTo` and switch.
  - Extract drops `__MACOSX`, `.git`, and folders that hold only `Thumbs.db`.
  - When the archive holds a `manifest.json` but none SMAPI would find, Mortar shows the extracted tree and the user picks the folder that is the mod (it must contain a reachable `manifest.json`) or cancels. The same picker lists the variant folders when the archive holds one UniqueID more than once (each widened to its highest folder with a single copy, labelled by path, with version and description when they differ). An update reuses the variant folder of the same name from the entry it replaces and asks again when none matches.
  - FOMOD detection runs first. If the store item has a FOMOD installer (`fomod/ModuleConfig.xml`, case-insensitive, at the item root or one folder down, UTF-8 or UTF-16), Mortar shows the installer steps, copies the resolved files instead of the raw extraction, and stores the chosen plugin names on the entry as `fomod` (step → group → names). Update and Roll back replay those choices (`internal/profile/fomod.go` `replayAsk` / `installAsk`). Mortar asks again when a saved choice no longer exists in the new config, or when the update adds a group the saved choices do not answer (`internal/fomod/resolve.go` `Unanswered`). The wizard is prefilled with the saved picks that still name a plugin in the new config (`Keep`).
  - SMAPI recurses until it finds a `manifest.json`.
  - Beside them `runs/` keeps the last 20 launches Mortar started for that profile:
  - `index.json` (per run: id, start and end, duration, SMAPI and game versions, outcome `ran`, `failed` or `crashed`, error and warning counts, and an optional cause naming the mod, short reason, plain-language detail and path)
  - one `<id>.txt` copy of the run's SMAPI log each, capped at the console's 20,000 lines of 256 bytes, written temp then rename
  - a run is stored when the game goes idle or the launch fails; a launch without mods stores none
- `saves/` inside a profile folder is the profile's own Saves folder when `separateSaves` is on ([Saves](#saves)); the swap's journal is `journal/<install id>-saves/saves.json` in the data folder.
- `trash/`: deleted profiles, kept 30 days; **Delete permanently** and **Empty trash** remove them at once ([Profile operations](#profile-operations)).
- `backups/<game>/`: zips of the Saves folder taken before mod updates, before Play, before a restore and on request, written to `<game>` under the game's `backupLocation` (empty is this folder), so one game's backups are never listed or restored for another. A save is a folder holding a file of its own name (Stardew Valley) or, for a game whose catalog entry lists `saveFiles` patterns, a file in the saves folder or one folder below it (Lethal Company's `LCSaveFile*` and `LCChallengeFile`; Valheim's `characters_local/*.fch` and `worlds_local/*.fwl`, less `!*_backup_*`), named by its path, with any `saveCompanions` beside it that share its stem (a Valheim world's `.db`); a zip holds only the saves and their companions, each under `Saves/`. A Saves folder with no save in it is not backed up, and a manual backup of a folder that is not a save makes none and rotated against its `saveBackupsKept` (1 to 50, default 5; profile-overridable), the one location and count every kind of save backup shares, each kind keeping that many on its own; one under ten minutes old stands in for a new one when the Saves folder has not changed since. Older zips in the default folder stay listed, restorable, deletable and pinnable. A new zip may have a sibling `<stamp>.json` recording why it was made, `{profile, kind}` with kind `update` (before a mod update, naming the profile), `restore` (before a restore), `launch` (before playing), `manual` (Saves tab **Back up now** or `mortar backups create <save>`, pinned), or `scheduled` (one save, named in `save`). A zip without one shows as unknown. Scheduled zips rotate per save against `saveBackupKeep`; each other kind rotates against `saveBackupsKept`, so no kind evicts another's. Only a whole-Saves zip (not `manual` or `scheduled`) stands in for a new one.
- `cache/`: API responses, mod pictures, the dataset index, and Content Patcher scan results.
- `<game>/last-played.json`: each save folder last launched with a profile (`profileId`, RFC3339 `at`), written when a run ends and SMAPI's log names the save it loaded.
- `queue.json`: the download queue's state, without `nxm://` keys.
- `downloads/<item id>.<ext>`: a download in progress, with `<name>.resume.json` beside it (expected size, `ETag`, source URL and the checksum when the server sent one). A failed or interrupted fetch keeps both; Cancel and Skip delete them.
- `download-history.json`: every finished queue item, the last 1,000, newest last, written temp then rename.
- `nexus-seen.json`: per Nexus mod id, what the user last looked at (`newestFileUnix`, `newestChange`, `lastLookedUnix`), capped at 2,000 mods with the least recently looked dropped first.
- `categories/<game>.json`: custom mod categories for that game (`id`, `name`, optional `color` from the profile palette). A deleted category clears that override on every profile entry.
- `tools/<game>.json`: external programs for that game (`internal/tools`), each with `id`, `name`, `executable`, `arguments` (a JSON array, never a shell string) and `workingDir`. Placeholders `{game}`, `{mods}`, `{saves}` and `{profile}` expand in arguments and the working directory when a tool is launched for a profile; an empty working directory uses the game install folder. The executable must exist and be a regular file on save. Launch uses `os/exec` without a shell, detached, with one info log line.
- `bundles/<game>.json`: named sets of mods for that game (`internal/bundles`). Each bundle has `id` (16 lowercase hex characters), `name` (at most 60 characters) and `mods[]` (`id`, `name`, `entryKey`, `source`). `RemoveMods` drops mods from a bundle (never the last). Applying a bundle copies those store entries into a profile through `AddEntry`; UniqueIDs the store does not hold are listed as missing and are not downloaded.
- `endorse-prompts.json`: per Nexus mod id, progress toward an endorse prompt (`clean`, `asked`, `never`, optional `askedAt` and `lastRun`). After five completed runs with no errors from that enabled Nexus mod, Mortar may prompt when `askEndorseMods` is on ([gui-design.md](gui-design.md#mods-tab)).

Each `entries[]` item:

The store keeps every item a profile names as `key` or `previousKey` and deletes the rest 30 days after their last use. `ProfilesWithMod` lists, for a game and UniqueID, the profiles that name it, by reading those `profile.json` files (not the store); UniqueIDs compare case-insensitively.

**Hero cover** (`internal/profile/cover.go`): Choose cover image… copies the picked file into the profile folder (PNG, JPEG or WebP from content, at most 16 MB; the original path is never kept). Duplicate copies it with the profile. `Covers` tries, in order:

1. The picked cover, served by `CoverMiddleware` at `/profile-cover/<game>/<id>` (validated game and id; only the three fixed file names).
2. The `picture` of the profile's Nexus entry with the highest `endorsementCount` as stored at install (no new call).
3. Steam's art at `/steam-art/<appid>`.

The frontend moves on when one fails to load and shows a solid tone after the last.

## Settings file

`settings.json` is one JSON file with a `formatVersion` and three blocks: `global`, `sources` (per mod source id) and `games` (per game id). A key is read at the most specific scope that sets it (source, game, install, loader, profile), then the broader ones, then its default (`internal/settings/scope.go`). Source-scoped keys sit in their source's block (Nexus's account and `nxm` keys, `autoTrackNexus`, `verifyNexusMD5`; Thunderstore's `handleLinks`); a file split this way is read and written as the flat field list below.

The registry (`internal/settings/registry.go`) lists each key with its scope, type and default for the CLI and Settings. A missing or unparseable file gives the defaults. A value that breaks its rule is replaced by the default when the file loads and refused with an error when written. Defaults in brackets.

- `language` (empty): interface locale. Empty follows the OS language when Mortar has a catalog for it, else English. The only catalog is `en`; any other non-empty value is dropped on load and refused on write.
- `accent` (`sand`): `sand`, `moss`, `copper` or `sky`.
- `background` (`image`): `image`, `desktop` or `solid`.
- `backgroundImage` (empty, the default wallpaper): the absolute path of the user's image; set only when it is a readable PNG, JPEG or WebP file, and empty clears it.
- `lastGame` (empty): the game last opened; any id.
- `lastProfile` (`{}`): game id to the id of the profile last open in it.
- `lastPlayed` (`{}`): game id to `{profile, at, gameVersion}`. `at` is RFC3339 and recorded when a launch reaches Running; `gameVersion` is the game's version from that launch's SMAPI log header or, for BepInEx, from the running game's bridge `status` once it reports the game's own version (`gameVersionSource` `game`; Unity's `Application.version` and an older bridge's answer are ignored), and the previous value stays when neither gave one. An entry with an empty game, profile or time, or a time that does not parse, is dropped.
- `gameFolders` (`{}`): game id to an install folder the user chose, which wins over store discovery; checked as a game install when set, and emptied to go back to discovery.
- `gameStores` (`{}`): game id to the store to use when several installs are found (`steam`, `flatpak-steam`, `gog`, `gog-heroic`, `lutris`, `bottles`); an unknown value is dropped on load.
- `launcherRoots` (`{}`): launcher id to folders the user added for it, searched before the usual places.
- `launchersConfirmed` (false): whether first run's launcher screen was finished; until then the app opens on it.
- `loaders` (`{}`): game id to the loader version Mortar installed.
- `dismissed` (`{}`): profile dismissal bucket to tokens for hidden warnings. Problems keeps dismissed conflicts, abandoned mods, listed requirements and settings available in its Dismissed section; restoring removes the token.
- `nexusUserId` (0), `nexusName` (empty), `nexusPremium` (false): the signed-in account, for display; a zero id means signed out.
- `nxmHandled` (false), `nxmPreviousHandlers` (`{}`), `nxmAsked` (false): whether Mortar handles the source link schemes, the handler each scheme had before (absent when none), and whether the user was asked.
- `thunderstoreHandleLinks` (unset, which means off): whether Mortar claims `ror2mm://` links from the system. Stored as `sources.thunderstore.handleLinks`; `source.SetHandleLinks` carries it to the source registry, and a source without the choice keeps its driver's default (Nexus on, Thunderstore off).
- `showAdultContent` (false): when off, browse drops hits a source flags as adult; installed mods are never hidden.
- `nxmPreviousName` (empty): display name of that previous handler.
- `nxmRedirectOtherGames` (on when `nxmPreviousHandlers` is set, else off): send non-Stardew `nxm://` links to the previous handler.
- `nexusPreferredDownloadServer` (empty): a seen `download_link.json` `short_name`, or empty for Automatic.

### Store integrity

Installing an item records the SHA-256 and size of every file in it, beside the store (`.manifests/<game>/<key>.json`) so the hashes are never copied into a profile. `store.Verify` hashes the item again and reports files missing, changed or extra; an item stored before hashes were recorded is baselined by its first verification, which cannot see earlier damage. For a Nexus item the check first looks in the downloads folder for an archive of that mod whose MD5 is the one Nexus lists for the file; a match is extracted the way an install extracts it and its hashes become the baseline, so damage done after the install is found.

This needs a Nexus sign-in and the original archive: without either, the item is baselined from its current files as before. A matching MD5 proves the archive is what Nexus served; it cannot show damage to an item that was already damaged when it was first verified, nor anything for a GitHub or local item (a local item's key is already its archive's SHA-256, which Repair uses). `store/verify.json` keeps each item's last verification time and verdict (`Damaged` feeds the Problems check). Removing an item drops its records.

A background pass (`storecheck.Run`) starts three minutes after launch and verifies items not checked in the last 7 days, oldest first, one at a time. It waits while a game runs or a download or install is active, sleeps four times each item's check time (at least one second) between items so it uses about a fifth of one core, and pauses during a check from Settings. Settings › Storage › **Check store files** verifies every item now with progress and a summary.

A damaged item shows on the Problems tab of each profile that holds it ("<mod> has damaged files") with **Repair**: the item is set aside, then a Nexus or GitHub item is queued for download again from the recorded source (the queue swaps it in; the damaged copy is put back if the queue refuses the request), and a local item is extracted again from its archive when that is still in the downloads folder, else Repair says so. Loader items (`smapi-*`, `bridge-*`) are repaired by reinstalling the loader.

## Profile operations

**Materialising store items into a profile** (install, duplicate, rebuild, re-extract, update from the store) is per file, in this order, falling through on `EXDEV` / `EOPNOTSUPP` / `EINVAL` / `ERROR_INVALID_FUNCTION` (capability cached by filesystem device id):

1. Copy-on-write clone (`FICLONE` on Linux, block cloning on Windows ReFS / Dev Drive, `clonefile` on macOS).
2. Hardlink, same filesystem.
3. Symlink.
4. Plain copy.

Files a mod may write (`config.json` at any depth, anything under `data/` or a saves-like folder (`saves`, `save`, `savedata`), and `*.mortar-old`) use clone or copy only. So do text files a user might open in an editor (`.json`, `.txt`, `.ini`, `.cfg`, `.xml`, `.yaml`, `.yml`, `.toml`, `.csv`, `.tmx`, `.md`), because most editors also save in place; drift still treats those as shipped files. SMAPI's `helper.Data.WriteJsonFile` uses `File.WriteAllText`, which truncates in place; a hard link or symlink would leak one profile's write into the store and every other profile. Deleting a profile unlinks its names only and never removes store files. Drift ignores those writable paths and does not treat a linked or cloned shipped file as modified.

**Operations:**

- **Toggle** a mod: rename the folder holding its `manifest.json` with a leading dot, which SMAPI skips (measured), and record it in `disabled`.
  - Enabling a mod whose required dependencies are already in the profile but disabled enables those in the same write; the toast says "Also enabled X". Optional dependencies are left alone.
  - When the manifest sits at the archive's root, that folder is the entry's own `mods/<store key>/`, so the entry is found by its key with or without the dot. Programs can create leading-dot names on NTFS.
- **Enable, disable and remove several at once:** one write to `profile.json` per action, under the same running-game lock.
- **Duplicate:** clone or copy the profile's `mods/` folder as it is (never hardlink or symlink, so an in-place write cannot leak into the source profile), mod-written data included, under a new id, and record origin `copy` with `copyOf` the source profile's name.
- **Delete:** move the profile folder to `trash/`, restorable for `trashRetentionDays` (default 30). **Delete permanently** (`Purge`) removes one trashed profile; **Empty trash** (`PurgeTrash` with the game id) removes every trashed profile for that game. Both refuse a symlink. Startup still deletes trash older than that retention.
- **Damaged:** `List` still returns a row `{id, error}` when `profile.json` cannot be read. Callers skip those rows; `ListDamaged` is what the Profiles page and `mortar profiles` use to show them. `StoreKeys` skips a damaged live profile so one corrupt file does not stop collection. **Repair** (`mortar profile repair`) rebuilds `profile.json` from the latest readable history snapshot, leaves `mods/` as it is, and renames the broken file to `profile.json.damaged-<timestamp>`; Undo puts that file back. Repair is refused when no snapshot exists.
- **Import from the game's Mods folder:** scan one level of `<game>/Mods` the way SMAPI and archive install do (a folder with `manifest.json`, or a folder of those folders).
  - SMAPI's bundled Console Commands and Save Backup and Mortar's bridge are left out of the preview and are not counted as skipped.
  - When two folders hold the same `UniqueID`, import one: the enabled copy if either is enabled, otherwise the newest version; the other is skipped with the reason `same mod as <folder>`.
  - Copy each remaining folder into the store with the same hashed-folder install path as a dropped folder (dedup by content, manifest identity, `UpdateKeys` as Nexus or GitHub source).
  - Dot-prefixed folders land disabled and the preview marks them "(disabled)". Skipped and failed folders show in the preview with their reason.
  - Each `config.json` is copied into the profile. The game folder is not written. The new profile is named "Imported mods" (or "Imported mods (2)", …) and records origin `game-mods`.
- **Move from the game's Mods folder:** `NewGameModsFolders` lists the mod folders in `<game>/Mods` that hold a usable mod, leaving out SMAPI's bundled mods, Mortar's bridge, folders that repeat a mod another folder holds, and folders the user dismissed (`DismissGameModsFolder`, kept in `dismissed` under `gameMods:<game>`, by top-level folder name). `MoveGameModsFolders(profile, folders)` copies each into the store and the profile as Import from the game's Mods folder does (config carried, a dot-prefixed folder lands disabled), then deletes it from the game folder by renaming it aside first (into the profile's removed-mods trash, or beside itself on another volume), so a file held open leaves it whole. A folder whose UniqueID the profile already holds is skipped and left in place. The move records one `imported` history event and is refused while the game runs that profile or the game process is up at all (`Store.GameRunning`).
- **Dot-hidden mods:** a folder inside an entry whose name starts with a dot that Mortar did not add (one it adds is a switched-off mod's own folder) hides every mod under it from SMAPI, so the entry does not list them. With the per-game `showDotHiddenMods` on, `DotHiddenMods` lists those mods per entry (`key`, the dotted `folder` relative to the entry, and the manifest's UniqueID, name, author and version); with it off it lists none. `ShowHiddenMod` opens one's folder and `UnhideMod` strips the leading dots from the folders above it (refused while the game runs, when the UniqueID is already loaded or the undotted name is taken) and adds the mod to its entry.
- **Extra mods folder:** `ExtraFolderMods` lists the per-game `extraModsFolder` the way Import from the game's Mods folder previews it (each row carries its top-level `folder`), and `InstallExtraFolderMod` installs one of those top-level folders into a profile through the same path as a dropped folder (hashed-folder store item, local source). A path that is not a direct, real child of that folder is refused. The folder itself is never written.
- **Outside edits:** beside `profile.json` Mortar keeps `mods-snapshot.json`, a cheap fingerprint of each entry folder (top-level name, file count, total size, newest mtime, skipping `config.json`, `*.mortar-old`, files under `data/` or a saves-like folder, and other files the update carry-over treats as user- or mod-written). On profile load and when the window regains focus (debounced) it compares the live `mods/` tree to that snapshot and to `profile.json`.
  - An unknown folder can be Adopted (the same hashed-folder install as Import from the game's Mods folder) or Removed (moved to `trash/`).
  - A deleted entry can be Restored from the store or Forgotten.
  - Changed shipped files can be kept (refresh the snapshot) or Reverted (recopy from the store, carrying over config as an update does).
  - Findings show on the Problems bar. A first scan with no snapshot records the current tree and reports nothing.
- **Compare:** `Diff` matches user mods of two profiles of the same game by UniqueID (bundled SMAPI and bridge entries omitted) and lists those only in A, only in B, and in both with a different version or enabled state. `CopyMods` copies selected UniqueIDs from one profile into the other through `AddEntry` (the store item already on disk; no download) and matches the source enabled state; a running game locks the destination as other mods-folder writes do. Copy works in both directions. The compare window filters those lists by name or UniqueID, copies the checked rows of an "only in" section, and **Match versions** switches differing entries through `UpdateEntries`, one atomic change (a failure undoes every swap already made; one history event; moves repeated for one entry, as a multi-mod store item yields, apply once) ([gui-design.md](gui-design.md#profile-management)).
- **Match a friend's profile** (Compare › A friend's link or file…): Import opened against an existing profile previews a share link or `.mortar` file beside that profile: already matching, missing (to download), different version, and UniqueIDs only in the local profile (Replace would remove those; Add keeps them).
- **Bundles:** a named set of UniqueIDs saved per game under `bundles/<game>.json`. Creating one snapshots the chosen mods' store keys and sources; applying it copies those store items into a profile. Mods Mortar does not hold stay listed as missing.
- **Templates:** `templates/<game>.json` holds named templates (`name`, `bundle[]` of non-bundled mods only, `disabled[]` mod ids that start disabled, `gameSettings`, `launchOptions`, `launchPrefix`, `launchEnv`, `overrides`, `launchPresets` and `defaultLaunchPreset`; `internal/templates`; their `entryKey`s are in the store keep set). `NewProfileFromTemplate` and `ApplyTemplate` share one fill (both split the mods first): the template's mods go through `bundles.ApplyMods` (one `template` history event), then its game settings replace the profile's and each non-empty launch part (options, prefix, environment, overrides, presets) is set. `ApplyTemplate` first calls `profile.Store.Baseline` (the newest history event when its snapshot is the current mods, else a new `restored` event) and returns an `Undo` (that event id, whether mods were added, the prior game settings and launch state); `UndoApplyTemplate` reverts to the baseline and restores the settings and launch state. `ApplyTemplate` first splits the template's mods against the profile: same store entry is already held, same UniqueID under another entry is a different version and is skipped, the rest are added; the profile's own mods are never removed. `PreviewApplyTemplate` returns that split plus the settings that would change and the added mods the store lacks (`missing`); the frontend queues the downloads in `ApplyResult.MissingMods` through `bundleWants`. `RenameTemplate` renames one (never onto another template's name) and `RestoreTemplate` puts a deleted `Template` back, which is the delete toast's Undo.
- **Also in other profiles:** `CopyMods` and `RemoveEntry` run the same UniqueIDs against other profiles of the game the user ticks. After an update finishes in the open profile, Mortar offers **Update \<mod\> in other profiles** for those that still hold the old store key (pinned destinations are named and skipped).
- **Back up and restore a file** (`packsvc/backup.go`; one action each in the profile menus, `profile backup` and `profile restore` in the CLI):
  - Back up writes one zip: `backup.json` (format version, game, every setting and entry of the profile, and a content hash per store item carried), the profile's history, config files and cover under `files/`, its own saves under `saves/` when it keeps them, and the store item of each mod under `store/<key>/`. The dialog's **Include mod files** (on by default, `--no-mods` clears it) carries every mod, so the file restores offline; off, it carries only the mods no source can download again. Bundled entries and rollback copies are never packed.
  - Restore makes a new profile named with `UniqueName`, never overwriting one. Store items go in only when their hash matches; mods the file lacks queue from their sources, and the ones no source has are listed as unavailable. It also reads the older profile zip (`profile.json` plus `mortar-export.json`, a SHA-256 per file, mods as they sit in the profile), which nothing writes any more: it needs the game from the caller, extracts with the archive caps, checks every hash, refuses paths that leave the zip and ignores an absolute `cover` path. The two are told apart by `backup.json`.
- **Typed config editing** (`internal/configsvc`): the window's config editor reads a mod's config files as typed schemas and writes one entry at a time. A mod's files are its SMAPI `config.json` (when its folder holds one) and the `.cfg` files in `<profile>/BepInEx/config` whose file name or `## Plugin GUID:` header matches the mod id; an empty id lists every `.cfg` of the profile. `Mods(game, profile)` builds the Config page's list in one pass: each user mod with a config source (its `config.json` with whether it differs from the shipped copy, the `.cfg` files its id or plugin GUIDs own, a captured in-game menu with the count of its pending edits), the unowned `.cfg` files, and how many mods have no config yet. `Schema` returns sections of entries, each with a type (`bool`, `int`, `float`, `enum`, `string`, `color` or `list`), value, default, description, range and acceptable values, and a `flags` marker for an enum whose values combine with commas.
  - A `.cfg` is read in BepInEx's own layout (`## description` lines, `# Setting type:`, `# Default value:`, `# Acceptable values:`, `# Acceptable value range:`, then `Key = value` under a `[Section]`). `Set` validates the value against the entry's type and range and rewrites only that entry's line, so every other line, comment and blank line stays as it was (`FuzzCfgSetKeepsOtherLines` holds it); `Reset` writes the entry's default back, and `ResetAll` resets every entry that has a default and returns how many have none.
  - A `config.json` is flattened in file order: a nested object becomes a section named by its dotted path, an array a `list` entry holding compact JSON, and a `#rrggbb` or `#rrggbbaa` string a `color`. Writes go through the profile's `SetJSON`, which joins the path onto the mod's folder (a path that leaves it is refused), parses the JSON, keeps key order, types and unknown fields, and writes through a temp file and rename. Where the Mortar SMAPI Bridge captured the mod's Generic Mod Config Menu options, their labels and ranges come with the entries.
  - Every write fails with the running error while the profile's game launches or runs, and a `.cfg` name is only ever a bare file name inside the profile's BepInEx config folder.
- **Pin and skip:** **Pin this version** in the UI is `pinned` (with an optional `pinReason`; CLI `keep` and `unkeep`); pinning and unpinning each write a `pinned` history event. While an entry is `pinned` no update is offered for it; `skipVersion` hides that exact newer version until a later one appears. Both are written with the profile and dropped from the per-profile update count, Update review and Update all.
- **When mod updates are checked:** at Mortar startup (when `checkModUpdatesOnStart` is on), and every `updateCheckIntervalMinutes` (default 60) for the open profile while Mortar runs; SMAPI's API answers are cached for an hour per profile fingerprint, and F5 or the app menu's update check asks again without the cache (`CheckUpdatesNow`).
  - SMAPI's API is asked 100 mods per request.
  - For the mods it flags, Nexus's v2 GraphQL API is asked once for all their current file lists (aliased `modFiles` queries, 50 mods per request; signed in only): an update is real when a newer non-archived file with the same display name exists or the installed file's version is below SMAPI's, and an unbumped manifest inside the newest file is not offered.
  - Signed out or when that call fails, the mod dataset's file list decides the same way, and a dataset page that lists nothing newer than SMAPI's version is treated as stale.
  - The same toggle also starts a background pass 5 minutes after Mortar opens, then every 4 hours: every installed game's profiles, skipping a game or profile that fails.
  - When a profile's update count is higher than last notified this session, a desktop notification **"Mod updates available"** names the profile with the largest such increase (`N mod updates available for <name>`).
- **Change history:** `internal/profile/history.go` appends an event list in `history.json` whose length is capped by `historyEventsKept` (default 200, 20 to 2000).
  - Each distinct entry snapshot is written gzipped to `snapshots/<sha256>.json.gz` (about a seventh of the plain JSON); an uncompressed `.json` snapshot is converted when it is read or the history is pruned. Snapshot and `history-files/` bytes are not capped.
  - Each event stores its added, removed and updated counts when it is recorded, so listing history reads only `history.json`; `counted` marks a file whose events all carry them, and an older file is counted from its snapshots once.
  - An event also keeps the profile's settings (`ProfileState`: groups, loader, game install, separate saves, launch options, prefix, env and presets, per-profile overrides, collection), and a change to only those records a `settings` event. Revert restores them with the entries; name, notes, colour, cover and profile order are not history. A `config.json` written by Mortar (`WriteConfig`, a preset, Reset) records a `config` event after one capturing the file as it was; Revert rolls configs back only when every event since the target is such an edit, and per-item revert restores one file. `TestEveryProfileChangeRecordsAnEventAndUndoesExactly` runs each mutation and its undo.
  - Revert restores an earlier snapshot. A revert that needs store items Mortar no longer holds names those mods and the window offers to download them.
  - A successful revert toasts Undo, which reverts to the snapshot that was current before. Replacing a profile from a share records the removals in that log.
  - Export zip leaves `history.json`, `snapshots/`, `history-files/`, and `runs/` out.
  - `RecentHistory` (and `mortar history --all`) merges those events from every non-damaged profile of the game, newest first, capped at 50.
  - Changes since last run are cached until the profile's `updated` time changes.
- **Update or roll back** an entry: copy the target version from the store into a fresh folder, then carry over what the mod or the user wrote, by comparing three copies of each file: the profile's, the store's copy of the current version, and the target version.
  - A file only the profile's copy has (such as `config.json` or mod data) is carried over.
  - A file the profile changed is carried over when the target version ships it unchanged from the current version. When the target version changed it too, the target's file wins and the profile's copy is kept beside it as `<name>.mortar-old`.
  - When the target version's manifest sets `DeleteOldVersion` (Stardrop's name, read case-insensitively like other manifest keys), carry-over applies only to user-written files such as `config.json`, not to other files the profile changed from the old version.
  - A file the profile holds unchanged from the current version that the target version no longer ships follows the per-game `oldFilesOnUpdate`: `delete` drops it, `keep` carries it into the new folder, and `ask` (default) moves it out of `mods/` to `old-files/<new key>/<UniqueID>/<path>` beside `profile.json` once the update is recorded. `PendingOldFiles` lists those sets per entry (`key`, `label`, `files[]` of `{uniqueId, path}`) and `ResolveOldFiles(key, keep)` puts them back into the mod folder (never over a file it has again) or moves them to `trash/<game>/removed-old-files/<profile id>/<stamp>/<key>`; `TrashOldFiles` does the same and returns a token that `RestoreOldFiles` takes to make the set pending again (the Delete toast's Undo); a set whose entry has since changed version or left the profile is deleted when listed. A mod whose manifest sets `DeleteOldVersion` never asks.
  - Keep the leading dot on disabled folders; then swap `key` and `previousKey` and remove the old folder.
  - Before updating a profile, zip the Saves folder into `backups/`.

## Command line

Mortar is GUI-first: the command line exposes only what the window can already do, and a new capability lands in the window first.

- Verbs: [HUMANS.md](../HUMANS.md#command-line).
- `mortar <verb>` (`internal/cli`) is decided in `main` before `application.New`, so it never takes the single-instance lock or opens a window; any other first argument, a link, a file path, or `--play=<game>/<profile>`, is a window launch.
- `--play` ids may not contain `/`, `\`, space or quotes; a running instance receives it as a second instance (`play:requested`) and Play follows the usual path, warnings included.
- A desktop shortcut's `--play` always plays in the usual window: a closed Mortar starts with its window shown and takes the request as a running one does. A Mortar that starts with `--play=<game>/<profile> --steam-session` (an Add to Steam shortcut while Mortar is closed; Steam's Game Mode on the Deck) runs in play mode (`shortcut.Service.Start`, `frontend/src/launch/playMode.ts`): the window starts hidden and the frontend renders only the launch layer, Play takes the usual path with every pre-Play check, and the window stays hidden while the game starts. When a check blocks Play (the pre-Play check, a changed game version, a save that needs other mods, the ask to launch without Steam, a failed start), the window comes up at 560×480 holding only that dialog, with the larger targets of touch or a gamepad. Play anyway hides it again; Cancel (or Esc, B, Close) quits; any other way out (Open Problems, Open Saves, Switch profile, adding the missing mods) or an error toast leaves play mode, and the full window opens on that profile as a normal session that outlives the game. In play mode `main` follows `launch:state` for the played game and quits once it has been Running and is Idle again, after the purge and settings restore, so Steam counts the shortcut's playtime from Mortar's own process. The Play action's window setting (`onPlay`) does nothing in play mode. A `--steam-session` start that finds a Mortar answering on the control channel does not hand off as a second instance (that exits at once); `main` sends `play.request` over the control channel before `application.New`, then `shortcut.Follow` polls `status` for the game and exits once it has been active and is idle again, so Steam counts the playtime either way. A game not started within 15 minutes (Play blocked and cancelled) ends the wait; so does a Mortar that quits.
- The CLI is a client of the running app: at startup the app (`internal/control`) listens on `127.0.0.1` with an OS-chosen port and writes `control.json` (`port`, a random 32-byte `token`, `pid`, `version`, `protocol`; mode 0600) in the data folder, removed on exit only while it is still that instance's file. A start that finds another Mortar answering `hello` with the token in `control.json` (a server build, which has no single-instance lock, or a desktop build without a session bus) waits five seconds for it to exit, as a restart's old process does, and otherwise stops with an error before it rotates the log or touches any data. A server build refuses to start on the account's own data (`HOME` is the account's home, or the default data folder is the account's) unless `MORTAR_SERVER_REAL_DATA=1`, since it has no single-instance lock beside a desktop Mortar; `scripts/selftest.sh` gives it a sandbox `HOME`. Without `WAILS_SERVER_PORT` it takes a free loopback port instead of Wails' default 8080; the desktop app opens no HTTP port. The control protocol (`controlwire.Protocol`, 1) is versioned: the `hello` method returns `{version, protocol}`, and the CLI calls it before its first request and fails with "this mortar CLI speaks control protocol N, the app speaks M" when they differ.
- Each connection carries one JSON request line (`token`, `method`, `params`) and gets one reply line (`result` or `error`); the token is compared in constant time.
- Methods run on the app's own services, so the window and the CLI never write the data folder at once, and a change emits `profiles:changed` with the game id, which reloads that game's profiles in the window.
- `launch` detaches the game from the request (`context.WithoutCancel`).
- `open` runs the binary again with the link, which a running window takes over the usual second-instance path.
- On Windows the GUI-subsystem exe attaches to its parent console (`AttachConsole`) unless its output is redirected.

## Trust boundaries

Everything from outside is untrusted: links, `.mortar` files, archives, API responses. Share links and `.mortar` files have their own caps and rules in [Sharing](#sharing).

- Extraction keeps every entry inside its destination; caps each entry at 256 MiB, decoder dictionaries and PPMd memory at 256 MiB, the archive at 2 GiB extracted and 20,000 entries; rejects symlink entries, Windows reserved names (`CON`, `NUL`, ...), `:` in names, and names that differ only by case.
- An `nxm://` link is taken only in the exact form `nxm://stardewvalley/mods/<mod id>/files/<file id>?key=<key>&expires=<unix>&user_id=<id>`, unexpired, and for the signed-in account's `user_id`; anything else is refused with the reason. A link Mortar was not waiting for asks which profile it is for before anything downloads.

## Failure behaviour

Once mods are installed, nothing external is needed to open, edit or launch a profile. Failures that reach the user are classified in `internal/usererr` (not found, busy, network, permission, disk full, damaged, invalid). Go wraps the cause as `[kind] message`; the window (`errorMessage` in `frontend/src/toasts/report.ts`) and the CLI (`Sentence` in `internal/cli`) map the kind to the same English sentence, with the cause in a Details tooltip or under `--json` / `-v`.

- **A mod source unreachable:** `internal/netstate` records, per source, whether its last real request hit a network error (DNS, timeout, refused) and when it last succeeded; an answer that is merely bad leaves the state alone, and Go emits `netstate:changed` when a source flips. While the window is focused it reads that state every 15 s and probes only the unreachable sources every five minutes. A banner names each down source with the time of the cached data shown for it ("as of"), or says nothing is saved yet; network actions that need a down source are disabled with that sentence as the tooltip (`frontend/src/shell/OfflineBanner.tsx`, `OfflineGate.tsx`), and Settings › Sources gives each source's reason in words.
- **SMAPI's API or the dataset unreachable:** the feature degrades and never blocks; update checks show "unknown", dependencies are checked after download.
- **Archive formats:** `internal/archive` reads zip, RAR, 7z, tar, and gzip, xz, lzma, zstd and bzip2 streams, found by magic bytes and never by extension (`archive.Extensions` is only what the pickers, the drop, the downloads watcher and the GitHub, CurseForge and Nexus name handling accept). A compressed stream whose payload has a `ustar` header is read as a tar (`.tar.gz`, `.tgz`, `.tar.xz`, `.tar.zst`, `.tar.bz2`, `.tar.lzma`; a plain `.tar` too); any other compressed stream is one file named from the archive's name without its suffix. A classic `.lzma` stream has no magic, so it is recognised by a valid properties byte, a power-of-two dictionary size and a sane length. Tar entries pass the zip guards: names through `admit`/`cleanName`, symlinks and hardlinks refused as `ErrLink`, devices, pipes and sparse files as `ErrSpecialFile`, and bytes counted against the entry and total caps while a budget caps what the stream decompresses. Libraries: stdlib `compress/gzip`, `compress/bzip2`, `github.com/ulikunitz/xz` (xz and lzma) and `github.com/klauspost/compress/zstd`. A v7 tar without the `ustar` marker is not recognised. The download queue keeps a bare compressed file as `<id>~~<original name>` (`archive.SavedName`; every other download stays `<id><ext>`), so the one extracted file takes its real name, and the downloads sweep reads the id back with `archive.SavedID`. A dragged-in file is extracted from its own path, and a LAN transfer carries already-extracted store items, so both keep their names.
- **A download cut off or corrupt:** extraction goes to a temp folder on the store's volume and moves into the store only when every entry passed its checksum (CRC32 in zip, RAR and 7z; gzip and zstd check their own); failure deletes the temp folder and the item can be retried. **Disk full** fails the same way and says how much space the item needs.
- **Mortar quits mid-operation:** every write is temp-then-rename (`datadir.WriteFile` / `WriteJSON` / `WriteStream`), and startup removes leftover temp folders. `crash.log` is capped at startup once `crash.seen` already covers it (seen resets if the file was truncated). A `mods/` folder deleted outside Mortar is rebuilt from the store from `profile.json`.
- **Startup repairs are reported once:** what startup repaired by itself (leftover store temp folders, a `mods/` folder rebuilt or cleaned, file names repaired, history snapshots compressed, an emptied crash log) is collected by `internal/tidy` and logged. When the startup work has finished and anything was repaired, the window shows one info notification, "Mortar tidied up N things", with the details (what, where, names) under **Details**; nothing is shown otherwise. Rebuilds that happen after startup are logged only.
- **A newer Mortar wrote a state file:** `profile.json`, `settings.json`, `queue.json` and `history.json` carry `formatVersion` (1; a file without it is read as 1). When the file on disk names a higher version, `datadir.WriteVersioned` refuses to write it, keeps a copy as `<name>.newer`, and returns an error telling the user to update Mortar; `datadir.CheckVersion` is where a future format migrates.
- **Steam not running:** `-applaunch` starts it. **Not installed:** a Steam copy can launch through SMAPI directly, without the overlay, after the user agrees.

## Games and the catalog

Everything that can be data is catalog data; code exists only where behaviour differs, as a driver found through a registry. Adding to each registry: [HUMANS.md](../HUMANS.md#adding-a-game).

- **Catalog:** `internal/components` holds `GameInfo` entries (id, name, enabled, marker, stores, paths, `saveFiles`, `saveCompanions`, loaders, sources, metadata, `r2modmanFolder`, and an optional `knownBroken` list of `{id, versions, reason, replacement}` entries: Mortar's curated known-broken mods and packages, `versions` being space-separated constraints such as `>=1.0 <1.5`; it is validated with the rest of the game and an older Mortar ignores it, so the v2 manifest schema is unchanged and the list ships empty) in the signed component manifest. `game.Catalog()` returns the verified manifest's games when it lists any, else the bundled ones, enabled or coming later. `GameInfo.Validate` guards the shape, and `TestEveryCatalogReferenceResolves` checks that every source, loader, metadata id, store field, path role and path token resolves.
- **Stores** (`internal/gamestore`): one driver per store key in the catalog's `stores` (`steam`, `gog`, `lutris`, `bottles`); a driver runs only for games whose entry names its key. `Discover` returns each game's installs with the store that reported them, and `Rank` orders stores when a default is chosen. A folder the user chose wins over discovery and has origin `folder`.
- **Installs and runtime** (`internal/game/install.go`, `internal/runtime`): an install is a store and a folder with a stable id, a platform (an `.exe` marker is a Windows build) and a runtime. `native` resolves a catalog path template with the host's folders; `proton` claims a Steam Windows build on Linux and resolves the template inside its `compatdata` prefix; `wine-prefix` claims a Windows build found in a Bottles bottle (the install carries the bottle as `prefix`), resolves the template inside the bottle's `drive_c/users/<user>`, and `runtime.Command` / `runtime.Run` wrap a launch or a Windows installer as `bottles-cli run -b <bottle> -e <exe> -- <args>` (`flatpak run --command=bottles-cli com.usebottles.bottles` for Flatpak Bottles). `game.PathFor` resolves a role (`saves`, `startupPreferences`, `errorLogs`) for an install; a game without that role in its entry has none.
- **Sources** (`internal/source`): a driver registers itself (`source/all` imports them) and implements `Source` plus optional capabilities found by type assertion: `Searcher`, `Categorizer` (category names a query's include and exclude lists match), `Gated`, `Schemer`, `Hoster` and `LinkOptIn`. `source.ForGame` lists a game's sources in catalog order, skipping a catalog entry with no driver. A scheme is claimed from the system only when its source's choice allows it (`source.SetHandleLinks`, else the driver's default), which is what OS registration and `source.IsLink` read. Drivers: Nexus (GraphQL search, `nxm`), GitHub, Thunderstore, Modrinth, CurseForge and itch.io. A `Gated` source says through `Unavailable()` what the user must set up first (itch.io's API key), or "" when it is ready: `source.Unavailable` is what `browse.Service.SearchableSources` hands the window, which greys the source's chip with that reason, and an `all` search leaves such a source out.
- **Browse** (`internal/browse`): a search names one source or `all`. `all` asks every searchable source of the game at once and interleaves the answers so each keeps its ranking; sources that fail are listed in `Failed`, and only when all fail is it an error. Hits of one mod from different sources fold into one card (`mergeSame`), on package identity or an explicit link and never on names: the game's loader, the SMAPI UniqueID or loader plugin id both hits resolve to (from the open profile's entries and installed manifests, else the SMAPI compatibility list's Nexus page and GitHub repository refs), the GitHub repository a hit's site links, or the Thunderstore package its summary points at; a hit with no identity or link stays its own card. The card being the earliest source in the player's `SourceOrder` then catalog order and the others its `Alts`. A page holds `source.PageSize` (20) hits. Hits a source flags `Adult` are dropped per source before interleaving unless `showAdultContent` is on, and `Total` shrinks by the dropped count.
  - **Filter:** `Filter{Include, Exclude, Sort, Installed, Obsolete, Broken}` narrows a search. `Include` keeps mods in any listed category, `Exclude` drops mods in any (names match case-insensitively), and a source that is not a `Categorizer` ignores them and, under `all` with a non-empty `Include`, is left out. `Sort` is one of the `source.Sort*` values (`downloads`, `updated`, `newest`, `endorsements`, `name`, `stars`, `forks`; empty is best match). A source implements `source.Sorter` to list the sorts its own API honours, and `SearchableSources` hands them to the window, whose Sort menu offers only those: Nexus `ModsSort` endorsements, downloads, updatedAt, createdAt, name; Thunderstore the cached full listing ordered by downloads, rating, updated, created or name; Modrinth `index` downloads, follows, updated, newest (no name sort); CurseForge `sortField` Popularity, TotalDownloads, LastUpdated, ReleasedDate, Name; GitHub repository search `sort` stars, forks, updated (no downloads, name or created sort); itch.io none. Nothing is sorted client-side within one source. Under `all`, only `MergedSorts` (`downloads`, `updated`) are offered: each source returns its page in that order and `sortMerged` stably places the pages against each other, a hit with no value for the sort (GitHub has no download count; an unparsable date) after every hit that has one. Name and newest are not merged sorts because Modrinth and GitHub cannot honour them. `Categories(game, source)` lists category names, cached a day; Nexus serves them only to a signed-in account, so without one the pickers are empty.
  - **Top mods:** an empty search text lists each source's top mods, and `searchCached` reuses that answer for ten minutes per source, game, page, sort and categories, so opening Browse costs each source one request.
  - **Show modes:** `Installed`, `Obsolete` and `Broken` are each `off`, `gray` or `hide`. `mark` sets a hit's `Obsolete` (the same words as the Problems author-marked check, `problems.ObsoleteText`), `Broken` (the game's compatibility list, read only when the game has one) and `Loader` (the game's loader page: its Nexus mod id, or its BepInEx pack on Thunderstore, `GameInfo.LoaderPackage`); `applyModes` removes the `hide` ones and counts them in `Page.Hidden`, while `gray` is the window's to dim.
- **Thunderstore** (`internal/source/thunderstore`): search reads the community's chunked package index (`/c/<key>/api/v1/package-listing-index/`, a gzip list of chunk URLs). The slimmed listing is cached at `<datadir>/cache/thunderstore/<key>-<hash of the index blob>.json` and used for an hour without asking; after that only the index blob is fetched, and the chunks only when its hash changed. A failed fetch falls back to the cached listing. Deprecated packages are not searchable but still resolve as dependencies; packages flagged NSFW are marked `Adult`. Search ranks name over owner over description matches, then downloads. `Resolve` returns a version's download URL, size and `Namespace-Name-Version` dependencies; `ParseLink` reads `ror2mm://v1/install/thunderstore.io/<namespace>/<name>/<version>/`. `Closure` treats a dependency's pinned version as a minimum and installs the newest, as r2modman does, unless a root of the same request names that package at an exact version (an imported profile or modpack); a profile already holding it at that version or newer is left alone.
- **Gated sources** (`internal/source/modrinth`, `internal/source/curseforge`, `internal/source/itch`): the drivers are registered, and a game lists one as a catalog `source`; the shipped games list only CurseForge (Stardew Valley). All install through the queue's direct path (`queue.ResolveDirect`, `expandDirect`): the request and its required dependencies resolve dependencies first, each project once and at most 16 deep, into queue items that carry the file's address, size and digest, and a `sha512:` digest is verified after download. An entry's source kind is `modrinth`, `curseforge` or `itch` with the project or game id as its name.
  - **Modrinth** talks to the public API v2 (`https://api.modrinth.com/v2`) with the `User-Agent` Modrinth requires (`Rethunk-Tech/mortar/<version> (+https://mortar.rethunk.tech)`). A game's source `key` is a facet (`categories:fabric`, `project_type:mod`; a bare word means a category). A search is that facet AND one OR group of the included categories AND a negated facet (`categories!=`) per excluded category; `index` is relevance, downloads, follows or updated. `Resolve` takes the newest version, or the one named, and its primary file with the published SHA-512; only `required` dependencies are followed. The queue holds Modrinth fetches to 4 at once, started 5 a second after a burst of 10, which is Modrinth's 300 requests a minute per address.
  - **CurseForge** talks to Core API v1 (`https://api.curseforge.com/v1`) with Mortar's own key in an `x-api-key` header, never an address or a log: `-X .../internal/source/curseforge.apiKey=...` at release build, else `MORTAR_CURSEFORGE_KEY` for dev builds; with neither the source is `Gated` ("this build has no CurseForge API key"). A game's source `gameId` is CurseForge's game id and `key` its "Mods" class id (Stardew Valley: 669 and 4643; CurseForge's `/games` lists neither Lethal Company nor Valheim). A file has no version number, so its version is its display name and an update names the file by id; the digest is `sha1:<hex>`, which the site publishes besides MD5 and which names the file for update checks; the queue does not verify it (the lint bans weak hashes). Only `RequiredDependency` (relation 3) is followed. An update check posts the installed mod ids to `/mods` and compares each newest stable file's SHA-1 and name with the installed one. When an author forbids distribution (`allowModDistribution` false, or no `downloadUrl` and a refused `download-url`), the driver never builds a CDN address: the request fails with `NotDistributableError`, the queue opens the mod's page (`/projects/<id>`) and the error says to download it there and add the file from the computer. A request with a forbidden dependency fails the same way, naming that mod. The queue holds CurseForge fetches to 3 at once.
  - **itch.io** talks to the server-side API (`https://itch.io/api/1/x`) with the player's own API key, sent in an `Authorization` header and never in an address, so an error that quotes the address cannot leak it. The key is in the OS keyring under `itch`; `itch.Service.SignIn` tests it against the API, stores it and keeps only the account name (`itchName`) in settings, and a rejected key stores nothing. Without a key the driver reports `ErrNeedsKey` through `Gated`. The game's source `key` is searched as a keyword beside the player's text, since the API has no tag filter; the API has no sort and no total, so `Total` counts this page and, when the page is full, one more page so browse offers a next one. `Resolve` picks the upload by id or file name, else the first one not flagged as a demo or a soundtrack, and asks itch.io for its time-limited download address; itch.io items have no dependencies.
- **In-profile matcher** (`internal/browse/installed.go`): one matcher answers whether a Browse card is already in the open profile, for the card's `In this profile` chip and the `Installed` Show mode. `Hold(info, profile, installed)` collects the Nexus mod ids, lower-cased GitHub repositories and Thunderstore `Namespace-Name`s from (1) each entry's own source, (2) the `UpdateKeys` of every installed mod's manifest (`manifest.NexusUpdateKey`, `GitHubUpdateKey`), so a mod added from an archive or another site still matches the page its manifest names, and (3) when the profile holds the bundled `mortar` entry, the GitHub repository of each loader companion the game's catalog names (found through the component manifest), which are reported as `Bundled` and shown as `Installed by Mortar`. `Holdings.Has(source, id)` answers for `nexus`, `thunderstore` and `github` ids.
- **Metadata** (`internal/metadata`): the catalog's `metadata` ids resolve to providers with the capabilities `Updates`, `Status` and `Dataset`; callers ask the registry for the game's providers and a game without one gets none of that capability.
- **Hosts** (`internal/host`): `host.GitHub` fetches release assets (using the user's `gh` login when there is one) and `host.Direct` any other HTTPS address; the caller picks the host for its URLs; the direct host writes through a temporary file and caps the size, and the GitHub host resumes a download.
- **Loaders** (`internal/loader`): a driver registers itself by id (`smapi`, `bepinex5`) and implements `Loader` (`Status`, `Install`, `Contribute`) plus optional capabilities found by type assertion: `Vanilla`, `Owner`, `WithLogs`, `WithPlayerLog` (the game's Unity player log, which the analyzers also read), `WithConfig` (config folders in the profile Mortar may edit), `WithLaunchSettings` (launch options the loader keeps in the profile's own files, such as BepInEx's console and log level), `Console`, `Releases`, `ProcessNames`, `SteamExe`. `loader.For` lists a game's loaders in catalog order, skipping a catalog entry with no driver. A launch starts as a `launchplan.Plan` that the loader adds to (`Contribute`, or `Vanilla` for a launch without mods); the profile's own launch options, prefix and environment follow, and `game.Starter` runs the plan through the install's store: Steam installs through `steam -applaunch`, which hands the start to the game and exits, every other store by running the game's executable, and a loader that replaces the executable is never relayed.
  - **Pipeline** (`launchsvc`): one install runs one launch at a time (the preparing claim is the lock), then the loader contributes (or `Vanilla`), a game whose profile holds the loader first has its enabled packages laid out in the profile (`profile.Store.SyncPackages`), then the deployer places the plan's install-side files (`internal/deploy`, journaled under `<data>/journal/<install id>` before the first file moves; a loader that redirects the game to the profile, as SMAPI's `--mods-path` does, declares none and skips it), profile game settings are applied and the changed-launch save backup is taken, a profile with `separateSaves` has its own Saves folder swapped in ([Saves](#saves)), the runtime is prepared (`bepinex5.EnsureWinHTTPOverride` on a Proton prefix that exists; persistent, idempotent, not journaled) and the store starts the game. When the game has exited, or the start failed, the placed files are purged, the saves swap undone and the settings restored; `RecoverDeploys` finishes what a crash or quit left at startup (the deploy journal and the saves journal both), skipping an install whose game still runs.
- **Installers** (`internal/installer`): an archive's shape picks a driver, asked in `detectionOrder`: `fomod` (a `fomod/ModuleConfig.xml`), `thunderstore-rules` (r2modman's package layout rules) and `plain`, which takes any archive and is asked last. `Layout` maps archive paths to files under the game's catalog targets, and every path is validated to stay inside its target and to be storable on Windows.
- **Deploy methods** (`internal/deploy`, `GameInfo.Deploy`): `redirect` means the loader points the game at the profile's folder and nothing is placed (SMAPI's `--mods-path`); `profile` means the profile holds the loader and its mods (the r2modman and Gale model): before a launch `SyncPackages` copies each enabled package's files into the profile, a package's config file only seeding it, and removes the files of packages no longer enabled (the list it placed is `<profile>/.mortar-packages.json`); the deployer then copies only the loader's install-side files into the install, journals every move first and, when the game exits, removes them and restores what they displaced. Packages are never linked into the install or the store, and nothing else in the game folder is read, moved or taken back. The catalog's `targets` say where each kind of file goes in the profile and how deep a file may sit.
  - **Install-side files:** the one deployer is `copy-into-install` (`internal/deploy/place.go`). It copies the loader's plan files (BepInEx's Doorstop pair, `winhttp.dll` and `doorstop_config.ini`) into the install as real files and never links them, since the game and its anti-cheat may write to them. A plan path that leaves the install is refused.
  - **Journal safety:** `Apply` hashes each source, records every operation (destination, source, SHA-256 and, for a destination that already exists, where the displaced file waits under `<journal>/displaced/<n>`) and persists `deploy.json` in `<data>/journal/<install id>` before the first file moves, then again after each file is placed (`Done`). The displaced file is renamed aside (a copy and remove across volumes). Each file is copied through a `.mortar-tmp` file beside its destination, synced and renamed (`datadir.CopyFile`), so a crash leaves the file whole or absent, the source's exec bit is kept and a hard-linked destination is never written through. `Apply` refuses with `ErrUnrecovered` while a journal of an earlier deploy exists, since a second manifest would overwrite the first's record of the player's own files.
  - **Purge:** it walks the operations backwards. A displaced file goes back over its destination. With none, a destination is removed only when Mortar placed it (`Done`) or, for a crash between placing and recording, when nothing was displaced and its hash is the recorded one, so a file of the player's own that Mortar did not place is never deleted. Folders `Apply` created are removed deepest first when empty, then the journal. `Recover` does nothing while the game runs and otherwise purges from the journal.
- **Frameworks** (`internal/framework`): a driver is keyed by a framework mod's id and registers itself. `Matches` says whether a mod is the framework or content written for it; while an enabled mod matches, the driver's `Analyze` adds asset conflicts, setting hints, cleanup suggestions and redundancy findings to the profile's problems. Content Patcher is the one driver.
- **Loader notes:** SMAPI (`redirect`) replaces the game's launcher once per install, reads its log from the game's error-log folder and matches it to a profile by the `Mods go here` line; its bundled mods are a store entry in every profile. BepInEx 5 (`profile`) keeps its core, plugins, patchers, config and log in the profile, where Doorstop's `--doorstop-target` points (`<profile>/BepInEx/core/BepInEx.Preloader.dll`), and needs only `winhttp.dll` and `doorstop_config.ini` beside the executable, which the deployer copies in and removes; under Proton the `winhttp=n,b` override is written into the prefix. A native Linux build (an install holding the catalog's `linuxMarker`) gets no files: it starts directly with the pack's `libdoorstop_x64.so` in `LD_PRELOAD` and the Doorstop target in `DOORSTOP_TARGET_ASSEMBLY`, as the pack's own start script would set them. Each loader names a companion mod (the SMAPI bridge, the BepInEx bridge) that is hidden in the profile and lets Mortar query the running game.
- **Pack formats** (`internal/pack`): `Format` readers turn another manager's list into a `Draft` (packages by source and native id, loose files, configs) and write nothing: r2modman and Gale codes (`#r2modman\n` plus base64 of a zip with `export.r2x` and `config/`, fetched by key from Thunderstore's legacy profile endpoint), r2modman profile folders (`mods.yml`), Gale's profiles read from its `data.sqlite3` (`pack.Gale`, read-only: a `profiles` row's mods JSON names each package as `Namespace-Name-Version`, and its `path` folder's `BepInEx/config` files are read too), and Thunderstore modpack packages (manifest dependencies, `config/`). `Code.ExportCode` publishes a draft as a code to that endpoint; a caller confirms with the player first. `packsvc.ExportModpack` writes a profile as a Thunderstore modpack zip (`manifest.json` depending on each enabled Thunderstore package as `Namespace-Name-Version`, a plain 256x256 `icon.png`, a `README.md` naming the mods left out for another source or for being switched off, and `BepInEx/config` as `config/`), which the modpack reader reads back as the same package set; `mortar profile export --format modpack` and the profile menu reach it.

### SMAPI

- **Pin and rollback:** the game setting `smapiPin` holds a SMAPI version Mortar installs instead of the latest (and stops offering updates for); any version already in the store is applied without a download, others come from that GitHub release. An unknown version is refused before the game is asked to close.
- **Patch-day sweep:** when the installed game or SMAPI version differs from the one recorded at the last sweep (`lastSweepGameVersion`, `lastSweepSMAPIVersion` in the game settings), every profile is checked for mods smapi.io marks broken for the new versions, with the fix (update, disable, none yet), and one toast leads to the summary.

- **Install and update:** download the release installer (4.5.2, published 2026-03-22, needs Stardew 1.6.14+; 2 to 4 releases a year) and run it unattended with `--install --no-prompt --game-path "<dir>"`; running it again updates. Measured on Linux: exit 0, no prompts, launcher replaced, bundled mods added.
  - **When:** Mortar installs SMAPI by itself, without asking: in the background when a profile is created or at startup while profiles exist and SMAPI is missing or broken, as first run's second step, and before Play when a game update has replaced the launcher. Only a newer release waits for the user, since an update can break mods.
  - **Windows:** the installer is `SMAPI <version> installer/internal/windows/SMAPI.Installer.exe`, self-contained (its `runtimeconfig.json` bundles .NET 6.0.36). Mortar extracts the whole zip and runs it from the installer folder, as `install on Windows.bat` does (the batch file refuses to run from a `%TEMP%` path).
  - **In a Bottles bottle:** a Windows build on a Linux host is recognised by its `Stardew Valley.exe` (`buildOS`) and installed the Windows way: Mortar extracts the same installer zip and runs `SMAPI.Installer.exe --install --no-prompt --game-path <dir>` inside the bottle through the install's runtime (`Install.RunInBottle`, `bottles-cli run -b <bottle> -e <exe> -- <args>`), then looks for `StardewModdingAPI.exe` as it does on Windows. Without a runtime to run it in, the install is refused. A launch of a Bottles install is a direct start (`env.Direct`) that wraps the game's executable in the same `bottles-cli run` command (`Install.BottleCommand`).
  - **New releases** come from the GitHub releases client ([GitHub releases](#github-releases)) and show as a banner; one click installs.
- **Versions:** the SMAPI version Mortar installed is kept in `settings.json`; otherwise, and for the game version, Mortar reads the first line of `SMAPI-latest.txt` (`SMAPI 4.5.2 with Stardew Valley 1.6.15 build 24356 on Unix ...`, measured).
- **Broken by a game update:** on Linux the installer renames the game's `StardewValley` to `StardewValley-original` and puts its launcher in its place, which a game update overwrites; Mortar checks at startup and before launch that `StardewValley-original` exists and `StardewValley` contains `StardewModdingAPI`, and Play reinstalls SMAPI first when it is not (the banner keeps a manual Reinstall). On Windows the launcher survives, and an incompatible SMAPI reports itself in its log, which the console surfaces with the same offer.
- **Bundled mods:** a profile's `mods/` replaces `Mods/`, so every profile gets SMAPI's Console Commands and Save Backup as a `smapi-<version>` store entry, taken from the installer Mortar downloaded for the installed version (`internal/<os>/install.dat`, a zip holding `Mods/ConsoleCommands` and `Mods/SaveBackup`, checked in 4.5.2). A SMAPI update replaces that entry in every profile.
- **Components:** `components.source.json` names each loader or companion mod by game, kind, GitHub source, release asset pattern, version policy and optional accepted game-version range.
  - Its `games` section holds each game's identity, carried unchanged into the manifest: id, name, Steam app id, marker file, loader name, GOG product id and folder, Lutris slug and keyword, and Nexus domain and numeric id.
  - Game implementations read it through `components.Client.Game`, which falls back per game to the bundled manifest, and the Nexus domain and numeric id come from `GameInfo.NexusDomain` and `NexusID` wherever they are needed; process names and launch behaviour stay in Go.
  - `cmd/components` resolves releases, downloads the named assets and writes the signed `components.json`; the same manifest is embedded at `internal/components/components.json` for offline and first-run fallback.
  - The Ed25519 signature uses the update key (`build/updater/public.key` is its embedded public half), and the detached signature is published beside the manifest. Each signed manifest is its own immutable `components-v2-<serial>` release; the `v2` is the manifest schema, since released clients read any manifest whose fields they recognise, so a schema change takes a new prefix.
  - The client finds the newest non-draft `components-v2-*` release through the GitHub releases API, fetches its manifest at startup through the daily meta cache, verifies it before parsing, rejects a lower serial, and falls back to the cached or bundled manifest.
  - Component source hosts are limited to `github.com` and `thunderstore.io`; current v1 assets are GitHub releases.
  - **Downloads:** every asset is checked against its manifest SHA-256 before extraction. The bridge is installed hidden in every profile as a `bridge-<version>-<hash>` store entry with source kind `mortar`, added at startup and profile creation, and replaced when the manifest version or hash changes. Hidden means as SMAPI's bundled mods are ([gui-design.md](gui-design.md#mods-tab)).
  - **Mortar SMAPI Bridge:** Mortar has no access to SMAPI's stdin, so a small SMAPI mod (`Rethunk-Tech/mortar-smapi-bridge`, `UniqueID` `Rethunk.MortarSmapiBridge`, protocol in its README) accepts console commands on a loopback port.
  - **Channel:** the mod writes `mortar-smapi-bridge.json` (`{port, token}`, user-only) in its folder; `internal/bridge` reads it from the running profile and sends `<token>\n<command>\n`, so the token never leaves the user's own files. Each loader names its companion (`WithCompanion`: mod folder, mod id, state file); the reply is `ok`, `ok <json>` or `error: <message>`, and `Query` (`status`, `plugins`) returns the JSON. The BepInEx companion (Mortar BepInEx Bridge, `Rethunk.MortarBepInExBridge`) writes `mortar-bepinex-bridge.json` in the profile's `BepInEx/config` and answers `ping`, `status` and `plugins`; it is hidden in profiles like the SMAPI one (`manifest.LoaderManaged`). While a game Mortar started runs, `launchsvc` asks its `status` every 2 s (`loader.RunningState`): the first game version is kept for the run and `lastPlayed`, the scene shows in the Running header, and each enabled package whose DLLs declare plugins gets a loaded or not-loaded badge in the mod list. A loaded plugin is the package's whose laid-out file the bridge names as its `location` (below `BepInEx/plugins`, matched to the entry that placed that file); without a location, the package's that declares its GUID at the version BepInEx reports. BepInEx keeps the newest version of a GUID, and between equal versions the first file its folder walk meets (`Chainloader.cs`, stable `OrderByDescending` over `Directory.GetFiles` order), which only the location tells, so an older bridge leaves both equal copies marked loaded. The game's plugins are a set, so nothing reads them as load order; the badges clear when the game stops. Commands run on the game's next tick and their output arrives in SMAPI's log.
  - **Stream overlay:** the settings card, OBS URL, labels switch and live preview are in [gui-design.md](gui-design.md#settings). When overlay is enabled, Mortar writes the bundled OBS page to `<data>/overlay/index.html`. At launch (and when the bundled bridge is first extracted into the store), Mortar writes the bridge mod's `config.json` (`OverlayEnabled`, `OverlayPort`, `OverlayToken`, 0600, atomic) so a change takes effect on the next Play. The overlay page polls `http://127.0.0.1:<port>/state?token=<token>`. A loader whose bridge keeps its settings in the profile instead (BepInEx, `loader.OverlayArmer`) gets the same three keys in `startup/overlay.json` in the profile folder, written at launch and removed while the overlay is off so the token stays out of profiles that do not use it. Both bridges serve the same `/state` shape: `inGame`, `playerName` and the game's own keys, and the BepInEx bridge adds `game` (`lethal-company`: `moon`, `crewAlive`, `crewTotal`, `day`, `quota`, `quotaProgress`, `daysLeft`, `credits`; `valheim`: `biome`, `day`, `bossesDefeated`, `bossCount`), which the page uses to pick its layout; a snapshot with no `game` is Stardew Valley's. The page and the settings card list each game's own fields.
- **Profiles folder:** SMAPI takes `--mods-path <path>`, absolute or relative to the game folder (`smapi.md:49`). Its `SMAPI_MODS_PATH` environment variable works only when SMAPI is started directly, since `steam -applaunch` cannot pass environment variables, so Mortar does not use it. Mortar never moves or writes the game folder's own `Mods`; **Import from the game's Mods folder** reads it to copy mods into the store and a new profile.
- **Scanning:** SMAPI recurses into subfolders until it finds a `manifest.json` and skips folders whose names start with a dot. Manifests are parsed leniently. Optional `UpdateCautionMessage` and `DeleteOldVersion` (Stardrop update hints) are read with the same case-insensitive key rules. Update review shows the installed manifest's caution when the new file is not in the store yet, requires an explicit tick on that row, and **Update all** skips cautioned mods until they are ticked.

### Launch

| Copy | How Mortar starts it |
| --- | --- |
| Steam | `steam -applaunch <appid> <args>`: Steam passes the arguments after the app ID to the game, which keeps the overlay, achievements and playtime tracking |
| GOG, Heroic or Minigalaxy | SMAPI directly (the Direct path) |
| Flatpak Steam | `flatpak run com.valvesoftware.Steam -applaunch 413150 --skip-terminal -- --mods-path <dir>` |

A launch through Flatpak Steam that times out while the override is missing uses the filesystem-access hint.

- **Linux:** `steam -applaunch 413150 --skip-terminal -- --mods-path <absolute path to the profile's mods/>`.
  - SMAPI's launcher script reads its own flags only before `--` and forwards only what follows it (SMAPI's unix launcher argument loop in the Pathoschild/SMAPI repository), which is why SMAPI's docs say arguments do not work on Linux.
  - `--skip-terminal` makes the script start SMAPI with `--no-terminal`; SMAPI still writes its log file then (`docs/technical/smapi.md:46`).
  - Measured: without `--` the path is ignored; with it SMAPI loads the profile, including through a real Steam client, where the game reached the main menu. Without `--skip-terminal` the launcher opened its console in `xterm`, unreadably small.
- **Windows:** Steam starts `Stardew Valley.exe`, not SMAPI. SMAPI's installer swaps the game's launcher only on Linux and macOS (`InteractiveInstaller.cs` `if (context.IsUnix)`), and on Windows asks for the launch option to keep achievements.
  - First run shows the line `"<game>\StardewModdingAPI.exe" %command%` to paste into Stardew's Steam launch options, with a copy button, and **Set it in Steam for me**, which writes `LaunchOptions` in the MostRecent account's `localconfig.vdf` while Steam is closed (Steam rewrites the file on exit).
    - The write merges the user's options: an existing SMAPI `%command%` line is left as it is; otherwise SMAPI is inserted before `%command%`, or `"<dir>\StardewModdingAPI.exe" %command%` is prepended to whatever was there.
    - The app's `LaunchOptions` key or its block under `apps` is created when missing; a file with no `apps` section is refused until the game has been launched from Steam once.
    - **Remove SMAPI from Steam's launch options** (offered after **Reset game install** on Windows) strips that SMAPI command from the same file, leaving the user's other options.
  - Mortar reads `LaunchOptions` from `localconfig.vdf`: first run warns up front when the line is missing, and at Play the options choose the failure hint shown if the launch times out. Mortar then adds `--mods-path <path>` after the app ID.
  - SMAPI finds its flags anywhere on its command line (`Array.LastIndexOf(args, "--mods-path")` and `args.Contains("--no-terminal")` in SMAPI 4.5.2 `Program.cs`) and ignores what it does not know, so the game path Steam substitutes for `%command%` does no harm wherever Steam places the `-applaunch` arguments; an absolute `--mods-path` wins over the game folder (`Path.Combine`).
  - Mortar does not pass `--no-terminal` on Windows. `StardewModdingAPI.exe` is a console program (PE subsystem 3, checked on the 4.5.2 Windows `install.dat`), so Windows gives it a console window whatever its flags; `--no-terminal` only stops SMAPI writing log lines into that window. A direct launch hides the window instead (`showSmapiConsole` off), and the Console tab follows the log file either way.
- **Console input:** a process Mortar starts gets a pipe for stdin that Mortar holds open until it exits (`launch.startCmd`). SMAPI's console-command loop (`LogManager.RunConsoleInputLoop`) skips empty reads, so on `/dev/null` or `NUL` it spun one core for the whole session (measured 2026-10-06: 93% of a core on Linux); on an open pipe it waits. Commands from the Console tab go through the bridge mod, not stdin.
- **SMAPI startup markers:** SMAPI's `Console.ReadKey` throws when stdin is not a console, so the "game crashed last time" prompt (`smapi-internal/StardewModdingAPI.crash.marker`, written on every fatal crash) ended SMAPI before the game opened, and the marker survived, so every later launch failed the same way (reproduced 2026-10-06 on Linux, a direct launch). The SMAPI loader's `Prelaunch` removes that marker and the update marker before each profile launch; `ErrorLogs/SMAPI-crash.txt` is kept.
- **Extra arguments:** a profile's `launchOptions` are split like shell words (spaces separate; single or double quotes keep spaces; a backslash escapes the next character) and appended after `--mods-path`, on Linux after the `--` too. `--mods-path`, `--no-terminal` and `--skip-terminal` are refused, since Mortar sets them. Changing them never touches `mods/`, so a running game does not block it.
- **Launch prefix and environment:** `launchPrefix` is split the same way (no shell evaluation; an unfinished quote or escape is refused) and, on Linux only, prepended to a Direct SMAPI command. `launchEnv` is one `NAME=value` per line (`[A-Za-z_][A-Za-z0-9_]*=.*`) and is passed to Direct launches on Windows and Linux. Steam `-applaunch` receives neither. Changing them never touches `mods/`.
- **Per-profile game settings:** an optional `game-settings.json` beside a profile's `profile.json` overrides the selected fields in Stardew's `startup_preferences` for that launch.
  - Mortar records the old values, applies the override before starting a profile with mods, and restores each field when the run ends only if the game still has Mortar's value; a value the game changed is kept.
  - Vanilla launches and profiles without overrides do not touch `startup_preferences`; a missing file is skipped with an info line.
- **Without mods:** Play without mods is `steam -applaunch 413150` with no arguments, or the game's own executable when Mortar starts it directly.
  - It has no profile and does not lock mods, and is refused while the game runs.
  - It counts as started when a game process is seen within the launch timeout, since there is no SMAPI log, and the Console gets a Mortar line "Started without mods". It records no `lastPlayed` and no run.
  - On Windows, when Steam's launch options hold the SMAPI `%command%` line, Steam still starts SMAPI, so Mortar warns first and never edits that file. If that check fails, Mortar does not start the game.
- **Before Play:** Play gathers missing required dependencies, unresolved non-dismissed non-cosmetic conflicts, pending updates, and mods flagged broken or obsolete. When any are present, a dialog lists each group (count and up to five names) with **Play anyway**, **Open Problems** (the Problems tab), and **Update and play** when updates are pending (the same update-before-Play pass). A **Don't check before Play** checkbox is applied as the `skipPlayCheck` profile override when the dialog is closed with Play or Cancel. Nothing found, or the resolved skip, continues with no dialog.
- **After a game update:** before Play the game version the installed SMAPI reports (as Game Select does) is compared with `lastPlayed.gameVersion`. When they differ, the profile's mods SMAPI's API marks broken for the new version are listed, and Play anyway, Open problems or Cancel follow. A first launch, with nothing recorded, does not warn.
- **Newest save:** after that check, Play asks `LastSaveGap`: the most recently written save, when it still uses mods the profile lacks or has disabled (dismissed UniqueIDs excluded as on the Saves tab). An unreadable save never blocks. **Play anyway**, **Open saves** or Cancel follow ([gui-design.md](gui-design.md#main-screen)). When that save was last played with a different profile, Before you play names it and offers **Switch profile** or **Play anyway**.
- **Update mods before Play:** when update before Play resolves on (the game pref `updateModsBeforePlayDefault`, overridable per profile in `overrides`), Play queues every offered, non-pinned, installable update first, waits for those queue items to finish or need a click, then starts the game. A history restore point is recorded before that pass; a failed update rolls those entries back. Pinned mods stay on their version. The setting is opt-in and the pass runs only when the user presses Play.
- **Save backup before a changed launch:** before a non-vanilla launch, if the profile's history has an event after the newest stored run (or there is no previous run), Mortar zips the Saves folder into `backups/` with cause kind `update` for that profile. A failed zip is logged and does not block Play.
- **Profile launch presets:** the profile's own `launchOptions`, `launchPrefix` and `launchEnv` are its built-in preset, named `Standard`; `launchPresets` hold further named ones, each validated like those fields (preset names are unique ignoring case and never `Standard`; at most 20). `Profile.ResolvePreset` picks the default preset when no name is given, else a preset by name or id; an unknown name refuses the launch before anything starts. A preset's `showConsole` replaces the `showSmapiConsole` override for that launch. `Service.StartPreset` (CLI `launch <game> <profile> --preset NAME`) launches with one preset without changing the default; each recorded run keeps the preset name (`Run.preset`). Editing presets never touches `mods/`. Game-wide **launch preset templates** (`settings.LaunchPresetTemplate`, stored per game as `launchPresetTemplates`; CLI `game launch-preset-templates <game> [add|remove|use]`) hold options, prefix, environment and the SMAPI console choice (`true`, `false` or empty to follow, like a profile preset's `showConsole`); `use` and the Edit profile **Add from game presets…** copy one into a profile's `launchPresets` through `Store.AddLaunchPreset`, which gives it a fresh id and numbers a clashing name. The copy is independent of the template.
- **Direct launch preview:** Edit profile shows the Direct SMAPI argv (and `NAME=value` environment lines) for the typed launch options, prefix and environment, with a copy control. Steam `-applaunch` is not that preview.
- **Profile shortcuts:** **Add a shortcut that plays this profile** writes `--play=<game>/<profile>` as the argument.
  - On Linux that is `~/.local/share/applications/tech.rethunk.Mortar.play-<game>-<profile>.desktop` (or `$XDG_DATA_HOME/applications/…`), named `<profile> (<game>)`.
  - On Windows it is a `.lnk` under the Start menu's Mortar folder, written through `WScript.Shell` COM.
  - **Remove the shortcut** deletes that file.
  - Rename and delete of a profile rewrite or remove the matching shortcut; a failed shortcut sync is logged and does not fail the profile operation.
  - **Add this profile to Steam** appends a non-Steam game to native Steam's `shortcuts.vdf` for the MostRecent account (quoted exe, launch options `--play=… --steam-session`, appid with the high bit set); an entry for Mortar's exe whose options include the profile's `--play=<game>/<profile>` is that profile's, whatever its other options or name, and is updated in place (name, launch options, art), keeping its appid and playtime; refused while Steam is running, and when only Flatpak Steam is found, since that sandbox cannot start Mortar.
  - A duplicate exe+options pair is left as it is.
  - When a cover or Steam hero image is a local file, Mortar copies it into that account's `userdata/…/config/grid` as portrait, capsule and hero art for the new shortcut.
- **Success or failure:** `steam -applaunch` returns at once.
  - A launch counts as started when `SMAPI-latest.txt` (`~/.config/StardewValley/ErrorLogs/`, `%APPDATA%\StardewValley\ErrorLogs\`) is rewritten within 60 s, and failed otherwise, with a hint (on Windows, the missing launch-options line).
  - When Mortar started SMAPI directly and it exits having written no log, the launch fails with its exit code.
  - A Steam launch's `steam` process only hands over and exits 0; that zero exit is ignored and only the log decides. A non-zero `steam` exit is a failure immediately.
- **Running:** a `StardewModdingAPI` process whose `--mods-path` is a profile's folder means that profile is in use; its folder is locked against changes until the process exits (Windows locks loaded files anyway). Reaching Running records `lastPlayed` for that game in `settings.json` (profile id and RFC3339 `at`); Launching and Failed do not.
- **Whose log:** the game has one `SMAPI-latest.txt` for every profile, so the Console and Share log show a log only in the profile that wrote it.
  - The session Mortar launched belongs to its profile.
  - The file on disk belongs to the profile whose mods folder matches SMAPI's `Mods go here: <path>` line (SMAPI writes the home folder as `~`, `PathUtilities.AnonymizePathForDisplay`).
  - A log without that line, from a launch outside Mortar, belongs to no profile.
  - **Runs:** when a launch Mortar started ends, or fails, a Summary of that run's SMAPI log is stored under the profile's `runs/` ([Storage](#storage)): versions, error and warning counts, whether SMAPI crashed or hit a fatal error, and the mods that logged errors with counts and their first message. Performance reports are stored alongside runs, with the current run id when available, and keep the newest 20 per profile.
  - **Loader log and crash:** a run's log is the profile's loader log (`loader.WithLogs.Path`): SMAPI's shared `SMAPI-latest.txt`, matched to the profile by its `Mods go here` line, or a log the loader keeps inside the profile's own folder (BepInEx's `LogOutput.log`), which can only be that profile's. A loader with a Unity player log (`WithPlayerLog`) marks the run `crashed` when that log, written since the run began, holds `Crash!!!` or `Fatal error` and the loader reported no crash of its own.
  - **Likely cause:** `launchsvc.CrashHint(game, profile)` explains the latest recorded run when its outcome is `crashed`, and is nil otherwise. It returns the run's recorded cause (mod key, name and the first line of its detail) when there is one; else it runs the loader's log analyzers over the loader log (and the player log) and takes the first finding, in log order, whose plugin is an enabled installed mod (a log names a plugin by display name, GUID or root namespace, so names match when one holds the other once case and punctuation are dropped); else, for a loader whose log holds .NET stacks (SMAPI: `loader.WithStackBlame`, `smapi.StackBlame`), it reads each exception block of the log (inner exceptions and `--- End of inner exception stack trace ---` included) and takes the last one whose stack runs through a mod: the first mod frame, nearest the throw, skipping StardewModdingAPI, HarmonyLib, MonoMod, StardewValley, xTile, System and other runtime or game namespaces; a stack of only Harmony patch frames (`DMD<...>`, `*_Patch1`) blames the Harmony id the log shows beside it. A frame matches an enabled mod when a namespace segment is its `EntryDll` name, the last part of its UniqueID or its name (two mods matching equally blame neither); the hint's `evidence` is that frame line and its `reason` the exception line, and the card adds **Stack frame: …**; else it reads the crash the run left (`internal/crashdump`, `launchsvc/dumphint.go`): for a game that runs as Windows code (natively or under Wine or Proton, in the prefix's profile), the Unity crash folders `%LOCALAPPDATA%\Temp\<company>\<product>\Crashes\Crash_*` newer than the run start (`error.log` first, its first native frame outside ntdll, kernel32 and the like; else `crash.dmp`) and the WER dumps `%LOCALAPPDATA%\CrashDumps\<exe>*.dmp` newer than the run start; a minidump is parsed in pure Go for its exception address (exception stream) and the module holding it (module list); on Linux, `coredumpctl info --since <start> <comm>` when installed and readable without root, taking the first frame's module outside libc. The faulting module blames an enabled mod when it is the mod's `EntryDll` or a file of that name within three folders of the mod's folder, with evidence "crash dump: faulting module X.dll (exception …)"; the game's executable, Unity (`UnityPlayer`) or Mono name that part of the game as the reason and no mod; else it returns the first finding's message with no mod, or nothing but the run id. The window shows it as a card on the profile page with **Disable and retry** for a named mod and **Bisect from here** ([Launch](#launch)).
  - The Console's Runs picker loads a stored log read-only, and Save log and Share log use that copy. A stored log belongs to its profile like the live one.
  - A run that ended with errors or a crash also opens a dialog naming the cause when Mortar can identify one: **Caused by `<ModName>`**, followed by one plain-language sentence and actions to switch it off or open its Nexus page.
    - When the crash names no mods, the dialog offers **Find the broken mod**: `internal/bisect` copies the profile into a scratch profile (`profile.ScratchCopy`: a `.scratch-<id>` folder beside the profiles that no listing shows, removed when the check ends and, after a crash, at the next start), halves enabled mods (keeping required dependencies), and relaunches through `launchsvc.RunForBisect` until one culprit remains; the window is `BisectDialog`.
    - Each step launches with the profile's launch method.
    - A step fails only when SMAPI logs an alert or the run ends crashed (abnormal exit); plain errors such as a skipped mod do not count, or the bisect would blame whichever mod logs one.
    - A step passes when the bridge writes a title-screen report under `<profile>/startup/` after that launch, or after 20 s at Running when the profile has no bridge folder; `bisectRunTimeout` still ends a hung step.
  - The Mods list, grid and sidebar badge each user mod that logged errors or warnings in that profile's newest stored run; a later run with none for that mod clears the badge.
- Trap: launching through Steam makes Steam Cloud download the user's saves, and SMAPI's Save Backup mod zips them into `save-backups/` in the game folder.

### Startup timings

- **What:** the bridge measures each mod's share of startup, from its own Entry to the title screen, and writes `<profile>/startup/<process start UTC>.json` (last 10 kept; schema in the bridge README). Times are exclusive: an asset edit triggered from another mod's update tick counts for the editor only.
- **Replaced methods:** the report's `replaces` lists, per Harmony ID (a mod's UniqueID by convention), the game methods it can replace outright: transpilers and `bool` prefixes. Problems adds them to each C# mod's footprint for the same-job check ([Mod data](#mod-data)).
- **Load early:** before each launch Mortar adds the bridge's UniqueID to `ModsToLoadEarly` in `<profile>/mods/SMAPI-config.json` (SMAPI's per-mods-folder settings), keeping other keys; a file that is not plain JSON is left alone. With the bridge first, every other mod's Entry runs after it.
- **Measured launch:** **Measure next launch** writes `<profile>/startup/.measure-next-launch`; the next launch removes it and writes `StartupProfile: true` into the bridge's `config.json`, so the bridge also times every other mod's Entry (from SMAPI's per-mod `SetApi` call, never by patching a mod's own method) and skips the title intro animation.
- **What is timed:** every SMAPI event handler (delegates swapped in place on SMAPI's event manager, restored at the title screen), every asset edit and load by mod and by the content pack it acts for, and Content Patcher's per-pack work (reading `content.json` and `config.json`, parsing patches, each patch's token update). Measured on the main profile (193 mods, 417 packs): 44 s of 46 s between the bridge's Entry and the title screen attributed; Content Patcher's first update tick is 26 s, Fashion Sense's GameLaunched 2.9 s.
- **Shown in:** Performance › Startup ([gui-design.md](gui-design.md#performance-tab)), reloaded when a run starts or ends; the Mods list's Startup column; and Since last run, which names each mod updated or added since the previous report that made startup at least 1 s slower (a smaller change is run-to-run noise).
- **Sampled launch:** when **Measure next launch** is set, Mortar starts a diagnostics EventPipe session as soon as the game process appears, collecting the .NET sample profiler and runtime JIT/loader events. It requests rundown when the bridge's title-screen report appears and writes `report-id.samples.json` under the profile's `startup` directory with the report's ID.
- **BepInEx:** only a measured launch is timed. The launch turns `.measure-next-launch` into `<profile>/startup/.measure-launch`, holding the catalog game's `titleScene` (Lethal Company `MainMenu`, Valheim `start`), and removes a leftover one on an unmeasured launch. The bridge's preloader patcher (`BepInEx/patchers/<package>/MortarBepInExBridge.Patcher.dll`) consumes it and adds a log listener before the chainloader runs, so it sees every plugin's `Loading [Name Version]` line, including plugins loaded before the bridge plugin; LogOutput.log has no timestamps and is flushed on a timer, so timing cannot come from it. A plugin's `entryMs` is the gap to the chainloader's next plugin line (constructor and Awake); its later work in Start, coroutines or scene hooks lands in the first-scene-to-title phase. The phases map onto the same fields: `bridgeEntry` preloader, `entryDone` "Chainloader started", `gameLaunched` "Chainloader startup complete", `titleMenu` first scene loaded, `titleScreen` the title scene. Rows carry plugin GUIDs; Mortar shows them under the enabled package whose DLLs declare each GUID, a package's plugins added together. Unity's Mono has no diagnostics port, so there is no sampling and no Sampled column. The same launch also turns on in-game measuring: the patcher sets `MORTAR_MEASURED_LAUNCH=1` in the process, and the bridge plugin then keeps frame stats from its own DontDestroyOnLoad object and, from the first `perf start`, wraps every plugin's Harmony patch methods (owners from `Harmony.GetAllPatchedMethods`, a patch belonging to the plugin whose assembly declares it) and its MonoBehaviours' Update, LateUpdate and FixedUpdate with timers; `launchsvc.MeasureInGame` reads `perf` and saves it with the profile's performance reports (`frame` holds the frame summary). The `perf` reply also carries `patchOwners` (Harmony ID to patched game methods).
- **In-game frame timing:** both companions answer `perf start` (restart the window; the first one begins timing) and `perf` (the summary, rebuilt once a second) with one shape: `{measured, seconds, frames, fps, frameMs{avg,p50,p95,p99,max}, monoUsedBytes, monoHeapBytes, gcCollections, baseline{frameMs, modsMs, withoutModsMs}, plugins[{guid, msPerFrame, p95Ms, peakMs, share, callsPerFrame}]}`. The SMAPI bridge wraps each mod's handlers of the per-frame events (update, render, one-second; the same delegate swap as startup timing) only from `perf start` for at most ten minutes, a frame running from one `UpdateTicking` to the next; SMAPI's own performance monitor has no 95th percentile or frame share, so it is not the source. The BepInEx bridge times each plugin's Harmony patches and Update, LateUpdate and FixedUpdate from its first `perf start` on a measured launch. `msPerFrame` averages over all frames, `p95Ms` is the 95th percentile of the per-frame cost over all frames (a histogram, about 10% resolution), `share` is the average over the average frame, and `baseline.withoutModsMs` is the average frame less the mods' timed code (not a launch with no mods). `launchsvc.MeasureInGame` (`loader.InGamePerf`, implemented by both loaders) saves the rows, named by package (a BepInEx plugin by the GUID its DLLs declare, a SMAPI mod by its UniqueID; a package's rows added up), with the frame summary and baseline as a performance report.
- **Sample attribution:** Mortar resolves sampled instruction addresses through method, module and assembly load records. It charges each sample to the innermost frame in an enabled mod assembly; unmapped samples are game and SMAPI time. The report exposes each mod's `sampleMs` and the remaining `sampledOtherMs`. Sampling failures do not fail the launch, and unmeasured launches do not start a diagnostics session.
- **Sampler findings:** on the main profile (2026-10-04, 53.5 s to the title), named mods held 81% of the sampled time and agreed with the bridge within a second for Content Patcher (25.8 s), Fashion Sense and JsonAssets; the sampler alone showed Better Artisan Good Icons at 9.0 s, spent in its patches on game code. A test or bisect launch waits for the sampler to stop its session before stopping the game, since the method rundown needs the live process.

### Antivirus scan

- **Where:** `Store.install` (`internal/store/store.go`) calls `checkExtracted` (`internal/store/scan.go`) on the folder a store item was extracted into, after junk is stripped and before the rename that makes it an item, so every path into the store passes it: `AddArchive`, `AddArchiveKey`, `AddHashedDir` and `AddDir` (LAN receives, backups, profile imports). Loader bundles (a key `LoaderOf` recognises) are Mortar's own downloads and are skipped. `main.go` hands the store a picker that reads the antivirus settings on each scan.
- **Scanners** (`internal/avscan`, one interface `Scan(ctx, dir) (Detection, bool, error)`): Windows AMSI through `amsi.dll` (`AmsiInitialize`, `AmsiOpenSession`, `AmsiScanBuffer` per 32 MiB of each file, `golang.org/x/sys/windows`, no cgo; a result of 32768 or more is malware, and AMSI names no threat, so the row says "malware reported by the Windows antivirus"); a clamd daemon over a unix socket (`zINSTREAM` per file in 64 KiB chunks, answers `FOUND` and `ERROR`; a file over clamd's stream limit is skipped; the socket is the setting, else `/run/clamav/clamd.ctl`, `/var/run/clamav/clamd.ctl`, `/run/clamd.scan/clamd.sock`, `/var/run/clamd.scan/clamd.sock`, `/tmp/clamd.socket`); a custom command (no shell; `{path}` replaced by the folder; exit 0 clean, any other code a detection named by the first line of stdout); off.
- **Settings** (`antivirus`, `antivirusSocket`, `antivirusCommand`; Settings › General › Antivirus): `automatic` (default) is AMSI on Windows and clamd elsewhere, `clamd`, `command`, `off`. The socket and the command are not portable fields. `settings.Service.AntivirusProduct` fills the "Scanner in use" row: on Windows the Security Center `AntiVirusProduct` names (one PowerShell call, 5 s) with "Windows antivirus (AMSI)" as the fallback, the clamd version, the command's program, or "No antivirus found".
- **Detection:** the install fails with `store.DetectedError` under `usererr.Malware` (`malware` on the wire) and the extracted files are deleted. The queue item fails with `errorKind` `malware` and a `Detection` (name, file, scanner, store key); Downloads shows "Flagged by <scanner>: <name> in <file>" with **Install anyway**, and a local install shows an error toast with the same action. The bound call's error carries the detection as typed fields: `usererr.Marshal` adds a `detail` (any `usererr.Detailer` in the chain; `store.DetectedError` gives `game`, `key`, `name`, `file`, `scanner`) beside `kind` in the Wails cause, and the frontend reads it with `detectionOf` (`frontend/src/toasts/avOverride.ts`), so the toast needs no error-text parsing. Both ask a confirm first, then call `profile.Service.AllowUnscanned` (the next install of that key skips the scan once) and record a `ChangeUnscanned` event in the profile's history; the retried queue item carries the override into the download history (`Override`). The CLI has the same answer in one call: `mortar install <game> <profile> <archive> --allow-unscanned` (`Params.Unscanned`) records the override and retries the install when the first attempt was flagged; without the flag the install fails with kind `malware`.
- **Real-time protection:** a file Windows' real-time protection blocks or deletes while Mortar writes or reads it is not a scan result, but reaches the same place: `store.RealTimeBlock` turns a Windows `ERROR_VIRUS_INFECTED` or `ERROR_VIRUS_DELETED` (225, 226), or a file that vanished from a staging folder (the store's temp folder, the queue's download folder), into a `usererr.Malware` `DetectedError` with `Removed` set, scanner "Windows real-time protection" and no name. The file is gone, so there is no Install anyway: the queue row and the toast say Windows removed it and that it can be restored from Windows Security's protection history.
- **Errors:** a scan that fails or times out (2 minutes) is not a detection: the mod installs, the log keeps the error and an `avscan:failed` event shows "The antivirus scan could not finish, so a mod was installed unscanned". "No scanner" (no AMSI provider, no reachable clamd) is silent.
- **Status:** `mortar antivirus status` (control method `antivirus.status`, `avscan.StatusOf`) prints the mode, the scanner kind (`amsi`, `clamd`, `command`, `off`), the product and whether a scan can start now (an AMSI session opens, clamd answers, the command runs), with the reason when not.
- **Acceptance:** `scripts/av-smoke.ps1` in the Windows VM needs only the installed Mortar, running. With `-ZipDir` (default `C:\\avsmoke`, give it a Defender exclusion first) holding the zip, it prints Defender's state, the AMSI providers and `mortar antivirus status`, builds a zip from parts at run time (Microsoft's AMSI test sample when the scanner is `amsi`, EICAR for clamd; the repo never holds either string), installs it into a throwaway profile through the CLI, expects the refusal with kind `malware` (from the AMSI scan of the extracted files or from real-time protection, and says which), repeats with `--allow-unscanned`, checks the profile history, and writes PASS/FAIL lines and `failures: N` to `%LOCALAPPDATA%\Temp\mortar-av-smoke.txt`.

### Saves

Saves live in one folder, `%APPDATA%\StardewValley\Saves` or `~/.config/StardewValley/Saves`, which Steam Cloud syncs, so Mortar never moves it; profiles share saves unless one sets `separateSaves`.

- **Per-profile saves** (`internal/savesiso`, `Profile.SeparateSaves`): a profile with `separateSaves` plays on `<profile>/saves` for the length of a launch, for a game whose catalog entry has a `saves` path. `Store.SetSeparateSaves(game, id, on, copyCurrent)` flips the flag; turning it on with `copyCurrent` copies the shared Saves folder into `<profile>/saves` unless that folder already holds something. The shared folder is only read, and turning the flag off leaves the profile's folder where it is.
  - `launchsvc` calls `savesiso.Apply` after the profile's game settings are applied and the changed-launch backup is taken, for a launch with mods, so a vanilla launch plays on the shared folder. `Apply` persists `Manifest{Journal, Saves, Profile, Held, Copied, Live}` as `saves.json` in `<data>/journal/<install id>-saves` before the shared folder moves, renames the shared folder to `<Saves>.mortar-shared` beside the game's save path (a rename, so it never copies), then points the save path at the profile's folder with a symlink. Where a symlink is refused it makes a working copy of the profile's folder at the save path instead and sets `Live` once that copy is complete.
  - `Purge` undoes it and checks the disk at every step, so it can run again after a crash: a complete working copy is written back to the profile through `<profile>/saves.new` and a rename, a link or copy at the save path is removed, then the held folder is renamed back (refused, with the path named, when something else sits at the save path). An incomplete copy is dropped, never written back. `Apply` refuses with `ErrUnrecovered` while a record of an earlier swap exists.
  - The swap is undone with the deploy when the game exits or the start fails, and `RecoverDeploys` finishes one a crash or quit left at startup (`savesiso.Recover`), skipping an install whose game still runs.
- Each profile's Saves card ([gui-design.md](gui-design.md#main-screen)) counts the saves that fit.
- Its Saves tab lists every save with the mods it has used that the profile lacks, read from the save itself. A card also shows which profile last played that save, from `<game>/last-played.json`.
- Players pick their save inside the game. Play still warns from the newest save when it needs mods this profile lacks ([Launch](#launch)); this tab is the full list.

- **Where mods leave traces:** SMAPI writes no mod list into a save, but mods leave keys prefixed with their `UniqueID`:
  - SMAPI's save data `smapi/mod-data/<uniqueid>/<key>`, lowercased whole (SMAPI's `DataHelper` in the Pathoschild/SMAPI repository)
  - `modData` keys such as `Sonozuki.MoreGrass/GrassOffsetX0`
- **Matching:** Mortar scans the save's `key` / `string` XML entries and, ignoring case, takes for each key the longest prefix ending at a `/`, `_` or `.` boundary that is a `UniqueID` in the mod dataset's index. Splitting at the first `_` would be wrong: 1,413 IDs contain `_`, and for 81 of them the part before it is another mod's ID; 1,081 have no dot.
- **Cost:** measured on a real save: 65 MB, 330,748 keys, 32 mods in 0.43 s. Results are cached by the save file's modification time. The same pass streams the file and writes nothing, and also reads `SaveGameInfo` for:
  - farmer, farm name, in-game date, `millisecondsPlayed` and `money`
  - farm layout `whichFarm`: 0 Standard, 1 Riverland, 2 Forest, 3 Hill-top, 4 Wilderness, 5 Four Corners, 6 Beach, 7 Meadowlands; -1 when the tag is missing
- **Limits:** mods that keep no per-save data leave no trace, and keys outlive a mod removed on purpose, so the warning says "this save has used", and each mod can be dismissed for that save.
- **Backups:** the Saves tab's Save backups lists the zips in `backups/` newest first with their time, cause, size and the farm names inside.
  - Restore, for one save or all of a zip, first zips the current Saves folder (cause `restore`), then extracts beside Saves and swaps each save folder in by rename, so a failure leaves the old one.
  - It refuses a zip path that would leave the extract folder, caps each file at 512 MiB, and is refused while the game is launching or running. Open backups folder uses the system file manager. **Back up now** and `mortar backups create <save>` zip that save only, kind `manual`, kept until unkept.
  - **Scheduled backups** (`savessvc.RunScheduledBackups`, started with the app): every 10 minutes Mortar checks whether `saveBackupHours` has passed since the last pass, measured from the newest `scheduled` zip after a restart. A due pass waits while the game is launching or running (including one Mortar did not start), then zips each save folder changed since its own newest scheduled zip into the backup folder, skips the rest, logs one line with saved, unchanged and failed counts, and emits `saves:scheduled` (`at`, `saved`, `unchanged`, `failed`, `error`): a failed pass toasts, and the game's Save backups settings show the last pass and when the next is due (`LastScheduledBackup`). Backup stamps more than 5 minutes ahead of the clock (a clock that once ran fast) are ignored, and a pass with failures retries after 30 minutes at most rather than a full interval.
- **Per-save backups:** `savessvc.SaveBackups(save)` lists, newest first, every zip whose index holds that save folder (kinds manual, scheduled, update, launch, restore, or unknown). A card's Backups section restores that save alone through `RestoreBackup` (same pre-restore zip and game-running refusal), pins or unpins, and deletes through `DeleteBackup`, which refuses a pinned zip and removes the zip with its cause file.
- **Per-save gap:** `savessvc.SaveGap(game, profile, save)` compares the mods the save was last played with (`last-played.json`) against the profile: `missing` (absent), `disabled` (present, disabled, same rule as `LastSaveGap`'s recorded list through `MissingFrom`) and `versionOlder` (enabled at a lower version than recorded). A save with no record has no gap.
- **Getting a lacking mod:** each one is located as Problems locates a missing dependency (`problems.Locate`).
  - A Nexus page or a GitHub repository gets Add to this profile, which queues it into the open profile; any other page gets an Open link.
  - Enabling a mod the profile has disabled is locked while the profile is launching or running.
  - Problems also suggests Content Patcher config values that enable compatibility patches for mods already enabled in the profile:
    - A change or dynamic token whose `When` pairs a `ConfigSchema` field (plain or `|contains=`) with `HasMod` of another enabled mod is a compatibility patch.
    - An on/off field (true/false, on/off, enabled/disabled, yes/no) whose current value, from the profile's `config.json` or the schema `Default`, runs none of the pack's compatibility patches is suggested with the values that would.
    - Fields that list NPCs are never suggested.
    - A variant picker (a palette, recolour or similar choice) is suggested from the pack's own mapping: a dynamic token that yields one of the field's allowed values only when a mod is installed (`Value: Earthy` when `HasMod: DaisyNiko.EarthyRecolour`) ties that value to the mod, and a field with two or more such values is a picker.
      - Its automatic choice is a blank value when `AllowBlank` is set, or the value those tokens require of the field (`Off`).
      - When the current choice names a mod the profile lacks, or is a generic choice while a mapped mod is enabled, the automatic choice (or else the value for the enabled mod) is suggested, worded as "made for that mod, which this profile lacks".
    - A recolour choice the pack does not map by `HasMod` (values naming Earthy Recolour, Starblue Valley, Vibrant Pastoral Recolor, Wittily Named Recolor or Eemie's Map Recolour, in the pack's own spelling) is suggested from the recolours the profile has enabled, and flagged when it names one the profile lacks (`internal/framework/contentpatcher/settings_recolour.go`). `auto`, `automatic`, `detect`, `off` and `none`, and fields the pack maps by `HasMod`, are left to the pack.
    - **Set to** writes only that field into `config.json`; Content Patcher fills the rest with defaults. Applying a suggested value also remembers that UniqueID, field and value so the reverse suggestion stays hidden until the field's current value changes.

### Mod data

- **Mod dataset:** SMAPI's `Pathoschild/StardewModDataset` (MIT or CC-BY-SA 4.0, published with explicit permission from the sites it lists, refreshed near the end of each month, 0.x with no version tags) records each Nexus mod page's current files with the SMAPI manifests inside them (`Downloads[].Mods[]`, `SizeInBytes`), not every file: Content Patcher has 2 there against 170 on Nexus.
  - **Fetching:** one page's entry when needed, from `https://raw.githubusercontent.com/Pathoschild/StardewModDataset/main/dataset/data/Nexus/<mod id / 1000>/<mod id>.json`; the `UniqueID` index (`dataset/indexes/pages by mod ID.json`, 1.5 MB, 28,634 IDs) monthly.
  - **Parsing** is lenient; a file it lacks is checked after download.
- **Update checks:** `POST https://smapi.io/api/v4.0.0/mods` with each mod's ID, `UpdateKeys` and installed version, plus `apiVersion`, `gameVersion` and `platform`, returns `suggestedUpdate`, which Mortar takes as given; `compatibilityStatus` and `brokeIn` come only with `includeExtendedMetadata: true`.
  - Unofficial versions (`metadata.unofficialUpdate` / `unofficial` / `unofficialForSmapi`, or those fields on `suggestedUpdate`) show as **Unofficial update available** with their link in the mod detail and Update review; **Update all** never installs them.
  - The API is public, unauthenticated and officially unreleased, so answers are cached for an hour in one cache shared by every profile (keyed by mod, update keys, installed version and environment, so a mod at the same version in several profiles is asked about once), misses go in batches of 100, concurrent checks wait for one another rather than asking twice, and after a failed ask Mortar serves stale or unknown answers for five minutes before asking again; failures never block.
  - Updates show as a count per profile and are applied only by the user; a pinned entry and a skipped version are left out of the count.
- **Dependencies:** `Dependencies[]` (`UniqueID`, `MinimumVersion`, `IsRequired` defaulting to true) plus `ContentPackFor` as a required dependency on its framework mod, all by `UniqueID`.
  - For a missing one, Mortar prefers the Nexus page named in its own `UpdateKeys`, else the page whose files hold it at the highest version (3,793 IDs appear on several pages), and takes the newest `MAIN` file satisfying `MinimumVersion`.
  - One found only on CurseForge is listed with its page link, to install from a downloaded archive; one found on no site Mortar has a driver for (an update key such as `ModDrop:N`) is listed by name with no link.
  - After an archive install and after a queue item finishes, the mods that landed are checked again, and any required dependency (`IsRequired` not false, or `ContentPackFor`) the profile still lacks is offered in a dialog whose Add them queues it by the Problems resolver; optional dependencies stay on the Problems bar.
- **Support:** Share log uploads the shown profile's `SMAPI-latest.txt` as it is on disk, or a stored run's log (`mortar logs share <game> <profile> [run]`; `--yes` skips the prompt), at most `launch.MaxLines` × 256 bytes, to smapi.io/log via `internal/logshare`, the Stardew community's standard support tool: `POST https://smapi.io/log` with a form-encoded body `input=<log text>`, no auth.
  - Save log… writes that same file when the profile owns it, otherwise the Console tab's lines, through the native save dialog (`picker.SaveFile`).
  - Only a loader with the `loader.LogShare` capability (SMAPI) offers Share log, since smapi.io's parser reads no other loader's log; `LoaderRef.share` gates the Console, crash and report-to-author entry points, and `support.CanShare` refuses the upload in the app and the CLI. Other loaders offer Save log and Copy log instead.
  - The server answers with a redirect to `/log/<id>`, which is the link, and answers a failed or empty upload with HTTP 200 and its page, so only a redirect counts as success (SMAPI's log parser in the Pathoschild/SMAPI repository).
  - A SMAPI log holds local paths, including the user's name, and anyone with the link can read it, so Mortar shows the log and asks first.
  - Save diagnostics writes a zip through the native save dialog (default name `mortar-diagnostics-<date>.zip`): `build.json` (Mortar's version, OS, architecture, portable flag, Go and Wails versions; WebKit's is not exposed), `settings.json` with `nexusName` and `nexusUserId` cleared and every field whose name says token, secret, key or password removed, `profiles.json` (ids, names, entry counts, mod names, versions and sources, no notes), `queue.json` without `nxm://` keys, `doctor.txt` (the same checks as `mortar doctor`), `runs.json` (the 3 newest launch runs across profiles, no log text), the last 2,000 lines of `mortar.log` (or the in-memory console), `mortar.prev.log` and `crash.log`, the open profile's SMAPI log when that profile owns it, and a `manifest.txt` saying what is in and what was stripped. The home folder is written as `~` in every text file. The bug report dialog's **Attach diagnostics** saves the same zip, then opens the GitHub issue; a URL cannot carry a file, so the toast says to drag the zip into the issue and offers **Show file**.
  - The keyring is not read.
  - Report a Mortar bug opens a new GitHub issue prefilled with Mortar's version, OS and architecture, and the game with its and SMAPI's versions; no log is attached.
- **Console links:** in visible log rows, exact installed mod names and `UniqueID`s link to that mod's panel, and paths under the profile's `mods/` folder or the game folder open their containing folder (`OpenConsolePath`, which resolves symlinks and refuses any other path).
- **Problems** warn and never block. Each check records per-family timings on the cached `Result` (`contentPatcher`, `conflicts`, `requirements`, `updates`, `others`) and logs `problems: <profile> <family> <duration> (<count> packs)`. They report:
  - missing dependencies
  - duplicate `UniqueID`s (resolved in a dialog that keeps one copy and switches the other off)
  - mods SMAPI's API marks broken, obsolete or abandoned for the game version, with `compatibilitySummary` when SMAPI supplies it, including a one-click replacement when the summary names a Nexus or GitHub target Mortar can install, or a `UniqueID` the mod dataset resolves
  - mods their own source flags, as `Broken` rows with `Source` naming the site (`internal/problems/source_flags.go`, advice that can be dismissed like an abandoned mod): Nexus mod pages whose cached status is not `published` (hidden, removed, under moderation, not published; read from the page cache, never fetched), and, through `source.StandingChecker`, Modrinth projects with status `archived` (`GET /projects?ids=`, 100 per request), CurseForge mods with status Inactive (7), Abandoned (8) or Deleted (9) or `isAvailable: false` (`POST /mods`, 500 per request) and GitHub repositories with `archived: true` (`GET /repos/<owner>/<repo>`, at most 20 per pass, stopping on a rate limit). Each site's answer for the profile's set of projects is cached for a day under `cache/standing-<site>-<hash>.json` (`meta.StandingPrefix`, which Clean up expires); a failed or rate-limited ask leaves the stale answer or no rows. Thunderstore deprecations are the `Deprecated` rows below
  - mods and packages the game's `knownBroken` catalog list names (`internal/problems/known_broken.go`): matched by mod id or Thunderstore "Namespace-Name" and version range, shown as `Broken` rows with `Source` "Mortar", the entry's reason and its replacement package
  - Content Patcher asset conflicts, each with a one-click fix
  - cleanup suggestions for unused frameworks, conservatively detected unused Content Patcher tilesheet packs (packs that only `Load` new sheets; one that edits an existing sheet is a retexture and never a candidate), and add-ons made for a recolour the profile does not have enabled
  - the profile's mods' rows from SMAPI's compatibility list (status, summary, the version it broke in, unofficial or replacement links); informational and not counted
  - redundant mods: **superseded** (the compatibility summary names a replacement that is enabled too; that mod's Broken and Compatibility rows are dropped), **shadowed** (a content pack every change of which later packs overwrite), and **sameJob** (C# mods doing the same job, or a smaller one covered by a larger; [Same job](#mod-data) below). A mod is listed once, and each same-job group is one row and one count
  - enabled mods that logged errors in this profile's newest stored run (warning when that run crashed or hit a fatal error, info otherwise; **Disable** and **Share log** on the stored run's log; cleared by a later clean run, switching the mod off, or updating it)
  - plugins the loader's log says failed to load or ran into errors (`LoadFailure`: the loader's log analyzers run over its log in the profile and the Unity player log, and each finding is attributed to an enabled package, or shown as the log wrote it when none declares the plugin)
  - a `[BepInPlugin]` GUID declared by more than one enabled package (`PluginClash`, read from the compiled plugins through `internal/dotnet`; BepInEx loads only one), with **Keep newer** disabling every copy but the one with the newest plugin version
  - installed Thunderstore packages the community's index marks deprecated (`DeprecatedPackage`), each with the replacement package the deprecated one's own summary names, if any, as **Replace with**
  - Abandoned mods are info-level and dismissible per profile like Content Patcher conflicts
- **What counts as a Content Patcher conflict:** two or more enabled packs (`ContentPackFor.UniqueID` `Pathoschild.ContentPatcher`) that `Load` the same target (warning: only one wins; a Load without `Priority` is `Exclusive`, and a below-default Load is a fallback, not a conflict, when either pack names the other, as a dependency or in `HasMod`: the lower pack names the stronger one, or the stronger pack's author named the lower one and set the priority gap on purpose) or that `EditImage`/`EditMap` the same target, or `EditData` the same entry or field (info, dismissible per profile via `settings.json` `dismissed`). Both kinds can be restored from Problems. `EditData` that only shares a target is not reported.
- Each conflict includes per-pack evidence: pack name, source file (`content.json` or an included file) and patch index, Action, Target, ToArea/FromArea for image and map edits, a short When summary, and Priority. `Problems` leaves the evidence out (it was 87% of the result: 291 KB of conflicts JSON became 25 KB on the main profile); `ConflictEvidence` returns one conflict's evidence when **Why?** on its row is expanded, and Copy report fetches it for the conflicts it lists. Expanding **Why?** lists that evidence; image edits load a PNG crop of each pack's overlapping source region (`ConflictImageCrop`) only when the row is expanded.
- Overlay image edits conflict only where an opaque 16×16 source cell lands; tokenised `FromFile` paths use every matching file, or fall back to the whole sheet when none match. Game setting `conflictScanDepth` `skipImages` compares overlay image edits by rectangle only (no opaque-cell PNG work).
- Loads whose files are all blank or JSON/image-identical are ignored; JSON equality is by parsed value, so formatting does not create a conflict.
- `FromFile` and recursive `Include` paths are relative to the content pack root.
- **When a change counts:**
  - A `When` `HasMod` condition (`"HasMod": "A, B"` or `"HasMod |contains=A": true/false`) counts only when that condition holds for the profile's enabled mods; other conditions are treated as met.
  - A change whose config conditions do not match the pack's current settings (`config.json`, else the schema `Default`) is not counted.
  - DynamicToken conditions use every statically reachable value; unknown game-state conditions stay possible, except an opposite literal `HasFlag` assumption in the same `When`.
  - Condition keys with an empty input (`"HasMod: |contains=…"`) read as the bare token, as Content Patcher reads them.
- **When two edits write the same place:**
  - Image edits compare their `ToArea` (or, without one, `FromArea`'s size or the source PNG's size at the top-left).
  - `EditData` edits compare `Entries` keys and `Fields` (entry plus field), under their `TargetField` path when one is set; the same literal value does not clash. List appends (`#-1`) never clash, and a key holding a token (`{{ModId}}`, a config or dynamic token) is that pack's own, since each pack fills its tokens itself. A value that is exactly one config token compares as that pack's configured value (`config.json`, else the schema default), so two packs set to the same value agree.
  - Map edits compare a `FromFile` patch's `ToArea`, each `MapTiles` position and layer, and `MapProperties` keys. A map patch without `ToArea` covers its `.tmx`/`.tmj` source's size (or `FromArea`'s) at the top-left; a `.tbin` source or any tokenized area counts as the whole asset.
  - Warps, `TextOperations` and tiles that only set properties merge, so they never conflict.
  - Edits that need different spouses (`Relationship:<NPC>`: `Engaged` or `Married`, or `Query: '{{Spouse}}' = '<NPC>'`) never apply together, nor do edits that require disjoint literal values of `LocationName`, `LocationContext`, `Season`, `Weather`, `DayOfWeek` or `FarmType`. An edit gated on a dynamic token counts as gated on a `FarmType` when, after config elimination, every definition of the token that yields a wanted value has a literal `FarmType` condition (a token true only for the custom farm type, or for Standard with a config that defaults off); a map edit with no `FarmType` is gated on the farm whose map it targets.
  - Two packs setting a map property to the same value agree and never conflict.
  - Overlapping image edits with the same source digest and `FromArea` agree and never conflict.
- **Measured and fixed** (main profile, CPU time, a copy of the data folder):
  - A check builds each patch's shape index and a pack's reachable dynamic tokens once and keeps both for the running check, rather than rebuilding them per pack pair and per patch. Conflicts, settings, redundant and cleanup: 0.56 s per check, against 0.92 s without the reuse, with identical output (same sha256).
  - The tilesheet map-file scan is saved in `cache/problems-map-scans.json` (gzip; path, size and modification time per map; entries of uninstalled folders pruned after each check): the first cleanup scan after launch takes 0.65 s instead of 0.82 s with a warm page cache, loading the 2,927 saved scans takes 29 ms, and the file is 330 KB.
  - Problems reads the newest run's id from the run index instead of its 0.65 to 1 MB log (5.1 ms to 4.2 ms per call, and no log read on every window focus).
  - The one-time zip-name repair walks the store and profiles (0.16 s CPU, 105k files) once: `names-repaired` in the data folder marks a clean pass, and later launches skip the walk. Every launch then points a mod record whose folder is gone at the one folder that differs from it only by U+FFFD standing for real characters (what the old extraction recorded), so switching that mod off keeps working.
- **Measured, not worth optimising** (main profile: 819 installed mods, 48,484 files under `mods/`):
  - The production frontend bundle is one 1.46 MB minified script, so code-splitting screens saves too little startup parse to pay for the lazy-loading seams.
  - A full walk of the store takes 82 ms (180 ms with a stat per file) over 53,758 files; a profile walk takes 72 ms (168 ms with stats) over 48,484 files.
  - The problem-scan cache is 2.5 MB gzip (31 MB raw); rewriting it after one pack changes takes about 0.55 s of CPU and loading it once per process 0.47 s. Each stays under the noise of a check; shrinking the cache is tracked for disk use, not speed.
  - A drift scan covers 48,484 files in about 220 ms (240 ms CPU), and a repeat check within 5 s reuses it. `Installed()` over 819 manifests takes 18 ms.
  - Queue history is capped at 1,000 items (299 KB, full on the main profile). `nexus-seen` is capped at 2,000. Runs are capped at 20 (the default `runsKept`).
  - JSON Lines for the append-only logs: reading, parsing and rewriting `history.json` (51 KB) costs 0.5 ms CPU per event and `download-history.json` (299 KB) 5.3 ms per finished download. Each history event also writes a snapshot file, events are edited in place (batches, change counts) and both files are trimmed to their cap, so an append-only format would still be rewritten.
  - Weighing the conflict fixes' master-switch rule by the assets a field reaches instead of its share of patches offered no new fix on the main profile and withheld fixes from small packs, so the one-fifth patch share stays.
  - Opening a 418-mod profile in the self-test build (Performance API) showed mod cards 171 ms after the click and the size footer at 1.1 s, with no main-thread task over 50 ms.
  - Cold start in the same build: the server answers its first request 112 to 128 ms after the process starts, the page is interactive (DOM) at 40 ms, and startup issues about 120 binding calls over its first 5 s (about 2 ms each) and none at idle.
- **Cosmetic or harmless:** an edit conflict whose every overlap is harmless is shown under **Cosmetic or harmless** and never counted as a problem. An overlap is harmless when both edits are images (they only change how something looks), when both are text edits (`Characters/Dialogue/*`, `Strings/*`, `Data/ExtraDialogue`, or `Data/Festivals/*` lines outside set-up, main event, shop and conditions: one mod's line shows instead of the other's), when either edit applies only in a literal `LocationName`, `LocationContext` or `Weather`, or when either is a one- or two-tile area at a tokenized position.
- A losing low-priority load gated by a user-changed config value produces a setting hint recommending the pack default, because the winning load makes that setting ineffective.
- **Cleanup:** frameworks that no enabled mod (or content pack) needs, but that a switched-off mod still names as a dependency or `ContentPackFor`, and enabled mods made for a recolour the profile does not have enabled (by name, such as an Earthy add-on without Earthy Recolour). They are listed, not counted as problems. **Remove** drops the framework from the profile ([gui-design.md](gui-design.md#problems-tab)).
- **Author-marked mods:** Problems also flags enabled mods whose cached Nexus page or installed manifest/file says obsolete or deprecated; this is informational and uses cached data only.
- **Same job:** Redundant lists enabled C# mods that change the same game members. A mod's footprint is the `StardewValley` properties and fields its `EntryDll` assigns, read from the compiled IL (`internal/dotnet`; a Netcode `set_Value` counts for the game member that loaded the wrapper; instance writes to an object the same method built, through an object initializer or a local only ever assigned a new object, are the mod configuring its own object and do not count; results cached by file size and modification time in `cache/problems-assemblies.json`), plus its Harmony-replaced methods from the startup report. Members that only drive input (`mouseClickPolling`, `lastClick`, `FacingDirection`) are dropped from every footprint, since they say how a mod acts and not what it does. Members are weighted ln(N/df) over the enabled C# mods with a footprint; a pair is flagged when the shared weight reaches 0.45 of the larger mod's total and some shared member is written by 12 mods at most (under 20 such mods: one footprint inside the other, every shared member written by three mods at most), unless one depends on the other, they share an author or download, or another enabled mod depends on either. A smaller mod is also listed, on its own row, as covered by a larger one when the larger changes 0.8 of its footprint by weight, the smaller footprint weighs at least 10 and every shared member is written by 12 mods at most; without those two guards, large mods cover one-member mods incidentally (118 such pairs on the main profile, 2 left with them). Measured on the 782-mod main profile: 177 code mods' assemblies read in 330 ms cold, 0.6 to 1.5 ms warm, and 7 ms to score.
- **Fixes and companions:** a conflict lists the settings that remove one pack from it: per pack, the narrowest on/off field that every clashing edit of that pack needs (one named for the target first, else the one gating the fewest patches), offered as **Set the field to its other value**. A field that would leave the pack nothing active, or that gates a fifth or more of its patches without being named for the target, is never offered. Overlapping edits are not reported between packs built to work together: packs in one entry, or where one names the other as a manifest dependency or in any `HasMod` condition (SVE and East Scarp patch around each other this way).
- **How the scan reads packs:** targets come from `content.json` and recursive `Action: Include` `FromFile` paths that stay inside the pack folder, with JSON comments and trailing commas tolerated; case and slashes are normalised; targets containing `{{...}}` are skipped. The scan is cached by each `content.json` mtime and runs with the other problem checks, off the UI thread. The bar lists the targets and can enablee pack off.

- **Generic Mod Config Menu:** menus a mod registers with GMCM or GMCM Options come from mortar-smapi-bridge, which runs inside the game: it writes each menu to `<profile>/gmcm/<UniqueID>.json` (index `_index.json`), and edits made through `mortar mods menu` wait in `<profile>/gmcm-pending/<UniqueID>.json` until the next launch, when the bridge applies them through the setters registered with GMCM, then the mod's save callback, and writes `<UniqueID>.result.json` with what it applied or skipped. The bridge finds the profile by walking up from its own folder to the first one holding `profile.json`. The config editor reads the captured menu for labels and ranges of `config.json` keys, and lists the menu itself as an **In-game menu** file: each page and section title is a section, each option a typed row (switch, number with its range, choice with the mod's labels, text), and widgets the bridge cannot set (colour, image, custom drawing) are read-only. A change there goes through `Store.SetGmcmOption`, which checks it against the capture, writes or drops the option's pending edit and records a history event; the pending files are part of the config capture history keeps, so Undo puts them back. A row whose edit waits shows the pending value with the captured one as its default, and the bridge's last skip reason for it.

- **Conflict winner:** "Make <mod> win" records the loser's UniqueID in the winner entry's `loadAfter` and adds it to the winner's installed `manifest.json` as an optional dependency, so SMAPI loads the winner later and its same-priority edits apply last. The profile's `manifest.json` is its own copy (an editable text file), so the store is untouched; the dependency is written again after an update, and an edit conflict decided this way shows as resolved and is not counted. Load-against-Load conflicts still need one mod disabled.
- **Asset map:** every asset an enabled mod changes (Content Patcher patch targets, with `EditData` split per entry, and `.xnb` files in a non-Content Patcher mod's folder), with each mod's Action and Priority and the winner. Mods are ranked in SMAPI load order (`internal/loadorder`), not profile order. Edits apply by priority, then load order, then patch order ([Content Patcher's EditData docs](https://github.com/Pathoschild/StardewMods/blob/develop/ContentPatcher/docs/author-guide/action-editdata.md), Priority), so the highest priority wins and a tie goes to the mod loaded last. Loads keep the highest priority, and on a tie the last loaded wins: `PatchManager.ApplyPatchesToAsset` replaces its pick with every later candidate that is not strictly lower, although the Load docs say "first". Two Exclusive loads (a Load without Priority is Exclusive) apply neither. A losing mod offers **Make win** only when it ties the winner's priority and no other mod in the group already loads after it through its dependencies, since only then does loading later change the result; otherwise the only fix is **Disable**. The index is built when the dialog opens and cached per profile under the same fingerprint as the problems result, so searching and paging reuse it (819-mod profile: 91,754 assets, 1,002 changed by more than one mod; about 1 s CPU on first open once the problems check has filled the content-pack cache, 8 s with that cache cold, then 40 to 120 ms per search or page). Json Assets and Dynamic Game Assets item IDs are not indexed: Dynamic Game Assets is retired in Stardew 1.6, and the three Json Assets packs on the 819-mod profile share no item name.
- **Update channel:** an entry's `updateChannel` is empty (main files only), `optional` (also newer OPTIONAL files on the same Nexus page) or `beta` (also prerelease versions); it filters offers where pins and skipped versions do.
- **Config presets:** a mod's `config.json` can be saved by name under `<data>/config-presets/<game>/<local id>/<name>.json` and applied to any profile's copy as one history event.
- **Groups and health:** a profile's `groups` name sets of entries that enable or disable together in one history event; after each problem check the counts are appended to `health.json` beside `profile.json` (newest 200 points).

- **Nexus-listed requirements:** Problems also report requirements named on a mod's Nexus page, including the author's note when present. They come from the batched page data (`nexussvc.Prime`, asked without a key when signed out), so a cold 811-mod profile costs 13 GraphQL requests. An outside link to a Nexus mod page of the same game counts as that mod; the game's loader (its Nexus page, or an outside link named as it) is never reported; any other outside download is a note with only Dismiss, since Mortar cannot add it. A page-wide outside requirement is only Optional for a file whose own manifest declares dependencies and names none like it, because Nexus lists it for every file of the page, sub-packs included.

## Nexus Mods

Sources: the API acceptable-use policy (help.nexusmods.com article 114), the SSO demo `Nexus-Mods/sso-integration-demo`, the `Nexus-Mods/node-nexus-api` client, and Vortex's (`Nexus-Mods/Vortex`) `NXMUrl.ts`.

- **Sign-in:** Settings takes a personal API key, kept in the OS keyring and never sent to a server of ours. `GET /v1/users/validate.json` gives the account's `user_id` and `is_premium`. Every request carries a truthful `Application-Name` and `Application-Version`.
- **Browser sign-in (off until Nexus issues a slug or client id):** `internal/nexussso` runs legacy SSO: dial `wss://sso.nexusmods.com`, send `{id, token, protocol: 2}`, open `https://www.nexusmods.com/sso?id=<uuid>&application=<slug>`, and read the API key off the socket. A dropped socket is redialed with the connection token (3 times), the wait ends after 5 minutes, and cancelling ends it at once. `nexussvc.StartSSO` hands the key to `SignIn`, so it is validated and keyring-stored like a pasted key; it streams `nexus:sso` events (`connected`, `waiting-browser`, `done`, `failed`), `CancelSSO` stops it and `SSOAvailable` is true only when the build sets `-X github.com/Rethunk-Tech/mortar/internal/nexussso.Slug=<slug>`. The same package has an OAuth2 PKCE client: S256, scopes `public openid profile`, and one fixed loopback redirect `http://127.0.0.1:51762/oauth/callback` (`nexussso.RedirectURI`; Nexus registers a non-dynamic callback). If that port cannot be opened the sign-in fails with "Port 51762 is in use; close the app using it and try again" and never tries another port. Tokens live in the keyring as `nexus-oauth`, refresh a minute before expiry and are deleted on sign-out. Which flow runs is chosen by build flags: `-X github.com/Rethunk-Tech/mortar/internal/nexussso.ClientID=<id>` selects OAuth PKCE (it wins over a slug), only `Slug` selects legacy SSO, and neither hides sign-in (`SSOAvailable` false). With a client id built in, `nexussvc.Authed` gives every Nexus call the access token as `Authorization: Bearer` (REST v1 and GraphQL v2), a pasted or legacy-SSO key is refused (`APIKeyAvailable` false, the key box is hidden) and the stored key is never read. The personal API key path stays compiled in until OAuth ships and is isolated in `nexussvc/apikey.go`, `nexus/auth.go` and the key box (each marked `remove with the API-key path once OAuth ships`). Registration facts: [docs/nexus-application.md](nexus-application.md).
- **Browse:** search uses the public v2 GraphQL endpoint (`POST https://api.nexusmods.com/v2/graphql`, `mods(filter: {gameDomainName, name WILDCARD, categoryName}, sort: ...)`), which needs no key. With no text the filter has no name clause, which lists the game's top mods; `sort` is endorsements (the default), downloads, updated or name, all descending but name. A category list is an AND in Nexus's filter, so included categories become one OR branch each, every branch also excluding the excluded ones. Category names come from the game's category list, which Nexus serves only to a signed-in account. GitHub search is `search/repositories` with the game's topic (`topic:stardew-valley-mod`; Lethal Company's is `lethal-company-mod`), and without a topic it does not search, cached ten minutes for its unauthenticated limit. Results only open the mod's page (or, for Premium, start a download the user asked for), like every other Nexus path.
- **Nexus updates and the user's say:** update checks are allowed, including the background check every four hours, which only notifies. A Nexus file is never downloaded or installed without the user's confirmation: nothing unattended queues one. Everything that does queue one follows a user click or a user-started action (Play with update before Play on, an install, an import, a restore, a Retry, the CLI), and a queue restored from a previous session is held paused at startup when it holds a Nexus file, until the user resumes it.
- **Update path:** a Nexus mod's update comes from SMAPI's API through the mod's `UpdateKeys` (`Nexus:<id>`), asked in batches ([Update checks](#mod-data)), and from there the Nexus file lists above decide the file. Mortar never searches Nexus once per installed mod for updates (`problems` skips `nexus` and `github` sources in its per-source update search): one search per installed mod would spend hundreds of requests of the hourly quota to repeat SMAPI's answer, and a GitHub repository search lists no versions. There is no per-mod Nexus search anywhere in the update path.
  - **Page data for many mods:** `nexus.Client.ModsByDomain` asks the GraphQL `legacyModsByDomain` for up to 50 mods in one request (Nexus caps a query's complexity at 10,000, and a mod with its requirements costs about 160) (name, version, status, summary, endorsements, dates, picture, author, uploader, category, whether the signed-in user endorsed it, the adult flag, downloads, and the page's Nexus requirements: a same-game Nexus mod keeps its id and page link, anything else is external and shown by name). `nexussvc.PrimeDetails` keeps whatever page data is cached and fresh and fetches only the rest, one request per 50 mods, into `cache/nexus/page-v2-<domain>-<id>.json`, which the Mods list calls for every Nexus mod in view, so hundreds of mods cost a handful of requests. Those entries are `Partial` (no file list, changelog or description); `Details` replaces one when the mod's panel opens. A rate limit or a signed-out account ends the lookup and returns what the cache holds, with the error.
- **Manual downloads:** per-game `offerNewDownloads` (default on) offers new archives (`archive.Extensions`) that land in the user Downloads folder (Linux: `xdg-user-dir DOWNLOAD` or `~/Downloads`; Windows: the Downloads known folder) or in Mortar's own download folder, one toast per batch (below). Nothing installs on its own.
  - A Nexus file name `<name>-<modId>-<version>-<timestamp>.<ext>` supplies the mod id; otherwise `dlwatch.Identify` peeks `manifest.json` inside a zip. `archivesvc.InstallDownload` uses the same archive path as a dropped file (FOMOD and folder asks included) and records `profile.KindNexus` with the mod id when known.
  - `internal/dlwatch` finds the Downloads folder and names archives; `archivesvc.DownloadsArchives` (and `mortar archive downloads <game>`) lists the not-yet-installed ones from both folders, deduplicated by path.
- **Folder watching:** `internal/folderwatch` runs one fsnotify watcher (top level of each folder only) for the open game's `Mods` folder, its `extraModsFolder`, Mortar's download folder (`ArchiveDir`, else `<data>/downloads`) and the user Downloads folder. A burst of changes settles for 500 ms, then one event with the game id fires (for `library:downloads`, a file written in place must also keep its size across two looks 1 s apart, while one renamed in, as browsers finish theirs, fires at once): `library:mods-folder`, `library:extra-folder` or `library:downloads`. Every 2 s the targets are re-read, so a changed open game or setting retargets, and a folder that does not exist yet is retried and fires once when it appears; a deleted one fires and is retried the same way. The window refetches the matching list on the event (new Mods-folder callout, extra-folder dialog, downloads dialog).
- **New-download offer:** on `library:downloads` the window calls `archivesvc.NewDownloads(game)`, which returns archives newer than the per-game `lastDownloadsSeen` mark (newest archive mtime, in the settings file) that are not already in a profile or the store, from both folders, then moves the mark. A file is never offered twice, across restarts too. Files the queue wrote (named by their 16-hex item id) are skipped, and the first call only sets the mark. Per-game `offerNewDownloads` (default on) gates it, and the window shows nothing while the game runs.
- **Rate limits** (measured on a free account): `x-rl-daily-limit: 20000`, `x-rl-hourly-limit: 2000`, with `-remaining` and `-reset` headers; the client reads them on every response and pauses before running out. Settings › Nexus account shows the remaining daily and hourly counts from the last response, with no call of its own.
- **Calls only on the user's action:** a mod's `picture_url` and `endorsement_count` (`GET /v1/games/stardewvalley/mods/<id>.json`) are fetched once, when it is installed, and cached; the picture itself is cached on disk under `cache/modpic` (startup prune by mtime to `MaxCacheBytes`, 64 MiB) and served to the window at `/mod-picture/` (the picture hosts of the Browse sources only: Nexus, Thunderstore, Modrinth, CurseForge, GitHub avatars and itch.io; images up to 8 MiB; Browse cards read their thumbnails through it too).
- **Mod page details** (`nexussvc.Details`): the page (`name`, `summary`, `description`, `picture_url`, `version`, `author`, `uploaded_by`, `uploaded_users_profile_url`, `category_id`, `endorsement_count`, `mod_downloads`, `mod_unique_downloads`, `created_time`, `updated_time`, `contains_adult_content`, `status`, `available`), `files.json`, `changelogs.json`, the requirements from one `legacyModsByDomain` request, and the category name from the game's `categories` (`GET /v1/games/stardewvalley.json`, cached 30 days) are kept in `<datadir>/cache/nexus/details-v4-stardewvalley-<mod id>.json` through the meta cache, never in `profile.json`.
  - They are fetched after each Nexus install and again when the detail dialog opens once they are a day old; signed out, rate-limited or offline, the cached copy is served however old.
  - When `available` is false the UI marks the mod **Hidden on Nexus**; when `status` is anything other than `published` it marks **Removed from Nexus**, with the page's updated (else created) date when known, in the detail panel and as a small marker on the list and grid.
  - Those pages are not offered as downloadable updates; the installed mod still runs.
  - Update review's row warning icon reads the same cache (`CachedDetails`) with the SMAPI-accurate `isNewer` compare and never fetches. Its **What's new** disclosure calls `nexussvc.UpdateChangelog` only when expanded: Nexus `changelogs.json` (own meta cache, 4 hours) filtered with `meta.CompareVersions` to versions newer than installed up to the new one, or, for a GitHub-sourced update, the cached GitHub releases in the same range (see GitHub releases). A failure shows **Changelog unavailable** and never blocks the review. The CLI's `updates --changelog` goes through the same call (`changelog` control method with the update's Nexus id and GitHub repo), so a GitHub-sourced mod prints its release bodies too.
  - Notes in that range that contain `breaking`, `incompatible`, `requires`, `now needs`, `new save`, `start a new`, `not save compatible` or `remove before updating` mark the update row with a warning icon ([gui-design.md](gui-design.md#download-queue)).
  - `description` and file descriptions are BBCode with `<br />` line breaks; `changelogs.json` maps each version, newest first, to HTML-escaped notes, and answers `[]` for a mod with none (measured on mods 541 and 1150, 2026-09-30).
- **Endorse and track:** only on the user's click, for a signed-in account. Endorse and abstain are `POST /v1/games/stardewvalley/mods/<id>/endorse.json` and `abstain.json` with `{version}`; the state is the page's `endorsement.endorse_status`, and when Nexus refuses to endorse a mod that was not downloaded, its own message is shown in a toast. Track is `POST` or `DELETE /v1/user/tracked_mods.json` with `{domain_name, mod_id}`, and the tracked list (`GET` the same path) is reused for 30 seconds. Settings › Nexus account **Untrack on Nexus** › **All…** and **Unused…** walk that list for the game's Nexus domain and untrack (the unused pass keeps mods any profile still names). The CLI is `mortar nexus untrack` ([HUMANS.md](../HUMANS.md#command-line)).
- **When a Nexus download may start:** the rule is in [AGENTS.md](../AGENTS.md); a Premium download the user asked for comes from the queue, Update or Import. A Nexus collection link previews and imports like a share link (same Preview, Import, and queue), and its downloads start only as that rule allows.
- **New since last look:** a mod's cached details are compared with its `nexus-seen.json` record. A newer current file upload or a changelog version than the record marks it New, and showing its details (the dialog or the sidebar) updates the record. A mod never looked at is not New, and nothing is fetched for this.
- **Files:** `GET /v1/games/stardewvalley/mods/<id>/files.json` lists every file (170 for Content Patcher) with `file_id`, `file_name`, `version`, `mod_version`, `category_name` (`MAIN`, `OPTIONAL`, `UPDATE`, `MISCELLANEOUS`, `OLD_VERSION`, `ARCHIVED`, or null), `size_kb` and `is_primary`. An update takes the `MAIN` file matching SMAPI's `suggestedUpdate`, else the `is_primary` one, and never an `OPTIONAL` file unless the profile already uses it. Before choosing, Mortar asks Nexus GraphQL v2 `modFiles { fileId scannedV2 }` (cached on the client). A file whose `scannedV2` is `QUARANTINED` is omitted from choice; a request for that file id fails the queue item (`Nexus has quarantined this file; Mortar will not download it`). A failed scan leaves the v1 list unchanged.
- **Downloads:** `GET /v1/games/stardewvalley/mods/<id>/files/<file id>/download_link.json`. Premium accounts get links directly; they expire, so Mortar asks just before downloading and again on a restart. A free account gets HTTP 403 ("...this is for premium users only", measured); it needs the `key` and `expires` from the `nxm://` link that the site's Mod Manager Download produces, one click per mod. Each answer lists several CDN mirrors (`name`, `short_name`, `URI`); Mortar remembers every `short_name` it has seen. Settings › Downloads **Preferred download server** chooses one of those names or **Automatic** (empty setting), and the queue takes the preferred mirror when present else Nexus's first.
- **`nxm://` links:** `nxm://<game>/mods/<mod id>/files/<file id>?key=<key>&expires=<unix>&user_id=<id>`; Mortar takes this form only for Stardew Valley (`stardewvalley`).
  - Only one app can own the scheme, and Wails' NSIS macro would delete and rewrite its key at install time without asking (`build/windows/nsis/wails_tools.nsh`, from Wails' template), taking it from Vortex or Mod Organizer 2.
  - So `nxm` is not in `build/config.yml`: Mortar registers it at runtime after the user agrees (`HKCU\Software\Classes\nxm` on Windows, with `DefaultIcon` at `mortar.exe,0`; on Linux a user-level `~/.local/share/applications/tech.rethunk.Mortar.desktop` lists `x-scheme-handler/nxm` and `xdg-mime default` is set; turning it off drops the type again), records the previous handler in `settings.json` (`nxmPreviousHandlers`, plus `nxmPreviousName` for the UI), and restores it when turned off or when uninstall runs `mortar.exe --release-links` before files are removed (the key is deleted when there was no previous handler).
  - When Mortar owns the scheme and a previous handler was recorded, Settings › Downloads **Send other games' links to …** (default on) forwards `nxm://` links whose game is not Stardew to that handler (Windows: the saved open command with `%1` replaced; Linux: the saved desktop entry's `Exec` with `%u` replaced).
- **Link bursts:** each `nxm://` launch is a second instance whose arguments the running one queues at once and handles in order, logging every link (`second instance:`, `nxm:`, `queue:` lines), so a burst loses nothing inside Mortar (16 simultaneous `gio open` launches: 16 handoffs, 16 links).
  - Chromium browsers (Chrome, Vivaldi, Edge) launch at most one external protocol per user gesture (`g_accept_requests` in `chrome/browser/external_protocol/external_protocol_handler.cc`), so Nexus Slow Download countdowns that end with no click in between are blocked in the browser, which logs `Not allowed to launch 'nxm://…' because a user gesture is required.` in that tab's console.
  - The Mortar browser extension (its own repo, <https://github.com/Rethunk-Tech/mortar-browser-extension>, MV3 for Chromium and Firefox) avoids that gate: on `www.nexusmods.com` it reads each `nxm://` anchor (the Start download manually link, inside the download widget's open shadow root) and sends it with `sendNativeMessage` to the host `tech.rethunk.mortar`, which is Mortar itself (`internal/nativehost`: Chromium passes the extension origin as the first argument, Firefox the manifest path and the extension id).
  - That process starts `mortar <link>`, so the link takes the same second-instance path.
  - The protocol is versioned: every extension message carries `protocol` and every reply carries Mortar's (`nativehost.Protocol`, 2). Mortar answers extension protocols `MinProtocol`..`MaxProtocol` (2..2; a message without one counts as 0) and refuses any other with `protocolError` `extensionTooOld` or `extensionTooNew`, recorded in `extension-contact.json` as `mismatch` for Settings › Downloads. The extension checks Mortar's number against its own range (a reply without one counts as 0) and asks the user to update whichever side is behind. A change to a message's shape bumps both sides.
  - The host also answers JSON requests without starting a download: `{"type":"installed","source":"nexus","sourceGameKey":"<nexus domain>"}` returns `modIds` for Nexus entries in the last-open profile of the game that domain maps to in the component manifest (empty when Mortar is not running); `{"type":"mod","source":"nexus","sourceGameKey":"<domain>","modId":<id>}` returns `open` (that profile's name, installed version, file id, and when the mod is in the active profile: `requiredBy` names, `pinned`, `skipVersion`, `skipSources`) and `others` (the remaining readable profiles, each with name, version and file id when that Nexus mod is present).
  - The page's game is that Nexus domain, not a hard-coded Stardew id. Every reply carries `games`, `[{id, name, sources:{<source id>:"<that source's key>"}}]` for each catalog game with a source key (`{"nexus":"<domain>"}`, and `thunderstore` for a game that lists it), so the extension maps a page's key to the Mortar game id and opens `mortar://<game id>/mod/<id>`. Data requests are still answered for Nexus pages only.
  - What the popup and content script show with those replies: [gui-design.md](gui-design.md#browser-extension).
  - A link that arrives again before its own `expires` time (from the page's own launch, from the extension, or from every open tab when the extension is reinstalled) is taken once; the record lives in memory, so a restart forgets it.
  - The extension injects itself into Nexus tabs that were open before it was installed.
  - On mod listings (`/games/<game>/mods`, `/<game>/mods`, search and collections) it marks the tiles of mods in the profile last open for that game; its listing filters are in [gui-design.md](gui-design.md#browser-extension). For **Gray out broken**, the `installed` reply's `brokenIds` come from Mortar's cached copy of SMAPI's compatibility list, leaving out a mod whose `brokeIn` is a later Stardew Valley version than the one last played, so that filter needs Mortar installed but not running. Installed means a Nexus-sourced entry, the game's loader (its Nexus page is `loaderModId` in the component manifest; SMAPI is 2400), or a local archive that kept Nexus's download name (`<name>-<mod id>-<version>-<unix time>.zip`).
  - When Mod manager download opens Nexus's "Download mod file" requirements dialog (`[role=dialog]` in `#next-shadow-root`), the extension follows its Download link at once: the `a.nxm-button-flamework` whose href carries `nmm=1`, is on nexusmods.com, and points at the page's own mod or at Nexus's `/api/files/<file id>/download` (`mortarIsOwnDialogDownload` in the extension's `modPanel.js`), once per dialog (requirement rows carry Mod Manager Download links to other mods, which are left alone), since Mortar resolves requirements itself; a file without that dialog, and Manual download, are left alone.
  - After Mortar confirms a link, the extension closes the tab when it was opened only for that download: every history entry is the same mod's page, whichever of its tabs (Navigation API `navigation.entries()`, which lists only same-origin entries, so a `history.length` longer than the list keeps the tab; where that API is missing, no tab is closed).
  - On Linux, turning nxm handling on, and every start while it is on, writes the host manifest into `NativeMessagingHosts/` of each installed Chromium browser under `$XDG_CONFIG_HOME` (Chrome, Chromium, Brave, Edge, Vivaldi) and into `~/.mozilla/native-messaging-hosts/`; turning it off removes them.
  - A Flatpak build writes none, since a browser outside the sandbox cannot run it.
  - The unpacked extension's id is fixed by the `key` in its manifest.
- **Browser problem panel:** the extension can request up to five active-profile problems involving a Nexus mod; it is read-only and never downloads or opens Nexus pages.
- **No re-hosting:** mod files and Nexus data stay on the user's machine; a share link holds IDs only.
- **Download queue:** an import or a profile's missing files run one queue (`internal/queue`), persisted in `<datadir>/queue.json` without the `nxm://` keys.
  - Items store as `nexus-<mod id>-<file id>`, and the entry records source kind `nexus` with the mod id, file id, version, picture URL and endorsement count, fetched once at install.
  - When a file from a Nexus page is installed into a profile that already has an entry from that page, the queue offers **Install together** with that entry, **Install separately**, or **Don't install** (default add for OPTIONAL and MISCELLANEOUS files, separate for a second MAIN).
  - Installs started from a save's missing mods, a missing dependency or a Problems fix send `latest`: the file they name came from the mod dataset or a save and may be old, so the queue follows Nexus `file_updates` from it to the newest listed file; share imports leave it off to reproduce the shared files.
  - A Nexus update downloads the file that supersedes the installed one (`nexus.Supersedes`), since a page can hold several downloads (a main file and optional packs) and its version is the main file's: the author's `file_updates` chain, else a newer file of the same download (display name or archive stem), else the one current file of the entry's category at the new version, else, for a MAIN entry on a page with exactly one current MAIN file, that file. The update check picks it from the file list it already fetches (one batched live call, with the cached full file lists of `cache/nexus/details-v4-*` filling in whatever the call did not return, signed out or rate-limited, and supplying `replacedBy`, which the batched query lacks). The page's version never decides: when the installed file is the newest of its download the mod has no update, however high the page's number (an author can bump the page without uploading a file), and when none supersedes it but a current file of another download exists the update is marked `pickFile` and nothing queues it. A queued update that still resolves to a file the profile already holds ends `skipped` with the reason "Already the newest file", and a batch that settles with only such items toasts "Nothing to update" instead of "Updated 0 mods". A mod whose newest version SMAPI reports from a `CurseForge:<id>` update key (the suggestion names no file) is resolved through the CurseForge driver (`problems.curseforgeSwitches`): the newest stable file becomes a package update of source `curseforge` at that file id, marked `switch` with `fromSource` when the entry was installed elsewhere, so the install swaps the entry in place by its mods like any update and the entry's source becomes CurseForge; a file that is not newer drops the update, and a project that forbids downloads outside CurseForge shows as `notDistributable` (no Update button, the row points to the page). Without a CurseForge key the SMAPI row stays as it was.
  - Premium accounts download without clicks.
  - A free account's head item waits for its click (**Open download page** and **Skip** on that row), and a matching `nxm://` link is routed to it instead of showing the arrival card.
  - An update or `latest` Nexus item is skipped on its own (`queue.skipHeld`) once the profile already holds that file id or a newer one from the same page; for an item whose current file is an optional file the profile holds, only that optional file's id counts. A request for an exact file, as a share import does, is left queued.
  - A Nexus file the game's store already holds (`nexus-<mod id>-<file id>`, from an install into any profile) installs from the store with no download and no click, taking its file name, version and picture from the profile entry that recorded it so Nexus is not asked, unless the profile has an entry from the same mod page, whose Install together choice needs the archive (an optional file without a manifest skips that question, so it installs from the store too).
  - A link's item gets its mod name and picture as soon as it is queued, so Up next shows them.
  - A reached rate limit, Nexus's or GitHub's, pauses the whole queue until its reset time.
  - GitHub items (`repo`, `tag`, `asset` instead of a mod id) need no sign-in and never wait for a click; see [GitHub releases](#github-releases).
  - Done, failed, cancelled and skipped rows can be dismissed one at a time or cleared together; that drops them from `queue.json` and from staged-key tracking, and never removes queued or in-progress items.
  - An install that unpacks without a SMAPI manifest pauses in `needs-root` with the staged store key and a folder tree until **Choose folder…** saves a content root (`AnswerRoot`) or cancel marks the item failed; FOMOD and multi-asset releases use `needs-fomod` and `needs-choice` the same way.
  - **Resume:** a retry or a restart sends `Range` from the partial's size and accepts 206, starts over on 200, and starts over when the `ETag` changed or the `Content-Range` does not match, at most three times; a Nexus link that has died is replaced through the download-link call before ranging on.
  - The fetch covers Nexus and CDN downloads; GitHub assets always start over, and `Content-MD5` is not checked.
  - The queue HTTP client waits 20s for response headers (the body may stream longer) and drops a transfer that sits idle past its idle timeout.
  - The worker runs under an app-lifetime context cancelled when Mortar quits.
  - Every finished item is appended to `download-history.json`.
- **Source kinds:** `profile.Source.Kind` is `local`, `nexus`, `github`, `thunderstore`, `modrinth`, `curseforge` or `itch` (constants `profile.KindLocal`, `KindNexus`, `KindGitHub`, `KindThunderstore`, `KindModrinth`, `KindCurseForge`, `KindItch`), plus `smapi` and `mortar` for the bundled entries. A `github` source holds `repo` (`owner/repo`), `tag` and `asset`; share links read them as `<owner>/<repo>@<tag>/<asset>`. A `thunderstore` source names `Namespace-Name` with the package version, and a `modrinth`, `curseforge` or `itch` source names the project, mod or game id with the version or upload id.

## GitHub releases

`internal/github` reads `/repos/<owner>/<repo>/releases` without sign-in. Answers are cached on disk for an hour and served stale when GitHub is unreachable. The unauthenticated limit is 60 calls an hour per IP, and a reached limit shows its retry time. An install or update takes the archive asset the picker settles on (below), or asks when it cannot; the download is capped at the archive extraction limit, drops a transfer that sits idle past its idle timeout, and stores under its `github-` key. SMAPI's own release lookup uses the same client.

**Trust:** a GitHub-sourced install counts as verified only when SMAPI's update API (`includeExtendedMetadata: true`) maps the manifest's `UniqueID` to the same repo. It is unknown when the API is unreachable, and never blocks.

**Installs and updates:**

- The queue resolves a GitHub item with `Releases` and `Select` (an update asks for SMAPI's suggested version, an install for the newest stable release), downloads with `github.Download`, unpacks into the store under `github.Key`, and reads the manifests' `UniqueID`s before the profile changes.
- Every ID verified installs; a known mismatch parks the item in `needs-confirm` (Install anyway or Skip); an unknown answer installs and marks the item "could not verify".
- A release with several archives is narrowed (`queue.pick`): the asset shaped like the one the user last chose from the repo (`github.Shape`, the name without versions, kept in `github-choices.json`), else `github.Installable` drops source archives, checksum files and other-platform builds (each filter skipped when it would leave nothing), else zips whose file list (`github.ZipNames`, the central directory read with ranged requests) one of the game's loaders recognises (`loader.ModArchive`: a SMAPI `manifest.json`, a Thunderstore-shaped root for BepInEx). One left installs; several park the item in `needs-choice`, and the user's pick is remembered for the repo. `queue add --source github` without `--file` resolves up front (the newest release without `--version`) and fails with the remaining assets listed when the pick is ambiguous.
- Update review's Update and Update all use GitHub when the mod's update key is `GitHub:<owner>/<repo>` and SMAPI's suggested update URL is on github.com (`problems.Update.GitHubRepo`); otherwise Nexus. A Nexus update carries a GitHub fallback repo (`GitHubFallback`): the manifest's GitHub key, or else the repo SMAPI's metadata lists for the mod. A free Nexus account must click for every file, so GitHub goes first: when the item would wait for that click, the queue looks for a GitHub release at the same version with exactly one archive and downloads it (once per item). Because a metadata repo may publish several mods, the staged archive must contain the updated mod's UniqueID (`FallbackID`); otherwise the item goes back to Nexus. Measured on the main profile (2026-10-04): 161 mods carry a metadata repo, and 34 have a one-archive release at their installed version. The update review notes the GitHub-first source on each such row. When an update check finds a manifest older than the download it came in (the installed file is already the suggested version), Mortar sets that manifest's `Version` to the suggested version in the profile's copy and in the store item, changing only the value and refreshing the drift snapshot, so SMAPI stops offering an installed update. A mod from another file of the same entry (an extra store key) is never rewritten, since the download's version says nothing about it.
- Update review's **What's new** lists the release bodies (markdown shown as text with links, publish date) for tags newer than the installed version up to the new one, at most 10 (`github.ReleasesBetween`, reading the cached releases list), in place of a Nexus changelog.
- A missing dependency the dataset does not place on Nexus takes the GitHub repo SMAPI's API records for it (`problems.Ref.GitHub`), and the problem bar's Add queues it.

## Sharing

- **Form:** Discord makes only `http://`, `https://` and `discord://` links clickable (Discord community posts 14574789338135 and 25441082215447), so a shared link is `https://mortar.rethunk.tech/<game id>/p#<payload>`, handed to the app as `mortar://<game id>/p/<payload>`. Each playable game's page is written from `scripts/share-page.html` by `scripts/site-games.ts` (the gate checks it), and all of them run `site/share/app.js`. Browsers never send the part after `#`, so no profile data reaches any server. The app accepts either form, or a bare payload, pasted into its import box.
- **Payload** (`internal/share`): compact JSON `[3, "<profile name>", "<game id>", {"<source id>": "<that source's game key>"}, [<entry>, ...], "<game version>"]`, the game version the profile was shared from being optional (left out when unknown), the leading number being the format version (only 3 is read; a Mortar meeting a newer one says to update). The game keys are stated once per link, e.g. `{"nexus":"stardewvalley"}`, and the share page builds its Nexus links from them, Brotli-compressed at quality 11 and base64url-encoded without padding.
  - An entry is an object naming its source, so a link names the exact file: `{"s":"nexus","mod":<id>,"file":<id>}` or `{"s":"github","repo":"<owner>/<repo>","tag":"<tag>","asset":"<asset>"}` or `{"s":"thunderstore","ns":"<namespace>","name":"<name>","version":"<version>"}`, plus the optional `disabled`, `fomod`, `note`, `tags` and `overlay` extras, and for the share page `kb` (the store item's size, rounded to two significant digits) and `min` (the newest `MinimumGameVersion` the entry's manifests declare). When a link would pass the cap, `kb` and `min` go first, then the extras.
  - The share page shows each mod's picture where public, keyless and cacheable URLs follow from the link (the GitHub owner's avatar, a Thunderstore package's icon at its version; Nexus pictures need an API key, and their thumbnail URLs are too long to carry: measured on a 644-mod profile, the link already used 5 KB of its 8 KB), its source and size, the total size, and a **Your game version** field prefilled with the shared game version that flags each mod whose `min` is newer.
  - Only enabled entries with a source are shared; local archives are listed at Share as left out, and so are switched-off entries.
  - An optional file without a manifest is an entry like any other, so the receiver downloads it as well. Files of one Nexus mod download in parallel; a file found to have no manifest (once downloaded, or in the store) goes back to the queue, already downloaded, while an earlier queued file of the same Nexus mod for the same profile is still under way, so the main file installs first and the optional file is laid over it; a manifest-less download skips the "add to the entry from this page or keep apart" question. Bundles and templates keep optional files after the mod they go over, with their `overlayFrom` and `overlayTo`, and apply them in that order.
  - SMAPI's bundled mods (the `smapi-<version>` entry) and the bridge (`bridge-<version>-<sha256 prefix>`) are never shared, listed or imported: every profile gets them from the signed component manifest.
  - About 240 mods fit a 2,000-character Discord message.
  - The link holds no `UniqueID`s, which barely compress.
  - Brotli (`github.com/andybalholm/brotli`, MIT; the standard library has none) is the compressor.
- **Share dialog** (`internal/sharesvc`, `frontend/src/share`): the link with a length meter against 2,000 characters, Copy as a message, the mods by source and what is left out with the reason. Over 240 mods, or when the payload passes the 8 KB cap, it suggests the file. `Share` and `SaveFile` take a list of entry keys, and an empty list means the whole profile, so sharing a selection encodes only those entries (a selected mod in a multi-mod archive shares the whole download).
- **Mod list as text:** the dialog also copies the profile's mod list as Markdown (`[Name](page URL)` with the version, grouped Enabled and Disabled when any are off), plain text (`Name vVersion - URL`) or Discord (the Markdown split into messages of at most 2,000 characters). Bundled SMAPI mods and the bridge are left out, as in shares, and the chosen format is kept for the session.
- **`.mortar` file:** a zip holding `profile.json` (the same format version and entries as a link, the game and its source keys, the name, notes, description and the shared mods' ids, `ids`, which bound the config files it may carry) and `configs/<format>/<local id>/<relative path>.json` for each enabled mod's `.json` files except `manifest.json`, and `loader/<path in the profile>` for the text config files (`.cfg`, `.json`, `.toml`, `.ini`, `.yml`, `.yaml`, `.txt`, valid UTF-8) under the config folders of the loader the profile runs (`loader.WithConfig`, BepInEx: `BepInEx/config`), leaving out the companion's state file. Files over 1 MiB, with unusual names, or past the totals are skipped and listed at Save. **Problem choices** (`problems` in `profile.json`, option on by default, File and LAN only; a link has no room for them) are the player's decisions about the profile's problems: `dismissed`, the problem tokens kept in `settings.Dismissed["~mortar/cp/<game>/<profile>"]` (dismissed conflicts, listed requirements, abandoned mods, compatibility settings and settled setting hints), and `wins`, each a pack of a download (named by its ref) that loads after a loser (`Component.LoadAfter` in the profile). Caps: 1,000 of each, tokens at most 300 bytes with a tab and no control characters; a file past them is refused whole, and the sender drops what does not fit. The receiver adds them to the target profile and never removes any (`sharesvc.applySharedChoices`): dismissals join its own, a win applies once both packs are on the profile (waiting for queued downloads like config files do) and is skipped when the profile already decided the pair the other way or lacks the loser. Import preview shows the count (`Preview.Choices`). The description, at most 280 characters, travels only in this file: a link stays `[version, name, game, sourceKeys, entries, gameVersion]`, since the field would grow the 8 KB encoded payload, and colour and icon travel in neither.
- **Import preview:** `sharesvc.Preview*` resolves every entry and creates nothing.
  - A Nexus file is confirmed with the mod's `files.json` (needs the sign-in; signed out, the preview stays with what the link and the dataset say).
  - A file that is gone or `ARCHIVED` is replaced by the `MAIN` file with the same version (from the listing, else from the dataset), else the primary file, marked "different file"; a mod with no files or a 404 is unavailable ("removed from Nexus", with its page), and a mod with files but no replacement is unavailable too.
  - Entries the target profile already holds by Nexus mod and file ID are installed.
  - UniqueIDs and dependencies come from the dataset page (`meta.Page`); a file the dataset lacks is "check later".
  - The shared mods and the target profile's mods go through `problems.Check`: a missing dependency Mortar can name on Nexus or GitHub becomes a dependency tile, one it cannot (CurseForge, unknown) is a listed problem, and a mod SMAPI's API marks broken for the game version is a problem with Leave out.
  - A GitHub reference is marked unverified, since its trust rule (see [GitHub releases](#github-releases)) can only run after the download.
  - A free account gets a note that each download takes one click on Nexus.
- **Import:** the dialog's tiles carry a tick each; **New profile from link** (or file) creates a profile named from the share, records origin `link` or `mortar`, and queues every available, ticked file through the download queue, and **Add to the selected profile** queues them into the profile Import was opened from.
  - Nothing downloads before that click, and a preview left behind is dropped on close.
  - Unavailable mods are listed in the new profile's notes.
  - A `.mortar` file's config files are written by `share.Apply` once their mods are installed: only `.json` files under a folder an installed mod of that import already has, re-validated at write time, and never over mods the profile already had. Its loader config files are written when the import makes or replaces the profile, only under the receiving profile's own loader config folders; an import into an existing profile keeps the files it already has.
  - Config files still waiting are kept in `<datadir>/pending-configs.json` (temp file, then rename) independently of live queue rows, and at startup Mortar applies them for downloads that are already done and again as the rest finish.
  - Finished queue rows ageing off or being cleared does not drop pending configs.
  - If the last download finishes while the game is using the profile, apply waits and retries when the game goes idle (and on a short timer until then).
- **Routing:** `mortar://` is in `protocols:` in `build/config.yml`, which the NSIS installer registers; `.mortar` is in `fileAssociations:` (the installer's `APP_ASSOCIATE` block in `wails_tools.nsh` uses the executable's icon).
  - On Linux, `nxm.System.RegisterLinks` (run when first run ends, and at startup in a production build when no desktop entry exists yet) writes `~/.local/share/mime/packages/mortar.xml` for `application/x-mortar`, keeps the user desktop entry listing the mortar scheme and file type, and sets both `xdg-mime` defaults; it is idempotent and takes an injected runner.
  - `Options.SingleInstance` with `OnSecondInstanceLaunch`: a link reaches the app as `events.Common.ApplicationLaunchedWithUrl` on a cold start (fired when the only argument contains `://`, `Rethunk-AI/wails` `v3/pkg/application/application_linux.go:73-83`) or in `SecondInstanceData.Args` when it is already running.
  - `sharesvc.Receive` reads both, plus `.mortar` paths and `file://` URLs (including Windows UNC `file://server/share/...`).
  - A share link or `.mortar` file opens the Import dialog with that value filled in, never importing by itself.
  - `mortar://<game>/mod/<id>` (game id as host, a positive decimal Nexus mod id with no leading zeros, no query or fragment) opens that game on its last-open profile, selects the matching Nexus mod on the Mods tab, or toasts that the id is not in that profile.
  - A `.mortar` file dropped on the window opens Import instead of installing as an archive.
- **Trust boundaries:** link parsing accepts only the known forms and caps the encoded payload at 8 KB and the decompressed payload at 64 KB before parsing; a `.mortar` file is capped at 32 MiB, 5,000 entries, 1 MiB per config and 32 MiB of configs, and any entry outside its layout fails the whole file; the clipboard is read only when the user presses Paste. Extraction limits: [Trust boundaries](#trust-boundaries).
- **LAN sharing** (`internal/lan`): with Settings › General **Share profiles on the local network** on, Mortar advertises `_mortar._tcp` (hashicorp/mdns) and serves HTTP on `lanPort` (default 47630).
  - Sends are refused while sharing is off.
  - A send is a `.mortar` payload (at most 32 MiB), built with the Share dialog's Included options (`share.Include`; `Send` takes them, the CLI sends everything). To a paired computer every option applies and archives added from disk travel as store items; to an unpaired one config files are dropped (they can hold keys, so only a paired computer gets them) and local archives are left out, the rest applies. The handshake protocol is 5.
  - **Pairing** makes two of the user's own computers trust each other, independent of any store account. Settings › General › Sharing: **Pair a computer** shows a single-use code (8 characters, two groups of four, valid 5 minutes); **Enter code** on the other computer picks the nearby computer and types it. Both then hold a 32-byte key for the other in `<data>/lan/peers.json` (mode 0600, with this computer's stable id); **Unpair** deletes it.
  - The exchange is `POST /pair/begin` and `/pair/finish`: X25519 (`crypto/ecdh`) from both sides, then HMAC proofs over the transcript (which binds both devices' names) and the X25519 secret keyed by a PBKDF2 stretch of the code (200,000 rounds), so a passive observer cannot test code guesses. The long-term key is HKDF of the X25519 secret, never of the code. A host locks a peer for 10 minutes after 5 wrong codes and burns the code after 15 wrong attempts in all. The threat model is the comment at the top of `internal/lan/pairing.go`.
  - The sender `GET`s `/hello` (the receiver's id and a one-minute nonce bound to that peer) then `POST`s `/share` with the payload, its listen port, its id and, when the receiver is paired, an HMAC-SHA256 proof under the pairing key over the nonce concatenated with SHA-256 of the payload (hex); the key is never sent.
  - The receiver compares with `hmac.Equal`. A proof from a paired peer plus a sender port marks the share **paired**: the response carries a 5-minute Bearer token scoped to the store keys of every entry (Nexus, GitHub, and Thunderstore packages that name a version), with a proof under the same key so the sender never grants a token an unpaired computer made up.
  - The receiver then `GET`s `/store/<game>/<key>` with that token; the sender streams a tar of each granted store folder (10,000 entries and 2 GiB caps, same extraction rules as other archives), and the receiver hashes what arrived (`store.HashDir`) and installs it through `Store.AddDir` only when that hash is the one the sender vouched for, refusing an entry with no vouched hash: a paired sender's share lists, for each entry, the store folder's hash with an HMAC over the game, entry key and hash under the pairing key (`entryDigests`, protocol 4), and the receiver checks that MAC before it accepts the hash, so what an eavesdropper serves on the unauthenticated transfer address cannot pass for what the sender holds. It records a GitHub or Thunderstore entry's source with `Store.Describe`. Sending between one's own machines is copying, so a paired receiver gets the files whatever the source or its licence.
  - Unpaired receivers still download each mod from its source.
  - Optional files travel as their own store items like any entry; a link or `.mortar` file carries each one's placement (`overlay`: `from`, `to`, `off`, added to its ref without a format bump, so older Mortars ignore it), and the receiver's queue (`Request.Overlay`) installs it from the store after its main file and lays it there with the same switch, without asking. A ref with no `overlay` is placed the way a download is.
  - Incoming shares are rate-limited per peer (10 s).
  - UI: [gui-design.md](gui-design.md#profile-management).
- **Windows firewall:** the per-user installer adds no firewall rule. Settings › General **Fix** elevates a delete-then-add of an inbound allow named `Mortar` for the installed executable (private and domain profiles, `netsh advfirewall`) when an inbound block rule matches it.

- **Nexus collection draft** (`sharesvc.ExportCollection`, profile menu **Export as Nexus collection draft…**): the inverse of the collection import, read-only (no Nexus write). It writes one `collection.zip` holding `collection.json` in Vortex's `ICollection` shape (source: [Vortex's `ICollection.ts`](https://github.com/Nexus-Mods/Vortex/blob/master/src/renderer/src/extensions/collections/types/ICollection.ts)), using the same Go types the importer parses, so `parseChoices` reads an export back.
  - `info`: `name`, `description` and `domainName` from the profile; `installInstructions` is the profile's notes; `modRules` is empty. Mortar cannot fill `info.author` / `authorUrl`; the curator sets them on Nexus.
  - `mods[]`: one per enabled, non-bundled entry, with the entry's note as `instructions`. Nexus entries are `source.type: "nexus"` with `modId`, `fileId`, `updatePolicy: "exact"` and `logicalFilename`; `md5`, `fileSize` (Nexus's KB times 1024, so approximate) and `optional` (file category OPTIONAL) come from the mod's file list, and are left out when signed out or the file is gone. FOMOD choices recorded at install become `choices` (`type: "fomod"`, steps, groups, plugin names; `idx` is the plugin's position in the group).
  - Not Nexus: a GitHub asset is a `direct` source with its release URL; a local archive is a `manual` source whose instructions ask the curator to host it. These are the collection's external resources.
  - Bundled configs: each enabled mod's `.json` files (all of them, since Mortar does not know which the user changed) go in the zip under `bundled/<local id>/`, with the mod's `manifest.json` that names it to the importer. Nexus takes the collection as a 7z of `collection.json` plus `bundled/`; Vortex packs it with node-7z and no 7z-writing Go library is in go.mod (`bodgit/sevenzip` is read-only), so the export is a zip and the toast gives the curator a one-line repack to 7z.

## Sync folder

`internal/syncsvc` keeps each profile's state in step between computers through a folder that another tool (Syncthing, Dropbox, a NAS) carries. It carries the profile's `.mortar` export (entries, sources and configs, never mod files, so every computer downloads each mod from its source). The folder is the `syncFolder` setting (Settings › Mods and profiles; empty is off), and `main.go` runs the service with a five-second quiet period.

- **Layout:** `<folder>/<game>/<remote id>.mortar` is the payload and `<remote id>.sync.json` the version file `{name, machine, machineName, vector}`. The vector maps a machine id to the newest revision that machine wrote. The payload is written first and the version file last, so a computer that sees a version finds the payload it names. The local state (`<data>/sync-state.json`) holds this machine's random id and, for each local profile, its remote id, the vector last written or applied and the profile's `updated` time then.
- **Scan:** at start, on every folder event (`syncsvc.FolderEvent`, from the folder watcher) and every minute, the service walks the game's profiles. A profile whose `updated` differs from the recorded one and has stayed unchanged for the quiet period is written out as the next revision on top of the vector it holds. A version file whose vector holds a revision this machine lacks becomes an **offer**; a version file no local profile is linked to becomes a `New` offer.
- **Answering:** an offer is never merged. `Resolve(game, remote, "theirs")` makes the profile match the payload through the share service's replace (creating the profile first for a `New` offer; mods it names download from their sources) and adopts the remote vector. `Resolve(game, remote, "mine")` keeps the local profile and writes it as a revision on top of both vectors. An offer for a profile changed on both sides is flagged `Conflict`, and the window offers the same two answers. `Diff` previews the mods an apply adds and removes.
- **Events:** the list of offers is emitted as `sync:offers` only when it changes.

  - `Exec=` is `$APPIMAGE` when Mortar runs from that AppImage's mount (`$APPDIR`), since desktop files do not expand variables and the mount vanishes on exit; a production build rewrites the entry at startup when its `Exec` target no longer exists, as when the user moves the AppImage, and writes it when it is missing; every non-packaged start refreshes the user icons once an entry exists (`Refresh` in `internal/nxm/handler_linux.go`).
  - The Flatpak uses GNOME Platform/SDK 50.
