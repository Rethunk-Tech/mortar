# Mortar architecture

How Mortar works: storage, profile semantics, trust boundaries, and the Stardew and Nexus facts that settle questions so they are not re-litigated. Decided work not yet built is in [design.md](design.md), screens in [gui-design.md](gui-design.md), standing rules in [AGENTS.md](../AGENTS.md).

## Product

Mortar finds a game, installs its mod loader, keeps each set of mods in its own profile, and launches the game with the chosen profile.

External profile import is available for Stardrop and Vortex when their default data is present:

- **Stardrop:** profiles from the platform application-data `Stardrop/Data/Profiles` folder; `EnabledModIds` match manifests in the configured game `Mods` folder. A profile that keeps configs per profile (`PreservedModConfigs`) writes its own copy over the folder's, or onto a downloaded mod once it installs, under the same caps as a `.mortar` file's configs; oversize ones are listed in the import preview.
- **Vortex:** profiles from its `state.v2` persistent JSON; each profile's `modState` is matched to the extracted staging folder. Configs live only in that staging folder.
- Present folders are copied into Mortar's store (each keeps its `config.json`); missing Nexus mods enter the same share-import resolver and download queue. Enabled UniqueIDs with no matching folder on disk are listed in the import preview as **Not found in the Mods folder**.

- **What matters:** Mortar working for personal use with a personal Nexus API key. Registering the app with Nexus is not a v1 goal.
- **Licence:** AGPL-3.0: the same as GPL-3.0 for the desktop app, and it covers a hosted share service.
- **Scope of the first release:** Stardew Valley only, on Windows and Linux, from Steam (including Flatpak Steam on Linux), GOG Galaxy / the GOG offline installer, Heroic's GOG library on Linux, and Lutris on Linux. macOS is out (fleet CI has no macOS runners, and Wails does not cross-compile to it).

## Stack

- **Wails v3**, upgraded one beta at a time on purpose; the pin and its Go floor are in `go.mod`. Betas are small fixes; there is no date for a stable v3.0.
- **Frontend:** React, TypeScript and MUI on Vite, from Wails' `react` template. Typed bindings from `wails3 generate bindings` into `frontend/bindings`. Client state in zustand. Lingui 6 for every string; English only.
- **Go services:** each backend area the UI calls is one Wails service (`application.NewService`), so its exported methods are bound to TypeScript.
- **Solid window:** `BackgroundTypeSolid` (`main.go`); the base, tint and surfaces are in [gui-design.md](gui-design.md#surfaces-and-colour). The wallpaper endpoint is `/background`; it honours `?mode=` (`image`, `desktop` or `solid`) and answers `Cache-Control: no-store`.
- **Frameless, with a themed title bar:** `Frameless: true`, and the app draws its own title bar marked `--wails-draggable: drag`. Measured on GNOME and on KDE Plasma 6.6 (Wayland, Fedora 44): drag, edge and corner resizing, the 768x432 minimum, double-click maximise and the window buttons work; neither compositor draws a drop shadow, so the app draws a 1px border and rounded corners. Trap: dragging works only once the Wails runtime is loaded (`@wailsio/runtime`, or `/wails/runtime.js`).
- **Credits:** Settings › About lists bundled licences from `frontend/src/settings/generated/credits.json`, which `scripts/gen-credits.ts` writes at every frontend build from `frontend/package.json`'s runtime dependencies and `go.mod`'s direct requires (licence read from each package's own metadata), plus Mortar (AGPL-3.0 from the repo `LICENSE`), the SMAPI Bridge, SMAPI and the default wallpaper.
- **Session-only state:** the notification history (the last 200 toasts, newest first) and the Console's command history live in memory and are written nowhere; a toast's Undo, Redo, Show or Retry in the history works only while that change is still the latest for the same mods.
- **Packages worth knowing:** `internal/game` holds the `Game` interface and `internal/game/stardew` its only implementation; `internal/archive` extracts zip, RAR and 7z.

## Storage

Everything lives in the user data folder, `%LOCALAPPDATA%\Mortar` or `$XDG_DATA_HOME/mortar`, never under the Windows install folder (the uninstaller deletes that one recursively). Settings › Data can **Move data folder…** to a chosen empty folder with enough free space, not inside the current folder and not while the game is running: Mortar copies everything, verifies the copy, writes `data-location` in the default folder so the next start finds it, removes the old copy, and restarts. WebView2's user data is `webview/` in that folder (`Options.Windows.WebviewUserDataPath`). Mortar's own state is JSON, each file written through a temp file and rename; no database. The Nexus key is in the OS keyring. The uninstaller also deletes `%APPDATA%\mortar.exe` if that leftover WebView2 path exists.

- `settings.json`: Mortar's preferences and small pieces of state, field by field under [Settings file](#settings-file).
- `store/<game>/<key>/`: each downloaded archive, extracted once. A `.complete` file marks a finished extract; startup and each use re-extract from a sibling `<key>.zip` / `.rar` / `.7z` when that marker is missing and the archive is still there, otherwise the item is incomplete and an install reports it instead of copying a half-extracted folder. A `mortar-root` file in that folder, when present, names the relative subfolder that is the mod (reused for the same Nexus file id; Mortar asks again if that path is gone). Keys: `nexus-<mod id>-<file id>`, `github-<owner>-<repo>-<tag>-<asset>-<sha256 prefix>` (the hash of the exact names tells apart names the folding makes equal), `local-<sha256 of the archive>`, `smapi-<version>` for SMAPI's bundled mods, and `bridge-<version>-<sha256 prefix>` for the Mortar SMAPI Bridge. One Nexus file can hold several SMAPI mods, so the key is the file.
- `store/index.json`: each store item's last use, meaning the last time any `profile.json` named it.
- `profiles/<game>/<profile id>/`:
  - `profile.json`, and beside it `mods/`, the folder SMAPI is pointed at.
  - Each entry is copied to `mods/<store key>/` as extracted, or only the `mortar-root` subtree when one is set.
  - Further files from the same Nexus page can join that entry (`extraStoreKeys`), each copied to `mods/<entry key>/<extra store key>/`. Update, Roll back and Remove cover every store item on the entry.
  - Extract drops `__MACOSX`, `.git`, and folders that hold only `Thumbs.db`.
  - When no `manifest.json` remains that SMAPI would find, Mortar shows the extracted tree and the user picks the folder that is the mod (it must contain a reachable `manifest.json`) or cancels. The same picker lists the variant folders when the archive holds one UniqueID more than once (each widened to its highest folder with a single copy, labelled by path, with version and description when they differ). An update reuses the variant folder of the same name from the entry it replaces and asks again when none matches.
  - FOMOD detection runs first. If the store item has a FOMOD installer (`fomod/ModuleConfig.xml`, case-insensitive, at the item root or one folder down, UTF-8 or UTF-16), Mortar shows the installer steps, copies the resolved files instead of the raw extraction, and stores the chosen plugin names on the entry as `fomod` (step → group → names). Update and Roll back replay those choices (`internal/profile/fomod.go` `replayAsk` / `installAsk`). Mortar asks again when a saved choice no longer exists in the new config, or when the update adds a group the saved choices do not answer (`internal/fomod/resolve.go` `Unanswered`). The wizard is prefilled with the saved picks that still name a plugin in the new config (`Keep`).
  - SMAPI recurses until it finds a `manifest.json`.
  - Beside them `runs/` keeps the last 20 launches Mortar started for that profile:
  - `index.json` (per run: id, start and end, duration, SMAPI and game versions, outcome `ran`, `failed` or `crashed`, error and warning counts, and an optional cause naming the mod, short reason, plain-language detail and path)
  - one `<id>.txt` copy of the run's SMAPI log each, capped at the console's 20,000 lines of 256 bytes, written temp then rename
  - a run is stored when the game goes idle or the launch fails; a launch without mods stores none
- `trash/`: deleted profiles, kept 30 days; **Delete permanently** and **Empty trash** remove them at once ([Profile operations](#profile-operations)).
- `backups/`: zips of the Saves folder taken before updates, as many kept as Settings › Updates says (`backupsKept` in `settings.json`, 1 to 50, default 5); one under ten minutes old stands in for a new one when the Saves folder has not changed since. A new zip may have a sibling `<stamp>.json` recording why it was made, `{profile, kind}` with kind `update` (before a mod update, naming the profile) or `restore` (before a restore); older zips have none and show as unknown.
- `cache/`: API responses, mod pictures, the dataset index, and Content Patcher scan results.
- `queue.json`: the download queue's state, without `nxm://` keys.
- `downloads/<item id>.<ext>`: a download in progress, with `<name>.resume.json` beside it (expected size, `ETag`, source URL and the checksum when the server sent one). A failed or interrupted fetch keeps both; Cancel and Skip delete them.
- `download-history.json`: every finished queue item, the last 1,000, newest last, written temp then rename.
- `nexus-seen.json`: per Nexus mod id, what the user last looked at (`newestFileUnix`, `newestChange`, `lastLookedUnix`), capped at 2,000 mods with the least recently looked dropped first.
- `categories/<game>.json`: custom mod categories for that game (`id`, `name`, optional `color` from the profile palette). A deleted category clears that override on every profile entry.
- `tools/<game>.json`: external programs for that game (`internal/tools`), each with `id`, `name`, `executable`, `arguments` (a JSON array, never a shell string) and `workingDir`. Placeholders `{game}`, `{mods}`, `{saves}` and `{profile}` expand in arguments and the working directory when a tool is launched for a profile; an empty working directory uses the game install folder. The executable must exist and be a regular file on save. Launch uses `os/exec` without a shell, detached, with one info log line.
- `bundles/<game>.json`: named sets of mods for that game (`internal/bundles`). Each bundle has `id` (16 lowercase hex characters), `name` (at most 60 characters) and `mods[]` (`uniqueId`, `name`, `entryKey`, `source`). Applying a bundle copies those store entries into a profile through `AddEntry`; UniqueIDs the store does not hold are listed as missing and are not downloaded.
- `endorse-prompts.json`: per Nexus mod id, progress toward an endorse prompt (`clean`, `asked`, `never`, optional `askedAt` and `lastRun`). After five completed runs with no errors from that enabled Nexus mod, Mortar may prompt when `askEndorseMods` is on ([gui-design.md](gui-design.md#mods-tab)).

`profile.json` fields:

| Field | Meaning |
| --- | --- |
| `id`, `name`, `notes` | Identity and free-text notes |
| `cover` | `cover.png`, `cover.jpg` or `cover.webp` beside the file, or empty |
| `order`, `hidden`, `created`, `updated` | Sidebar order, hide flag, timestamps |
| `origin` | Optional: `link`, `mortar`, `game-mods`, or `copy` |
| `copyOf` | Source profile name when `origin` is `copy` |
| `color` | Optional: `rose`, `orange`, `gold`, `lime`, `teal`, `sky`, `violet` or `pink` |
| `icon` | Optional: `sprout`, `leaf`, `wheat`, `fish`, `hammer`, `pickaxe`, `star`, `heart`, `mountain`, `sun`, `moon` or `sparkles` |
| `description` | At most 280 characters |
| `launchOptions` | Extra SMAPI arguments as typed |
| `launchPrefix` | Shell-quoted command prefix for direct launches (Linux; ignored on Windows and on Steam `-applaunch`) |
| `launchEnv` | One `NAME=value` environment variable per line for direct launches (ignored on Steam `-applaunch`) |
| `updateBeforePlay` | When true, Play applies offered updates (not pinned) before starting the game and keeps a history restore point to roll back if that pass fails ([Launch](#launch)) |
| `entries[]` | Installed archives in this profile |

Invalid `color`, `icon` or `description` values are dropped on load.

Each `entries[]` item:

| Field | Meaning |
| --- | --- |
| `key` | Store item in use |
| `previousKey`, `previousSource` | Rollback copy, or empty; source of that copy is restored on roll back |
| source | Reference used in share links |
| mods | Each: `UniqueID`, version, folder holding `manifest.json`, `needs` (required UniqueIDs), `optional` (those with `IsRequired` false; `ContentPackFor` stays required) |
| `extraStoreKeys`, `previousExtraStoreKeys` | Further files from the same Nexus page, copied under `mods/<entry key>/<extra store key>/`; the previous list is restored on roll back |
| `disabled` | UniqueIDs switched off |
| `added` | When the entry was put in the profile (zero when absent) |
| `pinned` | Keeps the entry on its version |
| `skipVersion` | One newer version hidden |
| `note` | At most 500 characters |
| `tags` | At most 8, each at most 24 characters |
| `categoryOverride` | Primary category: a custom category id or a Nexus category name |
| `fomod` | Optional FOMOD plugin names for that entry; Update and Roll back replay them, ask again on a missing choice or a new unanswered group, and prefill surviving picks |

The store keeps every item a profile names as `key` or `previousKey` and deletes the rest 30 days after their last use. `ProfilesWithMod` lists, for a game and UniqueID, the profiles that name it, by reading those `profile.json` files (not the store); UniqueIDs compare case-insensitively.

**Hero cover** (`internal/profile/cover.go`): Choose cover image… copies the picked file into the profile folder (PNG, JPEG or WebP from content, at most 16 MB; the original path is never kept). Duplicate copies it with the profile. `Covers` tries, in order:

1. The picked cover, served by `CoverMiddleware` at `/profile-cover/<game>/<id>` (validated game and id; only the three fixed file names).
2. The `picture` of the profile's Nexus entry with the highest `endorsementCount` as stored at install (no new call).
3. Steam's art at `/steam-art/<appid>`.

The frontend moves on when one fails to load and shows a solid tone after the last.

## Settings file

`settings.json` is one JSON file. A missing or unparseable file gives the defaults. A value that breaks its rule is replaced by the default when the file loads and refused with an error when written. Defaults in brackets.

- `language` (empty): interface locale. Empty follows the OS language when Mortar has a catalog for it, else English. The only catalog is `en`; any other non-empty value is dropped on load and refused on write.
- `accent` (`sand`): `sand`, `moss`, `copper` or `sky`.
- `background` (`image`): `image`, `desktop` or `solid`.
- `backgroundImage` (empty, the default wallpaper): the absolute path of the user's image; set only when it is a readable PNG, JPEG or WebP file, and empty clears it.
- `lastGame` (empty): the game last opened; any id.
- `lastProfile` (`{}`): game id to the id of the profile last open in it.
- `lastPlayed` (`{}`): game id to `{profile, at, gameVersion}`. `at` is RFC3339 and recorded when a launch reaches Running; `gameVersion` is Stardew's version from that launch's SMAPI log header, and the previous value stays when the log showed none. An entry with an empty game, profile or time, or a time that does not parse, is dropped.
- `gameFolders` (`{}`): game id to an install folder the user chose, which wins over store discovery; checked as a game install when set, and emptied to go back to discovery.
- `gameStores` (`{}`): game id to the store to use when several installs are found (`steam`, `flatpak-steam`, `gog`, `gog-heroic`, `lutris`); an unknown value is dropped on load.
- `loaders` (`{}`): game id to the loader version Mortar installed.
- `dismissed` (`{}`): profile dismissal bucket to tokens for hidden warnings. Problems keeps dismissed conflicts, abandoned mods, listed requirements and settings available in its Dismissed section; restoring removes the token.
- `nexusUserId` (0), `nexusName` (empty), `nexusPremium` (false): the signed-in account, for display; a zero id means signed out.
- `nxmHandled` (false), `nxmPrevious` (empty), `nxmAsked` (false): whether Mortar handles `nxm://` links, the handler it replaced, and whether the user was asked.
- `nxmPreviousName` (empty): display name of that previous handler.
- `nxmRedirectOtherGames` (on when `nxmPrevious` is set, else off): send non-Stardew `nxm://` links to the previous handler.
- `nexusPreferredDownloadServer` (empty): a seen `download_link.json` `short_name`, or empty for Automatic.
- `askEndorseMods` (true): when on, Mortar may prompt to endorse Nexus mods after five clean runs. Missing or null means true.
- `nexusSeenDownloadServers` (`[]`): `short_name` values Mortar has seen.
- `backupsKept` (5): 1 to 50.
- `listColumns` (`on`, `name`, `version`, `author`, `source`, `category`, `status`): the Mods list columns shown, from `on`, `name`, `version`, `latest`, `uniqueId`, `author`, `source`, `category`, `endorsements`, `downloads`, `updated`, `installed`, `needs`, `status`, `notes`, `lastRun`. An unknown id is refused on write and dropped on load, as are duplicates; `on` and `name` are always present and first; none left gives the default.
- `listSortColumn` (`name`), `listSortDir` (`asc`): any column id but `on` (which becomes `name`), and `asc` or `desc`; an unknown value is refused on write and becomes the default on load.
- `listGroupBy` (`status`): `none`, `status`, `category`, `source`, `tag`, `framework` or `author`.
- `checkModUpdatesOnStart` (true): check for mod updates at startup and in the background while Mortar runs ([Profile operations](#profile-operations)). Missing or null means true.
- `tellWhenSmapiOut` (true): toast when a newer SMAPI exists, at most once a day. Missing or null means true.
- `keepInTray` (false): when on, closing the window closes it while Mortar keeps running behind a system-tray icon, and showing Mortar builds a new window (Wayland lets no app restore a hidden window's position, so a fresh window is placed by the compositor as new); when off, close quits. Quitting on the last window is turned off in the Wails options for Linux and Windows so this choice stays Mortar's.
- `lanSharing` (false): when on, Mortar advertises itself on the local network and accepts profile sends ([Sharing](#sharing)).
- `lanPort` (47630): TCP port for that HTTP service; 0 lets the OS choose. Out of 0–65535 is refused on write and becomes 47630 on load.
- `lanAddresses` (`[]`): the last five successful LAN send targets (`host:port`), newest first.
- `includeBetaReleases` (false): when on, Mortar's self-update check also offers signed manifests from GitHub prereleases; when off, only the latest stable release manifest is used.
- `includePrereleaseModVersions` (false): when off, an offered mod update whose version has a semver prerelease tag is hidden unless the installed version is itself a prerelease.
- `checkOnlyEnabledMods` (false): when on, disabled mods are omitted from the request sent to SMAPI's update API.
- `enableModsWhenInstalled` (true): when off, newly installed profile entries start with every mod in that entry switched off. Missing or null means true.
- `smapiToastAt` (empty): RFC3339 time of the last SMAPI-update toast; a later toast is suppressed for 24 hours after it. Written only when the toast shows.
- `tipsSeen` (empty): the empty-state tips dismissed, from `mods`, `saves`, `console` and `share`; an unknown id is refused on write and dropped on load, as are duplicates.
- `overlayEnabled` (false), `overlayPort` (8123), `overlayToken` (empty): the Mortar SMAPI Bridge stream overlay. Port is 1024–65535; an out-of-range value is refused on write and becomes 8123 on load. The token is 32 random bytes as hex, created on first enable and on Regenerate. It is a secret: it is never logged, never exported, and stripped from diagnostics.
- `onPlay` (`stay`): `stay`, `minimise`, or `hide` when a game launches; the window is restored when the game exits.
- `backupBeforePlay` (`changed`): `changed` (mods or game version since last run), `always`, or `never`. `launchBackupsKept` (5) is how many launch save zips to keep (1–50).
- `updateModsBeforePlayDefault` (false): `UpdateBeforePlay` on a newly created profile.
- `runsKept` (20): stored SMAPI run logs per profile (1–100). `consoleLogCap` (20000): newest console lines in memory (1000–100000).
- `parallelDownloads` (3): Premium/GitHub fetch pool (1–8). Free Nexus stays one at a time.
- `updateCheckIntervalMinutes` (60): background mod-update interval (15–1440). `checkModUpdatesOnStart` still gates the startup check. `notifyModUpdates` (false): toast when a check finds updates.
- `keepDownloadArchives` (false): keep the zip after install. `storeRetentionDays` (30): unused store items; 0 keeps them forever.
- `nxmDefaultProfile` (empty): profile id for `nxm://` links; empty uses the last-opened profile.
- `defaultModsView` (`grid`): `grid` or `list`.
- `confirmRemovals` (true): ask before removing mods.
- `cosmeticConflicts` (`collapsed`): `collapsed`, `expanded`, or `hidden` on Problems.
- `backgroundBadgeChecks` (true): fill sidebar badges for other profiles.
- `startScreen` (`last`): `last` opens the last profile; `gameselect` opens Game Select.
- `dates` (`relative`): `relative` or `absolute`.
- `trashRetentionDays` (30): days a deleted profile stays restorable (1–365). `historyEventsKept` (200): history events per profile (20–2000).
- `notifyDownloadFinished` (true), `notifyDownloadFailed` (true), `notifyRunCrashed` (true): per-kind notices.
- `density` (`comfortable`): `comfortable` or `compact`. `gridCardSize` (`medium`): `small`, `medium`, or `large`. `showAuthorOnCards` (true): author line on grid cards.
- `reduceMotion` (`system`): `system`, `always`, or `never`. `profileHero` (`full`): `full`, `compact`, or `hidden`.
- `enableRequirements` (`always`): `always`, `ask`, or `never` when switching a mod on (`ask` does not auto-enable; there is no confirm dialog). `missingRequirements` (`ask`): `ask`, `autodownload`, or `never` after install.
- `reuseFomodChoices` (true): skip the FOMOD wizard when saved choices still match. `driftChecks` (true): scan for mods changed outside Mortar.
- `smapiBuilds` (`show`): `never`, `show`, or `include` unofficial/pre-release SMAPI builds. Mortar's own channel stays `includeBetaReleases`. `autoInstallMortarUpdates` (true): stage a found Mortar update without asking.
- `autoTrackNexus` (false): track a Nexus mod after install. `defaultLaunchMethod` (`steam`): `steam` or `direct`. `showSmapiConsole` (true): SMAPI's console window on a direct launch.
- `consoleLevel` (`info`): floor for new Console sessions (`trace`–`error`). `consoleTimestamps` (true), `consoleFollow` (true). Line cap is `consoleLogCap`.
- `lanName` (empty): advertised LAN device name; empty uses the host name. `lanAutoAcceptSameAccount` (false): auto-accept LAN shares from the same Nexus account.
- `downloadFolder` (empty): archive landing folder; empty is `<datadir>/downloads`.
- `shortcuts` (the Settings › Shortcuts table): action id to a chord (`Ctrl+K`, `Ctrl+Shift+F`, …). Missing ids take the defaults; an unknown id is refused on write and dropped on load; a chord used by two actions is refused on write.

**Export and import:** Settings › Data writes every portable preference: `language`, `accent`, `background`, `lastGame`, `backupsKept`, the four `list*` fields, the mod-update toggles (`checkModUpdatesOnStart`, `tellWhenSmapiOut`, `includePrereleaseModVersions`, `checkOnlyEnabledMods`, `enableModsWhenInstalled`), `keepInTray`, `includeBetaReleases`, `tipsSeen`, `nexusPreferredDownloadServer`, `nxmRedirectOtherGames`, and the CLI-visible prefs (`onPlay` through `downloadFolder`, including density, requirements, drift, launch, console, LAN name, and download folder) as `{"version": 1, ...}` through the native save dialog. Import reads such a file, refuses any other version, ignores unknown fields, sanitises each present value as a load does, and applies it only after a preview of what would change. Account and machine fields (`nexusUserId`, `nexusName`, `nexusPremium`, `nexusSeenDownloadServers`, `gameFolders`, `gameStores`, `loaders`, `lastProfile`, `lastPlayed`, `backgroundImage`, `dismissed`, `nxmHandled`, `nxmPrevious`, `nxmPreviousName`, `nxmAsked`, `lanSharing`, `lanPort`, `lanAddresses`) and `overlayToken` (with overlay enabled/port) are never exported, and the keyring is never read.

**Disk use and clean-up:** Settings › Data walks the data folder in the background without following symlinks and reports each live profile's `mods/` folder, then the store, cache, save backups, trash and the total. Cache size is that of `<datadir>/cache` (via the data-dir helpers). **Clear** empties that folder after confirm; problem scans rebuild it on the next check (`mortar cache size` / `mortar cache clear`). **Disk use by mod** lists each store item's size, live profiles that name it, the size of those profile copies, and last use from the store index, computed in Go and cached until the store or profiles change (`mortar data usage --by-mod`). **Remove** deletes one unused store item and is refused while any keep-set key still names it. **Clean up unused** previews, then deletes exactly the listed items: store items no live or trash profile, `previousKey`, history snapshot key or staged queue item names (the keep set the 30-day sweep uses, here without its 30-day grace), cache files older than their fetch lifetime (mod page details, categories, the dataset, SMAPI's update answers, GitHub releases), and leftover temp folders. A store key a profile names after the preview is re-checked and kept. Mod pictures have no lifetime and are counted but never cleaned. The Mods list **Size** column uses the same per-entry store sizes.

## Profile operations

**Copies, which the filesystem clones where it can.** Each profile gets its own copy of every entry.

- **btrfs:** Go's `io.Copy` between files uses `copy_file_range`, which btrfs turns into a reflink.
- **NTFS and ext4:** an ordinary copy.
- **Links are out:** SMAPI's `helper.Data.WriteJsonFile` writes any path inside the mod's folder (SMAPI's `DataHelper` in the Pathoschild/SMAPI repository) with `File.WriteAllText` (SMAPI's `JsonHelper` in the Pathoschild/SMAPI repository), which rewrites the file in place, so a hard link would leak one profile's data into the store and every other profile. SMAPI does load linked folders (measured).

**Operations:**

- **Toggle** a mod: rename the folder holding its `manifest.json` with a leading dot, which SMAPI skips (measured), and record it in `disabled`.
  - Enabling a mod whose required dependencies are already in the profile but switched off enables those in the same write; the toast says "Also enabled X". Optional dependencies are left alone.
  - When the manifest sits at the archive's root, that folder is the entry's own `mods/<store key>/`, so the entry is found by its key with or without the dot. Programs can create leading-dot names on NTFS.
- **Enable, disable and remove several at once:** one write to `profile.json` per action, under the same running-game lock.
- **Duplicate:** copy the profile's `mods/` folder as it is, mod-written data included, under a new id, and record origin `copy` with `copyOf` the source profile's name.
- **Delete:** move the profile folder to `trash/`, restorable for `trashRetentionDays` (default 30). **Delete permanently** (`Purge`) removes one trashed profile; **Empty trash** (`PurgeTrash` with the game id) removes every trashed profile for that game. Both refuse a symlink. Startup still deletes trash older than that retention.
- **Damaged:** `List` still returns a row `{id, error}` when `profile.json` cannot be read. Callers skip those rows; `ListDamaged` is what the Profiles page and `mortar profiles` use to show them. `StoreKeys` skips a damaged live profile so one corrupt file does not stop collection.
- **Import from the game's Mods folder:** scan one level of `<game>/Mods` the way SMAPI and archive install do (a folder with `manifest.json`, or a folder of those folders).
  - SMAPI's bundled Console Commands and Save Backup and Mortar's bridge are left out of the preview and are not counted as skipped.
  - When two folders hold the same `UniqueID`, import one: the enabled copy if either is enabled, otherwise the newest version; the other is skipped with the reason `same mod as <folder>`.
  - Copy each remaining folder into the store with the same hashed-folder install path as a dropped folder (dedup by content, manifest identity, `UpdateKeys` as Nexus or GitHub source).
  - Dot-prefixed folders land switched off and the preview marks them "(switched off)". Skipped and failed folders show in the preview with their reason.
  - Each `config.json` is copied into the profile. The game folder is not written. The new profile is named "Imported mods" (or "Imported mods (2)", …) and records origin `game-mods`.
- **Outside edits:** beside `profile.json` Mortar keeps `mods-snapshot.json`, a cheap fingerprint of each entry folder (top-level name, file count, total size, newest mtime, skipping `config.json`, `*.mortar-old`, and other files the update carry-over treats as user- or mod-written). On profile load and when the window regains focus (debounced) it compares the live `mods/` tree to that snapshot and to `profile.json`.
  - An unknown folder can be Adopted (the same hashed-folder install as Import from the game's Mods folder) or Removed (moved to `trash/`).
  - A deleted entry can be Restored from the store or Forgotten.
  - Changed shipped files can be kept (refresh the snapshot) or Reverted (recopy from the store, carrying over config as an update does).
  - Findings show on the Problems bar. A first scan with no snapshot records the current tree and reports nothing.
- **Compare:** `Diff` matches user mods of two profiles of the same game by UniqueID (bundled SMAPI and bridge entries omitted) and lists those only in A, only in B, and in both with a different version or enabled state. `CopyMods` copies selected UniqueIDs from one profile into the other through `AddEntry` (the store item already on disk; no download) and matches the source enabled state; a running game locks the destination as other mods-folder writes do. Copy works in both directions. The compare window filters those lists by name or UniqueID and **Copy all to \<profile\>** copies every visible row in a section ([gui-design.md](gui-design.md#profile-management)).
- **Match a friend's profile:** Import opened against an existing profile previews a share link or `.mortar` file beside that profile: already matching, missing (to download), different version, and UniqueIDs only in the local profile (Replace would remove those; Add keeps them).
- **Bundles:** a named set of UniqueIDs saved per game under `bundles/<game>.json`. Creating one snapshots the chosen mods' store keys and sources; applying it copies those store items into a profile. Mods Mortar does not hold stay listed as missing.
- **Also in other profiles:** `CopyMods` and `RemoveEntry` run the same UniqueIDs against other profiles of the game the user ticks. After an update finishes in the open profile, Mortar offers **Update \<mod\> in other profiles** for those that still hold the old store key (pinned destinations are named and skipped).
- **Export and restore a zip:**
  - Export snapshots `profile.json` (notes and appearance included), the cover, and each non-bundled entry's files as they are in the profile, enabled or switched off, configs included, under the store lock, then zips that tree with `mortar-export.json` (Mortar's version and a SHA-256 per file). `runs/` and `history.json` stay out of the zip.
  - Restore extracts with the archive caps, checks every hash, refuses paths that leave the zip, ignores an absolute `cover` path, and makes a new profile named with `UniqueName`, never overwriting one. Each entry goes into the store by content hash; pins, skipped versions, notes, tags, launch options, cover and hidden state come back.
  - Bundled SMAPI and bridge entries are not packed, and rollback copies (`previousKey`) are not either.
- **Edit `config.json`:** the mod dialog's Edit reads and writes only that file, after joining it onto the mod's folder in the profile (a path that leaves the folder is refused). Write parses the JSON, keeps key order, types and unknown fields, goes through a temp file and rename, and fails with the running error while the game is launching or running the profile.
- **Pin and skip:** while an entry is `pinned` no update is offered for it; `skipVersion` hides that exact newer version until a later one appears. Both are written with the profile and dropped from the per-profile update count, Update review and Update all.
- **When mod updates are checked:** at Mortar startup (when `checkModUpdatesOnStart` is on), when the user presses F5 on the Mods tab, and at most once an hour for the open profile while Mortar runs; SMAPI's API answers are cached for an hour per profile fingerprint. The same toggle also starts a background pass 5 minutes after Mortar opens, then every 4 hours: every installed game's profiles, skipping a game or profile that fails. When a profile's update count is higher than last notified this session, a desktop notification **"Mod updates available"** names the profile with the largest such increase (`N mod updates available for <name>`).
- **Change history:** `internal/profile/history.go` appends a bounded log in the profile folder of mods added, removed, updated, rolled back, or switched on or off. Revert restores an earlier snapshot. A revert that needs store items Mortar no longer holds names those mods and the window offers to download them. A successful revert toasts Undo, which reverts to the snapshot that was current before. Replacing a profile from a share records the removals in that log. Export zip leaves `history.json` and `runs/` out. `RecentHistory` (and `mortar history --all`) merges those events from every non-hidden, non-damaged profile of the game, newest first, capped at 50.
- **Update or roll back** an entry: copy the target version from the store into a fresh folder, then carry over what the mod or the user wrote, by comparing three copies of each file: the profile's, the store's copy of the current version, and the target version.
  - A file only the profile's copy has (such as `config.json` or mod data) is carried over.
  - A file the profile changed is carried over when the target version ships it unchanged from the current version. When the target version changed it too, the target's file wins and the profile's copy is kept beside it as `<name>.mortar-old`.
  - When the target version's manifest sets `DeleteOldVersion` (Stardrop's name, read case-insensitively like other manifest keys), carry-over applies only to user-written files such as `config.json`, not to other files the profile changed from the old version.
  - Keep the leading dot on disabled folders; then swap `key` and `previousKey` and remove the old folder.
  - Before updating a profile, zip the Saves folder into `backups/`.

## Command line

Mortar is GUI-first: the command line exposes only what the window can already do, and a new capability lands in the window first. Verbs: [HUMANS.md](../HUMANS.md#command-line). `mortar <verb>` (`internal/cli`) is decided in `main` before `application.New`, so it never takes the single-instance lock or opens a window; any other first argument, a link, a file path, or `--play=<game>/<profile>`, is a window launch. `--play` ids may not contain `/`, `\`, space or quotes; a running instance receives it as a second instance (`play:requested`) and Play follows the usual path, warnings included. The CLI is a client of the running app: at startup the app (`internal/control`) listens on `127.0.0.1` with an OS-chosen port and writes `control.json` (`port`, a random 32-byte `token`, `pid`, `version`; mode 0600) in the data folder, removed on exit. Each connection carries one JSON request line (`token`, `method`, `params`) and gets one reply line (`result` or `error`); the token is compared in constant time. Methods run on the app's own services, so the window and the CLI never write the data folder at once, and a change emits `profiles:changed` with the game id, which reloads that game's profiles in the window. `launch` detaches the game from the request (`context.WithoutCancel`). `open` runs the binary again with the link, which a running window takes over the usual second-instance path. On Windows the GUI-subsystem exe attaches to its parent console (`AttachConsole`) unless its output is redirected.

## Trust boundaries

Everything from outside is untrusted: links, `.mortar` files, archives, API responses. Share links and `.mortar` files have their own caps and rules in [Sharing](#sharing).

- Extraction keeps every entry inside its destination; caps each entry at 256 MiB, decoder dictionaries and PPMd memory at 256 MiB, the archive at 2 GiB extracted and 20,000 entries; rejects symlink entries, Windows reserved names (`CON`, `NUL`, ...), `:` in names, and names that differ only by case.
- An `nxm://` link is taken only in the exact form `nxm://stardewvalley/mods/<mod id>/files/<file id>?key=<key>&expires=<unix>&user_id=<id>`, unexpired, and for the signed-in account's `user_id`; anything else is refused with the reason. A link Mortar was not waiting for asks which profile it is for before anything downloads.

## Failure behaviour

Once mods are installed, nothing external is needed to open, edit or launch a profile.

- **SMAPI's API or the dataset unreachable:** the feature degrades and never blocks; update checks show "unknown", dependencies are checked after download.
- **A download cut off or corrupt:** extraction goes to a temp folder on the store's volume and moves into the store only when every entry passed its checksum (CRC32 in zip, RAR and 7z); failure deletes the temp folder and the item can be retried. **Disk full** fails the same way and says how much space the item needs.
- **Mortar quits mid-operation:** every write is temp-then-rename, and startup removes leftover temp folders. A `mods/` folder deleted outside Mortar is rebuilt from the store from `profile.json`.
- **Steam not running:** `-applaunch` starts it. **Not installed:** a Steam copy can launch through SMAPI directly, without the overlay, after the user agrees.

## Tests

Go tests run against local HTTP test servers replaying recorded Nexus, SMAPI API and dataset responses, inside the 10 s warm / 30 s cold gate budget. Recordings are scrubbed before commit: `users/validate.json` returns the account's name and email, so fixtures carry placeholder account fields. An opt-in smoke test copies a real Stardew install to scratch space, installs SMAPI with `--no-prompt`, launches a profile, and reads `SMAPI-latest.txt` for the loaded mods. Tests must set `XDG_DATA_HOME` (or `LOCALAPPDATA` on Windows) to a directory under `os.TempDir()`; `datadir.Dir` refuses any other location while `testing.Testing()` is true (`internal/datadir`).

Profiles and mods live in Mortar's data folder under Desktop Mode; grant Flatpak Steam read access to that folder when mods are launched through Flatpak Steam.

### SMAPI

- **Install and update:** download the release installer (4.5.2, published 2026-03-22, needs Stardew 1.6.14+; 2 to 4 releases a year) and run it unattended with `--install --no-prompt --game-path "<dir>"`; running it again updates. Measured on Linux: exit 0, no prompts, launcher replaced, bundled mods added.
  - **When:** Mortar installs SMAPI by itself, without asking: in the background when a profile is created or at startup while profiles exist and SMAPI is missing or broken, as first run's second step, and before Play when a game update has replaced the launcher. Only a newer release waits for the user, since an update can break mods.
  - **Windows:** the installer is `SMAPI <version> installer/internal/windows/SMAPI.Installer.exe`, self-contained (its `runtimeconfig.json` bundles .NET 6.0.36). Mortar extracts the whole zip and runs it from the installer folder, as `install on Windows.bat` does (the batch file refuses to run from a `%TEMP%` path).
  - **New releases** come from the GitHub releases client ([GitHub releases](#github-releases)) and show as a banner; one click installs.
- **Versions:** the SMAPI version Mortar installed is kept in `settings.json`; otherwise, and for the game version, Mortar reads the first line of `SMAPI-latest.txt` (`SMAPI 4.5.2 with Stardew Valley 1.6.15 build 24356 on Unix ...`, measured).
- **Broken by a game update:** on Linux the installer renames the game's `StardewValley` to `StardewValley-original` and puts its launcher in its place, which a game update overwrites; Mortar checks at startup and before launch that `StardewValley-original` exists and `StardewValley` contains `StardewModdingAPI`, and Play reinstalls SMAPI first when it is not (the banner keeps a manual Reinstall). On Windows the launcher survives, and an incompatible SMAPI reports itself in its log, which the console surfaces with the same offer.
- **Bundled mods:** a profile's `mods/` replaces `Mods/`, so every profile gets SMAPI's Console Commands and Save Backup as a `smapi-<version>` store entry, taken from the installer Mortar downloaded for the installed version (`internal/<os>/install.dat`, a zip holding `Mods/ConsoleCommands` and `Mods/SaveBackup`, checked in 4.5.2). A SMAPI update replaces that entry in every profile.
- **Components:** `components.source.json` names each loader or companion mod by game, kind, GitHub source, release asset pattern, version policy and optional accepted game-version range. Its `games` section holds each game's identity, carried unchanged into the manifest: id, name, Steam app id, marker file, loader name, GOG product id and folder, Lutris slug and keyword, and Nexus domain and numeric id. Game implementations read it through `components.Client.Game`, which falls back per game to the bundled manifest, and `nexus.Configure` takes the Nexus values at startup; process names and launch behaviour stay in Go. `cmd/components` resolves releases, downloads the named assets and writes the signed `components.json`; the same manifest is embedded at `internal/components/components.json` for offline and first-run fallback. The Ed25519 signature uses the update key (`build/updater/public.key` is its embedded public half), and the detached signature is published beside the manifest on the fixed `components` release. The client fetches it at startup through the daily meta cache, verifies it before parsing, rejects a lower serial, and falls back to the cached or bundled manifest. Component source hosts are limited to `github.com` and `thunderstore.io`; current v1 assets are GitHub releases.
  - **Downloads:** every asset is checked against its manifest SHA-256 before extraction. The bridge is installed hidden in every profile as a `bridge-<version>-<hash>` store entry with source kind `mortar`, added at startup and profile creation, and replaced when the manifest version or hash changes. Hidden means as SMAPI's bundled mods are ([gui-design.md](gui-design.md#mods-tab)).
  - **Mortar SMAPI Bridge:** Mortar has no access to SMAPI's stdin, so a small SMAPI mod (`Rethunk-AI/mortar-smapi-bridge`, `UniqueID` `Rethunk.MortarSmapiBridge`, protocol in its README) accepts console commands on a loopback port.
  - **Channel:** the mod writes `mortar-smapi-bridge.json` (`{port, token, pid}`, user-only) in its folder; `internal/bridge` reads it from the running profile, checks the pid, and sends `<token>\n<command>\n`, so the token never leaves the user's own files. Commands run on the game's next tick and their output arrives in SMAPI's log.
  - **Stream overlay:** the settings card, OBS URL, labels switch and live preview are in [gui-design.md](gui-design.md#settings). When overlay is enabled, Mortar writes the bundled OBS page to `<data>/overlay/index.html`. At launch (and when the bundled bridge is first extracted into the store), Mortar writes the bridge mod's `config.json` (`OverlayEnabled`, `OverlayPort`, `OverlayToken`, 0600, atomic) so a change takes effect on the next Play. The overlay page polls `http://127.0.0.1:<port>/state?token=<token>`.
- **Profiles folder:** SMAPI takes `--mods-path <path>`, absolute or relative to the game folder (`smapi.md:49`). Its `SMAPI_MODS_PATH` environment variable works only when SMAPI is started directly, since `steam -applaunch` cannot pass environment variables, so Mortar does not use it. Mortar never moves or writes the game folder's own `Mods`; **Import from the game's Mods folder** reads it to copy mods into the store and a new profile.
- **Scanning:** SMAPI recurses into subfolders until it finds a `manifest.json` and skips folders whose names start with a dot. Manifests are parsed leniently. Optional `UpdateCautionMessage` and `DeleteOldVersion` (Stardrop update hints) are read with the same case-insensitive key rules. Update review shows the installed manifest's caution when the new file is not in the store yet, requires an explicit tick on that row, and **Update all** skips cautioned mods until they are ticked.

### Launch

| Copy | How Mortar starts it |
| --- | --- |
| Steam | `steam -applaunch <appid> <args>` — Steam passes the arguments after the app ID to the game, which keeps the overlay, achievements and playtime tracking |
| GOG, Heroic or Minigalaxy | SMAPI directly (the Direct path) |
| Flatpak Steam | `flatpak run com.valvesoftware.Steam -applaunch 413150 --skip-terminal -- --mods-path <dir>` |

A launch through Flatpak Steam that times out while the override is missing uses the filesystem-access hint.

- **Linux:** `steam -applaunch 413150 --skip-terminal -- --mods-path <absolute path to the profile's mods/>`.
  - SMAPI's launcher script reads its own flags only before `--` and forwards only what follows it (SMAPI's unix launcher argument loop in the Pathoschild/SMAPI repository), which is why SMAPI's docs say arguments do not work on Linux.
  - `--skip-terminal` makes the script start SMAPI with `--no-terminal`; SMAPI still writes its log file then (`docs/technical/smapi.md:46`).
  - Measured: without `--` the path is ignored; with it SMAPI loads the profile, including through NOMAD's real Steam client, where the game reached the main menu. Without `--skip-terminal` the launcher opened its console in `xterm`, unreadably small.
- **Windows:** Steam starts `Stardew Valley.exe`, not SMAPI. SMAPI's installer swaps the game's launcher only on Linux and macOS (`InteractiveInstaller.cs` `if (context.IsUnix)`), and on Windows asks for the launch option to keep achievements.
  - First run shows the line `"<game>\StardewModdingAPI.exe" %command%` to paste into Stardew's Steam launch options, with a copy button, and **Set it in Steam for me**, which writes `LaunchOptions` in the MostRecent account's `localconfig.vdf` while Steam is closed (Steam rewrites the file on exit). The write merges the user's options: an existing SMAPI `%command%` line is left as it is; otherwise SMAPI is inserted before `%command%`, or `"<dir>\StardewModdingAPI.exe" %command%` is prepended to whatever was there. The app's `LaunchOptions` key or its block under `apps` is created when missing; a file with no `apps` section is refused until the game has been launched from Steam once. **Remove SMAPI from Steam's launch options** (offered after **Reset game install** on Windows) strips that SMAPI command from the same file, leaving the user's other options.
  - Mortar reads `LaunchOptions` from `localconfig.vdf`: first run warns up front when the line is missing, and at Play the options choose the failure hint shown if the launch times out. Mortar then adds `--mods-path <path>` after the app ID.
- **Extra arguments:** a profile's `launchOptions` are split like shell words (spaces separate; single or double quotes keep spaces; a backslash escapes the next character) and appended after `--mods-path`, on Linux after the `--` too. `--mods-path`, `--no-terminal` and `--skip-terminal` are refused, since Mortar sets them. Changing them never touches `mods/`, so a running game does not block it.
- **Launch prefix and environment:** `launchPrefix` is split the same way (no shell evaluation; an unfinished quote or escape is refused) and, on Linux only, prepended to a Direct SMAPI command. `launchEnv` is one `NAME=value` per line (`[A-Za-z_][A-Za-z0-9_]*=.*`) and is passed to Direct launches on Windows and Linux. Steam `-applaunch` receives neither. Changing them never touches `mods/`.
- **Per-profile game settings:** an optional `game-settings.json` beside a profile's `profile.json` overrides the selected fields in Stardew's `startup_preferences` for that launch.
  - Mortar records the old values, applies the override before starting a profile with mods, and restores each field when the run ends only if the game still has Mortar's value; a value the game changed is kept.
  - Vanilla launches and profiles without overrides do not touch `startup_preferences`; a missing file is skipped with an info line.
- **Without mods:** Play without mods is `steam -applaunch 413150` with no arguments, or the game's own executable when Mortar starts it directly.
  - It has no profile and does not lock mods, and is refused while the game runs.
  - It counts as started when a game process is seen within the launch timeout, since there is no SMAPI log, and the Console gets a Mortar line "Started without mods". It records no `lastPlayed` and no run.
  - On Windows, when Steam's launch options hold the SMAPI `%command%` line, Steam still starts SMAPI, so Mortar warns first and never edits that file. If that check fails, Mortar does not start the game.
- **After a game update:** before Play the game version the installed SMAPI reports (as Game Select does) is compared with `lastPlayed.gameVersion`. When they differ, the profile's mods SMAPI's API marks broken for the new version are listed, and Play anyway, Open problems or Cancel follow. A first launch, with nothing recorded, does not warn.
- **Newest save:** after that check, Play asks `LastSaveGap`: the most recently written save, when it still uses mods the profile lacks or has switched off (dismissed UniqueIDs excluded as on the Saves tab). An unreadable save never blocks. **Play anyway**, **Open saves** or Cancel follow ([gui-design.md](gui-design.md#main-screen)).
- **Update mods before Play:** when the profile's `updateBeforePlay` is true, Play queues every offered, non-pinned, installable update first, waits for those queue items to finish or need a click, then starts the game. A history restore point is recorded before that pass; a failed update rolls those entries back. Pinned mods stay on their version.
- **Save backup before a changed launch:** before a non-vanilla launch, if the profile's history has an event after the newest stored run (or there is no previous run), Mortar zips the Saves folder into `backups/` with cause kind `update` for that profile. A failed zip is logged and does not block Play.
- **Direct launch preview:** Edit profile shows the Direct SMAPI argv (and `NAME=value` environment lines) for the typed launch options, prefix and environment, with a copy control. Steam `-applaunch` is not that preview.
- **Profile shortcuts:** **Add a shortcut that plays this profile** writes `--play=<game>/<profile>` as the argument. On Linux that is `~/.local/share/applications/tech.rethunk.Mortar.play-<game>-<profile>.desktop` (or `$XDG_DATA_HOME/applications/…`), named `<profile> (<game>)`. On Windows it is a `.lnk` under the Start menu's Mortar folder, written through `WScript.Shell` COM. **Remove the shortcut** deletes that file. Rename and delete of a profile rewrite or remove the matching shortcut; a failed shortcut sync is logged and does not fail the profile operation. **Add this profile to Steam** appends a non-Steam game to native Steam's `shortcuts.vdf` for the MostRecent account (quoted exe, launch options `--play=…`, appid with the high bit set); refused while Steam is running, and when only Flatpak Steam is found, since that sandbox cannot start Mortar. A duplicate exe+options pair is left as it is. When a cover or Steam hero image is a local file, Mortar copies it into that account's `userdata/…/config/grid` as portrait, capsule and hero art for the new shortcut.
- **Success or failure:** `steam -applaunch` returns at once.
  - A launch counts as started when `SMAPI-latest.txt` (`~/.config/StardewValley/ErrorLogs/`, `%APPDATA%\StardewValley\ErrorLogs\`) is rewritten within 60 s, and failed otherwise, with a hint (on Windows, the missing launch-options line).
  - When Mortar started SMAPI directly and it exits having written no log, the launch fails with its exit code.
  - A Steam launch's `steam` process only hands over and exits 0; that zero exit is ignored and only the log decides. A non-zero `steam` exit is a failure immediately.
- **Running:** a `StardewModdingAPI` process whose `--mods-path` is a profile's folder means that profile is in use; its folder is locked against changes until the process exits (Windows locks loaded files anyway). Reaching Running records `lastPlayed` for that game in `settings.json` (profile id and RFC3339 `at`); Launching and Failed do not.
- **Whose log:** the game has one `SMAPI-latest.txt` for every profile, so the Console and Get help show a log only in the profile that wrote it.
  - The session Mortar launched belongs to its profile.
  - The file on disk belongs to the profile whose mods folder matches SMAPI's `Mods go here: <path>` line (SMAPI writes the home folder as `~`, `PathUtilities.AnonymizePathForDisplay`).
  - A log without that line, from a launch outside Mortar, belongs to no profile.
  - **Runs:** when a launch Mortar started ends, or fails, a Summary of that run's SMAPI log is stored under the profile's `runs/` ([Storage](#storage)): versions, error and warning counts, whether SMAPI crashed or hit a fatal error, and the mods that logged errors with counts and their first message. Performance reports are stored alongside runs, with the current run id when available, and keep the newest 20 per profile.
  - The Console's Runs picker loads a stored log read-only, and Save log and Get help use that copy. A stored log belongs to its profile like the live one.
  - A run that ended with errors or a crash also opens a dialog naming the cause when Mortar can identify one: **Caused by `<ModName>`**, followed by one plain-language sentence and actions to switch it off or open its Nexus page. When the crash names no mods, the dialog offers **Find the broken mod**: `internal/bisect` copies the profile, halves enabled mods (keeping required dependencies), and relaunches through `launchsvc.RunForBisect` until one culprit remains; the window is `BisectDialog`.
  - The Mods list, grid and sidebar badge each user mod that logged errors or warnings in that profile's newest stored run; a later run with none for that mod clears the badge.
- Trap: launching through Steam makes Steam Cloud download the user's saves, and SMAPI's Save Backup mod zips them into `save-backups/` in the game folder.

### Saves

Saves live in one folder, `%APPDATA%\StardewValley\Saves` or `~/.config/StardewValley/Saves`, which Steam Cloud syncs, so Mortar never moves it; profiles share saves.

- Each profile's Saves card ([gui-design.md](gui-design.md#main-screen)) counts the saves that fit.
- Its Saves tab lists every save with the mods it has used that the profile lacks, read from the save itself, as NOMAD recalled a mod once doing in game.
- Players pick their save inside the game. Play still warns from the newest save when it needs mods this profile lacks ([Launch](#launch)); this tab is the full list.

- **Where mods leave traces:** SMAPI writes no mod list into a save, but mods leave keys prefixed with their `UniqueID`:
  - SMAPI's save data `smapi/mod-data/<uniqueid>/<key>`, lowercased whole (SMAPI's `DataHelper` in the Pathoschild/SMAPI repository)
  - `modData` keys such as `Sonozuki.MoreGrass/GrassOffsetX0`
- **Matching:** Mortar scans the save's `key` / `string` XML entries and, ignoring case, takes for each key the longest prefix ending at a `/`, `_` or `.` boundary that is a `UniqueID` in the mod dataset's index. Splitting at the first `_` would be wrong: 1,413 IDs contain `_`, and for 81 of them the part before it is another mod's ID; 1,081 have no dot.
- **Cost:** measured on one of NOMAD's saves: 65 MB, 330,748 keys, 32 mods in 0.43 s. Results are cached by the save file's modification time. The same pass streams the file and writes nothing, and also reads `SaveGameInfo` for:
  - farmer, farm name, in-game date, `millisecondsPlayed` and `money`
  - farm layout `whichFarm`: 0 Standard, 1 Riverland, 2 Forest, 3 Hill-top, 4 Wilderness, 5 Four Corners, 6 Beach, 7 Meadowlands; -1 when the tag is missing
- **Limits:** mods that keep no per-save data leave no trace, and keys outlive a mod removed on purpose, so the warning says "this save has used", and each mod can be dismissed for that save.
- **Backups:** the Saves tab's Save backups lists the zips in `backups/` newest first with their time, cause, size and the farm names inside.
  - Restore, for one save or all of a zip, first zips the current Saves folder (cause `restore`), then extracts beside Saves and swaps each save folder in by rename, so a failure leaves the old one.
  - It refuses a zip path that would leave the extract folder, caps each file at 512 MiB, and is refused while the game is launching or running. Open backups folder uses the system file manager.
- **Getting a lacking mod:** each one is located as Problems locates a missing dependency (`problems.Locate`).
  - A Nexus page or a GitHub repository gets Add to this profile, which queues it into the open profile; any other page gets an Open link.
  - Switching on a mod the profile has switched off is locked while the profile is launching or running.
  - Problems also suggests Content Patcher config values that enable compatibility patches for mods already enabled in the profile:
    - A change or dynamic token whose `When` pairs a `ConfigSchema` field (plain or `|contains=`) with `HasMod` of another enabled mod is a compatibility patch.
    - An on/off field (true/false, on/off, enabled/disabled, yes/no) whose current value, from the profile's `config.json` or the schema `Default`, runs none of the pack's compatibility patches is suggested with the values that would.
    - Fields that list NPCs are never suggested.
    - A variant picker (a palette, recolour or similar choice) is suggested only from the pack's own mapping: a dynamic token that yields one of the field's allowed values only when a mod is installed (`Value: Earthy` when `HasMod: DaisyNiko.EarthyRecolour`) ties that value to the mod, and a field with two or more such values is a picker. Its automatic choice is a blank value when `AllowBlank` is set, or the value those tokens require of the field (`Off`). When the current choice names a mod the profile lacks, or is a generic choice while a mapped mod is enabled, the automatic choice (or else the value for the enabled mod) is suggested, worded as "made for that mod, which this profile lacks".
    - **Set to** writes only that field into `config.json`; Content Patcher fills the rest with defaults. Applying a suggested value also remembers that UniqueID, field and value so the reverse suggestion stays hidden until the field's current value changes.

### Mod data

- **Mod dataset:** SMAPI's `Pathoschild/StardewModDataset` (MIT or CC-BY-SA 4.0, published with explicit permission from Nexus Mods, CurseForge and ModDrop, refreshed near the end of each month, 0.x with no version tags) records each Nexus mod page's current files with the SMAPI manifests inside them (`Downloads[].Mods[]`, `SizeInBytes`), not every file: Content Patcher has 2 there against 170 on Nexus.
  - **Fetching:** one page's entry when needed, from `https://raw.githubusercontent.com/Pathoschild/StardewModDataset/main/dataset/data/Nexus/<mod id / 1000>/<mod id>.json`; the `UniqueID` index (`dataset/indexes/pages by mod ID.json`, 1.5 MB, 28,634 IDs) monthly.
  - **Parsing** is lenient; a file it lacks is checked after download.
- **Update checks:** `POST https://smapi.io/api/v4.0.0/mods` with each mod's ID, `UpdateKeys` and installed version, plus `apiVersion`, `gameVersion` and `platform`, returns `suggestedUpdate`, which Mortar takes as given; `compatibilityStatus` and `brokeIn` come only with `includeExtendedMetadata: true`. Unofficial versions (`metadata.unofficialUpdate` / `unofficial` / `unofficialForSmapi`, or those fields on `suggestedUpdate`) show as **Unofficial update available** with their link in the mod detail and Update review; **Update all** never installs them. The API is public, unauthenticated and officially unreleased, so answers are cached for an hour in one cache shared by every profile (keyed by mod, update keys, installed version and environment, so a mod at the same version in several profiles is asked about once), misses go in batches of 100, concurrent checks wait for one another rather than asking twice, and after a failed ask Mortar serves stale or unknown answers for five minutes before asking again; failures never block. Updates show as a count per profile and are applied only by the user; a pinned entry and a skipped version are left out of the count.
- **Dependencies:** `Dependencies[]` (`UniqueID`, `MinimumVersion`, `IsRequired` defaulting to true) plus `ContentPackFor` as a required dependency on its framework mod, all by `UniqueID`. For a missing one, Mortar prefers the Nexus page named in its own `UpdateKeys`, else the page whose files hold it at the highest version (3,793 IDs appear on several pages), and takes the newest `MAIN` file satisfying `MinimumVersion`. One found only on CurseForge or ModDrop is listed with its page link, to install from a downloaded archive. After an archive install and after a queue item finishes, the mods that landed are checked again, and any required dependency (`IsRequired` not false, or `ContentPackFor`) the profile still lacks is offered in a dialog whose Add them queues it by the Problems resolver; optional dependencies stay on the Problems bar.
- **Support:** Get help uploads the shown profile's `SMAPI-latest.txt` as it is on disk (at most `launch.MaxLines` × 256 bytes) to smapi.io/log, the Stardew community's standard support tool: `POST https://smapi.io/log` with a form-encoded body `input=<log text>`, no auth. Save log… writes that same file when the profile owns it, otherwise the Console tab's lines, through the native save dialog (`picker.SaveFile`). The server answers with a redirect to `/log/<id>`, which is the link, and answers a failed or empty upload with HTTP 200 and its page, so only a redirect counts as success (SMAPI's log parser in the Pathoschild/SMAPI repository). A SMAPI log holds local paths, including the user's name, and anyone with the link can read it, so Mortar shows the log and asks first. Save diagnostics writes a zip through the native save dialog: `build.json` (Mortar's version, OS, architecture, Go and Wails versions; WebKit's is not exposed), `settings.json` with `nexusName` and `nexusUserId` cleared and any key field removed, `profiles.json` (mod names, versions and sources, no notes), `queue.json` without `nxm://` keys, the last 2,000 lines of Mortar's log or in-memory console, the open profile's SMAPI log when that profile owns it, and a `README.txt` saying what is in and what was stripped. The keyring is not read. Report a Mortar bug opens a new GitHub issue prefilled with Mortar's version, OS and architecture, and the game with its and SMAPI's versions; no log is attached.
- **Console links:** in visible log rows, exact installed mod names and `UniqueID`s link to that mod's panel, and paths under the profile's `mods/` folder or the game folder open their containing folder (`OpenConsolePath`, which resolves symlinks and refuses any other path).
- **Problems** warn and never block. They report:
  - missing dependencies
  - duplicate `UniqueID`s (resolved in a dialog that keeps one copy and switches the other off)
  - mods SMAPI's API marks broken, obsolete or abandoned for the game version, with `compatibilitySummary` when SMAPI supplies it, including a one-click replacement when the summary names a Nexus or GitHub target Mortar can install, or a `UniqueID` the mod dataset resolves
  - Content Patcher asset conflicts, each with a one-click fix
  - cleanup suggestions for unused frameworks and conservatively detected unused Content Patcher tilesheet packs
  - enabled mods that logged errors in this profile's newest stored run (warning when that run crashed or hit a fatal error, info otherwise; **Switch off** and **Get help** on the stored run's log; cleared by a later clean run, switching the mod off, or updating it)
  - Abandoned mods are info-level and dismissible per profile like Content Patcher conflicts
- **What counts as a Content Patcher conflict:** two or more enabled packs (`ContentPackFor.UniqueID` `Pathoschild.ContentPatcher`) that `Load` the same target (warning: only one wins) or that `EditImage`/`EditMap` the same target, or `EditData` the same entry or field (info, dismissible per profile via `settings.json` `dismissed`). Both kinds can be restored from Problems. `EditData` that only shares a target is not reported.
- Each conflict includes per-pack evidence: pack name, source file (`content.json` or an included file) and patch index, Action, Target, ToArea/FromArea for image and map edits, a short When summary, and Priority. Expanding **Why?** on the Problems row lists that evidence; image edits load a PNG crop of each pack's overlapping source region (`ConflictImageCrop`) only when the row is expanded.
- Overlay image edits conflict only where an opaque 16×16 source cell lands; tokenised `FromFile` paths use every matching file, or fall back to the whole sheet when none match.
- Loads whose files are all blank or JSON/image-identical are ignored; JSON equality is by parsed value, so formatting does not create a conflict.
- `FromFile` and recursive `Include` paths are relative to the content pack root.
- **When a change counts:**
  - A `When` `HasMod` condition (`"HasMod": "A, B"` or `"HasMod |contains=A": true/false`) counts only when that condition holds for the profile's enabled mods; other conditions are treated as met.
  - A change whose config conditions do not match the pack's current settings (`config.json`, else the schema `Default`) is not counted.
  - DynamicToken conditions use every statically reachable value; unknown game-state conditions stay possible, except an opposite literal `HasFlag` assumption in the same `When`.
  - Condition keys with an empty input (`"HasMod: |contains=…"`) read as the bare token, as Content Patcher reads them.
- **When two edits write the same place:**
  - Image edits compare their `ToArea` (or, without one, `FromArea`'s size or the source PNG's size at the top-left).
  - `EditData` edits compare `Entries` keys and `Fields` (entry plus field); the same literal value does not clash.
  - Map edits compare a `FromFile` patch's `ToArea`, each `MapTiles` position and layer, and `MapProperties` keys. A map patch without `ToArea` covers its `.tmx`/`.tmj` source's size (or `FromArea`'s) at the top-left; a `.tbin` source or any tokenized area counts as the whole asset.
  - Warps, `TextOperations` and tiles that only set properties merge, so they never conflict.
  - Edits that need different spouses (`Relationship:<NPC>`: `Married`, or `Query: '{{Spouse}}' = '<NPC>'`) never apply together, nor do edits that require disjoint literal values of `LocationName`, `LocationContext`, `Season`, `Weather` or `DayOfWeek`.
  - Two packs setting a map property to the same value agree and never conflict.
  - Overlapping image edits with the same source bytes and `FromArea` agree and never conflict.
- **Cosmetic or harmless:** an edit conflict whose every overlap is harmless is shown under **Cosmetic or harmless** and never counted as a problem. An overlap is harmless when both edits are images (they only change how something looks), when either edit applies only in a literal `LocationName`, `LocationContext` or `Weather`, or when either is a one- or two-tile area at a tokenized position.
- A losing low-priority load gated by a user-changed config value produces a setting hint recommending the pack default, because the winning load makes that setting ineffective.
- **Cleanup:** frameworks that no enabled mod (or content pack) needs, but that a switched-off mod still names as a dependency or `ContentPackFor`. They are listed, not counted as problems. **Remove** drops the framework from the profile ([gui-design.md](gui-design.md#problems-tab)).
- **Author-marked mods:** Problems also flags enabled mods whose cached Nexus page or installed manifest/file says obsolete or deprecated; this is informational and uses cached data only.
- **Fixes and companions:** a conflict lists the settings that remove one pack from it: an on/off field that every clashing edit of that pack needs, offered as **Set the field to its other value**. Overlapping edits are not reported between packs built to work together: packs in one entry, or where one names the other as a manifest dependency or in any `HasMod` condition (SVE and East Scarp patch around each other this way).
- **How the scan reads packs:** targets come from `content.json` and recursive `Action: Include` `FromFile` paths that stay inside the pack folder, with JSON comments and trailing commas tolerated; case and slashes are normalised; targets containing `{{...}}` are skipped. The scan is cached by each `content.json` mtime and runs with the other problem checks, off the UI thread. The bar lists the targets and can switch one pack off.

- **Nexus-listed requirements:** Problems also report requirements named on a mod's Nexus page, including the author's note when present.

## Nexus Mods

Sources: the API acceptable-use policy (help.nexusmods.com article 114), the SSO demo `Nexus-Mods/sso-integration-demo`, the `Nexus-Mods/node-nexus-api` client, and Vortex's (`Nexus-Mods/Vortex`) `NXMUrl.ts`.

- **Sign-in:** Settings takes a personal API key, kept in the OS keyring and never sent to a server of ours. `GET /v1/users/validate.json` gives the account's `user_id` and `is_premium`. Every request carries a truthful `Application-Name` and `Application-Version`.
- **Rate limits** (measured on NOMAD's free account): `x-rl-daily-limit: 20000`, `x-rl-hourly-limit: 2000`, with `-remaining` and `-reset` headers; the client reads them on every response and pauses before running out. Settings › Nexus Mods shows the remaining daily and hourly counts from the last response, with no call of its own.
- **Calls only on the user's action:** a mod's `picture_url` and `endorsement_count` (`GET /v1/games/stardewvalley/mods/<id>.json`) are fetched once, when it is installed, and cached; the picture itself is cached on disk under `cache/modpic` and served to the window at `/mod-picture/` (Nexus image hosts only, images up to 8 MiB).
- **Mod page details** (`nexussvc.Details`): the page (`name`, `summary`, `description`, `picture_url`, `version`, `author`, `uploaded_by`, `uploaded_users_profile_url`, `category_id`, `endorsement_count`, `mod_downloads`, `mod_unique_downloads`, `created_time`, `updated_time`, `contains_adult_content`, `status`, `available`), `files.json`, `changelogs.json` and the category name from the game's `categories` (`GET /v1/games/stardewvalley.json`, cached 30 days) are kept in `<datadir>/cache/nexus/details-v3-stardewvalley-<mod id>.json` through the meta cache, never in `profile.json`. They are fetched after each Nexus install and again when the detail dialog opens once they are a day old; signed out, rate-limited or offline, the cached copy is served however old. When `available` is false the UI marks the mod **Hidden on Nexus**; when `status` is anything other than `published` it marks **Removed from Nexus**, with the page's updated (else created) date when known, in the detail panel and as a small marker on the list and grid. Those pages are not offered as downloadable updates; the installed mod still runs. Update review reads the same cache (`CachedDetails`) and shows changelog versions between the installed version and the latest using the SMAPI-accurate `isNewer` compare; it does not fetch. Notes in that range that contain `breaking`, `incompatible`, `requires`, `now needs`, `new save`, `start a new`, `not save compatible` or `remove before updating` mark the update row with a warning icon ([gui-design.md](gui-design.md#download-queue)). `description` and file descriptions are BBCode with `<br />` line breaks; `changelogs.json` maps each version, newest first, to HTML-escaped notes, and answers `[]` for a mod with none (measured on mods 541 and 1150, 2026-09-30).
- **Endorse and track:** only on the user's click, for a signed-in account. Endorse and abstain are `POST /v1/games/stardewvalley/mods/<id>/endorse.json` and `abstain.json` with `{version}`; the state is the page's `endorsement.endorse_status`, and when Nexus refuses to endorse a mod that was not downloaded, its own message is shown in a toast. Track is `POST` or `DELETE /v1/user/tracked_mods.json` with `{domain_name, mod_id}`, and the tracked list (`GET` the same path) is reused for 30 seconds. Settings › Nexus Mods **Untrack every \<game\> mod…** and **Untrack mods not in any profile…** walk that list for the game's Nexus domain and untrack (the unused pass keeps mods any profile still names). The CLI is `mortar nexus untrack` ([HUMANS.md](../HUMANS.md#command-line)).
- **When a Nexus download may start:** only from Nexus's own Mod Manager Download button (the `nxm://` link that button produces) or from a Premium API `download_link.json` fetch the user asked for in Mortar (queue, Update, Import). Mortar never starts a Nexus download from a listing tile, search result, or a control it injects on nexusmods.com. The browser extension reads and marks Nexus pages and relays those clicks; it never starts downloads or opens Nexus pages itself. Listing-tile "Add to Mortar" and collection import stay unbuilt ([design.md](design.md#later)).
- **New since last look:** a mod's cached details are compared with its `nexus-seen.json` record. A newer current file upload or a changelog version than the record marks it New, and showing its details (the dialog or the sidebar) updates the record. A mod never looked at is not New, and nothing is fetched for this.
- **Files:** `GET /v1/games/stardewvalley/mods/<id>/files.json` lists every file (170 for Content Patcher) with `file_id`, `file_name`, `version`, `mod_version`, `category_name` (`MAIN`, `OPTIONAL`, `UPDATE`, `MISCELLANEOUS`, `OLD_VERSION`, `ARCHIVED`, or null), `size_kb` and `is_primary`. An update takes the `MAIN` file matching SMAPI's `suggestedUpdate`, else the `is_primary` one, and never an `OPTIONAL` file unless the profile already uses it. Before choosing, Mortar asks Nexus GraphQL v2 `modFiles { fileId scannedV2 }` (cached on the client). A file whose `scannedV2` is `QUARANTINED` is omitted from choice; a request for that file id fails the queue item (`Nexus has quarantined this file; Mortar will not download it`). A failed scan leaves the v1 list unchanged.
- **Downloads:** `GET /v1/games/stardewvalley/mods/<id>/files/<file id>/download_link.json`. Premium accounts get links directly; they expire, so Mortar asks just before downloading and again on a restart. A free account gets HTTP 403 ("...this is for premium users only", measured); it needs the `key` and `expires` from the `nxm://` link that the site's Mod Manager Download produces, one click per mod. Each answer lists several CDN mirrors (`name`, `short_name`, `URI`); Mortar remembers every `short_name` it has seen. Settings › Nexus Mods **Preferred download server** chooses one of those names or **Automatic** (empty setting), and the queue takes the preferred mirror when present else Nexus's first.
- **`nxm://` links:** `nxm://<game>/mods/<mod id>/files/<file id>?key=<key>&expires=<unix>&user_id=<id>`; Mortar takes this form only for Stardew Valley (`stardewvalley`). Only one app can own the scheme, and Wails' NSIS macro would delete and rewrite its key at install time without asking (`build/windows/nsis/wails_tools.nsh`, from Wails' template), taking it from Vortex or Mod Organizer 2. So `nxm` is not in `build/config.yml`: Mortar registers it at runtime after the user agrees (`HKCU\Software\Classes\nxm` on Windows, with `DefaultIcon` at `mortar.exe,0`; on Linux a user-level `~/.local/share/applications/tech.rethunk.Mortar.desktop` lists `x-scheme-handler/nxm` and `xdg-mime default` is set; turning it off drops the type again), records the previous handler in `settings.json` (`nxmPrevious`, plus `nxmPreviousName` for the UI), and restores it when turned off or when uninstall runs `mortar.exe --release-links` before files are removed (the key is deleted when there was no previous handler). When Mortar owns the scheme and a previous handler was recorded, Settings › Nexus Mods **Send other games' links to …** (default on) forwards `nxm://` links whose game is not Stardew to that handler (Windows: the saved open command with `%1` replaced; Linux: the saved desktop entry's `Exec` with `%u` replaced). A desktop entry named `mortar.desktop` that Mortar wrote is rewritten under `tech.rethunk.Mortar.desktop` (scheme and file associations included) and then removed.
- **Link bursts:** each `nxm://` launch is a second instance whose arguments the running one queues at once and handles in order, logging every link (`second instance:`, `nxm:`, `queue:` lines), so a burst loses nothing inside Mortar (16 simultaneous `gio open` launches: 16 handoffs, 16 links). Chromium browsers (Chrome, Vivaldi, Edge) launch at most one external protocol per user gesture (`g_accept_requests` in `chrome/browser/external_protocol/external_protocol_handler.cc`), so Nexus Slow Download countdowns that end with no click in between are blocked in the browser, which logs `Not allowed to launch 'nxm://…' because a user gesture is required.` in that tab's console. The Mortar browser extension (`browser-extension/`, MV3 for Chromium and Firefox) avoids that gate: on `www.nexusmods.com` it reads each `nxm://` anchor (the Start download manually link, inside the download widget's open shadow root) and sends it with `sendNativeMessage` to the host `tech.rethunk.mortar`, which is Mortar itself (`internal/nativehost`: Chromium passes the extension origin as the first argument, Firefox the manifest path and the extension id). That process starts `mortar <link>`, so the link takes the same second-instance path. The host also answers JSON requests without starting a download: `{"type":"installed","game":"<nexus domain>"}` returns `modIds` for Nexus entries in the last-open profile of the game that domain maps to in the component manifest (empty when Mortar is not running); `{"type":"mod","game":"<domain>","modId":<id>}` returns `open` (that profile's name, installed version and file id) and `others` (the remaining non-hidden, readable profiles, each with name, version and file id when that Nexus mod is present). The page's game is that Nexus domain, not a hard-coded Stardew id. What the popup and content script show with those replies: [gui-design.md](gui-design.md#browser-extension). A link that arrives again before its own `expires` time (from the page's own launch, from the extension, or from every open tab when the extension is reinstalled) is taken once; the record lives in memory, so a restart forgets it. The extension injects itself into Nexus tabs that were open before it was installed. When Mod manager download opens Nexus's "Download mod file" requirements dialog (`[role=dialog]` in `#next-shadow-root`), the extension follows its Download link at once: the `a.nxm-button-flamework` whose href carries `nmm=1` and points at the page's own mod, once per dialog (requirement rows carry Mod Manager Download links to other mods, which are left alone), since Mortar resolves requirements itself; a file without that dialog, and Manual download, are left alone. After Mortar confirms a link, the extension closes the tab when it was opened only for that download: every history entry is the same mod's page, whichever of its tabs (Navigation API `navigation.entries()`, which lists only same-origin entries, so a `history.length` longer than the list keeps the tab; where that API is missing, no tab is closed). On Linux, turning nxm handling on, and every start while it is on, writes the host manifest into `NativeMessagingHosts/` of each installed Chromium browser under `$XDG_CONFIG_HOME` (Chrome, Chromium, Brave, Edge, Vivaldi) and into `~/.mozilla/native-messaging-hosts/`; turning it off removes them. A Flatpak build writes none, since a browser outside the sandbox cannot run it. The unpacked extension's id is fixed by the `key` in its manifest.
- **Browser problem panel:** the extension can request up to five active-profile problems involving a Nexus mod; it is read-only and never downloads or opens Nexus pages.
- **No re-hosting:** mod files and Nexus data stay on the user's machine; a share link holds IDs only.
- **Download queue:** an import or a profile's missing files run one queue (`internal/queue`), persisted in `<datadir>/queue.json` without the `nxm://` keys. Items store as `nexus-<mod id>-<file id>`, and the entry records source kind `nexus` with the mod id, file id, version, picture URL and endorsement count, fetched once at install. When a file from a Nexus page is installed into a profile that already has an entry from that page, the queue offers **Install together** with that entry, **Install separately**, or **Don't install** (default add for OPTIONAL and MISCELLANEOUS files, separate for a second MAIN). Installs started from a save's missing mods, a missing dependency or a Problems fix send `latest`: the file they name came from the mod dataset or a save and may be old, so the queue follows Nexus `file_updates` from it to the newest listed file; share imports leave it off to reproduce the shared files. Premium accounts download without clicks. A free account's head item waits for its click (**Open download page** and **Skip** on that row), and a matching `nxm://` link is routed to it instead of showing the arrival card. An update or `latest` Nexus item is skipped on its own (`queue.skipHeld`) once the profile already holds that file id or a newer one from the same page; a request for an exact file, as a share import does, is left queued. A Nexus file the game's store already holds (`nexus-<mod id>-<file id>`, from an install into any profile) installs from the store with no download and no click, taking its file name, version and picture from the profile entry that recorded it so Nexus is not asked, unless the profile has an entry from the same mod page, whose Install together choice needs the archive. A link's item gets its mod name and picture as soon as it is queued, so Up next shows them. A reached rate limit, Nexus's or GitHub's, pauses the whole queue until its reset time. GitHub items (`repo`, `tag`, `asset` instead of a mod id) need no sign-in and never wait for a click; see [GitHub releases](#github-releases). Done, failed, cancelled and skipped rows can be dismissed one at a time or cleared together; that drops them from `queue.json` and from staged-key tracking, and never removes queued or in-progress items. An install that unpacks without a SMAPI manifest pauses in `needs-root` with the staged store key and a folder tree until **Choose folder…** saves a content root (`AnswerRoot`) or cancel marks the item failed; FOMOD and multi-asset releases use `needs-fomod` and `needs-choice` the same way. **Resume:** a retry or a restart sends `Range` from the partial's size and accepts 206, starts over on 200, and starts over when the `ETag` changed or the `Content-Range` does not match, at most three times; a Nexus link that has died is replaced through the download-link call before ranging on. The fetch covers Nexus and CDN downloads; GitHub assets always start over, and `Content-MD5` is not checked. The queue HTTP client waits 20s for response headers (the body may stream longer) and drops a transfer that sits idle past its idle timeout. The worker runs under an app-lifetime context cancelled when Mortar quits. Every finished item is appended to `download-history.json`.
- **Source kinds:** `profile.Source.Kind` is `local`, `nexus` or `github` (constants `profile.KindLocal`, `KindNexus`, `KindGitHub`), plus `smapi` and `mortar` for the bundled entries. A `github` source holds `repo` (`owner/repo`), `tag` and `asset`; share links read them as `<owner>/<repo>@<tag>/<asset>`.

## GitHub releases

`internal/github` reads `/repos/<owner>/<repo>/releases` without sign-in. Answers are cached on disk for an hour and served stale when GitHub is unreachable. The unauthenticated limit is 60 calls an hour per IP, and a reached limit shows its retry time. An install or update takes the release's only archive asset, or asks when there are several; the download is capped at the archive extraction limit, drops a transfer that sits idle past its idle timeout, and stores under its `github-` key. SMAPI's own release lookup uses the same client.

**Trust:** a GitHub-sourced install counts as verified only when SMAPI's update API (`includeExtendedMetadata: true`) maps the manifest's `UniqueID` to the same repo. It is unknown when the API is unreachable, and never blocks.

**Installs and updates:**

- The queue resolves a GitHub item with `Releases` and `Select` (an update asks for SMAPI's suggested version, an install for the newest stable release), downloads with `github.Download`, unpacks into the store under `github.Key`, and reads the manifests' `UniqueID`s before the profile changes.
- Every ID verified installs; a known mismatch parks the item in `needs-confirm` (Install anyway or Skip); an unknown answer installs and marks the item "could not verify".
- A release with several archives parks the item in `needs-choice` until the user picks one.
- Update review's Update and Update all use GitHub when the mod's update key is `GitHub:<owner>/<repo>` and SMAPI's suggested update URL is on github.com (`problems.Update.GitHubRepo`); otherwise Nexus.
- A missing dependency the dataset does not place on Nexus takes the GitHub repo SMAPI's API records for it (`problems.Ref.GitHub`), and the problem bar's Add queues it.

## Sharing

- **Form:** Discord makes only `http://`, `https://` and `discord://` links clickable (Discord community posts 14574789338135 and 25441082215447), so a shared link is `https://mortar.rethunk.tech/stardew/p#<payload>`, handed to the app as `mortar://stardew/p/<payload>`. Browsers never send the part after `#`, so no profile data reaches any server. The app accepts either form, or a bare payload, pasted into its import box.
- **Payload** (`internal/share`): compact JSON `[1, "<profile name>", [<entry>, ...]]`, the leading number being the format version (an older Mortar meeting a newer one says to update), Brotli-compressed at quality 11 and base64url-encoded without padding. An entry is `[<nexus mod id>, <nexus file id>]`, or `"<owner>/<repo>@<tag>/<asset>"` for GitHub, so a link names the exact file. Only enabled entries with a source are shared; local archives are listed at Share as left out, and so are switched-off entries. SMAPI's bundled mods (the `smapi-<version>` entry) and the bridge (`bridge-<version>-<sha256 prefix>`) are never shared, listed or imported: every profile gets them from the signed component manifest. About 240 mods fit a 2,000-character Discord message. The link holds no `UniqueID`s, which barely compress. Brotli (`github.com/andybalholm/brotli`, MIT; the standard library has none) is the compressor.
- **Share dialog** (`internal/sharesvc`, `frontend/src/share`): the link with a length meter against 2,000 characters, Copy as a message, the mods by source and what is left out with the reason. Over 240 mods, or when the payload passes the 8 KB cap, it suggests the file. `Share` and `SaveFile` take a list of entry keys, and an empty list means the whole profile, so sharing a selection encodes only those entries (a selected mod in a multi-mod archive shares the whole download).
- **Mod list as text:** the dialog also copies the profile's mod list as Markdown (`[Name](page URL)` with the version, grouped Enabled and Disabled when any are off), plain text (`Name vVersion - URL`) or Discord (the Markdown split into messages of at most 2,000 characters). Bundled SMAPI mods and the bridge are left out, as in shares, and the chosen format is kept for the session.
- **`.mortar` file:** a zip holding `profile.json` (the same entries as a link, the name, notes, description and the shared mods' `UniqueID`s, which bound the config files it may carry) and `configs/<UniqueID>/<relative path>.json` for each enabled mod's `.json` files except `manifest.json`. Files over 1 MiB, with unusual names, or past the totals are skipped and listed at Save. The description, at most 280 characters, travels only in this file: a link stays `[version, name, entries]`, since the field would grow the 8 KB encoded payload, and colour and icon travel in neither.
- **Import preview:** `sharesvc.Preview*` resolves every entry and creates nothing. A Nexus file is confirmed with the mod's `files.json` (needs the sign-in; signed out, the preview stays with what the link and the dataset say). A file that is gone or `ARCHIVED` is replaced by the `MAIN` file with the same version (from the listing, else from the dataset), else the primary file, marked "different file"; a mod with no files or a 404 is unavailable ("removed from Nexus", with its page), and a mod with files but no replacement is unavailable too. Entries the target profile already holds by Nexus mod and file ID are installed. UniqueIDs and dependencies come from the dataset page (`meta.Page`); a file the dataset lacks is "check later". The shared mods and the target profile's mods go through `problems.Check`: a missing dependency Mortar can name on Nexus or GitHub becomes a dependency tile, one it cannot (CurseForge, ModDrop, unknown) is a listed problem, and a mod SMAPI's API marks broken for the game version is a problem with Leave out. A GitHub reference is marked unverified, since its trust rule (see [GitHub releases](#github-releases)) can only run after the download. A free account gets a note that each download takes one click on Nexus.
- **Import:** the dialog's tiles carry a tick each; **New profile from link** (or file) creates a profile named from the share, records origin `link` or `mortar`, and queues every available, ticked file through the download queue, and **Add to the selected profile** queues them into the profile Import was opened from. Nothing downloads before that click, and a preview left behind is dropped on close. Unavailable mods are listed in the new profile's notes. A `.mortar` file's config files are written by `share.Apply` once their mods are installed: only `.json` files under a folder an installed mod of that import already has, re-validated at write time, and never over mods the profile already had. Config files still waiting are kept in `<datadir>/pending-configs.json` (temp file, then rename) independently of live queue rows, and at startup Mortar applies them for downloads that are already done and again as the rest finish. Finished queue rows ageing off or being cleared does not drop pending configs. If the last download finishes while the game is using the profile, apply waits and retries when the game goes idle (and on a short timer until then).
- **Routing:** `mortar://` is in `protocols:` in `build/config.yml`, which the NSIS installer registers; `.mortar` is in `fileAssociations:` (the installer's `APP_ASSOCIATE` block in `wails_tools.nsh` uses the executable's icon). On Linux, `nxm.System.RegisterLinks` (run when first run ends, and at startup in a production build when no desktop entry exists yet) writes `~/.local/share/mime/packages/mortar.xml` for `application/x-mortar`, keeps the user desktop entry listing the mortar scheme and file type, and sets both `xdg-mime` defaults; it is idempotent and takes an injected runner. `Options.SingleInstance` with `OnSecondInstanceLaunch`: a link reaches the app as `events.Common.ApplicationLaunchedWithUrl` on a cold start (fired when the only argument contains `://`, `Rethunk-AI/wails` `v3/pkg/application/application_linux.go:73-83`) or in `SecondInstanceData.Args` when it is already running. `sharesvc.Receive` reads both, plus `.mortar` paths and `file://` URLs (including Windows UNC `file://server/share/...`). A share link or `.mortar` file opens the Import dialog with that value filled in, never importing by itself. `mortar://<game>/mod/<id>` (game id as host, a positive decimal Nexus mod id with no leading zeros, no query or fragment) opens that game on its last-open profile, selects the matching Nexus mod on the Mods tab, or toasts that the id is not in that profile. A `.mortar` file dropped on the window opens Import instead of installing as an archive.
- **Trust boundaries:** link parsing accepts only the known forms and caps the encoded payload at 8 KB and the decompressed payload at 64 KB before parsing; a `.mortar` file is capped at 32 MiB, 5,000 entries, 1 MiB per config and 32 MiB of configs, and any entry outside its layout fails the whole file; the clipboard is read only when the user presses Paste. Extraction limits: [Trust boundaries](#trust-boundaries).
- **LAN sharing** (`internal/lan`): with Settings › General **Share profiles on the local network** on, Mortar advertises `_mortar._tcp` (hashicorp/mdns) and serves HTTP on `lanPort` (default 47630). Sends are refused while sharing is off. A send is the same share-link payload as Import; a profile too large for that link cannot go over LAN. The sender `GET`s `/hello` (a one-minute nonce bound to that peer) then `POST`s `/share` with the payload, its listen port, and, when a Nexus API key is in the keyring, an HMAC-SHA256 proof of that key over the nonce concatenated with SHA-256 of the payload (hex); the key is never sent. The receiver compares with `hmac.Equal`. Matching proof plus a sender port marks **same account**: the response carries a 5-minute Bearer token scoped to that share's Nexus store keys (GitHub entries are omitted). The receiver then `GET`s `/store/<game>/<key>` with that token; the sender streams a tar of each granted store folder (10,000 entries and 2 GiB caps, same extraction rules as other archives) and the receiver installs through `Store.AddDirVerified`. Other receivers still download each mod from its source. Incoming shares are rate-limited per peer (10 s). UI: [gui-design.md](gui-design.md#profile-management).
- **Windows firewall:** a machine-scope NSIS install adds an inbound allow named `Mortar` for the installed executable on private and domain profiles (`netsh advfirewall`) and deletes that rule on uninstall; the shipped per-user installer does not. Settings › General **Fix** elevates the same delete-then-add when an inbound block rule matches Mortar's executable.

## Release

- **Packaging:** on Linux an AppImage, `wails3 task linux:create:appimage`, written to `bin/mortar-linux-x86_64.AppImage` on amd64 and `bin/mortar-linux-aarch64.AppImage` on arm64; nfpm `.deb`, `.rpm` and Arch packages (`wails3 task linux:nfpm`) from a binary linked with `-X main.packaged=deb`, shipping `share/metainfo/tech.rethunk.Mortar.metainfo.xml` (amd64: `mortar_*_amd64.deb`, `mortar-*-1.x86_64.rpm`, `mortar-*-1-x86_64.pkg.tar.zst`; arm64: `mortar_*_arm64.deb`, `mortar-*-1.aarch64.rpm`, `mortar-*-1-aarch64.pkg.tar.zst`); a Flatpak bundle on amd64 only (`wails3 task linux:flatpak`, `bin/mortar-linux-x86_64.flatpak`) built with `--runtime-repo=https://dl.flathub.org/repo/flathub.flatpakrepo` so the bundle can fetch its runtime, also installing that metainfo; and the same packaged ELF as `bin/mortar-linux-amd64` or `bin/mortar-linux-arm64` for the AUR `mortar-bin` PKGBUILD in `build/linux/aur/` (`arch=('x86_64' 'aarch64')`). Stardew Valley itself has no native ARM Linux build and runs through Box64 or FEX on those machines. The Flathub manifest `build/linux/flatpak/tech.rethunk.Mortar.yml` finish-args expose Heroic and Lutris config (read-only), default Linux GOG and Heroic install folders and Flatpak Lutris/Heroic app data (read-write, for SMAPI), plus native and Flatpak Steam libraries and Mortar's data folder. Installs or Lutris `working_dir` paths outside those trees are invisible until the user runs `flatpak override --user --filesystem=<path> tech.rethunk.Mortar`; Mortar's in-app **Grant access** for Flatpak Steam only adds Mortar's data folder to Steam's sandbox (`internal/steam`), not extra paths on Mortar itself. On Windows an NSIS installer built with `INSTALL_SCOPE=user` (`build/windows/Taskfile.yml` passes `-DWAILS_INSTALL_SCOPE=user`), installing to `$LOCALAPPDATA\Programs\Mortar` without admin (firewall rule: [Sharing](#sharing)); the updater's Windows asset is the bare `mortar-windows-amd64.exe`. The signed manifest lists both Linux AppImages plus that Windows exe so the in-app updater matches `runtime.GOARCH`.
- **CI:** the workflow, how `wails3` is built from the fork, and the update key are in [HUMANS.md](../HUMANS.md#release). Linux arm64 runs only on `v*` tags (`ubuntu-24.04-arm`); a dispatch dry-run is amd64 only. Local arm64 packages (deb/rpm/Arch, not AppImage) are `wails3 task linux:build:arm64`: arm64 .debs extracted into `tmp/linux-arm64-sysroot`, then `zig cc -target aarch64-linux-gnu.2.39`. AppImage stays CI-native because linuxdeploy-aarch64 needs qemu plus a full runtime, not just the -dev sysroot.
- **Self-update:** `internal/updatesvc` drives Wails' updater (`app.Updater`) with the `endpoint` provider reading the signed manifest at `https://github.com/Rethunk-AI/mortar/releases/latest/download/manifest.json`. With Settings › Updates **Include beta releases** on, it also checks the newest GitHub prerelease's signed manifest and offers whichever is newer; off leaves stable-only behaviour. The manifest's asset URLs name the release tag (`releases/download/v<version>/…`), so a release published mid-update cannot swap the file under it. Settings › Updates and the app menu's Check for updates share one check; a production AppImage or Windows build also checks in the background on a timer (first pass after startup, then every four hours), downloads and verifies any newer signed release without prompting, and leaves it staged. The title bar shows **Update ready — applies when you close Mortar** with **Restart now** once staging finishes; quitting Mortar applies the staged build (the same swap as **Restart now**), and a failed background download is retried on the next check with one info log line. A release is installed only when its manifest entry carries a signature, since the verifier also accepts a bare digest. Updates are off, and the updater is never configured, in a build without the `production` tag (`wails3 dev`), a server build, a version containing `dev`, or a packaged build (`-X main.packaged=…` from nfpm, Flatpak or AUR); those last say "Updated by your package manager" in Settings › Updates. The AppImage and Windows builds keep the updater.
- **What's new:** `<datadir>/last-run-version` records the Mortar version from the previous run. After startup, when the running version is newer, Mortar fetches that release's GitHub notes once and shows them in a dialog; dismissing it writes the current version to `last-run-version`. Offline or unreachable GitHub skips silently and leaves the file unchanged so the next start tries again.
- **Signing key:** [HUMANS.md](../HUMANS.md#release).
- **Why not the GitHub provider:** Wails' GitHub updater provider verifies no signature, only an optional checksum asset.
- **Self-contained AppImage** (fork branch `mortar/v3.0.0-beta.26`, `v3/internal/commands/appimage.go`, offered upstream as branch `fix/v3-appimage-webkit-helpers`): the bundled `libwebkitgtk-6.0.so.4` has its compiled-in `/usr/libexec/webkitgtk-6.0` rewritten to the same-length relative `././libexec/webkitgtk-6.0/`, AppRun runs the app from `$APPDIR/usr` with the user's folder in `OWD` (Mortar resolves relative launch arguments against it, `sharesvc.LaunchDir`), helper modes are kept, only the linked WebKit flavour is bundled, and the runtime adds `$APPDIR` read-only to WebKit's sandbox. The injected-bundle path stays absolute because bwrap bind-mounts it, so WebKit logs one missing-bundle warning per start. Measured on Fedora 44 KDE live with no WebKitGTK installed, sandbox on, built as `release.yml` builds it.
- **Updater fixes in the fork** (`Rethunk-AI/wails` branch `mortar/v3.0.0-beta.26`, `v3/pkg/updater`): staging goes beside the target and a cross-filesystem rename falls back to a copy, since `/tmp` is tmpfs on Fedora; inside an AppImage the updater replaces and relaunches `$APPIMAGE` rather than the read-only mount; and `Config.OnUpdateApplied` runs once after an update. Mortar uses it on Windows to rewrite `DisplayVersion` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Rethunk.TechMortar` (the installer's `UNINST_KEY`), leaving a portable copy without that key alone.
- **Linux desktop integration:** packaged installs (nfpm `.deb`/`.rpm`/Arch, AUR `mortar-bin`, Flatpak) own the system desktop entry `tech.rethunk.Mortar.desktop` (`Exec=mortar %u`, `MimeType` for `mortar://`, `application/x-mortar` and `nxm://`), install `application/x-mortar` MIME XML under `/usr/share/mime/packages`, and ship hicolor icons at 512×512, 256×256 and scalable SVG. Those packages depend on `xdg-utils` (except Flatpak, whose runtime has no `xdg-mime`; the export of the desktop file and MIME types does that job). A packaged binary (`-X main.packaged=` / `-X …/internal/nxm.packaged=`, `deb` or `flatpak`) does not write a user-level desktop entry, icons or MIME XML at startup; turning the nxm switch on still runs `xdg-mime default` against that desktop id except inside Flatpak (`packaged=flatpak` or `/.flatpak-info`). Nothing installs an AppImage's embedded `.desktop` file, so an AppImage still writes its own (see [Sharing](#sharing)). The application id is `tech.rethunk.Mortar` (`Options.Linux.ApplicationID`: GtkApplication / Wayland `app_id` and X11 `StartupWMClass`). That id is not the single-instance D-Bus name (`tech.rethunk.mortar`); the Flatpak finish-args own `tech.rethunk.mortar.SingleInstance`. `Exec=` is `$APPIMAGE` when Mortar runs from that AppImage's mount (`$APPDIR`), since desktop files do not expand variables and the mount vanishes on exit; every start rewrites the entry when that path has changed, as it does when the user moves the AppImage, and, in a production build, writes it at startup when it is missing. A `mortar.desktop` whose `Exec` is this binary or another Mortar build is rewritten as `tech.rethunk.Mortar.desktop`, its mime defaults moved, then deleted. The Flatpak uses GNOME Platform/SDK 50.
