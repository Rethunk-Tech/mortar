# Mortar architecture

How Mortar works: storage, profile semantics, the game catalog and its registries, and the Stardew, Nexus and wire-format facts that settle questions. Decided work not yet built is in [design.md](design.md), screens in [gui-design.md](gui-design.md), standing rules in [AGENTS.md](../AGENTS.md), threat model and guards in [security.md](security.md). Behaviour the code and its tests already state is named here by owning symbol, not narrated.

## Product

Mortar finds a game, installs its mod loader, keeps each set of mods in its own profile, and launches the game with the chosen profile. Windows and Linux only (fleet CI has no macOS runners, and Wails does not cross-compile to it). Licence: AGPL-3.0-only. The signed catalog lists every game ([Games and the catalog](#games-and-the-catalog)); a game's `enabled` flag makes it selectable.

**External profile import** (Profiles › **Import…**) reads r2modman, Gale, Stardrop (Stardew Valley only), Vortex and Mod Organizer 2 from their default data (`packsvc.LocalProfiles`, `migrate.Detect`; Gale's `data.sqlite3` is read-only through pure-Go `modernc.org/sqlite`). Vortex and MO2 take the game's names from its catalog `importIds`; a game without them has neither. Present folders are copied into the store; missing Nexus mods go through the share-import resolver and download queue.

## Stack

- **Wails v3**, pinned in `go.mod` ([AGENTS.md](../AGENTS.md)). React, TypeScript, MUI and Lingui on Vite; typed bindings from `wails3 generate bindings` into `frontend/bindings`; client state in zustand.
- **Go services:** each backend area the UI calls is one Wails service whose exported methods are bound to TypeScript. Methods only Go calls carry a `//wails:ignore` doc directive, so the bindings expose only what the GUI calls.
- **Window:** solid and frameless with the app's own title bar unless `systemTitleBar` is on ([gui-design.md](gui-design.md#surfaces-and-colour)). Trap: dragging works only once the Wails runtime is loaded (`@wailsio/runtime` or `/wails/runtime.js`).
- **Session-only state:** the toast history and the Console's command history live in memory; a toast's Undo, Redo, Show or Retry works only while that change is still the latest for the same mods.

## Storage

Everything lives in the user data folder, `%LOCALAPPDATA%\Mortar` or `$XDG_DATA_HOME/mortar`, never under the Windows install folder (the uninstaller deletes that recursively). State is JSON written through a temp file and rename (`datadir.WriteFile`/`WriteJSON`/`WriteStream`); no database. The Nexus key is in the OS keyring.

- **Move** (Settings › Storage): copy to a chosen empty folder (not inside the current one, not while the game runs), verify, write `data-location` in the default folder, remove the old copy, restart. It never follows symlinked folders, junctions or mount points; free space is probed with a real clone or link because FAT, exFAT and SMB count every name (`datasvc.Measure`).
- **Portable mode:** a `portable` file beside the executable (symlinks resolved) puts data at `<exe dir>/data`, ignores `data-location` and refuses Move. The marker is ignored inside a Flatpak and an AppImage mount; one beside an executable in an unwritable folder stops the start with `datadir.PortableError`. A portable copy has its own single-instance id (hash of its data folder).
- **Missing data folder:** a `data-location` naming a missing folder (unplugged drive) is never created; on Windows a message box offers the default location, a folder picker or quit. Every startup failure is appended to `startup.log` in the default folder.

Layout (shapes: the named package):

- `store/`: each downloaded archive extracted once, content-addressed. `blobs/<sha256>/` holds the extracted files (identical content under different keys shares one blob; `.complete` marks a finished extract, written to a temp folder and renamed, and `mortar-root` names the subfolder that is the mod), `loaders/<game>/<loader>/<version>/` a loader's bundle, and `index.json` maps (game, key) to the blob and records the key's source, package and version, its last use, and so what the 30-day sweep may delete. Keys: `nexus-<mod id>-<file id>` (a Nexus file can hold several SMAPI mods, so the key is the file), `github-<owner>-<repo>-<tag>-<asset>-<hash>` (the hash separates names the folding makes equal), `pkg-<hash of name and version>` (Thunderstore), `local-<sha256 of the archive>`, `<loader id>-<version>` (SMAPI included), `bridge-<version>-<hash>`. `.manifests/<game>/<key>.json` and `verify.json` are integrity records ([Store integrity](#store-integrity)).
- `profiles/<game>/<profile id>/`: `profile.json` ([below](#profilejson)) and `mods/` (the folder SMAPI is pointed at). Each entry is copied to `mods/<store key>/`, or only its `mortar-root` subtree; further files from the same Nexus page join as `extraStoreKeys` under `mods/<entry key>/<extra store key>/`, and Update, Roll back and Remove cover every store item on the entry.
  - **Mod-folder picker:** an archive with a `manifest.json` SMAPI would not find, or one UniqueID in several folders, asks the user for the folder that is the mod; an update reuses the same-named variant.
  - **FOMOD** detection runs first (`fomod/ModuleConfig.xml` at the item root or one folder down). The resolved files are copied instead of the raw extraction and the chosen plugin names stored on the entry as `fomod`; Update and Roll back replay them (`internal/profile/fomod.go`) and ask again when a choice no longer exists or the update adds an unanswered group (`internal/fomod/resolve.go` `Unanswered`).
  - `runs/` holds the newest `runsKept` launches Mortar started; `saves/` is the profile's own Saves folder when `separateSaves` is on ([Saves](#saves)).
- `backups/<game>/`: zips of the Saves folder taken before mod updates, before Play, before a restore and on request, never listed or restored for another game. A save is a folder holding a file of its own name (Stardew Valley) or, when the catalog entry lists `saveFiles` patterns, matching files plus `saveCompanions` sharing their stem (`saveUserFolders`: inside each subfolder).
  - Rotation: each kind keeps `saveBackupsKept` on its own, so no kind evicts another's; `scheduled` zips rotate per save against `saveBackupKeep`. A whole-Saves zip (not `manual`, not `scheduled`) under ten minutes old stands in for a new one when the Saves folder is unchanged. A sibling `<stamp>.json` `{profile, kind}` records why; without one the zip shows as unknown.
- `downloads/<item id>.<ext>` with a `.resume.json` sidecar ([Download queue](#download-queue)); `<game>/last-played.json` (each save folder last launched with a profile, written when a run ends and SMAPI's log names the save it loaded); `tools/<game>.json` (`arguments` is a JSON array, never a shell string, launched through `os/exec` without a shell); `queue.json` holds no `nxm://` keys.

### Optional files

`internal/profile/overlay.go`, `overlayset.go`. A Nexus file with no `manifest.json` anywhere and no installer (Nexus "Optional" files that swap some files of the main one) is an overlay of the profile's entry from the same Nexus mod that holds a manifest: its own store item and `profile.json` entry with no mods and no folder, `overlayOf` naming the main entry's key. Without a main entry it is refused (`NoBaseError`).

- **Placement**, first match wins: a single top folder named like one of the main entry's mod folders; else the layout under which most of its files already exist in the main entry; else Mortar asks (`RemapAsk.overlay`). The answer is stored as `overlayFrom` and `overlayTo`.
- **Invariant:** optional files are laid over the main folder in entry order (later wins), each replaced file removed and the new name linked or cloned from the optional store item (`datadir.MaterializeFile`), so no store item is ever written. Switching one off (`overlayOff`) or removing it restores the main entry's own file for every path any optional file covered and deletes paths only optional files brought.
- **With the main entry:** removing it removes its optional files; updating or rolling it back takes them off first (so carry-over never sees them as user edits) and lays them over the new folder; rebuild, Restore, Revert and Undo lay them again. Optional files of one main entry replacing the same files (`OverlayFiles`) switch each other off in the same write. A profile export zip carries the main folder with them taken off and each optional store item under `overlays/<entry key>/`.

### `profile.json`

Fields and caps: `internal/profile` (`Profile`, `Entry`). Invalid `color` or `icon` are dropped on load, and a `description` key, which Mortar no longer writes, moves to the top of `notes`. Rules not obvious from the structs:

- `overrides` holds profile-overridable game prefs; `settings.ResolveAt` uses the profile value, else the key's own scope, else the registry default.
- `install` and `loader` name the game install and loader the profile runs (empty means the game's selected install and primary loader). `launchEnv` and `launchPrefix` apply to direct launches only.
- `groups` are named sets of entry keys that enable and disable together. A name is a `/` path (`Looks/Hats` lies inside `Looks`), so nesting is only in the name: a share's `grp`, a saved group and an older Mortar all see a plain group of that name, and a parent needs no group of its own. Switching, renaming or deleting a group acts on the groups inside it.
- `intentSince`, `intentOffered`: when Mortar began keeping install reasons and whether the player answered the one-time offer to classify older entries (a content pack stays explicit even when required: `InferImplicit`, `internal/profile/implicit.go`).

`entries[]`:

- `key` is the store item in use; for an entry cut from a folder game's archive `<item>#<path>` with `item` and `file`. Mods in an entry are components with `id` `<format>:<local>` (e.g. `smapi:Pathoschild.ContentPatcher`).
- `previousKey`/`previousSource`/`previousExtraStoreKeys` are the Roll back copy; on an updated archive's first entry `replaced` is the JSON of the entries it superseded.
- `implicit`: Mortar brought the entry in for another mod; absent means the player asked. Set at creation, copied by every path that copies an entry, changed only by Mark explicit/implicit; loader and bridge entries are always implicit. An entry with several mods shows one main mod with the entry's reason and the rest implicit; the main mod is the base the others build on (the one requiring no other mod of the entry that most require).

The store keeps every item a profile names as `key` or `previousKey` and deletes the rest 30 days after last use. `ProfilesWithMod` reads `profile.json` files, not the store.

**Hero cover** (`internal/profile/cover.go`): the picked cover, else the `picture` of the profile's Nexus entry with the highest stored `endorsementCount` (no new call), else Steam art at `/steam-art/<appid>` (`game.ArtMiddleware`); the frontend moves on when one fails.

## Settings file

`settings.json` has a `formatVersion` and three blocks: `global`, `sources` (per mod source id) and `games` (per game id). A key is read at the most specific scope that sets it (source, game, install, loader, profile), then broader ones, then its default (`internal/settings/scope.go`). A missing or unparseable file gives the defaults; an invalid value is replaced by the default on load and refused on write.

Each key's meaning, scope, type, default and allowed values are defined once, in code: field comments on `Settings` (`internal/settings/settings.go`) and the registry (`internal/settings/registry.go`). `mortar settings get` lists every key with its value.

**Export and import:** Settings › General › Settings file writes the fields in `portableFields` (`internal/settings/portable.go`); import (`internal/settings/import.go`) refuses any other version and applies only after a preview. Account and machine state (Nexus identity, game folders and stores, loaders, last played, dismissals, handler state, LAN settings, `backgroundImage`, `overlayToken`) is never exported; the keyring is never read.

**Clean-up** (Settings › Storage; `internal/datasvc`): **Clean up…** previews, then deletes exactly the listed items; its keep set is `datasvc.KeepSet`, the set the startup 30-day sweep also builds, and a store key a profile names after the preview is re-checked and kept.

### Store integrity

Installing an item records the SHA-256 and size of every file beside the store (`.manifests/<game>/<key>.json`), so hashes are never copied into a profile. `store.Verify` reports files missing, changed or extra. An item with no record is baselined by its first verification, which cannot see earlier damage.

- For a Nexus item with a sign-in, verification first looks in the downloads folder for an archive of that mod whose MD5 equals the one Nexus lists; a match is extracted as an install extracts it and becomes the baseline, so post-install damage is found. GitHub and local items have no such check (a local item's key is its archive's SHA-256, which Repair uses).
- The background pass `storecheck.Run` verifies items not checked in 7 days, one at a time, only while idle (no game, download or install), at a fraction of one core. `store/verify.json` keeps each verdict (`Damaged` feeds Problems).
- **Repair** of a damaged item sets it aside and re-obtains it from its recorded source (a local item from its archive if still in downloads; loader items by reinstalling the loader); the damaged copy is put back if the queue refuses.

## Profile operations

**Materialising store items into a profile** (install, duplicate, rebuild, update) is per file, in order, falling through on `EXDEV`/`EOPNOTSUPP`/`EINVAL`/`ERROR_INVALID_FUNCTION`: copy-on-write clone, hardlink, symlink, copy (`internal/datadir/materialize.go`). Files a mod may write (`config.json`, `data/` and saves-like folders, `*.mortar-old`, editor-openable text files) use clone or copy only: SMAPI's `helper.Data.WriteJsonFile` truncates in place, so a link would leak one profile's write into the store and every other profile. Drift ignores those paths. Deleting a profile unlinks its names and never removes store files.

Operations (each a method of `internal/profile` `Store` or a named service; the tests state the edge cases):

- **Toggle:** rename the folder holding the mod's `manifest.json` with a leading dot (SMAPI skips it) and record it in `disabled`; enabling a mod also enables its present-but-disabled required dependencies in the same write. Bulk operations are one `profile.json` write under the running-game lock.
- **Profile folder** (`folder.go`): `MoveToFolder` copies the profile elsewhere (possibly another drive) and replaces its usual folder with a symlink (a junction on Windows when symlinks are not allowed), so every path built from the profile id still resolves; `Profile.Folder` is read from that link and never written. Across drives hardlinks fall back to copies.
- **Duplicate** clones or copies `mods/` (never hardlink or symlink, so an in-place write cannot leak into the source). **Delete** moves to `trash/` for `trashRetentionDays`; `Purge` and `PurgeTrash` refuse a symlink.
- **Damaged profile:** an unreadable `profile.json` is listed by `ListDamaged` and skipped by `List` and `StoreKeys`, so one corrupt file does not stop collection. **Repair** (`mortar profile repair`) rebuilds it from the latest readable history snapshot, leaves `mods/`, and renames the broken file to `profile.json.damaged-<timestamp>`; refused with no snapshot.
- **Import and Move from the game's Mods folder** (`import.go`, `gamemods.go`): scans one level of `<game>/Mods` as SMAPI does, for a game whose loader has `loader.ManifestMods` (only SMAPI's; the Import tile, the new-folders callout, the Vortex and MO2 fallback folder and the folder watch exist for no other loader, and a folder game imports from its own mods folder instead), and enters each folder through the dropped-folder path; Import never writes the game folder. Trap: a symlink-deploying manager (Vortex) imports as the files the links point to (`datadir.CopyTreeResolvingLinks`), while the store otherwise refuses links that leave a folder. Move then deletes the folder by renaming it aside first (a file held open leaves it whole), matches by UniqueID case-insensitively, and is refused while any game process is up.
- **Dot-hidden mods:** a dot-prefixed folder inside an entry that Mortar did not add hides every mod under it from SMAPI; `showDotHiddenMods` lists them and `UnhideMod` strips the dots. **Extra mods folders** (`extraModsFolder`) are listed by the game's loader: SMAPI manifests for Stardew (the extra folder itself when its top holds `manifest.json`), and for a game the installer takes Thunderstore packages for (`installer.TakesPackages`) each folder holding a manifest or a DLL, or the extra folder itself when its top holds one (a build's output). `InstallExtraFolderMod` installs one through the dropped-folder path and never writes the folder; the entry's `Source.Folder` remembers the folder, so the next install from it replaces that entry even when the mod's id changed, and an unchanged folder adds nothing. Every game's extra folders are watched; on a change, or when a folder is added or given a profile, the window installs all of the folder's mods into its `extraModsProfiles` profile (none: the open profile). `autoInstallFolders` (0.3.9 to 0.3.13) is migrated on read into the last game's extra folders.
- **Outside edits** (`drift.go`): `mods-snapshot.json` is a cheap fingerprint of each entry folder, skipping what carry-over treats as user- or mod-written. On profile load and window refocus the live `mods/` tree is compared to it and to `profile.json`; a first scan with no snapshot records the tree and reports nothing.
- **Compare:** **Match versions** switches differing entries through `UpdateEntries` as one atomic change (a failure undoes every swap; one history event).
- **Saved groups and templates** (`internal/savedgroups`, `internal/templates/apply.go`): `Apply` copies missing store items in, in one history batch; template `entryKey`s are in the store keep set; `ApplyTemplate` never removes the profile's own mods, takes `profile.Store.Baseline` first and returns an `Undo`.
- **Back up and restore a file** (`internal/packsvc/backup.go`; `profile backup`/`profile restore`): one zip with `backup.json` (a content hash per carried store item), history, configs, cover, saves and, unless `--no-mods`, each mod's store item so the file restores offline. Restore makes a new profile via `UniqueName`, never overwriting, and takes a store item only when its hash matches.
- **Typed config editing** (`internal/configsvc`): a mod's config files are its SMAPI `config.json` and the `.cfg` files in `<profile>/BepInEx/config` whose file name or `## Plugin GUID:` header matches the mod id. A `.cfg` `Set` rewrites only that entry's line; `config.json` keeps key order, types and unknown fields and refuses a path that leaves the mod folder. Every write fails while the profile's game launches or runs.
- **Pin and skip:** a pinned entry is offered no update; `skipVersion` hides that exact newer version until a later one appears. Both drop out of the update count, Update review and Update all.
- **Update checks** (`internal/control/updates_apply.go`, `internal/profile/service_update.go`): SMAPI's API is asked 100 mods per request; for the mods it flags, Nexus GraphQL v2 gives their current file lists (signed in only). An update is real when a newer non-archived file with the same display name exists or the installed file's version is below SMAPI's; an unbumped manifest inside the newest file is not offered. Signed out or on failure the mod dataset's file list decides the same way.
- **Change history** (`internal/profile/history.go`): events in `history.json` capped by `historyEventsKept`, each with a gzipped snapshot of the entries (`snapshots/<sha256>.json.gz`) and the profile's settings; name, notes, colour, cover and profile order are not history. A `config.json` Mortar writes records a `config` event after one capturing the file as it was; Revert rolls configs back only when every event since the target is such an edit. Invariant: every profile mutation records an event and undoes exactly (`TestEveryProfileChangeRecordsAnEventAndUndoesExactly`). Export zips leave out history, snapshots and runs.
- **Update or roll back** an entry (`internal/profile/update.go`): the target version is copied into a fresh folder, then what the mod or user wrote is carried over by comparing three copies of each file (the profile's, the store's copy of the current version, the target): a file only the profile has is carried over; a file the profile changed is carried over when the target ships it unchanged, else the target wins and the profile's copy is kept as `<name>.mortar-old`. A manifest `DeleteOldVersion` (Stardrop's name) limits carry-over to user-written files such as `config.json`. A file the target no longer ships follows `oldFilesOnUpdate` (`delete`, `keep`, `ask`; `oldfiles.go`). The Saves folder is zipped into `backups/` first.

## Command line

Mortar is GUI-first: the CLI exposes only what the window can already do, and a new capability lands in the window first. Verbs: [HUMANS.md](../HUMANS.md#command-line).

- `mortar <verb>` (`internal/cli`) is decided in `main` before `application.New`, so it never takes the single-instance lock or opens a window; any other first argument, a link, a file path or `--play=<game>/<profile>` is a window launch. Under `--json` a failure is `{error, kind, code}` on stderr plus `detail` (typed fields of a `usererr.Detailer`) when the app sent one.
- **Play mode** (`--play=<game>/<profile> --steam-session`: an Add to Steam shortcut while Mortar is closed, Steam's Game Mode on the Deck): the window starts hidden and renders only the launch layer; Play takes the usual path with every pre-Play check, and a blocking check shows the window holding only that dialog. `main` quits once the played game has been Running and is Idle again, after purge and settings restore, so Steam counts playtime from Mortar's own process. If a Mortar already answers on the control channel, the start sends `play.request` over it and `shortcut.Follow` waits for the game.
- **Control channel** (`internal/control`; the CLI is a client of the running app): loopback on an OS-chosen port, with `control.json` (`port`, random `token`, `pid`, `version`, `protocol`; 0600) in the data folder, removed on exit only while still that instance's file. Methods run on the app's own services, so window and CLI never write the data folder at once. The CLI calls `hello` first and fails on a `controlwire.Protocol` mismatch; a start finding another Mortar answering `hello` waits five seconds for it to exit, then stops before it touches data. A server build refuses to start on the account's own data unless `MORTAR_SERVER_REAL_DATA=1` (`scripts/selftest.sh` sets a sandbox `HOME`); the desktop app opens no HTTP port.

## Trust boundaries

Everything from outside is untrusted: links, `.mortar` files, archives, API responses. [security.md](security.md) holds the guard and test for each input, including extraction and size caps, `nxm://` link validation and share payload caps.

## Failure behaviour

Once mods are installed, nothing external is needed to open, edit or launch a profile. Failures reaching the user are classified in `internal/usererr`. Go wraps the cause as `[kind] message`; the window (`errorMessage` in `frontend/src/toasts/report.ts`) and the CLI (`Sentence` in `internal/cli`) map the kind to the same English sentence, with the cause in a Details tooltip or under `--json`/`-v`.

- **A mod source unreachable:** `internal/netstate` records per source (smapi.io's update API included) whether its last real request hit a network error; a bad answer leaves state alone. A banner names each unreachable source and disables network actions needing one (`frontend/src/shell/OfflineBanner.tsx`, `OfflineGate.tsx`). Trap: SMAPI's API or the dataset unreachable degrades and never blocks: update checks show "unknown", dependencies are checked after download.
- **Archive formats** (`internal/archive`): zip, RAR, 7z, tar and gzip, xz, lzma, zstd, bzip2 streams, found by magic bytes, never extension (`archive.Extensions` is only what pickers, drop and the downloads watcher accept). A compressed stream whose payload has a `ustar` header is read as a tar; any other is one file named from the archive's name minus its suffix, queued as `<id>~~<original name>` (`archive.SavedName`) so the extracted file takes its real name. A classic `.lzma` stream has no magic, so it is recognised by its properties byte, dictionary size and length.
- **A download cut off or corrupt:** extraction goes to a temp folder on the store's volume and moves in only when every entry passed its checksum; failure deletes the temp folder and the item can be retried; **disk full** fails the same way and says how much space the item needs.
- **Mortar quits mid-operation:** every write is temp-then-rename and startup removes leftover temp folders; a `mods/` folder deleted outside Mortar is rebuilt from the store from `profile.json`. What startup repaired itself is collected by `internal/tidy` and shown as one info notification.

## Resource limits

Go's soft memory limit (`memlimit.go`; `GOMEMLIMIT` wins) is a collector target, not a cap: a lower limit costs far more GC CPU on large installs. The memory budget (`scripts/mem-budget.sh`) holds because the Thunderstore index is stream-decoded as it downloads, the picture cache keeps small thumbnails and a bounded profile hero, and the wallpaper is served at the window's pixel width. Installs run one at a time.

## Tests

Go tests run against local HTTP test servers replaying recorded Nexus, SMAPI API and dataset responses ([testing.md](testing.md)). Recordings are scrubbed before commit: `users/validate.json` returns the account's name and email, so fixtures carry placeholder account fields. Tests must set `XDG_DATA_HOME` (or `LOCALAPPDATA` on Windows) to a directory under `os.TempDir()`; `datadir.Dir` refuses any other location while `testing.Testing()` is true.

## Games and the catalog

Everything that can be data is catalog data; code exists only where behaviour differs, as a driver found through a registry. Adding to each registry: [HUMANS.md](../HUMANS.md#adding-a-game). Catalog entries are hand-curated; the exception is a game the player adds for themselves. Each registry below is a package under `internal/`; its driver list, capability interfaces and per-driver tests are in the package.

- **Catalog:** `internal/components` holds `GameInfo` entries in the signed component manifest (`GameInfo.Validate` guards the shape; `TestEveryCatalogReferenceResolves` checks every source, loader, metadata id, store field, path role and path token resolves). `game.Catalog()` returns the verified manifest's games when it lists any, else the bundled ones. Optional blocks an older Mortar ignores (so the v2 schema is unchanged): `graphics` and `knownBroken`.
- **Custom games** (`internal/customgame`, `components.SetUserGames`): Game select › **Add a game…** saves a name, the game's executable and one of five loaders (`customgame.BepInEx5`, `BepInEx6`, `MelonLoader`, `Shimloader`, `Folder`) in `custom-games.json`. Each becomes a `GameInfo` shaped like a shipped game of that loader (`ValidateUser`: `Validate` without the store rule), id `custom-<slug>`, answered after the signed catalog's and never shadowing it; the executable's folder is its install folder (`gameFolders`), so no store driver is involved. The entry is never uploaded or synced and adds no setting: every per-game setting applies as for a shipped game on the same loader (the registry reads the loader's capabilities, not the game id).
- **Stores** (`internal/gamestore`): one driver per store key in the catalog's `stores` (`steam`, `gog`, `lutris`, `bottles`, `ea`, `epic`, `xbox`, `standalone`, `flatpak`), run only for games naming its key. A native Linux build starts through `linuxStart`, else `linuxMarker`. A user-chosen folder wins over discovery (origin `folder`); a `manualFolder` game names no store and only has that folder. `GameInfo.MarkerDir` is the folder under the install root holding the marker (The Sims 4: `Game/Bin`).
- **Installs and runtime** (`internal/game/install.go`, `internal/runtime`): an install is a store and a folder with a stable id, a platform (an `.exe` marker is a Windows build) and a runtime:

  | Runtime | Claims | Path template resolves in | Start |
  | --- | --- | --- | --- |
  | `native` | native builds | the host's folders | direct |
  | `proton` | a Steam Windows build on Linux | its `compatdata` prefix | Steam |
  | `wine-prefix` | a Windows build in a Bottles bottle | the bottle's `drive_c/users/<user>` | `bottles-cli run` (through `flatpak run` for Flatpak Bottles) |
  | `launcher-prefix` | a Windows build in the prefix its own launcher (Heroic, Lutris) keeps | that prefix | `heroic://launch` or `lutris lutris:rungame/<slug>` when the plan needs only DLL overrides (Heroic also takes arguments), else direct |
  | `mortar-proton` | any other Windows build on Linux (chosen folder, EA, a Heroic or Lutris build whose prefix is unknown) | a prefix Mortar keeps per game, `<data>/prefixes/<game>/pfx` | `<proton>/proton waitforexitandrun <exe>` with `STEAM_COMPAT_DATA_PATH` and `STEAM_COMPAT_CLIENT_INSTALL_PATH`, as Heroic and Lutris start Proton outside Steam |

  `runtime.FindProton` picks the build; Flatpak Steam's builds need its runtime and are excluded. A plan's `dll-override` requirements reach the prefix as `WINEDLLOVERRIDES` for a direct start and as a `user.reg` edit (`wineoverride.Ensure`, from `launchsvc.ensureRuntime`) for a start a launcher relays, so the first start, before the prefix exists, loads them.
- **Sources** (`internal/source`): a driver registers itself (`source/all` imports them) and implements `Source` plus optional capabilities found by type assertion (`Searcher`, `Categorizer`, `Gated`, `Sorter`, `ItemLister`, ...). Drivers: Nexus, GitHub, Thunderstore, Modrinth, CurseForge, itch.io, Patreon, Vintage Story Mod DB ([games.md](games.md#vintage-story)), Paradox Mods. A `Gated` source says through `Unavailable()` what the user must set up first; an `all` search leaves it out.
- **Browse** (`internal/browse`): `all` sorted by downloads or update date is one ranked list across sources; a source that cannot sort that way is left out and named in `Unsorted`; best match interleaves each source's page, since scores do not compare across sites. Only all sources failing is an error. Hits of one mod from different sources fold into one card on package identity, an explicit link, or the same name by the same author (`mergeSame`; the catalog's `authors` aliases count one person's names on different sites as one). A name alone never merges: a hit sharing its name with a better-downloaded hit from another site by another author is marked `reuploadOf` instead. `Hold` (`installed.go`) matches a card to the open profile by each entry's source and the `UpdateKeys` of every installed manifest.
- **Thunderstore** (`internal/source/thunderstore`): search reads the community's chunked package index cached under `cache/thunderstore/` and revalidated by the index blob's hash. Deprecated packages are not searchable but still resolve as dependencies. `Closure` treats a pinned dependency version as a minimum and installs the newest, as r2modman does, unless a root of the request names an exact version or the per-game `dependencyVersions` (profile-overridable, `queue.Deps.ExactDependencies`) asks for the version the author pinned, as Gale does; managers a community lists as packages (r2modman, Gale) are programs and never install as dependencies.
- **Paradox Mods** (`internal/source/paradox`, queue direct path): a mod id is global across Paradox's games, so the driver serves only the games it names (`games`) and refuses another game's mod; the download address is built only from an opaque file name of letters, digits and dashes. The API publishes no digest, so the queue verifies nothing; the archive checks and the antivirus scan still apply. Cities: Skylines II has a `role` target (`pdx`, path role `pdxMods`) whose `sources` names `paradox`: the `source-target` installer runs before every other driver and lays the archive out whole below `paradox-<mod id>`, whatever the BepInEx rules would make of its DLLs. Like Tray files, the placed files are recorded per entry with their hashes, removed with it, and never replace a file nobody placed.
- **Gated sources** (`modrinth`, `curseforge`, `itch`) install through the queue's direct path (`queue.ResolveDirect`): the request and its required dependencies resolve first, each project once and at most 16 deep; a `sha512:` digest is verified after download. The queue holds each source to its own request pace and concurrency (`internal/queue/limit.go`).
  - **Modrinth:** a game's source `key` is a facet (`categories:fabric`; a bare word is a category).
  - **CurseForge:** Mortar's own API key goes in `x-api-key`, never in an address or log: `-X .../internal/source/curseforge.apiKey=...` at release build, else `MORTAR_CURSEFORGE_KEY`; with neither the source is `Gated`. A game's source `gameId` is CurseForge's game id and `key` its "Mods" class id. A file has no version number: its version is its display name and an update names the file by id. The `sha1:` digest is not verified because the lint bans weak hashes. When an author forbids distribution the driver never builds a CDN address: it fails with `NotDistributableError` and the queue opens the mod's page.
  - **itch.io:** the player's own key goes in `Authorization`, never in an address (an error quoting the address cannot leak it), and is kept in the OS keyring under `itch`; settings keep only the account name. The API has no sort and no total.
- **Handoff sources** (Patreon `internal/source/patreon`, itch.io page `internal/source/itch`): no search, download or update check; the player saves the file from the site and the Downloads watcher adds it (`archivesvc.InstallHandoffDownload`). Why: Patreon has no API for a post's files and its terms bar automated access; the itch.io page form covers a catalog entry `{"id": "itch"}` with no key. A share ref carries the id and no file.
- **Loaders** (`internal/loader`): a driver registers by id and implements `Loader` (`Status`, `Install`, `Contribute`) plus optional capabilities by type assertion. A launch is a `launchplan.Plan` the loader adds to; the profile's launch options, prefix and environment follow, and `game.Starter` runs it through the install's store: Steam through `steam -applaunch` (hands the start to the game and exits), every other store by running the game's executable. A direct Play can start more than one instance with the same profile environment, spaced by `delaySeconds`, and cancel between them.
  - **Pipeline** (`internal/launchsvc/pipeline.go`): one install runs one launch at a time (the preparing claim is the lock). Order: loader contributes; enabled packages are laid out in the profile (`SyncPackages`) when the profile holds the loader; the deployer places install-side files (journaled before the first file moves); profile game settings apply and the changed-launch save backup is taken; the profile's own Saves folder, options file and mod config folder (path role `modConfig`) are swapped in where asked ([Saves](#saves)); the runtime is prepared; the store starts the game. When the game exits or the start fails, placed files are purged, swaps undone, settings restored. `RecoverDeploys` finishes what a crash left at startup, skipping an install whose game still runs.
- **Installers** (`internal/installer`): an archive's shape picks a driver in `detectionOrder` (`fomod`, `thunderstore-rules`, `plain` last); every laid-out path is validated to stay inside its target and be storable on Windows. **Frameworks** (`internal/framework`): a driver keyed by a framework mod's id adds asset conflicts, hints, cleanup suggestions and redundancy findings to the profile's problems while an enabled mod matches; Content Patcher is the only one. **Hosts** (`internal/host`): `host.GitHub` fetches release assets (using the user's `gh` login when present; resumes), `host.Direct` any other HTTPS address.
- **Pack formats** (`internal/pack`): `Format` readers turn another manager's list into a `Draft` and write nothing; `packsvc.ExportModpack` and `packsvc.ExportR2z` write files their own readers read back as the same package set.
- **Known-broken lists** (`internal/components/knownbroken.go`): Mortar's own list per game of mods known not to work, kept apart from the catalog in `Rethunk-Tech/mortar-known-broken` (one `lists/<game>.json`; CI stamps a serial, minifies, signs it with the catalog's key and uploads it with its `.sig` to the rolling release `lists`). `KnownBrokenFor` fetches a game's list on first use (`components/signedlist.go`, shared with the log suppressions), verifies it, refuses a lower serial than the cached one and caches it a day (`known-broken-<game>.json`, dropped by Clean up after 30 days unused); no copy ships in the build. An entry names the mod by its id per site, flags versions up to `through` (a newer one is taken as fixed, an uncomparable one is not flagged), may limit itself to `gameVersions`, and is `broken`, `superseded` or `notRecommended`, with a reason and an optional package to use instead. It reaches Problems (rows with source "Mortar", and through them the Mods chip), Browse (`Broken`, or `Obsolete` for superseded, and Add asks first), share-code and game-mods import previews, the update review (`problems.withKnownBroken`: an update to a still-flagged version is a caution to accept, which Play's automatic update also holds back; one past a flagged installed version says so) and the patch-day sweep (`launchsvc.sweepKnownBroken`); the Problems cache key carries the list's serial.
- **Mod development** (`internal/devsvc`, the Develop tab in `frontend/src/develop/`): a loader entry's `devTemplate` names a GitHub template repo and tag (validated: each part starts with a letter or digit, no `..`). The template is a .NET template: `.template.config/template.json` (its `sourceName` is the mod's name; each other placeholder is a symbol whose `replaces` must be unique ignoring case and inside no other, which `ReadForm` refuses otherwise) and `.template.config/mortar.host.json`, which marks the parameters Mortar remembers per player, the ones it fills itself (`repositoryUrl`, `loaderPackVersion`: the loader's newest release) and a `pattern` or `maxLength` to check. Mortar downloads the tag's archive from codeload once into `cache/dev-templates/`, asks for the parameters in the template's order (`TemplateForm`), checks each value (required, pattern, length, choices, never a leading dash) and runs `dotnet new install` and `dotnet new <shortName>` in its own hive (`cache/dev-template-hive`), so nothing is installed for the player's own `dotnet new`. With GitHub chosen it first runs `gh repo create --template` and `gh repo clone`, then puts the generated files in the clone's place. The project then gets `.mortar/template.json` (template, tag, name and values, for filling a newer template the same way), `Config.Build.user.props` with `GameRootDir` at the resolved install, and a first commit; nothing is pushed. The build output `artifacts/bin/<Name>/debug` (an unpacked package: DLL, manifest, icon, README) becomes an extra mods folder bound to the development profile, created as "<Game> Development" when none is picked, and the project is kept in the game's `devProjects` with the template icon's hash. Build parses MSBuild's `file(line,col): error CODE: text` lines; Build on save watches `src/<Name>` (`dev:source`); Pack builds Release and `Validate` checks the newest zip against Thunderstore's manifest, icon and README rules, and says when the icon is still the template's; Release adds a CHANGELOG entry, commits it and tags `vX.Y.Z` on a clean tree; Test with 2 copies is `launchsvc.StartInstances`, a direct launch whose instance count holds for that launch only. Self-test servers take the template from `MORTAR_DEV_TEMPLATE_URL` (`server` build tag).

### Folder games

`internal/loader/folder`: a game with no mod loader names the loader `folder`, a `mods` path role (where the game reads mods, possibly outside the install) and a `mods` target whose root is a profile subfolder (`{profile}/Mods`).

- **Entries:** an added archive lays out below the target as packed and becomes one entry per laid-out file (key `<store item>#<slash path>` with `Entry.Item` and `Entry.File`), unless it lays out a file whose extension is in the target's `keepWhole` list: then one entry holds every file, keyed by the store item. Trap: everything reading the store (backups, listings, keep set, sizes) uses `Entry.StoreKey()`, never the key, so an archive counts once.
- **Replacement:** an install replaces an earlier archive only as its update (a Nexus or CurseForge file whose update names the old file id, `Source.WithReplacing`, or a GitHub asset of the same repository and shape); every entry of the superseded archive is replaced together, each keeping its on/off state, and the first new entry records them so Roll back restores all.
- **Shared-path files (Tray):** files whose extension a target lists in `extensions`, on a target whose `role` names a shared path (The Sims 4's `tray`), are placed at install in that folder, never swapped at launch, held by an entry of their own (`Entry.Tray`) recording each file and its SHA-256. A file of the player's own there is never replaced: the install is refused naming it, or an identical file is left and not claimed. Recorded files are released only while no entry of any profile of the game holds them and the file still has the recorded hash; update and roll back place new files before releasing old.
- **Catalog fields:** `caches` names rebuildable files below a path role; `requiredSettings` become Problems rows of kind `game-setting`. A mod with no source and no manifest is a `local` entry `folder:<store key>`; nothing updates it.
- **Launch:** the loader plans one file per file below the target with `launchplan.PlanFile.Root` `mods`; the deployer places them under `deploy.View.Roots["mods"]` with the same journal and crash recovery as install-side files, so the shared folder holds none of a profile's data after the launch. `SyncPackages` records each file it lays out with hash, size and time in `.mortar-packages.json` and never overwrites a copy changed since.
- **Install-side mods folder:** a `mods` path of `{install}` or below it needs no deployer of its own (`TestAModsFolderInsideTheInstallIsFilledAndPurgedWithTheInstallUnchanged`). With `{install}` itself an archive is laid out as packed from the install root, so the folder's top folders are what a profile owns for write-back, and Import from the game's Mods folder offers nothing (`profile.errModsFolderIsInstall`). Not covered: an archive packed without its folders (Cyberpunk's loose `.reds`), and Witcher 3's `mods.settings` load order.
- **Settings:** `gameSettingsMode` (`edit` or `warn`) decides whether Mortar writes the catalog's `requiredSettings` into the profile's own copy of the `options` file before a launch (`launchsvc.swapOptions`) or only reports them; `cacheClearing` deletes the catalog's `caches` once per change of the profile's mod set hash. `scripts/selftest.sh regress --game sims4` drives a stand-in Sims 4 install through two profiles and checks the player's files are identical afterwards.

### Deploy methods

`internal/deploy`, `GameInfo.Deploy`.

- **`redirect`:** the loader points the game at the profile's folder; nothing is placed (SMAPI's `--mods-path`).
- **`profile`:** the profile holds the loader and mods (the r2modman and Gale model): before a launch, and in the background right after a mod is removed or switched on or off (a launch waits for that run), `SyncPackages` copies each enabled package's files into the profile (a package's config file only seeds it) and removes files of packages no longer enabled; the deployer copies only the loader's install-side files into the install (BepInEx's Doorstop pair, its config pointing at the profile's absolute preloader path so a start that passes no Doorstop flags still loads the profile) as real files, never links (the game and its anti-cheat may write to them), journals every move first and restores what they displaced when the game exits. Packages are never linked into the install or the store, and a plan path leaving the install is refused.
- **Journal** (`deploy.go`, `oplog.go`; `crash_test.go` crashes after every step of Apply and Purge): `Apply` records every operation (destination, source, SHA-256, where a displaced file waits under `<journal>/displaced/<n>`) and persists `deploy.json` in `<data>/journal/<install id>` before the first file moves; later steps go to an append-only `deploy.log` that recovery replays over the record, ignoring a last line a crash cut short. `Apply` refuses with `ErrUnrecovered` while an earlier deploy's journal exists.
- **Purge invariants** (`deploy_test.go`, `writeback_test.go`): a displaced file goes back over its destination; with nothing displaced a destination is removed only while its hash is the recorded one, so a player's own file Mortar did not place is never deleted. A crash between any two steps leaves the bytes in the profile, the shared folder or both, never neither, and `Recover` finishes the same walk (nothing while the game runs).
- **Write-back** (`writeback_test.go`; the profile owns what a launch changes in files it placed, the shared folder is scratch): after the game exits, a changed file placed into a path role's folder is copied over the profile's copy before removal, and a file created during play inside a folder an entry owns is adopted (never through a link). The profile's copy is the only target, never a store item; a file at the role's root, in a folder no entry owns or in the saves folder is never adopted. When the profile's folder is gone bytes are never removed without a copy: a changed file over a displaced one is renamed `<name>.mortar-rescued` before the player's file returns. What cannot be adopted or was rescued is recorded in `<journal>.shared.json` and listed by profile health.
  - **A mod's BepInEx config** (`modconfigs.go`; files named for its plugin GUIDs or package name): switching the mod off moves it to `<profile>/config-aside/` and switching it on brings it back; removing the mod deletes it, so adding it again starts from its defaults.
  - **`changed/<path>` is the one rule** for update, roll back, uninstall and a switched-off package: a changed copy is moved under `<profile>/changed/`, never deleted, and comes back when an archive ships it again or the entry is reinstalled; backups carry it. In a `.mortar` payload it travels like config files (`Include.ConfigFiles`, `profile.WriteChangedFiles` on receive), and the payload reader refuses any path not a clean relative one inside the content folder or `changed/`.
- **Files an update drops:** a changed file whose entry was replaced by a version that no longer ships it follows `oldFilesOnUpdate`; one whose entry was switched off or removed is held under `changed/` whatever the setting (`.mortar-held.json` records when) and deleted at the next sync once held longer than `trashRetentionDays`. A dropped file nobody changed is removed in every mode.

### Loader notes

Each loader names a hidden companion mod (the SMAPI bridge, the BepInEx bridge) that lets Mortar query the running game ([Mortar SMAPI Bridge](#mortar-smapi-bridge)). Launch arguments and file routes per loader are in the driver (`internal/loader/*`, `internal/loader/thunderpack/specs.go`); the facts below are the ones it cannot say.

- **BepInEx 5** (`profile`): keeps core, plugins, patchers, config and log in the profile, where Doorstop's `--doorstop-target` points, and needs only the pack's Doorstop proxy (`winhttp.dll`, `version.dll` or `winmm.dll`, read from the pack) and `doorstop_config.ini` beside the executable. A native Linux build (an install holding `linuxMarker`) gets no files: it starts directly with the pack's `libdoorstop_x64.so` in `LD_PRELOAD`. Settings walked: `bepinex5Pin` is read through the loader service; `skipIntro` through the BepInEx bridge (`ArmIntroSkip`); the Console page and the stream overlay through the driver's log and `ArmOverlay`; `enableRequirements`, `missingRequirements` and `dependencyVersions` from the packages' Thunderstore dependencies; `extraModsFolder` takes packages and build output folders; `graphicsApi`, `gameSettingsMode` and `cacheClearing` where the game's catalog entry has their block; game-scoped pipeline settings apply as they are; `cosmeticConflicts`, `conflictScanDepth`, `showDotHiddenMods` and the SMAPI settings are not read (no asset index, no dot-folder rule).
- **Folder** (`internal/loader/folder`, built in): the game has no loader; its mods are files the deployer places in the folder the game reads for the length of a launch. Settings walked: no pin and no Loader page; `skipIntro` is not read (no companion mod); requirements are not read (loose files declare none); `extraModsFolder` takes loose mod folders; the Console page shows only where a log reader exists (`vslog` for Vintage Story); `cosmeticConflicts` and `conflictScanDepth` only where the game's mod formats index asset edits (`framework.IndexesAssets`); game-scoped pipeline settings apply as they are; the SMAPI and BepInEx settings are not read.
- **MelonLoader** (`profile`, `internal/loader/melonloader`): one catalog component shared by every MelonLoader game; the profile is MelonLoader's base folder and only `version.dll` is placed beside the executable. A game with no catalog `routes` runs MelonLoader 0.7's recursive layout; one that lists `routes` (r2modman's `melonloader` rules) takes the classic layout. Only Windows x64 builds are covered. `UserData/MelonPreferences.cfg` names no types, so an entry's type is read off its value (`internal/configsvc/melon.go`). Settings walked: `melonloaderPin` is read through the loader service; the game-scoped settings the pipeline applies to any loader apply as they are; `skipIntro` is not read (it needs a companion mod and MelonLoader has none); the SMAPI loader settings are not read.
- **ReturnOfModding, GDWeave, Lovely, Northstar, Rivet, Unity Mod Manager and Shimloader** (`profile`, `internal/loader/thunderpack`: one driver, a `Spec` per loader in `specs.go`, from r2modman's ecosystem schema): the loader is the game's Thunderstore package (the catalog loader's `package`), read from the game's community index like BepInEx's pack, so a mod's dependency on it is the loader's own. An update removes the previous release's placed files, replaces only the folders the release owns and seeds files the player may edit. Only a library or launcher that must sit beside the executable is placed for a launch, with `dll-override` `native,builtin` for each top-level library under Proton. Traps: Northstar's `NorthstarLauncher.exe` starts in place of the game (`Plan.OverrideExe`, a direct start), so a Steam install under Steam's own Proton is refused; Unity Mod Manager passes both the Doorstop 3 and the Doorstop 4 spelling of the target and switch, since each ignores the other's. None writes a log Mortar reads, so a launch is up when the game process is; only Thunderstore packages and Windows builds. Settings walked: each loader's pin (`returnofmoddingPin`, `gdweavePin`, `lovelyPin`, `northstarPin`, `rivetPin`, `ummPin`, `shimloaderPin`) is read through the loader service; game-scoped pipeline settings apply as they are; the console filters have no log to filter; `skipIntro` is not read (no companion mod); `graphicsApi`, `gameSettingsMode` and `cacheClearing` read catalog blocks these games lack; `nxmDefaultProfile` needs a Nexus source, which they lack; the SMAPI and BepInEx settings, `showDotHiddenMods` and `extraModsFolder` are for those loaders' folders.

## Stardew Valley

Primary sources: SMAPI's repository (technical docs, manifest and scanner models, unix launcher) and the Stardew Valley wiki's Modding pages.

### Finding the game

Steam app `413150`, through `libraryfolders.vdf`. A machine can hold several Steam accounts, so per-account files such as `localconfig.vdf` are read for the account marked `MostRecent` in `config/loginusers.vdf`. Native Steam is preferred over Flatpak Steam. Store identity comes from the game's catalog entry ([Components](#components)); locators are `internal/gamestore` drivers, one `*_test.go` per store. Facts the drivers do not say:

- **Flatpak Steam:** its sandbox cannot read Mortar's data folder until `flatpak override --user --filesystem=<data dir>:ro com.valvesoftware.Steam` (copy or Grant access).
- **EA App (Windows):** the catalog's `stores.ea.folder` below the `EA Games` and `Electronic Arts` folders and user-added folders; the EA App's own install data is never read. On Linux an EA game is found in a Bottles bottle or a Lutris entry.
- **Epic (Windows):** Play opens `com.epicgames.launcher://apps/<AppName>?action=launch&silent=true` (as r2modman and Gale do) so the launcher signs the game in; Mortar follows the game by its loader's log.
- **Xbox (Windows):** the package name from the catalog is validated and passed to PowerShell as an environment variable, never script text.
- **Heroic and Lutris (Linux):** Heroic's GOG and Epic (`epic-heroic`) installs and Lutris entries run in the prefix their launcher names (`launcher-prefix`; Heroic falls back to `mortar-proton`). Play hands off to the launcher (`heroic://launch`, `lutris lutris:rungame/<slug>`) when the plan needs only DLL overrides (Heroic also takes arguments), which Mortar writes into the prefix's `user.reg` first.

Lutris, GOG, Heroic and Minigalaxy launches start SMAPI directly with `--mods-path`. With several installs found the choice is `gameStores` in `settings.json`; a user-chosen folder in `gameFolders` wins.

**Reset game install** (Stardew settings): after confirm, deletes the validated install folder (SMAPI and leftover mods included); saves and profiles are kept. Refused while the game runs and when the path is the filesystem root or the user's home. Steam then opens `steam://validate/413150`; other stores toast that the game should be reinstalled. **Steam Deck:** Mortar installs in Desktop Mode; in Game Mode add it as a non-Steam game, and grant Flatpak Steam read access to Mortar's data folder.

### SMAPI

- **Pin and sweep:** `smapiPin` holds a SMAPI version Mortar installs instead of the latest (and stops offering updates for). A patch-day sweep (`lastSweepGameVersion`, and the loader's `lastSweepVersion`) checks every profile for mods smapi.io marks broken when the game or SMAPI version changes. A loader that reads no game version compares the install's Steam build instead (`game.InstallBuild`), and sweeps other loaders' profiles for missing dependencies alone.
- **Install and update:** the release installer runs unattended with `--install --no-prompt --game-path "<dir>"`; running it again updates, replacing the launcher and adding the bundled mods. Mortar installs SMAPI itself, without asking, when a profile is created, at startup while SMAPI is missing or broken, on first run and before Play when a game update replaced the launcher; only a newer release waits for the user (an update can break mods), as a banner ([GitHub releases](#github-releases)).
  - **Windows:** Mortar extracts the whole installer zip and runs the self-contained `SMAPI.Installer.exe` from the installer folder, as `install on Windows.bat` does (the batch file refuses a `%TEMP%` path).
- **Broken by a game update:** on Linux the installer renames `StardewValley` to `StardewValley-original` and puts its launcher in place, which a game update overwrites. Mortar checks at startup and before launch that `StardewValley-original` exists and `StardewValley` contains `StardewModdingAPI`; Play reinstalls SMAPI first when not. On Windows the launcher survives and an incompatible SMAPI reports itself in its log.
- **Bundled mods:** a profile's `mods/` replaces `Mods/`, so every profile gets SMAPI's Console Commands and Save Backup as a `smapi-<version>` store entry from the installer Mortar downloaded (`install.dat`, a zip holding `Mods/ConsoleCommands` and `Mods/SaveBackup`). A SMAPI update replaces that entry in every profile.
- **Profiles folder:** SMAPI takes `--mods-path <path>`, absolute or relative to the game folder. Its `SMAPI_MODS_PATH` variable works only when SMAPI starts directly (`steam -applaunch` cannot pass environment variables), so Mortar does not use it. Mortar never moves or writes the game folder's own `Mods`.
- **Scanning:** SMAPI recurses into subfolders until it finds a `manifest.json` and skips folders starting with a dot. Optional `UpdateCautionMessage` and `DeleteOldVersion` (Stardrop update hints) are read with the same case-insensitive key rules; **Update all** skips cautioned mods until the row is ticked.

#### Components

`components.source.json` names each loader or companion mod by game, kind, GitHub source, release asset pattern, version policy and optional accepted game-version range; its `games` section holds each game's identity and its `authors` section the people known by different names on different mod sites. `cmd/components` resolves releases, downloads the named assets and writes the signed `components.json`, embedded at `internal/components/components.json` for offline and first-run fallback. Process names and launch behaviour stay in Go.

- **Signature:** Ed25519 with the update key (`build/updater/public.key` is the embedded public half); the detached signature is published beside the manifest. Each signed manifest is its own immutable `components-v2-<serial>` release; `v2` is the manifest schema (released clients read any manifest whose fields they recognise, so a schema change takes a new prefix).
- **Client** (`internal/components`): finds the newest non-draft `components-v2-*` release through the GitHub releases API, fetches its manifest at startup, verifies before parsing, rejects a lower serial and falls back to the cached or bundled manifest. Source hosts are limited to `github.com` and `thunderstore.io`. Every asset is checked against its manifest SHA-256 before extraction.
- The bridge is installed hidden in every profile as a `bridge-<version>-<hash>` store entry with source kind `mortar`, replaced when the manifest version or hash changes ([gui-design.md](gui-design.md#mods-tab)).

#### Mortar SMAPI Bridge

Mortar has no access to SMAPI's stdin, so a small SMAPI mod (`Rethunk-Tech/mortar-smapi-bridge`, `UniqueID` `Rethunk.MortarSmapiBridge`, protocol in its README) accepts console commands on a loopback port.

- **Channel** (`internal/bridge`): the mod writes `mortar-smapi-bridge.json` (`{port, token}`, user-only) in its folder; Mortar reads it from the running profile and sends `<token>\n<command>\n`, so the token never leaves the user's own files. Commands run on the game's next tick and their output arrives in SMAPI's log. The BepInEx companion (`Rethunk.MortarBepInExBridge`) writes `mortar-bepinex-bridge.json` in the profile's `BepInEx/config`. Both bridges read `startup/skip-intro` in the profile folder (`loader.WriteIntroSkip`, set before each launch from the `skipIntro` setting).
- **Log sources:** the BepInEx bridge wraps Unity's log handler and starts each managed message with `⟦src=Type::Method;obj=<hierarchy path>⟧ ` (the first caller outside Unity's engine modules; a release Mono has no IL offsets, so the line's text with its numbers masked as `#` tells one method's calls apart); `launch.parseBepInEx` lifts it into `Entry.Source`/`Object` and `formatBepInEx` writes it back to run logs. An engine message (no tag) is keyed in the Console by `unity:<masked first line>` and the `Scene hierarchy path` its lines name (`frontend/src/console/logSource.ts`). Hidden sources are per game: the defaults from `Rethunk-Tech/mortar-log-suppressions` (a signed list per game, published and fetched like the known-broken lists through `components/signedlist.go`, cached as `log-suppressions-<game>.json`) less those the player showed again (`shownLogSources`), plus the player's own (`hiddenLogSources`), merged by `settings.HiddenLogSources` and `console/hiddenSources.ts`; the Console filters them, and before each launch `launchsvc.writeHiddenLogSources` writes the call sites to `startup/hidden-log-sources` (`method<TAB>masked text<TAB>object` lines), which the bridge drops before they reach the log. A list entry `mod:<Mod>` with masked `text` names a message by its log column instead (SMAPI's own notices, the game's GOG Galaxy errors): `launchsvc` hands those to `launch.SetHiddenMessages` at start-up and before each launch, and the log parser drops them with their continuation lines for every reader (Console, run logs, Problems).
- **Running state:** while a game Mortar started runs, `launchsvc` asks `status` periodically (`loader.RunningState`); each enabled package whose DLLs declare plugins gets a loaded or not-loaded badge. Trap: BepInEx keeps the newest version of a GUID and, between equal versions, the first file its folder walk meets (`Chainloader.cs`), which only the bridge's `location` tells, so the loaded plugin is the package whose laid-out file the bridge names.
- **Stream overlay** (UI: [gui-design.md](gui-design.md#settings)): Mortar writes the bundled OBS page to `<data>/overlay/index.html` and, at launch, the bridge mod's `config.json` (`OverlayEnabled`, `OverlayPort`, `OverlayToken`; 0600, atomic; a loader whose bridge keeps settings in the profile gets the same keys in `startup/overlay.json`, removed while the overlay is off). The page polls the bridge's `/state` with the token.

### Launch

Steam starts a profile with `steam -applaunch <appid> <args>` (Steam passes the arguments after the app ID to the game, keeping overlay, achievements and playtime; Flatpak Steam through `flatpak run com.valvesoftware.Steam`); GOG, Heroic and Minigalaxy start SMAPI directly. The pipeline is under [Games and the catalog](#games-and-the-catalog) (Loaders); the facts below are the ones the code cannot show.

- **Linux Steam:** `steam -applaunch 413150 --skip-terminal -- --mods-path <absolute path to the profile's mods/>`. SMAPI's launcher script reads its own flags only before `--` and forwards only what follows (unix launcher argument loop in Pathoschild/SMAPI), which is why SMAPI's docs say arguments do not work on Linux. `--skip-terminal` makes the script start SMAPI with `--no-terminal`; SMAPI still writes its log. Without `--` the path is ignored, and without `--skip-terminal` the launcher opens its console in an unreadably small `xterm`.
- **Windows Steam:** Steam starts `Stardew Valley.exe`, not SMAPI: SMAPI's installer swaps the launcher only on Linux and macOS. First run shows `"<game>\StardewModdingAPI.exe" %command%` to paste into Stardew's Steam launch options, and **Set it in Steam for me** writes `LaunchOptions` in the MostRecent account's `localconfig.vdf` while Steam is closed (Steam rewrites the file on exit; `internal/steam/localconfig.go`). Mortar then adds `--mods-path <path>` after the app ID: SMAPI finds its flags anywhere on its command line and ignores unknown ones. Without the SMAPI line Mortar starts `StardewModdingAPI.exe` itself (`game.steamSkipsLoader`) at the cost of the Steam overlay.
  - Mortar does not pass `--no-terminal` on Windows: `StardewModdingAPI.exe` is a console program, so Windows gives it a console window whatever the flags. A direct launch hides the window instead (`showSmapiConsole` off); the Console tab follows the log file either way.
- **Console input:** a process Mortar starts gets a stdin pipe it holds open until exit (`launch.startCmd`). SMAPI's console-command loop skips empty reads, so on `/dev/null` or `NUL` it spins a core for the whole session; on an open pipe it waits. Console tab commands go through the bridge mod, not stdin.
- **SMAPI startup markers:** SMAPI's `Console.ReadKey` throws when stdin is not a console, so the "game crashed last time" prompt (`smapi-internal/StardewModdingAPI.crash.marker`, written on every fatal crash) ends SMAPI before the game opens and the surviving marker fails every later launch. The SMAPI loader's `Prelaunch` removes that marker and the update marker before each profile launch; `ErrorLogs/SMAPI-crash.txt` is kept.
- **Launch options:** `--mods-path`, `--no-terminal` and `--skip-terminal` are refused in a profile's `launchOptions` since Mortar sets them; `launchPrefix` (Linux only) and `launchEnv` apply to Direct launches only, since Steam `-applaunch` receives neither; an unknown preset name refuses the launch before anything starts. Changing any of these never touches `mods/`, so a running game does not block it.
- **Without mods:** `steam -applaunch 413150` with no arguments, or the game's executable when started directly; no profile, no mods lock, no `lastPlayed` or run recorded. On Windows a Steam launch-options line holding SMAPI still starts SMAPI, so Mortar warns first (and never edits that file).
- **Before Play:** Play gathers missing required dependencies, unresolved non-cosmetic conflicts, pending updates, mods flagged broken or obsolete, a changed game version and the newest save's gap into one dialog; `skipPlayCheck` skips it. With `updateModsBeforePlayDefault` on, Play queues every installable, non-pinned update first, records a history restore point and rolls back entries whose update fails. Before a non-vanilla launch with a history event after the newest stored run, the Saves folder is zipped into `backups/` (kind `update`); a failed zip does not block Play.
- **Success or failure:** `steam -applaunch` returns at once, so a launch counts as started when `SMAPI-latest.txt` is rewritten within 60 s, else failed with a hint; a Steam launch's `steam` exit 0 is ignored, a non-zero exit fails at once. A `StardewModdingAPI` process whose `--mods-path` is a profile's folder means that profile is in use and locked against changes.
- **Whose log:** the game has one `SMAPI-latest.txt` for every profile, so the Console and Share log show a log only in the profile that wrote it: the session Mortar launched belongs to its profile; the file on disk belongs to the profile whose mods folder matches SMAPI's `Mods go here: <path>` line (SMAPI writes the home folder as `~`); a log without that line (a launch outside Mortar) belongs to none. A BepInEx log is inside the profile and necessarily that profile's. A run's stored Summary (`internal/launch/summary.go`) is `crashed` when a Unity player log written since the run began holds `Crash!!!` or `Fatal error` and the loader reported no crash itself.
- **Likely cause:** `launchsvc.CrashHint` explains the latest `crashed` run; the first hit wins: the run's recorded cause; the loader's log analyzers; a .NET stack blame (`dotnetstack.Blames`; two equal matches blame neither); a crash dump or the Windows Application event log (`internal/crashdump`), blaming a mod only when the faulting module is its `EntryDll` or a same-named file within three folders of its folder.
- **Bisect** (**Find the cause…**, offered when the crash names no mods; `internal/bisect`): halves enabled mods (keeping required dependencies) on a scratch profile (`profile.ScratchCopy`, removed when the check ends and, after a crash, at the next start). A step fails only when SMAPI logs an alert or the run ends crashed; plain errors such as a skipped mod do not count, or the bisect would blame whichever mod logs one.
- Trap: launching through Steam makes Steam Cloud download the user's saves, and SMAPI's Save Backup mod zips them into `save-backups/` in the game folder.

### Startup timings

The bridge measures each mod's share of startup and writes `<profile>/startup/<process start UTC>.json` (schema in the bridge README); times are exclusive. The report's `replaces` lists, per Harmony ID, the game methods a mod can replace outright, which Problems adds to each C# mod's footprint ([Same job](#same-job)). Before each launch Mortar adds the bridge's UniqueID to `ModsToLoadEarly` in `<profile>/mods/SMAPI-config.json`. UI: Performance › Startup ([gui-design.md](gui-design.md#performance-tab)).

- **Measured launch:** **Measure next launch** writes `<profile>/startup/.measure-next-launch`; the next launch removes it and sets `StartupProfile: true` in the bridge's `config.json`, so the bridge also times every other mod's Entry (from SMAPI's per-mod `SetApi` call, never by patching a mod's method), event handlers, asset edits and loads, and samples stacks through an EventPipe session. Sampling failures do not fail the launch.
- **BepInEx:** only a measured launch is timed (the marker becomes `.measure-launch` holding the catalog game's `titleScene`): `LogOutput.log` has no timestamps and is flushed on a timer, so the bridge's preloader patcher adds its own log listener before the chainloader runs. Unity's Mono has no diagnostics port, so there is no stack sampling; the patcher wraps Harmony's `Patch` entry points and the bridge times each plugin's patch methods and Update loops instead (`launchsvc.MeasureInGame`, `perf_bridge.go`).

### Antivirus scan

- **Where:** `Store.install` calls `checkExtracted` (`internal/store/scan.go`) on the extracted folder before the rename that makes it an item, so every path into the store passes it (archive, hashed dir, LAN receive, backup, profile import). Loader bundles are Mortar's own downloads and are skipped.
- **Scanners** (`internal/avscan`): Windows AMSI (names no threat), clamd over a unix socket (`antivirusSocket`, else the distributions' default sockets), a custom command (no shell; `{path}` replaced by the folder; exit 0 clean, any other code a detection named by the first stdout line), or off (`antivirus`). Socket and command are not portable settings.
- **Detection:** the install fails with `store.DetectedError` under `usererr.Malware` and the extracted files are deleted; the queue item fails with `errorKind` `malware`, the detection carried as typed `detail` fields (`usererr.Marshal`; read by `detectionOf` in `frontend/src/toasts/avOverride.ts`, no error-text parsing). **Install anyway** calls `profile.Service.AllowUnscanned` (the next install of that key skips the scan once) and records a `ChangeUnscanned` history event; CLI `--allow-unscanned`.
- **Errors:** a scan that fails or times out is not a detection: the mod installs and an `avscan:failed` event says so. A file Windows blocks or deletes while Mortar writes it (`ERROR_VIRUS_INFECTED`/`ERROR_VIRUS_DELETED`) reaches the same place through `store.RealTimeBlock` with `Removed` set, so there is no Install anyway.

### Saves

Saves live in one folder, `%APPDATA%\StardewValley\Saves` or `~/.config/StardewValley/Saves`, which Steam Cloud syncs, so Mortar never moves it; profiles share saves unless one sets `separateSaves`.

- **Per-profile saves** (`internal/savesiso`): a `separateSaves` profile plays on `<profile>/saves` for the length of a launch with mods. `Apply` persists a `Manifest` before the shared folder moves, renames the shared folder to `<Saves>.mortar-shared` (a rename, never a copy) and points the save path at the profile's folder with a symlink, or a working copy (`Live`) where symlinks are refused. `Purge` undoes it, checking the disk at every step so it can run again after a crash; an incomplete copy is never written back. `Apply` refuses with `ErrUnrecovered` while an earlier swap's record exists; `RecoverDeploys` finishes a crashed one. The same package swaps a single file (the game's options file) and a mod config folder.
- **Where mods leave traces:** SMAPI writes no mod list into a save, but mods leave keys prefixed with their `UniqueID` (`smapi/mod-data/<uniqueid>/<key>`, `modData` keys such as `Sonozuki.MoreGrass/GrassOffsetX0`). Mortar scans the save's `key`/`string` XML entries and takes for each key the longest prefix ending at a `/`, `_` or `.` boundary that is a `UniqueID` in the mod dataset's index, ignoring case. Splitting at the first `_` would be wrong: many IDs contain `_`. Mods that keep no per-save data leave no trace and keys outlive a removed mod, so the warning says "this save has used".
- **Backups** (`internal/backup`, `internal/savessvc`; kinds and rotation: [Storage](#storage)): Restore first zips the current Saves folder (kind `restore`), extracts beside Saves and swaps each save folder in by rename, so a failure leaves the old one; it is refused while the game is launching or running. `RunScheduledBackups` waits while a game runs (including one Mortar did not start) and zips each save changed since its own newest scheduled zip.
- **Per-save gap:** `savessvc.SaveGap` compares the mods the save was last played with (`last-played.json`) against the profile (`missing`, `disabled`, `versionOlder`); a save with no record has no gap. Each lacking mod is located as Problems locates a missing dependency (`problems.Locate`). UI: [gui-design.md](gui-design.md#main-screen).

### Mod data

- **Mod dataset:** SMAPI's `Pathoschild/StardewModDataset` (MIT or CC-BY-SA 4.0, published with explicit permission from the sites it lists) records each Nexus mod page's current files with the SMAPI manifests inside, not every file. A file it lacks is checked after download.
- **Update checks:** `POST https://smapi.io/api/v4.0.0/mods` returns `suggestedUpdate`, taken as given; `compatibilityStatus` and `brokeIn` come only with `includeExtendedMetadata: true`. Unofficial versions show as **Unofficial update available** and **Update all** never installs them. The API is public, unauthenticated and officially unreleased: answers are cached in one cache shared by every profile, misses go in batches of 100, and after a failed ask Mortar serves stale or unknown answers for a while; failures never block.
- **Dependencies:** `Dependencies[]` (`IsRequired` defaults to true) plus `ContentPackFor` as a required dependency on its framework mod. For a missing one Mortar prefers the Nexus page named in its own `UpdateKeys`, else the page whose files hold it at the highest version (one ID can appear on several pages), and takes the newest `MAIN` file satisfying `MinimumVersion`; one found only on CurseForge is listed with its page link, one on no site Mortar has a driver for by name only.
- **Support:** Share log uploads the SMAPI log to smapi.io (`internal/logshare`, `POST https://smapi.io/log`, no auth). Trap: the server answers a success with a redirect to `/log/<id>` and a failed or empty upload with HTTP 200 and its page, so only a redirect counts as success. A SMAPI log holds local paths including the user's name and anyone with the link can read it, so Mortar shows the log and asks first. Only a loader with the `loader.LogShare` capability (SMAPI) offers it (`support.CanShare`). **Save diagnostics** writes a zip with a `manifest.txt` saying what is in and stripped; redaction: [security.md](security.md#local-state-and-secrets).

### Problems

Problems warn and never block. The checks are in `internal/problems` (one file per family, each with a `_test.go`). Rules that are not obvious from the code:

- **Minimum game version:** compared against the loader's game version or, where it knows none, the version the game's last run logged (Vintage Story's `Game Version: v…` line).
- **Broken, obsolete, abandoned:** from SMAPI's API for the game version, with a one-click replacement when its `compatibilitySummary` names a Nexus or GitHub target Mortar can install. A mod whose replacement is enabled too is **superseded** and loses its Broken and Compatibility rows. Abandoned is info-level and dismissible per profile.
- **Source flags** (`source_flags.go`): `Broken` rows naming the site: Nexus pages whose cached status is not `published` (read from the page cache, never fetched) and, through `source.StandingChecker`, archived, inactive, deleted or unavailable projects on Modrinth, CurseForge and GitHub (a bounded number per pass, stopping on a rate limit), each answer cached a day. Thunderstore deprecations are `DeprecatedPackage` rows with **Replace with** the package the deprecated one's own summary names.
- **Known broken** (`known_broken.go`): the game's `knownBroken` list, matched by mod id or Thunderstore "Namespace-Name" and version range. **Redundant:** shadowed content packs and [Same job](#same-job); a mod is listed once. `PluginClash` (`pluginclash.go`): a `[BepInPlugin]` GUID declared by more than one enabled package (read from compiled plugins through `internal/dotnet`; BepInEx loads only one), with **Keep newer**.
- **Paths too long** (`longpath.go`, Windows builds only): an entry with a file the game would read at a full path of 260 UTF-16 characters or more (MAX_PATH counts the NUL; `LongPathsEnabled` is not read, since it lifts the limit only for `longPathAware` programs). Mortar's own file calls take long paths, so nothing fails while copying; Wine opens such a path, so Linux never checks. The walk is slow, so it starts after the rest of the check and is kept per mods fingerprint: the window's loads (`ProblemsNoWait`) answer without it and `problems:changed` brings the rows; `Problems` (the pre-Play check, the CLI, background badges) waits for it.
- **Nexus-listed requirements** come from batched page data (`nexussvc.Prime`). The game's loader is never reported; any other outside download is a note with only Dismiss. Trap: Nexus lists a page-wide outside requirement for every file of the page, sub-packs included, so it is only Optional for a file whose own manifest declares dependencies and names none like it.
- **Content Patcher config suggestions** (`internal/framework/contentpatcher/settings.go`): an on/off `ConfigSchema` field whose value runs none of the pack's `HasMod` compatibility patches is suggested with the values that would; fields that list NPCs are never suggested. **Set to** writes only that field into `config.json` and remembers the field and value so the reverse suggestion stays hidden until the value changes.

#### Content Patcher conflicts

Rules: `internal/framework/contentpatcher` (`contentpatcher.go`, `winner.go`, `conflict_evidence.go`). The invariants:

- **What counts:** two or more enabled packs that `Load` the same target (warning: only one wins; a Load without `Priority` is `Exclusive`), or that `EditImage`/`EditMap` the same target or `EditData` the same entry or field (info, dismissible per profile). `EditData` that only shares a target is not reported. Overlap is never reported between packs built to work together (one entry, or one names the other as a manifest dependency or in a `HasMod` condition).
- **Only edits that can both apply count:** a `HasMod` condition counts only when it holds for the enabled mods; a change whose config conditions do not match the pack's current settings (`config.json`, else schema `Default`) is not counted; edits needing different spouses, or disjoint literal `LocationName`, `LocationContext`, `Season`, `Weather`, `DayOfWeek` or `FarmType` values, never apply together. Image edits conflict only where an opaque 16x16 source cell lands; JSON equality is by parsed value.
- **Cosmetic or harmless:** a conflict whose every overlap is harmless (both image edits, both text edits, a literal `LocationName`/`LocationContext`/`Weather` gate, a one- or two-tile area) shows under **Cosmetic or harmless** and is never counted.
- **Conflict winner:** "Make <mod> win" records the loser's UniqueID in the winner entry's `loadAfter` and adds it to the winner's installed `manifest.json` as an optional dependency, so SMAPI loads the winner later; the profile's `manifest.json` is its own copy, so the store is untouched, and the dependency is rewritten after an update. Load-against-Load conflicts still need one mod disabled.

#### Same job

Redundant lists enabled C# mods that change the same game members (`internal/dotnet`, `contentpatcher/footprint.go`, `internal/problems/samejob.go`; thresholds: the `sameJob*` constants). A mod's footprint is the `StardewValley` properties and fields its `EntryDll` assigns, read from the compiled IL, plus its Harmony-replaced methods from the startup report; input-only members are dropped. 

Members are weighted ln(N/df); a pair is flagged when the shared weight is a large share of the larger mod's total and some shared member is written by few mods, unless one depends on the other, they share an author or download, or another enabled mod depends on either. A smaller mod is also listed as covered by a larger one under a stricter share and the same rarity guard (large mods otherwise cover one-member mods incidentally).

#### Asset map

Every asset an enabled mod changes (`contentpatcher/assetmap.go`, `internal/problems/assetmap.go`) with each mod's Action and Priority and the winner; mods are ranked in SMAPI load order (`internal/loadorder`), not profile order. Trap: for Loads the last loaded wins on a tie although the Content Patcher docs say "first" (`PatchManager.ApplyPatchesToAsset` replaces its pick with every later candidate that is not strictly lower); two Exclusive loads apply neither. A losing mod offers **Make win** only when it ties the winner's priority and no other mod in the group already loads after it through its dependencies.

#### Generic Mod Config Menu

Menus a mod registers with GMCM or GMCM Options come from mortar-smapi-bridge, which runs inside the game: it writes each menu to `<profile>/gmcm/<UniqueID>.json`. Edits made through `mortar mods menu` wait in `<profile>/gmcm-pending/<UniqueID>.json` until the next launch, when the bridge applies them through the setters registered with GMCM and writes `<UniqueID>.result.json`. Widgets the bridge cannot set (colour, image, custom drawing) are read-only. `Store.SetGmcmOption` (`internal/profile/gmcm.go`) checks a change against the capture and records a history event; the pending files are part of the config capture history keeps, so Undo puts them back.

#### Other per-entry settings

- **Update channel:** an entry's `updateChannel` is empty (main files only), `optional` (also newer OPTIONAL files on the same Nexus page) or `beta` (also prerelease versions); it filters offers where pins and skipped versions do. GitHub reads `beta` as prereleases (`github.Select`); CurseForge and Modrinth read the three as release, release and beta, and release, beta and alpha files (`source.Stability`).
- **Config presets:** a mod's `config.json` can be saved by name under `<data>/config-presets/<game>/<local id>/<name>.json` and applied to any profile's copy as one history event. After each problem check the counts are appended to `health.json` beside `profile.json`.

## Nexus Mods

Client `internal/nexus` (REST v1, GraphQL v2), service `internal/nexussvc`; endpoint shapes and caching are in their tests. Registration with Nexus: [nexus-application.md](nexus-application.md).

- **Sign-in:** Settings takes a personal API key, kept in the OS keyring and never sent to a server of ours. `GET /v1/users/validate.json` gives the account's `user_id` and `is_premium`. Every request carries a truthful `Application-Name` and `Application-Version`.
- **Browser sign-in:** build flags pick the flow: `-X github.com/Rethunk-Tech/mortar/internal/nexussso.ClientID=<id>` selects OAuth PKCE (wins over a slug), only `-X .../internal/nexussso.Slug=<slug>` selects legacy SSO, neither hides sign-in. OAuth uses one fixed loopback redirect (`nexussso.RedirectURI`; Nexus registers a non-dynamic callback, so a taken port fails the sign-in); tokens live in the keyring as `nexus-oauth` and a pasted key is refused. The API-key path is isolated in `internal/nexussvc/apikey.go`, `internal/nexus/auth.go` and the key box, each marked "Remove with the API-key path once OAuth ships".
- **Browse:** search uses the public v2 GraphQL endpoint, which needs no key. Trap: a category list is an AND in Nexus's filter, so included categories become one OR branch each, every branch also excluding the excluded ones; category names come from the game's category list, which Nexus serves only to a signed-in account. GitHub search is `search/repositories` with the game's topics (`topic:stardew-valley-mod`; Lethal Company `lethal-company-mod` and the catalog's further topics), one search per topic merged by the chosen sort. Each page comes from the most favourable way open: the cache; GraphQL when the user's `gh` login lends a token (every topic and the owner word as aliases of one request, a hundred rows each, only the fields a card reads, every covered page cached); the REST search; and while REST refuses, github.com's own search page (`Accept: application/json`, ten rows a page). Each way waits out its own refusal (Retry-After, else `X-Ratelimit-Reset`, else a minute) without asking again, and the search page is read one request at a time, half a second apart, under Mortar's own User-Agent.
- **Downloads need the user** ([AGENTS.md](../AGENTS.md)): update checks (including the background check, which only notifies) are allowed, but a Nexus file is never downloaded or installed without a user action, and a queue restored from a previous session is held paused at startup when it holds a Nexus file. A Nexus collection link previews and imports like a share link.
- **Update path:** a Nexus mod's update comes from SMAPI's API through the mod's `UpdateKeys` (`Nexus:<id>`) ([Update checks](#mod-data)), and the Nexus file lists then decide the file. Trap: Mortar never searches Nexus once per installed mod (`problems` skips `nexus` and `github` sources in its per-source update search): that would spend hundreds of the hourly quota to repeat SMAPI's answer. Page data for many mods is one GraphQL `legacyModsByDomain` request per 50 mods (`nexus.Client.ModsByDomain`), cached by `nexussvc.PrimeDetails` (`Partial`: no file list, changelog or description until `Details` replaces it).
- **Manual downloads:** per-game `offerNewDownloads` offers new archives landing in the Downloads folders, one toast per batch; nothing installs on its own (`internal/dlwatch`). A Nexus file name `<name>-<modId>-<version>-<timestamp>.<ext>` supplies the mod id, otherwise `dlwatch.Identify` peeks `manifest.json` in a zip.
- **Mod page details** (`nexussvc.Details`): cached in `cache/nexus/`, never in `profile.json`; signed out, rate-limited or offline, the cached copy is served however old. `available` false marks **Hidden on Nexus**, `status` other than `published` **Removed from Nexus**; those pages are not offered as updates.
- **Files:** an update takes the `MAIN` file matching SMAPI's `suggestedUpdate`, else the `is_primary` one, and never an `OPTIONAL` file unless the profile already uses it. A file whose GraphQL v2 `scannedV2` is `QUARANTINED` is omitted, and a request for it fails the queue item.
- **Download links:** premium accounts get links directly; they expire, so Mortar asks just before downloading and again on a restart. A free account gets HTTP 403 and needs the `key` and `expires` from the `nxm://` link of the site's Mod Manager Download, one click per mod. Settings › Downloads **Preferred download server** picks among the CDN mirrors an answer lists. Endorse and track happen only on the user's click.

### `nxm://` links

`nxm://<domain>/mods/<mod id>/files/<file id>?key=<key>&expires=<unix>&user_id=<id>`; Mortar takes this form only for a Nexus domain a catalog game maps to, unexpired and for the signed-in account's `user_id` (`internal/nxm/link.go` `Parse`; guards: [security.md](security.md#network-and-links)). A link Mortar was not waiting for asks which profile it is for before anything downloads.

- **Registration:** only one app can own the scheme, and Wails' NSIS macro would delete and rewrite its key at install time without asking (`build/windows/nsis/wails_tools.nsh`), taking it from Vortex or Mod Organizer 2. So `nxm` is not in `build/config.yml`: Mortar registers it at runtime after the user agrees, records the previous handler in `settings.json` (`nxmPreviousHandlers`) and restores it when turned off or when uninstall runs `mortar.exe --release-links`. Other games' links can be forwarded to the recorded handler (`internal/nxm/forward.go`).
- **Bursts:** each `nxm://` launch is a second instance whose arguments the running one queues at once and handles in order; a link that arrives again before its own `expires` is taken once (in memory only).
- **Browser limit:** Chromium browsers launch at most one external protocol per user gesture, so Nexus Slow Download countdowns that end with no click in between are blocked.

### Browser extension host

The extension lives in its own repo (Rethunk-Tech/mortar-browser-extension; UI in [gui-design.md](gui-design.md#browser-extension)). It avoids the gesture gate: on `www.nexusmods.com` it reads each `nxm://` anchor and sends it with `sendNativeMessage` to the host `tech.rethunk.mortar`, which is Mortar itself (`internal/nativehost`). That process starts `mortar <link>`, so the link takes the same second-instance path.

- **Protocol:** every extension message and reply carries `protocol`; Mortar answers `MinProtocol`..`MaxProtocol` and records a refusal in `extension-contact.json` as `mismatch`. A change to a message's shape bumps both sides (shapes: `internal/nativehost/nativehost.go`); refusal rules: [security.md](security.md#network-and-links).
- **Data requests** are read-only and start no download: `installed` and `mod` answer from the last-open profile of the game the Nexus domain maps to. Every reply carries `games` so the extension maps a page's key to the Mortar game id and opens `mortar://<game id>/mod/<id>`. The extension follows the Download link of Nexus's requirements dialog only when it points at the page's own mod, because Mortar resolves requirements itself.
- **Project requests** (`installedProjects` for CurseForge and Mod DB pages, `installProject` for Paradox and Modrinth): the extension hands CurseForge `curseforge://install` and Mod DB `vintagestorymodinstall://` clicks over as `link`, which `source.IsLink` accepts like `nxm://`.
- **Host manifest:** on Linux, turning nxm handling on (and every start while on) writes the host manifest into each installed browser's `NativeMessagingHosts/` folder; turning it off removes them (`internal/nxm/nativehost_linux.go`). A Flatpak build writes none.

### Download queue

An import or a profile's missing files run one queue (`internal/queue`), persisted in `<datadir>/queue.json` without `nxm://` keys. **No re-hosting:** mod files and Nexus data stay on the user's machine; a share link holds IDs only. Rules a change must keep:

- Items store as `nexus-<mod id>-<file id>`; the entry records source kind `nexus` with mod id, file id, version, picture URL and endorsement count, fetched once at install. Source kinds (`profile.Kind*`) include `smapi` and `mortar` for bundled entries; a `github` source holds `repo`, `tag`, `asset` (share links read them as `<owner>/<repo>@<tag>/<asset>`).
- **`latest`:** installs started from a save's missing mods, a missing dependency or a Problems fix follow Nexus `file_updates` to the newest listed file, because the file they name came from the dataset or a save and may be old. Share imports leave it off to reproduce the shared files.
- **Which file an update downloads** (`nexus.Supersedes`, `internal/nexus/choose.go`): a page can hold several downloads (a main file and optional packs) and its version is the main file's, so the page's version never decides. In order: the author's `file_updates` chain; a newer file of the same download (display name or archive stem); the one current file of the entry's category at the new version; for a MAIN entry on a page with exactly one current MAIN file, that file. When the installed file is the newest of its download the mod has no update, however high the page's number; when none supersedes it but a current file of another download exists the update is marked `pickFile` and nothing queues it.
- **Update to CurseForge:** a mod whose newest version SMAPI reports from a `CurseForge:<id>` update key is resolved through the CurseForge driver (`problems.curseforgeSwitches`): the newest stable file becomes an update of source `curseforge`, marked `switch` with `fromSource` when installed elsewhere; a project that forbids downloads outside CurseForge shows as `notDistributable`.
- A free account's head item waits for its click (**Open download page**, **Skip**) and a matching `nxm://` link is routed to it. A Nexus file the game's store already holds installs from the store with no download and no click, unless the profile has an entry from the same mod page, whose Install together choice needs the archive. A reached rate limit, Nexus's or GitHub's, pauses the whole queue until its reset.
- **Large downloads and free space** (`internal/queue/size.go`): just before the first byte, `guardSize` takes the size the source gave up front. The archive (less any partial already on disk) plus twice its size for extraction plus a margin must fit on the downloads folder's volume and on the data folder's (one sum when the downloads folder is inside it), or the item fails with `NoSpaceError` (`errorKind` `disk`) with no way to override. A download over `LargeDownloadBytes` parks in `StateConfirmLarge` until `ConfirmLarge` (sets `largeOk`, which survives a restart) or `Cancel`. An item with no size up front skips both checks and keeps the after-the-fact `DiskFullError`. The Nexus check runs after the store lookup, so an item installed from the store never asks.
- **Resume** (`github.Download`, the one path every queue download takes, loader and component downloads included): a retry, restart or unpause sends `Range` from the partial's size, with `If-Range` (the strong `ETag`, else `Last-Modified`) while the address is unchanged. It accepts 206 only when `Content-Range` starts at the offset and its total equals the recorded size, and starts over (at most three times) on 200, a changed validator or total, or a partial nothing vouches for. A new address (another Thunderstore CDN, a fresh Nexus link) resumes the same partial when the total matches; the final size, checksum, Nexus MD5 and package digest checks then decide, and a mismatch deletes the file. A network error, a stall or a pause keeps the partial and its `<name>.resume.json`; a failed check, Cancel and Skip delete them.
- **Queue states** besides the final ones: `paused` is a user pause of one item; it cancels the transfer, keeps the partial, survives a restart and holds no download slot. `paused` with `autoResume` is an item that yielded its slot to **Download now** (`Top`): it starts again by itself, in queue order, when a slot is free, and after a restart (a Nexus one waits for the queue to be resumed). `Top` moves the item to the front behind its pending dependencies (`Item.needs`), which move and unpause with it. `HoldForPlay` (when a launching or running game resolves `pauseDownloadsWhilePlaying` true for its profile) pauses running downloads the same way and starts none until the game exits; installs go on. Order is the order of `queue.json`'s `items`.

## GitHub releases

`internal/github` reads `/repos/<owner>/<repo>/releases` without sign-in. Answers are cached on disk and served stale when GitHub is unreachable. The unauthenticated limit is per IP; a reached limit shows its retry time. SMAPI's own release lookup uses the same client.

- **Trust** (`internal/github/verify.go`): a GitHub-sourced install counts as verified only when SMAPI's update API (`includeExtendedMetadata: true`) maps the manifest's `UniqueID` to the same repo. A known mismatch parks the item in `needs-confirm` (Install anyway or Skip); an unknown answer installs and marks it "could not verify", as does every release for a game whose loader reads no manifests (no update key to check); nothing here blocks.
- **Asset picker** (`internal/github/pick.go`): for a release with several archives the first rule that leaves one wins (the asset shaped like the one the user last chose, kept in `github-choices.json`; else installable assets; else zips one of the game's loaders recognises); several left park the item in `needs-choice`.
- **GitHub vs Nexus for updates:** Update review uses GitHub when the mod's update key is `GitHub:<owner>/<repo>` and SMAPI's suggested update URL is on github.com; otherwise Nexus. A free Nexus account must click for every file, so a Nexus update carries a GitHub fallback repo (`GitHubFallback`) and, when the item would wait for that click, the queue downloads a GitHub release at the same version with exactly one archive whose staged contents hold the updated mod's UniqueID (`FallbackID`), else the item goes back to Nexus.
- When an update check finds a manifest older than the download it came in (the installed file is already the suggested version), Mortar sets that manifest's `Version` to the suggested version in the profile's copy and the store item, so SMAPI stops offering an installed update; a mod from another file of the same entry is never rewritten.

## Sharing

- **Form:** Discord makes only `http://`, `https://` and `discord://` links clickable, so a link is `https://mortar.rethunk.tech/<game id>/p#<payload>`, handed to the app as `mortar://<game id>/p/<payload>`. Each playable game's share page is built from `web/src/pages/[game]/p/index.astro`, all running `web/public/share/app.js`. Browsers never send the part after `#`, so no profile data reaches any server. The app accepts either form, or a bare payload.
- **Payload** (`internal/share/share.go`): compact JSON `[3, "<profile name>", "<game id>", {"<source id>": "<that source's game key>"}, [<entry>, ...], "<game version>"]`, Brotli, base64url without padding. The leading number is the format version (only 3 is read); the game version is optional. The link holds no `UniqueID`s, which barely compress. The encoded payload is capped at `MaxEncoded` (the share page's limit). `web/test/testdata/go-link.txt` is the link the app's encoder made, read by both the Go and site tests.
  - **Entry** = object naming its source (`s`), so a link names the exact file (the shapes are `share.Ref`). A new source leaves the format version unchanged: an older Mortar rejects an unknown source as a bad entry.
  - **Optional extras:** `imp` (implicit entry), `grp`, `overlay`, `fomod`, `pin` and others (`share.Ref`); for the share page `kb` (store item size) and `min` (newest `MinimumGameVersion`). Past the cap `kb` and `min` go first, then the extras except `imp`. A share with no `imp` entry may predate install reasons, so the receiver infers them (a listed package another listed package requires is implicit; members of a cycle nothing outside requires stay explicit); profile codes, `.r2z` files and modpacks are inferred the same way.
  - **What is shared:** only enabled entries with a source; local archives and switched-off entries are listed at Share as left out. Every entry cut from one store item is one ref keyed by `Entry.StoreKey()`, carrying the switched-off entries' ids in `disabled`. SMAPI's bundled mods and the bridge are never shared, listed or imported. CurseForge downloads with the receiver's own key (without one the preview lists it unavailable); itch.io and Patreon entries travel as the page alone; optional files install after their main file (`Request.Overlay`).
- **One import engine** (`sharesvc/pack.go`): `sharesvc` reads every format (`PreviewLink`, `PreviewFile`, `PreviewLocalProfile`) and previews it through the same resolver. A pack (`internal/pack` reads it into a `Draft`) becomes `share.Ref` packages plus config and loose files written below the loader's import folders (`pack.ProfileFiles`; executable types and anything else left out are listed in `SkippedPrograms`). A mod the other manager added from disk (`pack.LocalMod`: a Gale profile's `BepInEx/plugins/<name>` folder, or in a code or `.r2z` a plugins folder no package names that holds a DLL) installs as a local entry through `profile.Store.InstallLocalFolder`, so the store's antivirus scan applies. A package the community index cannot resolve is an unavailable row with `ReasonNotInIndex`, so the rest still imports. The CLI's `profile import` runs the same preview and import.
- **Import** (`internal/sharesvc`, `preview.go`): the preview resolves every entry and creates nothing (a Nexus file that is gone or `ARCHIVED` is replaced by the `MAIN` file with the same version, else the primary file, marked "different file"); nothing downloads before the user's click.
- **`.mortar` file:** a zip holding `profile.json` (same format version and entries as a link, plus name, notes and the shared mods' ids `ids`, which bound the config files it may carry), `configs/<format>/<local id>/<relative path>.json` for each enabled mod's `.json` files except `manifest.json`, and `loader/<path in the profile>` for text config files under the config folders of the loader the profile runs (`loader.WithConfig`). Files over the size cap, with unusual names or past the totals are skipped and listed at Save. An old file's `description` is read into the notes, on top. The profile's favourite star travels only in this file; colour and icon travel in neither.
  - `share.Apply` writes config files once their mods are installed: only under a folder an installed mod of that import already has, re-validated at write time, never over mods the profile already had; waiting ones are kept in `<datadir>/pending-configs.json`, independently of queue rows.
  - **Problem choices** (`problems` in `profile.json`; File and LAN only): `dismissed` tokens (kept in `settings.Dismissed["~mortar/cp/<game>/<profile>"]`) and `wins` (`Component.LoadAfter`), bounded in count and token size; a file past them is refused whole. The receiver only adds (`sharesvc.applySharedChoices`) and skips a win when the profile decided the pair the other way.
- **Routing:** `mortar://` is in `protocols:` in `build/config.yml` and `.mortar` in `fileAssociations:`. A link reaches the app as an argument: a cold start reads `os.Args` and a running instance gets a second-instance handoff (`sharesvc.Receive`, `main.go`); it opens the Import dialog filled in, never importing by itself. `mortar://<game>/mod/<id>` (a positive decimal Nexus mod id with no leading zeros) selects the Nexus mod on the Mods tab (`route.go`).
- **Trust boundaries:** payload, `.mortar` and clipboard caps and the per-source id validation: [security.md](security.md#network-and-links). The clipboard is read only when the user presses Paste.
- **LAN sharing** (`internal/lan`): with Settings › General **Share profiles on the local network** on, Mortar advertises `_mortar._tcp` and serves HTTP on `lanPort`; sends are refused while sharing is off and incoming shares are rate-limited per peer. A send is a `.mortar` payload. To a paired computer every option applies and archives added from disk travel as store items; to an unpaired one config files are dropped (they can hold keys) and local archives left out. UI: [gui-design.md](gui-design.md#profile-management).
  - **Pairing** makes two of the user's own computers trust each other, independent of any store account: a single-use code shown on one and typed on the other leaves a 32-byte key in `<data>/lan/peers.json` (0600). Construction and limits: [security.md](security.md#network-and-links).
  - **Store transfer** (`transfer.go`): invariant: the receiver installs through `Store.AddDir` only when the hash of what arrived (`store.HashDir`) equals the one the sender vouched for, and refuses an entry with no vouched hash. Sending between one's own machines is copying, so a paired receiver gets the files whatever the source or licence.
- **Windows firewall:** the per-user installer adds no firewall rule. Settings › General **Fix** relaunches Mortar elevated (`--firewall-allow`), which writes the rules through `INetFwPolicy2` (`internal/lan/firewall_windows.go`) for every network profile, removing every inbound block rule for the executable first (Windows names the ones it creates after the file description, not `Mortar`). When every connected network is Public and the allow-any-address setting is off, Mortar does not listen and LAN use returns a Permission error (`errPublicNetwork`).
- **Nexus collection draft** (`sharesvc.ExportCollection`): read-only; a `collection.zip` holding `collection.json` in Vortex's `ICollection` shape, using the importer's Go types so `parseChoices` reads an export back. Nexus takes a collection as a 7z and no 7z-writing Go library is in go.mod, so the export is a zip and the toast gives a repack command.

## Sync folder

`internal/syncsvc` keeps each profile's state in step between computers through a folder that another tool (Syncthing, Dropbox, a NAS) carries. It carries the profile's `.mortar` export (never mod files, so every computer downloads each mod from its source). The folder is the `syncFolder` setting unless a game's `syncMode` is `own` (that game's `syncOwnFolder`) or `off` (`Settings.SyncFolderFor`).

- **Layout:** `<folder>/<game>/<remote id>.mortar` is the payload and `<remote id>.sync.json` the version file `{name, machine, machineName, vector}`; the vector maps a machine id to the newest revision that machine wrote. The payload is written first and the version file last, so a computer that sees a version finds the payload it names. Local state `<data>/sync-state.json` holds this machine's random id and, per local profile, its remote id and the vector last written or applied.
- **Offers** (`syncsvc.go`): a version file whose vector holds a revision this machine lacks becomes an **offer**, never merged. `Resolve(game, remote, "theirs")` makes the profile match the payload through the share service's replace and adopts the remote vector; `"mine"` keeps the local profile and writes a revision on top of both vectors. A profile changed on both sides is flagged `Conflict`.

## Release

Build and publish mechanics, the update key and the manifest tooling: [release.md](release.md). Facts that settle questions it does not hold:

- **Linux artifacts:** the AppImage is built in an ubuntu:22.04 container with the fork's `gtk3` tag because 22.04 has no WebKitGTK 6.0, so it bundles GTK 3 and WebKitGTK 4.1 and needs that container's glibc; AppRun sources `build/linux/appimage/glibc-check.sh`, so an older host gets a dialog pointing to the Flatpak. nfpm packages and the AUR ELF are linked with `-X main.packaged=...`. The AppImage's unpackaged binary ships as the portable `bin/mortar-linux-<arch>`, which updates itself and writes its own desktop entry and nxm handler. The package remove script (`build/linux/nfpm/preremove.sh`, skipped on upgrade) runs `mortar quit`, `--release-links` and `uninstall-cleanup` as the user who ran the package manager through sudo or pkexec (per-user state is out of root's reach otherwise).
- **Flatpak sandbox:** paths outside the finish-args are invisible until `flatpak override --user --filesystem=<path> tech.rethunk.Mortar`. The sandbox cannot see the host's Steam or processes, so Mortar goes through `flatpak-spawn --host` (`internal/sandbox`) and the game never inherits the sandbox. Add to Steam is refused in the Flatpak (host Steam cannot start `/app/bin/mortar`).
- **Windows:** a per-user NSIS installer is the only scope (`WAILS_INSTALL_SCOPE` in `build/windows/nsis/wails_tools.nsh`), installing to `$LOCALAPPDATA\Programs\Mortar` without admin (a machine-wide build would register a second copy beside it). The installer and uninstaller close a running Mortar first with `mortar quit` (refused while downloads or the game run unless `--force`); if it is still running five seconds later the user is asked to close it, and Cancel stops the install.
- **Self-update:** `internal/updatesvc` drives Wails' updater (`app.Updater`) with the `endpoint` provider reading the signed manifest; signing key `main.go` `updateKey` (the private half never enters the repository). Wails' GitHub provider is not used because it verifies no signature, only an optional checksum asset.
  - A production AppImage, portable Linux binary or Windows build checks in the background (`internal/updatesvc/background.go`), verifies a newer release and leaves it staged; quitting applies it. A release is installed only when its manifest entry carries a valid signature. Asset URLs name the release tag, so a release published mid-update cannot swap the file under it.
  - **Off:** a build without the `production` tag (`wails3 dev`), a server build, a version containing `dev`, or a packaged build (`-X main.packaged=…` from nfpm, Flatpak, AUR). The bare Linux binaries are listed in the manifest under platform `linux-portable` (`updatesvc.PortablePlatform`; `release:manifest` rewrites their inferred `linux`, which the per-file signatures do not cover), so each flavour replaces itself with its own kind of file.
- **What's new:** `<datadir>/last-run-version` records the previous run's version; when the running version is newer, Mortar fetches that release's GitHub notes once and shows them; offline leaves the file so the next start tries again.
- **Wails behaviour Mortar relies on** (upstream, except `OnUpdateApplied`, which only the `Rethunk-AI/wails` branch `mortar/v3-next` carries): a self-contained AppImage (each WebKit helper directory moves into the AppDir's `usr/lib` and the bundled library's compiled-in path is patched to a relative one, with AppRun running from `$APPDIR/usr/lib` and the user's folder in `OWD` (`sharesvc.LaunchDir`), so it resolves inside and outside WebKit's bubblewrap sandbox; only `/usr/lib`, `/usr/lib64`, `/usr/libexec` are searched, so other projects' AppDirs under `/usr/local` are never bundled). The updater (`v3/pkg/updater`): staging goes beside the target and a cross-filesystem rename falls back to a copy (`/tmp` is tmpfs on Fedora); inside an AppImage it replaces and relaunches `$APPIMAGE`, not the read-only mount; `Config.OnUpdateApplied` lets Mortar rewrite `DisplayVersion` on Windows.
- **Linux desktop integration:** packaged installs (nfpm, AUR, Flatpak) own the system desktop entry, MIME XML and icons, and a packaged binary writes none at startup. Nothing installs an AppImage's embedded `.desktop` file, so an AppImage writes its own with `Exec=` set to `$APPIMAGE` (desktop files do not expand variables and the mount vanishes on exit), rewritten at startup when its target no longer exists (`Refresh` in `internal/nxm/handler_linux.go`). Application id and single-instance id are both `tech.rethunk.Mortar`; a portable copy appends a hash of its data folder.
