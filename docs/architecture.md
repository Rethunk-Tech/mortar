# Mortar architecture

How Mortar works: storage, profile semantics, the game catalog and its registries, trust boundaries, and the Stardew, Nexus and wire-format facts that settle questions so they are not re-litigated. Decided work not yet built is in [design.md](design.md), screens in [gui-design.md](gui-design.md), standing rules in [AGENTS.md](../AGENTS.md). Behaviour the code and its tests already state is named here by owning symbol and test, not narrated.

## Product

Mortar finds a game, installs its mod loader, keeps each set of mods in its own profile, and launches the game with the chosen profile.

- **Nexus sign-in:** a personal API key, or the browser sign-in a build's `nexussso` flags select ([Nexus Mods](#nexus-mods)).
- **Licence:** AGPL-3.0 (GPL-3.0 for the desktop app, and it also covers a hosted share service).
- **Games:** the signed catalog lists every game ([Games and the catalog](#games-and-the-catalog)); a game's `enabled` flag makes it selectable. Windows and Linux only: macOS is out (fleet CI has no macOS runners, and Wails does not cross-compile to it). Installs are found from Steam (including Flatpak Steam), GOG Galaxy and the GOG offline installer, the EA App, Epic Games Store, Xbox, standalone folders and Flatpak, and on Linux Heroic's GOG library, Minigalaxy, Lutris and Bottles.

**External profile import** reads r2modman, Gale, Stardrop (Stardew Valley only), Vortex and Mod Organizer 2 when their default data is present, through the Profiles page's **Import…** wizard: `packsvc.LocalProfiles` reads r2modman profile folders and Gale's `data.sqlite3` (read-only, pure-Go `modernc.org/sqlite`, only profiles whose game slug is the game's Thunderstore community); `migrate.Detect` reads Vortex (`state.v2`), MO2 and Stardrop (`Stardrop/Data/Profiles`; `PreservedModConfigs` are written under the same caps as a `.mortar` file's configs). Vortex and MO2 take the game's names from its catalog entry (`importIds`: `vortex` is the game extension's `GAME_ID`, `mo2` the game plugin's `GameName`); a game without `importIds` (Lethal Company) has neither. Present folders are copied into the store; missing Nexus mods enter the share-import resolver and download queue. Tests: `internal/migrate`, `internal/packsvc/service_test.go`.

## Stack

- **Wails v3**, upgraded one beta at a time on purpose. The pin and its Go floor are in `go.mod`.
- **Frontend:** React, TypeScript and MUI on Vite (Wails' `react` template). Typed bindings from `wails3 generate bindings` into `frontend/bindings`; client state in zustand; Lingui 6 for every string, English only.
- **Go services:** each backend area the UI calls is one Wails service (`application.NewService`) whose exported methods are bound to TypeScript; methods only Go calls carry a `//wails:ignore` doc directive, so the bindings expose only what the GUI calls.
- **Solid window:** `BackgroundTypeSolid` (`main.go`); base, tint and surfaces: [gui-design.md](gui-design.md#surfaces-and-colour). The wallpaper endpoint `/background` honours `?mode=` (`image`, `desktop`, `solid`) and answers `Cache-Control: no-store`.
- **Frameless, themed title bar:** `Frameless: true`; the app draws its own title bar marked `--wails-draggable: drag`; the minimum size is 768x432. GNOME and KDE draw no drop shadow for it, so the app draws a 1px border and rounded corners. Trap: dragging works only once the Wails runtime is loaded (`@wailsio/runtime` or `/wails/runtime.js`).
- **Credits:** Settings › About lists bundled licences from `frontend/src/settings/generated/credits.json`, written at every frontend build by `scripts/gen-credits.ts` from `frontend/package.json` runtime dependencies and `go.mod` direct requires; SMAPI, BepInEx and the two bridges are downloaded into a profile, never bundled, so they are not listed.
- **Session-only state:** the toast history (last 200) and the Console's command history live in memory only; a toast's Undo, Redo, Show or Retry works only while that change is still the latest for the same mods.
- **Packages:** one directory per area under `internal/`; every game is the catalog-driven `catalogOnly` in `internal/game`, and `game.Starter` starts a launch plan the way the install's store requires ([Games and the catalog](#games-and-the-catalog)).

## Storage

Everything lives in the user data folder, `%LOCALAPPDATA%\Mortar` or `$XDG_DATA_HOME/mortar`, never under the Windows install folder (the uninstaller deletes that recursively). State is JSON written through a temp file and rename (`datadir.WriteFile`/`WriteJSON`/`WriteStream`); no database. The Nexus key is in the OS keyring. WebView2 data is `webview/`.

- **Move** (Settings › Storage): copy to a chosen empty folder (not inside the current one, not while the game runs), verify, write `data-location` in the default folder, remove the old copy, restart. Clones where the filesystem can (btrfs, XFS reflink, ReFS), re-links hard links, never follows symlinked folders, junctions or mount points; free space is probed with a real clone or link because FAT, exFAT and SMB count every name (`datasvc.Measure`).
- **Portable mode:** a `portable` file beside the executable (symlinks resolved) puts data at `<exe dir>/data`, ignores `data-location` and refuses Move. The marker is ignored inside a Flatpak and an AppImage mount; one beside an executable in an unwritable folder stops the start with `datadir.PortableError` rather than quietly keeping data on the host. A portable copy has its own single-instance id (hash of its data folder). Tests: `internal/datadir/portable_test.go`.
- **Missing data folder:** a `data-location` naming a missing folder (unplugged drive) is never created; on Windows a message box offers the default location, a folder picker or quit. Every startup failure is appended to `startup.log` in the default folder.

Files in the data folder (shapes: the named package):

- `settings.json` ([Settings file](#settings-file)); `queue.json` (without `nxm://` keys); `download-history.json` (last 1,000); `nexus-seen.json` (per mod: `newestFileUnix`, `newestChange`, `lastLookedUnix`; capped at 2,000, least recent dropped); `cache/`; `trash/`.
- `store/<game>/<key>/`: each downloaded archive, extracted once. `.complete` marks a finished extract (extracted to a temp folder, then renamed; an item without it is incomplete and an install reports it); `mortar-root` names the relative subfolder that is the mod. Keys: `nexus-<mod id>-<file id>` (a Nexus file can hold several SMAPI mods, so the key is the file), `github-<owner>-<repo>-<tag>-<asset>-<sha256 prefix>` (the hash of the exact names separates names the folding makes equal), `local-<sha256 of the archive>`, `smapi-<version>`, `bridge-<version>-<sha256 prefix>`. `store/index.json` is each item's last use (last time any `profile.json` named it); `store/.manifests/<game>/<key>.json` and `store/verify.json` are integrity records ([Store integrity](#store-integrity)).
- `profiles/<game>/<profile id>/`: `profile.json` ([below](#profilejson)) and `mods/` (the folder SMAPI is pointed at). Each entry is copied to `mods/<store key>/` as extracted, or only the `mortar-root` subtree; further files from the same Nexus page join as `extraStoreKeys` under `mods/<entry key>/<extra store key>/`, and Update, Roll back and Remove cover every store item on the entry. Extract drops `__MACOSX`, `.git` and folders holding only `Thumbs.db`.
  - **Mod-folder picker:** an archive with a `manifest.json` that SMAPI would not find, or one UniqueID in several folders, asks the user for the folder that is the mod; an update reuses the same-named variant.
  - **FOMOD** detection runs first (`fomod/ModuleConfig.xml`, case-insensitive, at the item root or one folder down, UTF-8 or UTF-16). The resolved files are copied instead of the raw extraction and the chosen plugin names stored on the entry as `fomod`; Update and Roll back replay them (`internal/profile/fomod.go`) and ask again when a choice no longer exists or the update adds an unanswered group (`internal/fomod/resolve.go` `Unanswered`).
  - `runs/`: the last 20 launches Mortar started (`index.json`; one `<id>.txt` copy of the run's SMAPI log, capped at the console's 20,000 lines of 256 bytes); a launch without mods stores none.
  - `saves/` is the profile's own Saves folder when `separateSaves` is on ([Saves](#saves)); the swap journal is `journal/<install id>-saves/saves.json`.
- `backups/<game>/`: zips of the Saves folder taken before mod updates, before Play, before a restore and on request, under the game's `backupLocation` (empty is this folder); one game's backups are never listed or restored for another.
  - A save is a folder holding a file of its own name (Stardew Valley) or, when the catalog entry lists `saveFiles` patterns, a file in the saves folder or one folder below (Lethal Company `LCSaveFile*`; Valheim `characters_local/*.fch`, `worlds_local/*.fwl` less `!*_backup_*`) plus `saveCompanions` sharing its stem (a Valheim world's `.db`). A zip holds only saves and companions under `Saves/`; a Saves folder with no save is not backed up.
  - Rotation: each kind keeps `saveBackupsKept` (1 to 50, profile-overridable) on its own, so no kind evicts another's; `scheduled` zips rotate per save against `saveBackupKeep`. A whole-Saves zip (not `manual`, not `scheduled`) under ten minutes old stands in for a new one when the Saves folder is unchanged. A sibling `<stamp>.json` `{profile, kind}` records why (`update`, `restore`, `launch`, `manual` (pinned) or `scheduled`); without one the zip shows as unknown.
- `downloads/<item id>.<ext>` with `<name>.resume.json` (expected size, `ETag`, `Last-Modified`, source URL, checksum when sent): a failed, interrupted or paused fetch keeps both; Cancel and Skip delete them.
- `<game>/last-played.json`: each save folder last launched with a profile (`profileId`, RFC3339 `at`), written when a run ends and SMAPI's log names the save it loaded.
- `categories/<game>.json` (custom categories), `tools/<game>.json` (`internal/tools`: `arguments` is a JSON array, never a shell string; `{game}`, `{mods}`, `{saves}`, `{profile}` expand; launched through `os/exec` without a shell), `saved-groups/<game>.json`, `endorse-prompts.json` (after five completed runs with no errors from an enabled Nexus mod, when `askEndorseMods` is on: [gui-design.md](gui-design.md#mods-tab)).

### Optional files

`internal/profile/overlay.go`, `overlayset.go` (tests: `overlay_test.go`, `internal/queue/overlay_test.go`). A Nexus file with no `manifest.json` anywhere and no installer (Nexus "Optional" files that swap some files of the main one) is an overlay of the profile's entry from the same Nexus mod that holds a manifest. It is its own store item and its own `profile.json` entry with no mods and no folder, `overlayOf` naming the main entry's key. Without a main entry it is refused (`NoBaseError`: "<archive> has no manifest. Install the main file of <mod> first, then this optional file goes on top of it."); an archive with no Nexus mod ID and no manifest is refused as "No SMAPI mod was found in this archive".

- **Placement**, first match wins: a single top folder named like one of the main entry's mod folders (case-insensitive); else the layout under which most of its files already exist in the main entry; else a single top folder whose children match names in a mod folder; else Mortar asks (`RemapAsk.overlay`). The answer is stored as `overlayFrom` and `overlayTo`.
- **Invariant:** optional files are laid over the main folder in entry order (later wins), each replaced file removed and the new name linked or cloned from the optional store item (`datadir.MaterializeFile`), so no store item is ever written. Switching one off (`overlayOff`) or removing it restores the main entry's own file for every path any optional file covered and deletes paths only optional files brought.
- **Alternatives:** optional files of one main entry replacing any of the same files (`OverlayFiles`) switch each other off in the same write; an install whose source names the file it replaces (`Source.WithReplacing`) takes the old optional entry's place.
- **With the main entry:** removing it removes its optional files; updating or rolling it back takes them off first (so carry-over never sees them as user edits) and lays them over the new folder; rebuild, Restore, Revert and Undo lay them again. Mods, problems, load order and update checks see only entries with mods. A profile export zip carries the main folder with them taken off and each optional store item under `overlays/<entry key>/`.

### `profile.json`

Fields and caps: `internal/profile` (`Profile`, `Entry`). Invalid `color`, `icon` or `description` are dropped on load. Rules not obvious from the structs:

- `origin` is `link`, `mortar`, `game-mods`, `copy` (with `copyOf`) or `collection`. `overrides` holds profile-overridable game prefs (`defaultLaunchMethod`, `showSmapiConsole`, `backupBeforePlay`, `saveBackupsKept`, `updateModsBeforePlayDefault`, `skipPlayCheck`); `settings.ResolveAt` uses the profile value, else the key's own scope, else the registry default.
- `install` and `loader` name the game install and loader the profile runs (empty means the game's selected install and primary loader). `launchPrefix` is Linux only; `launchEnv` and `launchPrefix` are ignored on Steam `-applaunch`; `launchPresets[]` with `defaultLaunchPreset` (empty is the profile's own settings). `groups` are named sets of entry keys that enable and disable together; a name is a `/` path (`Looks/Hats` lies inside `Looks`), so nesting is only in the name: a share's `grp`, a saved group and an older Mortar all see a plain group of that name, and a parent needs no group of its own. Switching, renaming or deleting a group acts on the groups inside it, and saving one to the library takes their mods.
- `intentSince`, `intentOffered`: when Mortar began keeping install reasons and whether the player answered the one-time offer to classify older entries (libraries, required mods, sheet suppliers; a content pack stays explicit even when required: `InferImplicit` in `internal/profile/implicit.go`, `frontend/src/mods/LegacyReasonsCallout.tsx`).

`entries[]`:

- `key` is the store item in use; for an entry cut from a folder game's archive `<item>#<path>` with `item` and `file`. Mods in an entry are components: `id` (`<format>:<local>`, e.g. `smapi:Pathoschild.ContentPatcher`), version, manifest folder, `needs`, `optional`, `contentPackFor`; `disabled` lists disabled mod ids.
- `previousKey`/`previousSource`/`previousExtraStoreKeys` are the Roll back copy; on an updated archive's first entry `replaced` is the JSON of the entries it superseded. `tray`/`trayFiles` record Tray files with SHA-256.
- `implicit`: Mortar brought the entry in for another mod (resolver dependency, a Nexus link download supplying a required mod, an import entry another listed entry requires); absent means the player asked. Set at creation, copied by every path that copies an entry, changed only by Mark explicit/implicit; loader and bridge entries are always implicit. An entry with several mods shows one main mod with the entry's reason and the rest implicit; the main mod is the base the others build on (one requiring no other mod of the entry that most require).
- `pinned`, `skipVersion`, `note` (500), `tags` (8, each 24), `categoryOverride`, `displayName`/`displayAuthor`/`displayVersion` (what this profile shows for a one-mod entry; the mod is never changed), `added`, `source` (the reference used in share links).

The store keeps every item a profile names as `key` or `previousKey` and deletes the rest 30 days after last use. `ProfilesWithMod` reads `profile.json` files, not the store.

**Hero cover** (`internal/profile/cover.go`, `cover_test.go`): a picked cover is copied into the profile folder (PNG, JPEG, WebP by content, at most 16 MB; the original path is never kept). `Covers` tries in order: the picked cover (`/profile-cover/<game>/<id>`); the `picture` of the profile's Nexus entry with the highest stored `endorsementCount` (no new call); Steam art at `/steam-art/<appid>` (`game.ArtMiddleware`: cached hero, else public `library_hero.jpg`, else the hero or header `IStoreBrowseService/GetItems` names). The frontend moves on when one fails and shows a solid tone after the last.

## Settings file

`settings.json` has a `formatVersion` and three blocks: `global`, `sources` (per mod source id) and `games` (per game id). A key is read at the most specific scope that sets it (source, game, install, loader, profile), then broader ones, then its default (`internal/settings/scope.go`). Source-scoped keys sit in their source's block (Nexus account and `nxm` keys, `autoTrackNexus`, `verifyNexusMD5`; Thunderstore `handleLinks`); the file is read and written as the flat field list. A missing or unparseable file gives the defaults; an invalid value is replaced by the default on load and refused on write.

Each key's meaning, scope, type, default and allowed values are defined once, in code: field comments on `Settings` (`internal/settings/settings.go`) and the registry (`internal/settings/registry.go`; defaults from `Defaults()`, checked by a test). `mortar settings get` lists every key with its value.

**Export and import:** Settings › General › Settings file writes the fields in `portableFields` (`internal/settings/portable.go`) as `{"version": 1, ...}`; import (`internal/settings/import.go`) refuses any other version and applies only after a preview. Account and machine state (Nexus identity, game folders and stores, loaders, last profile and last played, dismissals, nxm handler state, LAN settings, `backgroundImage`) and `overlayToken` are never exported; the keyring is never read.

**Disk use and clean-up** (Settings › Storage; `internal/datasvc`): **Clean up…** previews, then deletes exactly the listed items; its keep set is `datasvc.KeepSet`, the set the startup 30-day sweep also builds (here without the grace), and a store key a profile names after the preview is re-checked and kept. Mod pictures have no lifetime: counted, never cleaned.

### Store integrity

Installing an item records the SHA-256 and size of every file beside the store (`.manifests/<game>/<key>.json`), so hashes are never copied into a profile. `store.Verify` re-hashes and reports files missing, changed or extra. An item with no record is baselined by its first verification, which cannot see earlier damage.

- For a Nexus item with a sign-in, verification first looks in the downloads folder for an archive of that mod whose MD5 equals the one Nexus lists; a match is extracted as an install extracts it and becomes the baseline, so post-install damage is found. Otherwise the item is baselined from its current files. GitHub and local items have no such check (a local item's key is its archive's SHA-256, which Repair uses).
- The background pass `storecheck.Run` (`internal/storecheck`) starts three minutes after launch, verifies items not checked in 7 days one at a time, waits while a game runs or a download or install is active, and sleeps four times each item's check time between items (about a fifth of one core). `store/verify.json` keeps each verdict (`Damaged` feeds Problems). **Check store files** verifies every item now.
- **Repair** of a damaged item sets it aside and re-obtains it from its recorded source (a local item from its archive if still in downloads; loader items by reinstalling the loader); the damaged copy is put back if the queue refuses.

## Profile operations

**Materialising store items into a profile** (install, duplicate, rebuild, re-extract, update) is per file, in order, falling through on `EXDEV`/`EOPNOTSUPP`/`EINVAL`/`ERROR_INVALID_FUNCTION` (capability cached by filesystem device id): copy-on-write clone (`FICLONE`, Windows ReFS/Dev Drive block cloning), hardlink on one filesystem, symlink, copy (`internal/datadir/materialize.go`).

Files a mod may write use clone or copy only: `config.json` at any depth, anything under `data/` or a saves-like folder (`saves`, `save`, `savedata`), `*.mortar-old`, and text files a user might open in an editor (`.json`, `.txt`, `.ini`, `.cfg`, `.xml`, `.yaml`, `.yml`, `.toml`, `.csv`, `.tmx`, `.md`; most editors save in place). Reason: SMAPI's `helper.Data.WriteJsonFile` (`File.WriteAllText`) truncates in place, so a hard link or symlink would leak one profile's write into the store and every other profile. Drift ignores the writable paths and does not treat a linked or cloned shipped file as modified. Deleting a profile unlinks its names and never removes store files.

**Operations** (each is a method of `internal/profile` `Store` or a service named below; the cited tests state the edge cases):

- **Toggle:** rename the folder holding the mod's `manifest.json` with a leading dot (SMAPI skips it; measured) and record it in `disabled`; enabling a mod also enables its present-but-disabled required dependencies in the same write. Bulk operations are one `profile.json` write under the running-game lock (`enable.go`, `enable_test.go`).
- **Profile folder** (`internal/profile/folder.go`, `folder_test.go`): `MoveToFolder` copies the profile to `<folder>/<game>-<id>` (possibly another drive), then replaces its usual folder with a symlink (a junction on Windows when symlinks are not allowed) to it, so every path built from the profile id still resolves; `Profile.Folder` is read from that link and never written. `MoveHome` reverses it, `Delete` brings a linked profile home before the trash move, and `CheckFolder` reports a missing, profile-less or read-only folder. Materialising into the folder follows the rules above, so across drives hardlinks fall back to copies.
- **Duplicate** clones or copies `mods/` as is (never hardlink or symlink, so an in-place write cannot leak into the source); origin `copy`. **Delete** moves to `trash/` for `trashRetentionDays` (startup deletes older); `Purge` and `PurgeTrash` refuse a symlink (`trash.go`).
- **Damaged profile:** an unreadable `profile.json` is listed by `ListDamaged` and skipped by `List` and `StoreKeys`, so one corrupt file does not stop collection. **Repair** (`mortar profile repair`, `repair.go`) rebuilds it from the latest readable history snapshot, leaves `mods/`, and renames the broken file to `profile.json.damaged-<timestamp>`; refused with no snapshot.
- **Import from the game's Mods folder** (`import.go`, `import_loose.go`, `import_test.go`): scans one level of `<game>/Mods` as SMAPI does and enters each folder through the dropped-folder path (hashed-folder install, dedup by content); result is profile "Imported mods", origin `game-mods`; the game folder is never written. Trap: a symlink-deploying manager (Vortex links each file from staging) imports as the files the links point to (`datadir.CopyTreeResolvingLinks`), while the store otherwise refuses links that leave a folder.
- **Move from the game's Mods folder** and **compare and sync** (`gamemods.go`, `gamemods_test.go`): copy as Import does, then delete the folder by renaming it aside first (so a file held open leaves it whole); matching is by UniqueID, case-insensitive; refused while any game process is up (`Store.GameRunning`); dismissed folders are kept in `dismissed` under `gameMods:<game>`.
- **Dot-hidden mods:** a dot-prefixed folder inside an entry that Mortar did not add hides every mod under it from SMAPI; per-game `showDotHiddenMods` lists them and `UnhideMod` strips the dots (`dothidden.go`). **Extra mods folder** (`extraModsFolder`): `InstallExtraFolderMod` installs one top-level folder through the dropped-folder path and never writes the folder.
- **Outside edits** (`drift.go`, `drift_test.go`): `mods-snapshot.json` beside `profile.json` is a cheap fingerprint of each entry folder (name, file count, total size, newest mtime; skipping `config.json`, `*.mortar-old`, `data/`, saves-like folders and other files carry-over treats as user- or mod-written). On profile load and window refocus (debounced) the live `mods/` tree is compared to it and to `profile.json`; a first scan with no snapshot records the tree and reports nothing. Findings show on the Problems bar (Adopt, Remove, Restore, Forget, Keep, Revert).
- **Compare:** `Diff` matches user mods of two profiles by UniqueID (bundled omitted); `CopyMods` copies through `AddEntry` (store item already on disk; no download); **Match versions** switches differing entries through `UpdateEntries` as one atomic change (a failure undoes every swap; one history event). A running game locks the destination. UI: [gui-design.md](gui-design.md#profile-management).
- **Saved groups and templates** (`internal/savedgroups`, `internal/templates/apply.go`, `templates_test.go`): a saved group snapshots mods with store keys, sources, install reasons and optional files; `Apply` copies missing store items in, in one history batch. Templates (`templates/<game>.json`; their `entryKey`s are in the store keep set) add game settings, launch options and presets; `ApplyTemplate` never removes the profile's own mods, takes `profile.Store.Baseline` first and returns an `Undo`.
- **Back up and restore a file** (`internal/packsvc/backup.go`, `backup_test.go`; `profile backup`/`profile restore`): one zip with `backup.json` (format version, game, every setting and entry, a content hash per carried store item), history, config files and cover under `files/`, the profile's own saves under `saves/` and each mod's store item under `store/<key>/`. **Include mod files** (`--no-mods` clears it) carries every mod so the file restores offline; off, only mods no source can download again. Restore makes a new profile via `UniqueName`, never overwriting, and takes a store item only when its hash matches.
- **Typed config editing** (`internal/configsvc`, `FuzzCfgSetKeepsOtherLines`): a mod's config files are its SMAPI `config.json` and the `.cfg` files in `<profile>/BepInEx/config` whose file name or `## Plugin GUID:` header matches the mod id. A `.cfg` `Set` rewrites only that entry's line; `config.json` goes through the profile's `SetJSON` (path refused if it leaves the mod folder; key order, types and unknown fields kept); GMCM captures add labels and ranges ([Generic Mod Config Menu](#generic-mod-config-menu)). Every write fails while the profile's game launches or runs.
- **Pin and skip:** **Pin this version** is `pinned` (optional `pinReason`; CLI `keep`/`unkeep`) and writes a `pinned` history event. A pinned entry is offered no update; `skipVersion` hides that exact newer version until a later one appears. Both drop out of the update count, Update review and Update all.
- **Update checks** (`internal/control/updates_apply.go`, `internal/profile/service_update.go`): at startup (`checkModUpdatesOnStart`) and every `updateCheckIntervalMinutes` for the open profile; SMAPI API answers are cached an hour per profile fingerprint and F5 bypasses the cache. SMAPI's API is asked 100 mods per request; for the mods it flags, Nexus GraphQL v2 is asked once for their current file lists (50 mods per request; signed in only). An update is real when a newer non-archived file with the same display name exists or the installed file's version is below SMAPI's; an unbumped manifest inside the newest file is not offered. Signed out or on failure the mod dataset's file list decides the same way. A background pass runs 5 minutes after open, then every 4 hours, over every installed game's profiles, notifying only on an increase.
- **Change history** (`internal/profile/history.go`, `historystorage.go`): events in `history.json`, capped by `historyEventsKept` (20 to 2000). Each distinct entry snapshot is gzipped to `snapshots/<sha256>.json.gz`; snapshot and `history-files/` bytes are not capped. An event also keeps the profile's settings (`ProfileState`); name, notes, colour, cover and profile order are not history. A `config.json` Mortar writes records a `config` event after one capturing the file as it was; Revert rolls configs back only when every event since the target is such an edit. Invariant: every profile mutation records an event and undoes exactly (`TestEveryProfileChangeRecordsAnEventAndUndoesExactly`, `undo_coverage_test.go`). `RecentHistory` (`mortar history --all`) merges every non-damaged profile of the game, newest first, capped at 50. Export zips leave out `history.json`, `snapshots/`, `history-files/`, `runs/`.
- **Update or roll back** an entry (`internal/profile/update.go`, tests `update_test.go`, `syncrules_test.go`): the target version is copied from the store into a fresh folder, then what the mod or user wrote is carried over by comparing three copies of each file (the profile's, the store's copy of the current version, the target). A file only the profile has is carried over; a file the profile changed is carried over when the target ships it unchanged, else the target wins and the profile's copy is kept as `<name>.mortar-old`. A manifest `DeleteOldVersion` (Stardrop's name, read case-insensitively) limits carry-over to user-written files such as `config.json`. A file the target no longer ships follows per-game `oldFilesOnUpdate` (`delete`, `keep`, `ask`): `ask` moves it to `old-files/<new key>/<UniqueID>/<path>` beside `profile.json` (folder games: `old-files/<entry key>/_files/<path>`), and a delete moves it to `trash/<game>/removed-old-files/<profile id>/<stamp>/<key>` (`oldfiles.go`, `oldfiles_test.go`). Disabled folders keep their leading dot; the Saves folder is zipped into `backups/` first.

## Command line

Mortar is GUI-first: the CLI exposes only what the window can already do, and a new capability lands in the window first. Verbs: [HUMANS.md](../HUMANS.md#command-line).

- `mortar <verb>` (`internal/cli`) is decided in `main` before `application.New`, so it never takes the single-instance lock or opens a window; any other first argument, a link, a file path or `--play=<game>/<profile>` is a window launch. Output flags (`--json`, `-v`, `--verbose`) may precede the verb (`leadingFlags`). Under `--json` a failure is `{error, kind, code}` on stderr plus `detail` (typed fields of a `usererr.Detailer`) when the app sent one. `--play` ids may not contain `/`, `\`, space or quotes; a running instance receives it as a second instance (`play:requested`).
- **Play mode** (`--play=<game>/<profile> --steam-session`: an Add to Steam shortcut while Mortar is closed, Steam's Game Mode on the Deck; `shortcut.Service.Start`, `frontend/src/launch/playMode.ts`): the window starts hidden and renders only the launch layer; Play takes the usual path with every pre-Play check, and a blocking check shows the window at 560x480 holding only that dialog. `main` quits once the played game has been Running and is Idle again, after purge and settings restore, so Steam counts playtime from Mortar's own process. If a Mortar already answers on the control channel, a `--steam-session` start sends `play.request` over it before `application.New` and `shortcut.Follow` (`follow.go`) polls `status` until the game has been active and is idle again (a game not started within 15 minutes ends the wait).
- **Control channel** (`internal/control`; the CLI is a client of the running app): the app listens on `127.0.0.1` on an OS-chosen port and writes `control.json` (`port`, random 32-byte `token`, `pid`, `version`, `protocol`; 0600) in the data folder, removed on exit only while still that instance's file. Each connection carries one JSON request line (`token`, `method`, `params`) and one reply line (`result`/`error`); the token is compared in constant time. Methods run on the app's own services, so window and CLI never write the data folder at once (`control_test.go`). `controlwire.Protocol` (1): the CLI calls `hello` first and fails on mismatch. A start finding another Mortar answering `hello` waits five seconds for it to exit, then stops before it touches data. A server build refuses to start on the account's own data unless `MORTAR_SERVER_REAL_DATA=1` (`scripts/selftest.sh` gives it a sandbox `HOME`) and takes a free loopback port without `WAILS_SERVER_PORT`; the desktop app opens no HTTP port.
- `launch` detaches the game from the request (`context.WithoutCancel`). With `updateModsBeforePlayDefault` it first queues the updates needing no choice (`queueUpdates`, `internal/control/methods.go`) and waits up to five minutes; a failed update stops the launch, a download a free Nexus account must click through does not. `install` queues the required mods its new mods lack when `missingRequirements` resolves to downloading (`queueMissing`). On Windows the GUI-subsystem exe attaches to its parent console (`AttachConsole`) unless output is redirected.

## Trust boundaries

Everything from outside is untrusted: links, `.mortar` files, archives, API responses. Share links and `.mortar` files have their own caps in [Sharing](#sharing). Threat model and the test for each input: [security.md](security.md).

- Extraction keeps every entry inside its destination; caps each entry at 32 GiB, decoder dictionaries and PPMd memory at 256 MiB (a separate constant), the archive at 64 GiB extracted (above 2 GiB, also 1024 times its own size) and 20,000 entries; rejects symlink entries, Windows reserved names (`CON`, `NUL`, ...), `:` in names and names differing only by case.
- An `nxm://` link is taken only as `nxm://<domain>/mods/<mod id>/files/<file id>?key=<key>&expires=<unix>&user_id=<id>` for a Nexus domain a catalog game maps to, unexpired, for the signed-in account's `user_id`; anything else is refused with the reason. A link Mortar was not waiting for asks which profile it is for before anything downloads.

## Failure behaviour

Once mods are installed, nothing external is needed to open, edit or launch a profile. Failures reaching the user are classified in `internal/usererr` (not found, busy, network, permission, disk full, damaged, invalid). Go wraps the cause as `[kind] message`; the window (`errorMessage` in `frontend/src/toasts/report.ts`) and the CLI (`Sentence` in `internal/cli`) map the kind to the same English sentence, with the cause in a Details tooltip or under `--json`/`-v`.

- **A mod source unreachable:** `internal/netstate` records per source (smapi.io's update API included) whether its last real request hit a network error; a bad answer leaves state alone. Unreachable sources are probed every five minutes, a banner names each and disables network actions needing one (`frontend/src/shell/OfflineBanner.tsx`, `OfflineGate.tsx`). Trap: SMAPI's API or the dataset unreachable degrades and never blocks: update checks show "unknown", dependencies are checked after download.
- **Archive formats** (`internal/archive`, `formats.go`, `stream.go`): zip, RAR, 7z, tar and gzip, xz, lzma, zstd, bzip2 streams, found by magic bytes, never extension (`archive.Extensions` is only what pickers, drop and the downloads watcher accept). A compressed stream whose payload has a `ustar` header is read as a tar (a v7 tar without `ustar` is not recognised); any other is one file named from the archive's name minus its suffix. A classic `.lzma` stream has no magic, so it is recognised by a valid properties byte, power-of-two dictionary size and sane length. Tar entries pass the zip guards (`ErrLink`, `ErrSpecialFile`). Libraries: stdlib `compress/gzip` and `compress/bzip2`, `github.com/ulikunitz/xz` (xz, lzma), `github.com/klauspost/compress/zstd`. A bare compressed file is queued as `<id>~~<original name>` (`archive.SavedName`, `SavedID`) so the extracted file takes its real name.
- **A download cut off or corrupt:** extraction goes to a temp folder on the store's volume and moves in only when every entry passed its checksum (CRC32 in zip, RAR, 7z; gzip and zstd check their own); failure deletes the temp folder and the item can be retried; **disk full** fails the same way and says how much space the item needs.
- **Mortar quits mid-operation:** every write is temp-then-rename and startup removes leftover temp folders; a `mods/` folder deleted outside Mortar is rebuilt from the store from `profile.json`.
- **Startup repairs are reported once:** what startup repaired itself is collected by `internal/tidy`, logged, and shown as one info notification ("Mortar tidied up N things").

## Resource limits

- Go's soft memory limit is 512 MiB (`memlimit.go`, `debug.SetMemoryLimit`; `GOMEMLIMIT` wins, `GOGC` untouched): a collector target, not a cap; a lower limit costs far more GC CPU on large installs.
- A Problems check on a large profile stays under 1152 MiB peak PSS (`scripts/mem-budget.sh`, `MORTAR_MEM_DATA`): the Thunderstore index is stream-decoded as it downloads, the picture cache keeps 192 px thumbnails and a 1920 px profile hero, and the wallpaper is served at the window's pixel width.
- Archive decoders cap xz, lzma, zstd and RAR windows at 256 MiB, and installs run one at a time.
- The download dialog hashes each archive once, remembered by path, size and mtime in `cache/archive-hashes.json`; `datasvc.Usage` is reused for a minute; a data folder move hashes the source while copying and clones files on btrfs.
- `store.Verify` re-checks each store item weekly at a fraction of a core.

## Tests

Go tests run against local HTTP test servers replaying recorded Nexus, SMAPI API and dataset responses, inside the 10 s warm gate budget. Recordings are scrubbed before commit: `users/validate.json` returns the account's name and email, so fixtures carry placeholder account fields. An opt-in smoke test copies a real Stardew install to scratch, installs SMAPI with `--no-prompt`, launches a profile and reads `SMAPI-latest.txt` for the loaded mods. Tests must set `XDG_DATA_HOME` (or `LOCALAPPDATA` on Windows) to a directory under `os.TempDir()`; `datadir.Dir` refuses any other location while `testing.Testing()` is true.

## Games and the catalog

Everything that can be data is catalog data; code exists only where behaviour differs, as a driver found through a registry. Adding to each registry: [HUMANS.md](../HUMANS.md#adding-a-game). Catalog entries are hand-curated; the one exception is a game the player adds for themselves (below). Each registry below is a package under `internal/`; its driver list, capability interfaces and per-driver tests are in the package, not restated here.

- **Catalog:** `internal/components` holds `GameInfo` entries in the signed component manifest (`GameInfo.Validate` guards the shape; `TestEveryCatalogReferenceResolves` checks every source, loader, metadata id, store field, path role and path token resolves). `game.Catalog()` returns the verified manifest's games when it lists any, else the bundled ones. Optional blocks an older Mortar ignores (so the v2 schema is unchanged): `graphics` and `knownBroken` (`{id, versions, reason, replacement}`, `versions` space-separated constraints such as `>=1.0 <1.5`).
- **Custom games** (`internal/customgame`, `components.SetUserGames`, `customgame_test.go`): Game select › **Add a game…** saves a name, the game's executable and one of five loaders (BepInEx 5, BepInEx 6 IL2CPP, MelonLoader, Shimloader, or `folder` with a `Mods` folder beside the executable; Shimloader also saves the game's Thunderstore community, which supplies the loader and the mods, and takes the r2modman routes, with the proxy and UE4SS placed beside the executable the player chose, which is the shipping build in `Binaries/Win64`; Voices of the Void is added this way) in `custom-games.json` in the data folder. Each becomes a `GameInfo` shaped like a shipped game of that loader (`Entry.Info`, checked by `ValidateUser`, which is `Validate` without the store rule), id `custom-<slug>`, and `components.Games` and `components.Game` answer with them after the signed catalog's, never shadowing one of its ids. The executable's folder is stored as the game's install folder (`gameFolders`), so no store driver is involved. The entry is never uploaded or synced and names no mod site except a Shimloader game's Thunderstore community, so other mods come from archives. Settings: it adds none and every per-game setting applies exactly as for a shipped game on the same loader (the registry keys the block by game id and reads the loader's capabilities, not the game); the tray lists it from the next start.
- **Stores** (`internal/gamestore`): one driver per store key in the catalog's `stores` (`steam`, `gog`, `lutris`, `bottles`, `ea`, `epic`, `xbox`, `standalone`, `flatpak`), run only for games naming its key. A native Linux build starts through `linuxStart`, else `linuxMarker`. A user-chosen folder wins over discovery (origin `folder`); a `manualFolder` game names no store and only has that folder (Voices of the Void, an itch.io download). `GameInfo.MarkerDir` is the folder under the install root holding the marker (The Sims 4: `Game/Bin`); the install folder stays the root.
- **Installs and runtime** (`internal/game/install.go`, `internal/runtime`): an install is a store and a folder with a stable id, a platform (an `.exe` marker is a Windows build) and a runtime:

  | Runtime | Claims | Path template resolves in | Start |
  | --- | --- | --- | --- |
  | `native` | native builds | the host's folders | direct |
  | `proton` | a Steam Windows build on Linux | its `compatdata` prefix | Steam |
  | `wine-prefix` | a Windows build in a Bottles bottle (install carries `prefix`) | the bottle's `drive_c/users/<user>` | `bottles-cli run -b <bottle> -e <exe> -- <args>` (`flatpak run --command=bottles-cli com.usebottles.bottles` for Flatpak Bottles) |
  | `mortar-proton` | any other Windows build on Linux (chosen folder, Heroic, Lutris, EA) | a prefix Mortar keeps per game, `<data>/prefixes/<game>/pfx` | as Heroic and Lutris start Proton outside Steam: `<proton>/proton waitforexitandrun <exe>` with `STEAM_COMPAT_DATA_PATH` (that folder) and `STEAM_COMPAT_CLIENT_INSTALL_PATH` (the Steam with the build) |

  `runtime.FindProton` picks the build (`mortarproton.go`, `mortarproton_test.go`); Flatpak Steam's builds need its runtime and are excluded. A loader's DLL overrides reach the prefix as `WINEDLLOVERRIDES`, so the first start, before Proton has made the prefix, loads them.
- **Sources** (`internal/source`): a driver registers itself (`source/all` imports them) and implements `Source` plus optional capabilities found by type assertion (`Searcher`, `Categorizer`, `Gated`, `Sorter`, `ItemLister`, ...). Drivers: Nexus, GitHub, Thunderstore, Modrinth, CurseForge, itch.io, Patreon, Vintage Story Mod DB ([vintage-story.md](vintage-story.md#sources)). A `Gated` source says through `Unavailable()` what the user must set up first; an `all` search leaves it out.
- **Browse** (`internal/browse`, tests `merge_test.go`, `sort_test.go`, `flags_test.go`, `installed_test.go`): `all` sorted by downloads or update date is one ranked list across sources (`ranked.go`), each source read in its largest pages (`source.Sizer`); a source that cannot sort that way (GitHub under downloads) is left out and named in `Unsorted`. Best match interleaves each source's page, since scores do not compare across sites. Only all sources failing is an error. Hits of one mod from different sources fold into one card on package identity, an explicit link, or the same name by the same author, both folded to letters and digits, with the catalog's `authors` aliases counting one person's names on different sites as one (`mergeSame`). A name alone never merges: a hit sharing its name with a better-downloaded hit from another site by another author is marked `reuploadOf` instead. Nothing is sorted client-side within one source; under `all` only `MergedSorts` (`downloads`, `updated`) are offered because Modrinth and GitHub cannot honour name or newest. `Hold` (`installed.go`) matches a card to the open profile by each entry's source and the `UpdateKeys` of every installed manifest.
- **Thunderstore** (`internal/source/thunderstore`): search reads the community's chunked package index (`/c/<key>/api/v1/package-listing-index/`, a gzip list of chunk URLs), cached at `<datadir>/cache/thunderstore/<key>-<hash of the index blob>.json`, used an hour without asking, then revalidated by the index blob's hash. Deprecated packages are not searchable but still resolve as dependencies. `ParseLink` reads `ror2mm://v1/install/thunderstore.io/<namespace>/<name>/<version>/`. `Closure` treats a pinned dependency version as a minimum and installs the newest, as r2modman does, unless a root of the request names an exact version or the per-game `dependencyVersions` (profile-overridable, `queue.Deps.ExactDependencies`) asks for the version the author pinned, as Gale does (`closure_test.go`); managers a community lists as packages (r2modman, Gale) are programs and never install as dependencies.
- **Gated sources** (`modrinth`, `curseforge`, `itch`; shipped games list CurseForge, and itch.io for The Sims 4) install through the queue's direct path (`queue.ResolveDirect`): the request and its required dependencies resolve first, each project once and at most 16 deep; a `sha512:` digest is verified after download.
  - **Modrinth:** public API v2 (`https://api.modrinth.com/v2`) with the `User-Agent` Modrinth requires (`Rethunk-Tech/mortar/<version> (+https://mortar.rethunk.tech)`). A game's source `key` is a facet (`categories:fabric`; a bare word is a category). The queue holds Modrinth fetches to 4 at once, started 5 a second after a burst of 10 (Modrinth's 300 requests a minute per address).
  - **CurseForge:** Core API v1 (`https://api.curseforge.com/v1`) with Mortar's own key in `x-api-key`, never in an address or log: `-X .../internal/source/curseforge.apiKey=...` at release build, else `MORTAR_CURSEFORGE_KEY` for dev builds; with neither the source is `Gated`. A game's source `gameId` is CurseForge's game id and `key` its "Mods" class id (Stardew Valley: 669 and 4643). A file has no version number: its version is its display name and an update names the file by id. The digest is `sha1:<hex>`, which the queue does not verify because the lint bans weak hashes. When an author forbids distribution (`allowModDistribution` false, or no `downloadUrl` and a refused `download-url`) the driver never builds a CDN address: it fails with `NotDistributableError` and the queue opens the mod's page. The queue holds CurseForge fetches to 3 at once. A multi-class search merges by sort, stops at 1,000 results and survives one class failing (`classes_test.go`).
  - **itch.io:** server-side API (`https://itch.io/api/1/x`) with the player's own key in `Authorization`, never in an address (an error quoting the address cannot leak it), kept in the OS keyring under `itch`; settings keep only the account name. The API has no sort and no total, so `Total` counts this page plus one when the page is full. `Resolve` picks the upload by id or file name, else the first not flagged demo or soundtrack.
  - **GitHub and Nexus sorts:** GitHub repository search `sort` is stars, forks, updated (no downloads, name, created); Nexus `ModsSort` endorsements, downloads, updatedAt, createdAt, name.
- **Handoff sources** (Patreon `internal/source/patreon`, itch.io page `internal/source/itch`): no search, download or update check; the player saves the file from the site and the Downloads watcher adds it (`archivesvc.InstallHandoffDownload`). Why: Patreon has no API for a post's files and its terms bar automated access; the itch.io page form covers a catalog entry `{"id": "itch"}` with no key. A share ref carries the id and no file.
- **Loaders** (`internal/loader`): a driver registers by id (`smapi`, `bepinex5`, `folder`) and implements `Loader` (`Status`, `Install`, `Contribute`) plus optional capabilities by type assertion. A launch is a `launchplan.Plan` the loader adds to; the profile's launch options, prefix and environment follow, and `game.Starter` runs it through the install's store: Steam through `steam -applaunch` (hands the start to the game and exits), every other store by running the game's executable. A direct Play (not a Steam or store URL relay) can start more than one instance with the same profile environment, spaced by `delaySeconds`, and cancel between them.
  - **Pipeline** (`internal/launchsvc/pipeline.go`, tests `pipeline_test.go`, `pipeline_recover_test.go`, `install_lock_test.go`): one install runs one launch at a time (the preparing claim is the lock). Order: loader contributes; enabled packages are laid out in the profile (`SyncPackages`) when the profile holds the loader; the deployer places install-side files (journaled before the first file moves); profile game settings apply and the changed-launch save backup is taken; a `separateSaves` profile's Saves folder is swapped in ([Saves](#saves)); the runtime is prepared (`bepinex5.EnsureWinHTTPOverride` on an existing Proton prefix); the store starts the game. When the game exits or the start fails, placed files are purged, the saves swap undone, settings restored. `RecoverDeploys` finishes what a crash or quit left at startup, skipping an install whose game still runs.
- **Installers** (`internal/installer`): an archive's shape picks a driver in `detectionOrder` (`fomod`, `thunderstore-rules`, `plain` last); every laid-out path is validated to stay inside its target and be storable on Windows. **Frameworks** (`internal/framework`): a driver keyed by a framework mod's id adds asset conflicts, setting hints, cleanup suggestions and redundancy findings to the profile's problems while an enabled mod matches; Content Patcher is the only one. **Metadata** (`internal/metadata`) providers have capabilities `Updates`, `Status`, `Dataset`; **hosts** (`internal/host`): `host.GitHub` fetches release assets (using the user's `gh` login when present; resumes), `host.Direct` any other HTTPS address.
- **Pack formats** (`internal/pack`): `Format` readers turn another manager's list (r2modman and Gale codes: `#r2modman\n` plus base64 of a zip with `export.r2x` and `config/`, fetched by key from Thunderstore's legacy profile endpoint; r2modman folders; Gale `data.sqlite3`; Thunderstore modpacks) into a `Draft` and write nothing. `packsvc.ExportModpack` (`mortar profile export --format modpack`) writes a modpack zip that the modpack reader reads back as the same package set. `packsvc.ExportR2z` (`mortar profile export --format r2z`) writes an r2modman `.r2z` that the r2modman reader reads back as the same package set, without posting a public code.

### Folder games

`internal/loader/folder` (`folder_test.go`; profile side `internal/profile/foldergame_test.go`, `syncrules_test.go`): a game with no mod loader names the loader `folder`, a `mods` path role (where the game reads mods, possibly outside the install) and a `mods` target whose root is a profile subfolder (`{profile}/Mods`).

- **Entries:** an added archive lays out below the target as packed and becomes one entry per laid-out file (key `<store item>#<slash path>` with `Entry.Item` and `Entry.File`), unless it lays out a file whose extension is in the target's `keepWhole` list: then one entry holds every file, keyed by the store item. Trap: everything reading the store (backups, listings, keep set, sizes) uses `Entry.StoreKey()`, never the key, so an archive counts once.
- **Replacement:** an install replaces an earlier archive only as its update (a Nexus or CurseForge file whose update names the old file id, `Source.WithReplacing`, or a GitHub asset of the same repository and shape); every entry of the superseded archive is replaced together, each keeping its on/off state, and the first new entry records them so Roll back restores all.
- **Shared-path files (Tray):** files whose extension a target lists in `extensions`, on a target whose `role` names a shared path (The Sims 4's `tray`), are placed at install in that folder, never swapped at launch, held by an entry of their own (`Entry.Tray`) recording each file and its SHA-256. A file of the player's own there is never replaced: the install is refused naming it, or an identical file is left and not claimed. Recorded files are released only while no entry of any profile of the game holds them and the file still has the recorded hash; update and roll back place new files before releasing old.
- **Catalog fields:** `caches` names rebuildable files below a path role; `requiredSettings` become Problems rows of kind `game-setting`. A mod with no source and no manifest is a `local` entry `folder:<store key>`; nothing updates it.
- **Launch:** the loader plans one file per file below the target with `launchplan.PlanFile.Root` `mods`; the deployer places them under `deploy.View.Roots["mods"]` with the same journal and crash recovery as install-side files, so the shared folder holds none of a profile's data after the launch. `SyncPackages` records each file it lays out with hash, size and time in `.mortar-packages.json` and never overwrites a copy changed since.
- **Install-side mods folder:** a `mods` path of `{install}` or below it needs no deployer of its own (`TestAModsFolderInsideTheInstallIsFilledAndPurgedWithTheInstallUnchanged`): the same deployer fills the folder for a launch and the install hashes identical afterwards, a game file a mod replaced coming back from `displaced/` and folders Mortar made going. With `{install}` itself an archive is laid out as packed from the install root (The Witcher 3's `mods`, `dlc` and `bin/config`, Cyberpunk 2077's `archive/pc/mod` and `r6/scripts`), so the folder's top folders are what a profile owns for write-back, and Import from the game's Mods folder offers nothing (`profile.errModsFolderIsInstall`). Entries: The Witcher 3, Cyberpunk 2077, Darkest Dungeon, Starbound, Hogwarts Legacy. Not covered: an archive packed without its folders (Cyberpunk's loose `.reds`) lands in the install root, and Witcher 3's `mods.settings` load order is not written.
- **Settings:** `gameSettingsMode` (`edit` or `warn`) decides whether Mortar writes the catalog's `requiredSettings` into the profile's own copy of the `options` file before a launch (`launchsvc.swapOptions`) or only reports them. `cacheClearing` deletes the catalog's `caches` once, on the first launch after the profile's mod set hash (`profile.ModSetHash`, recorded as `cacheSet`) changes. `newProfileSeparateSaves` makes `Store.Create` start a profile with separate saves. `scripts/selftest.sh regress --game sims4` drives a stand-in Sims 4 install through two profiles and checks the player's files are identical afterwards.

### Deploy methods

`internal/deploy`, `GameInfo.Deploy`. `redirect`: the loader points the game at the profile's folder; nothing is placed (SMAPI's `--mods-path`). `profile`: the profile holds the loader and mods (the r2modman and Gale model): before a launch `SyncPackages` copies each enabled package's files into the profile (a package's config file only seeds it) and removes files of packages no longer enabled; the deployer copies only the loader's install-side files into the install (BepInEx's Doorstop pair `winhttp.dll` and `doorstop_config.ini`, the config's target made the profile's absolute preloader path so a start that passes no Doorstop flags, such as an Epic Games link, still loads the profile) as real files, never links (the game and its anti-cheat may write to them), journals every move first and removes them, restoring what they displaced, when the game exits. Packages are never linked into the install or the store, and a plan path leaving the install is refused.

- **Journal** (`deploy.go`, `oplog.go`; `crash_test.go` crashes after every step of Apply and Purge): `Apply` hashes each source, records every operation (destination, source, SHA-256, where a displaced file waits under `<journal>/displaced/<n>`) and persists `deploy.json` in `<data>/journal/<install id>` before the first file moves, never rewriting it during the deploy; later steps go to an append-only `deploy.log`, and recovery replays the log over the record, ignoring a last line a crash cut short. Each file is copied through a `.mortar-tmp`, synced and renamed (`datadir.CopyFile`); a hard-linked destination is never written through. `Apply` refuses with `ErrUnrecovered` while an earlier deploy's journal exists.
- **Purge invariants** (`deploy_test.go`, `writeback_test.go`): a displaced file goes back over its destination; with nothing displaced a destination is removed only while its hash is the recorded one, so a player's own file Mortar did not place is never deleted. A crash between any two steps leaves the bytes in the profile, the shared folder or both, never neither, and `Recover` finishes the same walk (nothing while the game runs).
- **Write-back** (`writeback_test.go`, `writeback_review_test.go`; the profile owns what a launch changes in files it placed, the shared folder is scratch): a changed file placed from a profile copy into a path role's folder is copied over the profile's copy before removal, and a file created during play inside a folder an entry owns is adopted (up to 64 MiB a file and 512 MiB a purge, never through a link). The profile's copy is the only target, never a store item; a file at the role's root, in a folder no entry owns or in the saves folder is never adopted; write-back happens only after the game exits. When the profile's folder is gone bytes are never removed without a copy: a changed file over a displaced one is renamed `<name>.mortar-rescued` before the player's file returns. What cannot be adopted or was rescued is recorded in `<journal>.shared.json` and listed by profile health ("Left in the shared folder").
  - **`changed/<path>` is the one rule** for update, roll back, uninstall and a switched-off package: a changed copy is moved there under `<profile>/changed/`, never deleted, and comes back when an archive ships it again or the entry is reinstalled; backups carry it. In a `.mortar` payload it travels exactly as config files do (`Include.ConfigFiles`, `MaxConfigBytes`, same caps, `profile.WriteChangedFiles` on receive), and the payload reader refuses any path not a clean relative one inside the content folder or `changed/`.
- **Files an update drops:** a changed file whose entry was replaced by a version that no longer ships it follows `oldFilesOnUpdate` (`keep`, `delete`, `ask`); one whose entry was switched off or removed is held under `changed/` whatever the setting (`.mortar-held.json` records when) and deleted at the next sync once held longer than `trashRetentionDays`. A dropped file nobody changed is removed in every mode.

### Loader notes

- **SMAPI** (`redirect`): replaces the game's launcher once per install, reads its log from the game's error-log folder and matches it to a profile by the `Mods go here` line; its bundled mods are a store entry in every profile.
- **BepInEx 5** (`profile`): keeps core, plugins, patchers, config and log in the profile, where Doorstop's `--doorstop-target` points (`<profile>/BepInEx/core/BepInEx.Preloader.dll`), and needs only the pack's Doorstop proxy (`winhttp.dll`, `version.dll` or `winmm.dll`, read from the pack: In Silence's pack renames it to `version.dll`) and `doorstop_config.ini` beside the executable; under Proton the proxy's native override (`winhttp=n,b`) is written into the prefix. A game's loader entry may add `routes` (`dir`, `extensions`, `track`: r2modman's install rules for folders such as `BepInEx/Sideloader` or `QMods`), which `bepinex5.Route` tries before its own folders under the same refusals. A native Linux build (an install holding `linuxMarker`) gets no files: it starts directly with the pack's `libdoorstop_x64.so` in `LD_PRELOAD` and the Doorstop target in `DOORSTOP_TARGET_ASSEMBLY`.
- **BepInEx 6 IL2CPP** (catalog `major: 6`): enters through `BepInEx.Unity.IL2CPP.dll` on the .NET runtime it ships in `dotnet/`, named by absolute path in the Doorstop config and CLR flags. Its install also puts the game's Unity base libraries (version from `<game>_Data/globalgamemanagers`, fetched once from `unity.bepinex.dev` into `cache/unity-libs/`) in `BepInEx/unity-libs/`, so the first start needs no network.
- **MelonLoader** (`profile`, `internal/loader/melonloader`): the loader is one catalog component shared by every MelonLoader game (`game` `melonloader`, `name` `loader`: the `LavaGang/MelonLoader` release's `MelonLoader.x64.zip`, hashed by the generator); a version other than the catalog's is downloaded from GitHub's release list and refused unless it matches GitHub's digest or the release's `.sha512` file. The profile is MelonLoader's base folder: the launch passes `--melonloader.basedir <profile>` (Wine `Z:` form under Proton) and `--melonloader.agfregenerate` until the profile holds the game's generated assemblies, and only `version.dll` is placed beside the executable, with the prefix's `version=native,builtin` override (`internal/wineoverride`, also used for BepInEx's `winhttp`). Vanilla passes `--no-mods`; the log is `MelonLoader/Latest.log`. The profile's `console` and `logLevel` launch settings live in its marker file and become launch arguments, as BepInEx's become `BepInEx.cfg` entries: `--melonloader.hideconsole` when the console is off, and `--melonloader.debug` (plus `--melonloader.harmonyloglevel 4` and `--melonloader.captureplayerlogs` for the highest level), all read in `MelonLoader/LoaderConfig.cs` of LavaGang/MelonLoader. A game with no catalog `routes` runs MelonLoader 0.7's recursive layout (a package's `UserData` goes to `UserData/<package>`, everything else to `Mods/<package>` with its structure); one that lists `routes` (r2modman's `melonloader` rules: BONEWORKS, BONELAB, RUMBLE, Hard Bullet, Patch Quest, Backpack Hero) takes the classic layout, where a folder named like a route's last segment, then the longest matching extension, then the `default` route place a file. Only Windows x64 builds are covered (no `MelonLoader.x86.zip`, no native Linux build). Settings walked for the driver: the loader pin (`melonloaderPin`) is read through the loader service; the game-scoped settings the launch pipeline applies to any loader (launch method, Proton version, backups, runs and console filters, play check, cache clearing) apply as they are; `skipIntro` is not, since it needs a companion mod and MelonLoader has none; the SMAPI loader settings are not. **Config:** `UserData/MelonPreferences.cfg` (TOML, one `[Category]` per melon, the description as the comment above an entry) is edited as a typed file (`internal/configsvc/melon.go`); the file names no types, ranges or defaults, so an entry's type is read off its value, and a category belongs to a mod when its name and the package's name contain one another. **Load order:** plugins register before mods, each group by `MelonBase.SortMelons`: a topological walk where a melon follows the assemblies it references or names in `MelonAdditionalDependencies`, the smallest name first, then a stable sort by `MelonPriority` (`dotnet.ScanMelon`, `dotnet.MelonOrder`, read from the DLLs' assembly attributes).
- **ReturnOfModding, GDWeave, Lovely, Northstar, Rivet, Unity Mod Manager and Shimloader** (`profile`, `internal/loader/thunderpack`: one driver, a `Spec` per loader, from r2modman's ecosystem schema, installers and launch instructions, checked against the packages on Thunderstore): the loader is the game's Thunderstore package, named by the catalog loader's `package` (required) and read from the game's community index like BepInEx's pack, so a mod's dependency on it is the loader's own. An install lays the package's loader folder out in the profile and records the files to place; an update removes the previous release's placed files (Lovely's proxy was `version.dll` before 0.10), replaces only the folders the release owns and seeds files the player may edit. Only a library or launcher that must sit beside the executable is placed for a launch (below `markerDir`, so Hades II's is in `Ship`), with `dll-override` `native,builtin` for each top-level library under Proton. Per loader:

Under Proton `wsock32` is overridden for the proxy in `bin/x64_retail`.
  - **Rivet** (Scrap Mechanic: `ReDoIngMods-Rivet`): `version.dll` is placed beside the executable, in `Release`; `-rivetEnable true -rivetTarget <profile>/Rivet/Loader.dll -rivetDirectory <profile>/Rivet/Mods`; every mod file goes to `Rivet/Mods/<package>/<path>`; vanilla is `-rivetEnable false`.

  - **Shimloader** (Unreal Engine games: Palworld, Astroneer, Panicore, SOULCALIBUR VI, Grain Rot, MECCHA CHAMELEON, MINOS, RV There Yet?, Windrose; package `Thunderstore-unreal_shimloader`, from r2modman's `ShimloaderInstaller.ts` and `ShimloaderGameInstructions.ts` and Gale's `shimloader.rs`): the package's top `dwmapi.dll` (the one in `UE4SS/` is dropped), `UE4SS/UE4SS.dll` as `ue4ss.dll` and `UE4SS/UE4SS-settings.ini` are placed beside the game's shipping build, the loader entry's `placeDir` (`<data folder>/Binaries/Win64`, the schema's `dataFolderName`); `UE4SS/Mods` goes to `shimloader/mod`, and the install creates `shimloader/{mod,pak,cfg,overlay}`; `--mod-dir`, `--pak-dir`, `--cfg-dir` and `--overlay-dir` name them (Wine `Z:` form under Proton, as Gale); `dwmapi` is overridden under Proton. Voices of the Void has no store, so the catalog lacks it.
  None writes a log Mortar reads (UE4SS's `UE4SS.log` sits in the game's folder, which neither r2modman nor Gale reads), so a launch is up when the game process is; a thunderpack game takes only Thunderstore packages, and only Windows builds are started. Settings walked for the drivers: each loader's pin (`returnofmoddingPin`, `gdweavePin`, `lovelyPin`, `northstarPin`, `rivetPin`, `ummPin`, `shimloaderPin`) is read through the loader service; the game-scoped settings the launch pipeline applies to any loader (launch method, Proton version, backups before Play and how many are kept, update before Play, run history, play check, old files on update, enabling mods when installed) apply as they are; the console filters have no log to filter; `skipIntro` is not read (no companion mod); `graphicsApi`, `gameSettingsMode` and `cacheClearing` read catalog blocks (`graphics`, `requiredSettings`, `caches`) these games have none of; `nxmDefaultProfile` needs a Nexus source, which they have none of; the SMAPI and BepInEx settings, `showDotHiddenMods` and `extraModsFolder` are for those loaders' folders.

### SMAPI

- **Pin:** game setting `smapiPin` holds a SMAPI version Mortar installs instead of the latest (and stops offering updates for). A patch-day sweep (`lastSweepGameVersion`, `lastSweepSMAPIVersion`) checks every profile for mods smapi.io marks broken when the game or SMAPI version changes. A loader that reads no game version compares the install's Steam build instead (`game.InstallBuild`; `lastPlayed.build` for the Play dialog's "game was updated" check and the before-Play backup, a `build <id>` label in `lastSweepGameVersion` for the sweep), and sweeps other loaders' profiles for missing dependencies alone.
- **Install and update:** the release installer runs unattended with `--install --no-prompt --game-path "<dir>"`; running it again updates without prompts, replacing the launcher and adding the bundled mods. Mortar installs SMAPI itself, without asking, when a profile is created, at startup while SMAPI is missing or broken, on first run and before Play when a game update replaced the launcher; only a newer release waits for the user (an update can break mods), as a banner from the GitHub releases client ([GitHub releases](#github-releases)).
  - **Windows:** the installer is `SMAPI <version> installer/internal/windows/SMAPI.Installer.exe`, self-contained (its `runtimeconfig.json` bundles .NET 6.0.36). Mortar extracts the whole zip and runs it from the installer folder, as `install on Windows.bat` does (the batch file refuses a `%TEMP%` path).
  - **Bottles bottle:** a Windows build on a Linux host is recognised by `Stardew Valley.exe` (`buildOS`); the installer zip runs inside the bottle (`Install.RunInBottle`) and a launch is a direct start wrapped in `bottles-cli run` (`Install.BottleCommand`).
- **Versions:** the installed SMAPI version is kept in `settings.json`; otherwise, and for the game version, Mortar reads the first line of `SMAPI-latest.txt` (`SMAPI 4.5.2 with Stardew Valley 1.6.15 build 24356 on Unix ...`).
- **Broken by a game update:** on Linux the installer renames `StardewValley` to `StardewValley-original` and puts its launcher in place, which a game update overwrites. Mortar checks at startup and before launch that `StardewValley-original` exists and `StardewValley` contains `StardewModdingAPI`; Play reinstalls SMAPI first when not. On Windows the launcher survives and an incompatible SMAPI reports itself in its log.
- **Bundled mods:** a profile's `mods/` replaces `Mods/`, so every profile gets SMAPI's Console Commands and Save Backup as a `smapi-<version>` store entry from the installer Mortar downloaded (`internal/<os>/install.dat`, a zip holding `Mods/ConsoleCommands` and `Mods/SaveBackup`, checked in 4.5.2). A SMAPI update replaces that entry in every profile.
- **Profiles folder:** SMAPI takes `--mods-path <path>`, absolute or relative to the game folder (`smapi.md:49`). Its `SMAPI_MODS_PATH` variable works only when SMAPI starts directly (`steam -applaunch` cannot pass environment variables), so Mortar does not use it. Mortar never moves or writes the game folder's own `Mods`.
- **Scanning:** SMAPI recurses into subfolders until it finds a `manifest.json` and skips folders starting with a dot; manifests are parsed leniently. Optional `UpdateCautionMessage` and `DeleteOldVersion` (Stardrop update hints) are read with the same case-insensitive key rules; **Update all** skips cautioned mods until the row is ticked.

#### Components

`components.source.json` names each loader or companion mod by game, kind, GitHub source, release asset pattern, version policy and optional accepted game-version range; its `games` section holds each game's identity, and its `authors` section the people known by different names on different mod sites; both are carried unchanged into the manifest. `cmd/components` resolves releases, downloads the named assets and writes the signed `components.json`, embedded at `internal/components/components.json` for offline and first-run fallback; game implementations read it through `components.Client.Game`. Process names and launch behaviour stay in Go.

- **Signature:** Ed25519 with the update key (`build/updater/public.key` is the embedded public half); the detached signature is published beside the manifest. Each signed manifest is its own immutable `components-v2-<serial>` release; `v2` is the manifest schema (released clients read any manifest whose fields they recognise, so a schema change takes a new prefix).
- **Client** (`internal/components`): finds the newest non-draft `components-v2-*` release through the GitHub releases API, fetches its manifest at startup through the daily meta cache, verifies before parsing, rejects a lower serial and falls back to the cached or bundled manifest. Source hosts are limited to `github.com` and `thunderstore.io`. Every asset is checked against its manifest SHA-256 before extraction.
- The bridge is installed hidden in every profile as a `bridge-<version>-<hash>` store entry with source kind `mortar`, replaced when the manifest version or hash changes. Hidden means as SMAPI's bundled mods ([gui-design.md](gui-design.md#mods-tab)).

#### Mortar SMAPI Bridge

Mortar has no access to SMAPI's stdin, so a small SMAPI mod (`Rethunk-Tech/mortar-smapi-bridge`, `UniqueID` `Rethunk.MortarSmapiBridge`, protocol in its README) accepts console commands on a loopback port.

- **Channel** (`internal/bridge`): the mod writes `mortar-smapi-bridge.json` (`{port, token}`, user-only) in its folder; Mortar reads it from the running profile and sends `<token>\n<command>\n`, so the token never leaves the user's own files. The reply is `ok`, `ok <json>` or `error: <message>`; commands run on the game's next tick and their output arrives in SMAPI's log. The BepInEx companion (`Rethunk.MortarBepInExBridge`) writes `mortar-bepinex-bridge.json` in the profile's `BepInEx/config` and answers `ping`, `status`, `plugins`. Both bridges read `startup/skip-intro` in the profile folder (`loader.WriteIntroSkip`, set before each launch from the `skipIntro` setting) to skip the game's intro; SMAPI's skips the title screen's animation.
- **Running state:** while a game Mortar started runs, `launchsvc` asks `status` every 2 s (`loader.RunningState`); each enabled package whose DLLs declare plugins gets a loaded or not-loaded badge. Trap: BepInEx keeps the newest version of a GUID and, between equal versions, the first file its folder walk meets (`Chainloader.cs`), which only the bridge's `location` tells, so the loaded plugin is the package whose laid-out file the bridge names.
- **Stream overlay** (UI: [gui-design.md](gui-design.md#settings)): Mortar writes the bundled OBS page to `<data>/overlay/index.html` and, at launch, the bridge mod's `config.json` (`OverlayEnabled`, `OverlayPort`, `OverlayToken`; 0600, atomic; a loader whose bridge keeps settings in the profile gets the same keys in `startup/overlay.json`, removed while the overlay is off). The page polls `http://127.0.0.1:<port>/state?token=<token>`. Both bridges serve one `/state` shape: `inGame`, `playerName` and the game's own keys; the BepInEx bridge adds `game` (`lethal-company`: `moon`, `crewAlive`, `crewTotal`, `day`, `quota`, `quotaProgress`, `daysLeft`, `credits`; `valheim`: `biome`, `day`, `bossesDefeated`, `bossCount`), which picks the layout; a snapshot with no `game` is Stardew Valley's.

### Launch

| Copy | How Mortar starts it |
| --- | --- |
| Steam | `steam -applaunch <appid> <args>`: Steam passes the arguments after the app ID to the game, keeping overlay, achievements and playtime |
| GOG, Heroic, Minigalaxy | SMAPI directly (the Direct path) |
| Flatpak Steam | `flatpak run com.valvesoftware.Steam -applaunch 413150 --skip-terminal -- --mods-path <dir>` |

The pipeline is under [Games and the catalog](#games-and-the-catalog) (Loaders); the facts below are the ones the code cannot show.

- **Linux Steam:** `steam -applaunch 413150 --skip-terminal -- --mods-path <absolute path to the profile's mods/>`. SMAPI's launcher script reads its own flags only before `--` and forwards only what follows (unix launcher argument loop in Pathoschild/SMAPI), which is why SMAPI's docs say arguments do not work on Linux. `--skip-terminal` makes the script start SMAPI with `--no-terminal`; SMAPI still writes its log (`docs/technical/smapi.md:46`). Without `--` the path is ignored, and without `--skip-terminal` the launcher opens its console in an unreadably small `xterm`.
- **Windows Steam:** Steam starts `Stardew Valley.exe`, not SMAPI: SMAPI's installer swaps the launcher only on Linux and macOS (`InteractiveInstaller.cs` `if (context.IsUnix)`) and on Windows asks for a launch option to keep achievements. First run shows `"<game>\StardewModdingAPI.exe" %command%` to paste into Stardew's Steam launch options, and **Set it in Steam for me** writes `LaunchOptions` in the MostRecent account's `localconfig.vdf` while Steam is closed (Steam rewrites the file on exit; `internal/steam/localconfig.go`). Mortar then adds `--mods-path <path>` after the app ID: SMAPI finds its flags anywhere on its command line (`Array.LastIndexOf(args, "--mods-path")`, SMAPI 4.5.2 `Program.cs`) and ignores unknown ones. Without the SMAPI line Mortar starts `StardewModdingAPI.exe` itself (`game.steamSkipsLoader`, `internal/game/start.go`) at the cost of the Steam overlay.
  - Mortar does not pass `--no-terminal` on Windows: `StardewModdingAPI.exe` is a console program (PE subsystem 3, checked on the 4.5.2 Windows `install.dat`), so Windows gives it a console window whatever the flags. A direct launch hides the window instead (`showSmapiConsole` off); the Console tab follows the log file either way.
- **Console input:** a process Mortar starts gets a stdin pipe it holds open until exit (`launch.startCmd`, `internal/launch/launch.go`). SMAPI's console-command loop skips empty reads, so on `/dev/null` or `NUL` it spins a core for the whole session; on an open pipe it waits. Console tab commands go through the bridge mod, not stdin.
- **SMAPI startup markers:** SMAPI's `Console.ReadKey` throws when stdin is not a console, so the "game crashed last time" prompt (`smapi-internal/StardewModdingAPI.crash.marker`, written on every fatal crash) ends SMAPI before the game opens and the surviving marker fails every later launch. The SMAPI loader's `Prelaunch` removes that marker and the update marker before each profile launch; `ErrorLogs/SMAPI-crash.txt` is kept.
- **Arguments, prefix, environment, presets** (`internal/profile/launchpreset.go`, `launchpreset_test.go`): a profile's `launchOptions` are split like shell words and appended after `--mods-path` (on Linux after `--` too); `--mods-path`, `--no-terminal`, `--skip-terminal` are refused since Mortar sets them. `launchPrefix` (Linux only) and `launchEnv` (`NAME=value` per line) apply to Direct launches only; Steam `-applaunch` receives neither. The profile's own set is the built-in preset `Standard`; `launchPresets` holds up to 20 more (names unique ignoring case, never `Standard`); an unknown preset name refuses the launch before anything starts. Changing any of these never touches `mods/`, so a running game does not block it.
- **Per-profile game settings:** an optional `game-settings.json` beside `profile.json` overrides selected fields in Stardew's `startup_preferences` for that launch; Mortar restores each field when the run ends only if the game still has Mortar's value (`internal/launchsvc/gamesettings.go`).
- **Without mods:** `steam -applaunch 413150` with no arguments, or the game's executable when started directly; no profile, no mods lock, no `lastPlayed` or run recorded. On Windows a Steam launch-options line holding SMAPI still starts SMAPI, so Mortar warns first (and never edits that file).
- **Before Play:** Play gathers missing required dependencies, unresolved non-cosmetic conflicts, pending updates, mods flagged broken or obsolete, a changed game version and the newest save's gap (`savessvc.LastSaveGap`) into one dialog (**Play anyway**, **Open Problems**, **Update and play**); **Don't check before Play** is the `skipPlayCheck` override. With `updateModsBeforePlayDefault` on, Play queues every installable, non-pinned update first, records a history restore point and rolls back entries whose update fails. Before a non-vanilla launch with a history event after the newest stored run, the Saves folder is zipped into `backups/` (kind `update`); a failed zip does not block Play.
- **Profile shortcuts** (`internal/shortcut`, `internal/steam/shortcuts.go`): a shortcut writes `--play=<game>/<profile>` (Linux `~/.local/share/applications/tech.rethunk.Mortar.play-<game>-<profile>.desktop`; Windows a Start menu `.lnk`). **Add this profile to Steam** appends a non-Steam game to native Steam's `shortcuts.vdf` for the MostRecent account (launch options `--play=… --steam-session`, appid with the high bit set) and updates an existing entry for the same `--play=` in place, keeping appid and playtime, and copies a local cover or hero into the account's `userdata/…/config/grid`; refused while Steam runs and when only Flatpak Steam is found.
- **Success or failure:** `steam -applaunch` returns at once, so a launch counts as started when `SMAPI-latest.txt` (`~/.config/StardewValley/ErrorLogs/`, `%APPDATA%\StardewValley\ErrorLogs\`) is rewritten within 60 s, else failed with a hint; a Steam launch's `steam` exit 0 is ignored, a non-zero exit fails at once. A `StardewModdingAPI` process whose `--mods-path` is a profile's folder means that profile is in use and locked against changes; reaching Running records `lastPlayed` in `settings.json`.
- **Whose log:** the game has one `SMAPI-latest.txt` for every profile, so the Console and Share log show a log only in the profile that wrote it: the session Mortar launched belongs to its profile; the file on disk belongs to the profile whose mods folder matches SMAPI's `Mods go here: <path>` line (SMAPI writes the home folder as `~`, `PathUtilities.AnonymizePathForDisplay`); a log without that line (a launch outside Mortar) belongs to none. A BepInEx log is inside the profile and necessarily that profile's.
- **Runs:** when a launch Mortar started ends or fails, a Summary of its log is stored under `runs/` (`internal/launch/summary.go`). A loader with a Unity player log marks the run `crashed` when that log, written since the run began, holds `Crash!!!` or `Fatal error` and the loader reported no crash itself.
- **Likely cause:** `launchsvc.CrashHint` (`crashhint.go`, `stackhint.go`, `dumphint.go`, tests of the same names) explains the latest `crashed` run; the first hit wins: the run's recorded cause; the loader's log analyzers; a .NET stack blame (`dotnetstack.Blames` in `internal/loader/dotnetstack`, used by the SMAPI, BepInEx 5 and MelonLoader drivers and, from the game's log and crash report, Vintage Story; `stack_test.go`; two equal matches blame neither); a crash dump (`internal/crashdump`), blaming a mod only when the faulting module is its `EntryDll` or a same-named file within three folders of its folder; else the first finding's message with no mod.
- **Bisect** (**Find the broken mod**, offered when the crash names no mods; `internal/bisect`, `launchsvc.RunForBisect`): halves enabled mods (keeping required dependencies) on a scratch profile (`profile.ScratchCopy`, removed when the check ends and, after a crash, at the next start). A step fails only when SMAPI logs an alert or the run ends crashed; plain errors such as a skipped mod do not count, or the bisect would blame whichever mod logs one. A step passes when the bridge writes a title-screen report under `<profile>/startup/`, or after 20 s at Running when the profile has no bridge folder.
- Trap: launching through Steam makes Steam Cloud download the user's saves, and SMAPI's Save Backup mod zips them into `save-backups/` in the game folder.

### Startup timings

- **What:** the bridge measures each mod's share of startup, from its own Entry to the title screen, and writes `<profile>/startup/<process start UTC>.json` (last 10 kept; schema in the bridge README). Times are exclusive: an asset edit triggered from another mod's update tick counts for the editor only. The report's `replaces` lists, per Harmony ID, the game methods a mod can replace outright; Problems adds them to each C# mod's footprint ([Same job](#same-job)). Before each launch Mortar adds the bridge's UniqueID to `ModsToLoadEarly` in `<profile>/mods/SMAPI-config.json`.
- **Measured launch:** **Measure next launch** writes `<profile>/startup/.measure-next-launch`; the next launch removes it and writes `StartupProfile: true` into the bridge's `config.json`, so the bridge also times every other mod's Entry (from SMAPI's per-mod `SetApi` call, never by patching a mod's method), every SMAPI event handler (delegates swapped in place, restored at the title screen), every asset edit and load by mod and content pack, and Content Patcher's per-pack work, and skips the title intro animation. UI: Performance › Startup ([gui-design.md](gui-design.md#performance-tab)).
- **Sampled launch:** a measured launch also starts a diagnostics EventPipe session and writes `report-id.samples.json`; each sample is charged to the innermost frame in an enabled mod assembly, unmapped samples are game and SMAPI time (`sampleMs`, `sampledOtherMs`). Sampling failures do not fail the launch.
- **BepInEx:** only a measured launch is timed: `.measure-next-launch` becomes `<profile>/startup/.measure-launch` holding the catalog game's `titleScene` (Lethal Company `MainMenu`, Valheim `start`), which the bridge's preloader patcher consumes to add a log listener before the chainloader runs (`LogOutput.log` has no timestamps and is flushed on a timer, so timing cannot come from it). A plugin's `entryMs` is the gap to the chainloader's next plugin line. Unity's Mono has no diagnostics port and cannot read another thread's stack, so there is no stack sampling. Instead the patcher wraps Harmony's `Patch` entry points (`patchMs`: time a plugin's assembly spent applying patches, the outermost call timed) and the bridge plugin times each plugin's patch methods and Update loops from the first frame to the title scene (`sampleMs`, shown as Sampled, with `sampledOtherMs` for the rest); both appear in the report only for a measured launch.
- **In-game frame timing:** a measured BepInEx launch arms the bridge through `<profile>/startup/.measure-launch`; from the first `perf start` the bridge wraps every plugin's Harmony patch methods and MonoBehaviour Update, LateUpdate and FixedUpdate with timers. Both companions answer `perf start` and `perf` with `{measured, seconds, frames, fps, frameMs{avg,p50,p95,p99,max}, monoUsedBytes, monoHeapBytes, gcCollections, baseline{frameMs, modsMs, withoutModsMs}, plugins[{guid, msPerFrame, p95Ms, peakMs, share, callsPerFrame}]}`; the SMAPI bridge wraps each mod's per-frame event handlers for at most ten minutes (SMAPI's own performance monitor has no 95th percentile or frame share). `p95Ms` is a histogram (about 10% resolution) and `baseline.withoutModsMs` is the average frame less the mods' timed code. `launchsvc.MeasureInGame` (`perf_bridge.go`) saves the rows as a performance report.

### Antivirus scan

- **Where:** `Store.install` calls `checkExtracted` (`internal/store/scan.go`, `scan_test.go`) on the extracted folder before the rename that makes it an item, so every path into the store passes it (archive, hashed dir, LAN receive, backup, profile import). Loader bundles are Mortar's own downloads and are skipped.
- **Scanners** (`internal/avscan`): Windows AMSI through `amsi.dll` (`AmsiScanBuffer` per 32 MiB of each file; a result of 32768 or more is malware; AMSI names no threat); clamd over a unix socket (`zINSTREAM`, 64 KiB chunks; socket: the setting, else `/run/clamav/clamd.ctl`, `/var/run/clamav/clamd.ctl`, `/run/clamd.scan/clamd.sock`, `/var/run/clamd.scan/clamd.sock`, `/tmp/clamd.socket`); a custom command (no shell; `{path}` replaced by the folder; exit 0 clean, any other code a detection named by the first stdout line); or off. Settings `antivirus` (`automatic`, `clamd`, `command`, `off`), `antivirusSocket`, `antivirusCommand`; socket and command are not portable fields.
- **Detection:** the install fails with `store.DetectedError` under `usererr.Malware` and the extracted files are deleted; the queue item fails with `errorKind` `malware`. The error carries the detection as typed `detail` fields (`usererr.Marshal`; read by `detectionOf` in `frontend/src/toasts/avOverride.ts`, no error-text parsing). **Install anyway** calls `profile.Service.AllowUnscanned` (the next install of that key skips the scan once) and records a `ChangeUnscanned` history event; CLI `--allow-unscanned`.
- **Real-time protection:** a file Windows blocks or deletes while Mortar writes or reads it (`ERROR_VIRUS_INFECTED`/`ERROR_VIRUS_DELETED`, 225 and 226, or a file vanished from a staging folder) reaches the same place through `store.RealTimeBlock` with `Removed` set, so there is no Install anyway.
- **Errors:** a scan that fails or times out (2 minutes) is not a detection: the mod installs and an `avscan:failed` event says so; "no scanner" is silent. `mortar antivirus status` (`avscan.StatusOf`) prints mode, scanner kind, product and whether a scan can start.
- **Acceptance:** `scripts/av-smoke.ps1` in the Windows VM (installed, running Mortar; `-ZipDir` default `C:\avsmoke` needs a Defender exclusion) builds a zip at run time from parts (Microsoft's AMSI test sample for `amsi`, EICAR for clamd; the repo never holds either string), installs it into a throwaway profile through the CLI, expects the `malware` refusal, repeats with `--allow-unscanned`, and writes PASS/FAIL and `failures: N` to `%LOCALAPPDATA%\Temp\mortar-av-smoke.txt`.

### Saves

Saves live in one folder, `%APPDATA%\StardewValley\Saves` or `~/.config/StardewValley/Saves`, which Steam Cloud syncs, so Mortar never moves it; profiles share saves unless one sets `separateSaves`.

- **Per-profile saves** (`internal/savesiso`, `savesiso_test.go`, `fileswap_test.go`): a `separateSaves` profile plays on `<profile>/saves` for the length of a launch with mods. `Apply` persists `Manifest{Journal, Saves, Profile, Held, Copied, Live}` as `saves.json` in `<data>/journal/<install id>-saves` before the shared folder moves, renames the shared folder to `<Saves>.mortar-shared` (a rename, never a copy) and points the save path at the profile's folder with a symlink, or a working copy (`Live`) where symlinks are refused. `Purge` undoes it, checking the disk at every step so it can run again after a crash; an incomplete copy is never written back. `Apply` refuses with `ErrUnrecovered` while an earlier swap's record exists; `RecoverDeploys` finishes a crashed one.
- **Where mods leave traces:** SMAPI writes no mod list into a save, but mods leave keys prefixed with their `UniqueID` (SMAPI's `smapi/mod-data/<uniqueid>/<key>`, `modData` keys such as `Sonozuki.MoreGrass/GrassOffsetX0`). Mortar scans the save's `key`/`string` XML entries and, ignoring case, takes for each key the longest prefix ending at a `/`, `_` or `.` boundary that is a `UniqueID` in the mod dataset's index. Splitting at the first `_` would be wrong: many IDs contain `_`, and for some the part before it is another mod's ID. Mods that keep no per-save data leave no trace and keys outlive a removed mod, so the warning says "this save has used".
- **Cost:** one streaming pass, cached by the save file's mtime. The same streaming pass reads `SaveGameInfo` for farmer, farm name, in-game date, `millisecondsPlayed`, `money`, and the farm layout `whichFarm`: 0 Standard, 1 Riverland, 2 Forest, 3 Hill-top, 4 Wilderness, 5 Four Corners, 6 Beach, 7 Meadowlands; -1 when the tag is missing.
- **Backups** (`internal/savessvc`; naming, kinds and rotation: [Storage](#storage)): Restore first zips the current Saves folder (kind `restore`), extracts beside Saves and swaps each save folder in by rename, so a failure leaves the old one; it refuses a zip path that would leave the extract folder, caps each file at 512 MiB, and is refused while the game is launching or running. `RunScheduledBackups` (`scheduled.go`, `scheduled_test.go`) checks every 10 minutes whether `saveBackupHours` has passed (measured from the newest `scheduled` zip after a restart), waits while a game runs (including one Mortar did not start) and zips each save changed since its own newest scheduled zip; stamps more than 5 minutes ahead of the clock are ignored.
- **Per-save gap:** `savessvc.SaveGap` compares the mods the save was last played with (`last-played.json`) against the profile (`missing`, `disabled`, `versionOlder`; `gap_test.go`); a save with no record has no gap. Each lacking mod is located as Problems locates a missing dependency (`problems.Locate`). UI: [gui-design.md](gui-design.md#main-screen).

### Mod data

- **Mod dataset:** SMAPI's `Pathoschild/StardewModDataset` (MIT or CC-BY-SA 4.0, published with explicit permission from the sites it lists, refreshed near the end of each month, 0.x with no version tags) records each Nexus mod page's current files with the SMAPI manifests inside (`Downloads[].Mods[]`, `SizeInBytes`), not every file. Fetched per page from `https://raw.githubusercontent.com/Pathoschild/StardewModDataset/main/dataset/data/Nexus/<mod id / 1000>/<mod id>.json`; the `UniqueID` index (`dataset/indexes/pages by mod ID.json`) monthly. A file it lacks is checked after download.
- **Update checks:** `POST https://smapi.io/api/v4.0.0/mods` with each mod's ID, `UpdateKeys`, installed version, plus `apiVersion`, `gameVersion`, `platform`, returns `suggestedUpdate`, taken as given; `compatibilityStatus` and `brokeIn` come only with `includeExtendedMetadata: true`. Unofficial versions (`metadata.unofficialUpdate`/`unofficial`/`unofficialForSmapi`) show as **Unofficial update available** and **Update all** never installs them. The API is public, unauthenticated and officially unreleased: answers are cached an hour in one cache shared by every profile, misses go in batches of 100, and after a failed ask Mortar serves stale or unknown answers for five minutes; failures never block.
- **Dependencies:** `Dependencies[]` (`UniqueID`, `MinimumVersion`, `IsRequired` defaulting to true) plus `ContentPackFor` as a required dependency on its framework mod. For a missing one Mortar prefers the Nexus page named in its own `UpdateKeys`, else the page whose files hold it at the highest version (one ID can appear on several pages), and takes the newest `MAIN` file satisfying `MinimumVersion`; one found only on CurseForge is listed with its page link, one on no site Mortar has a driver for (e.g. `ModDrop:N`) by name only. After an install, a still-missing required dependency is offered in a dialog whose Add them queues it.
- **Support:** Share log uploads `SMAPI-latest.txt` (or a stored run's log) to smapi.io via `internal/logshare`: `POST https://smapi.io/log`, form-encoded `input=<log text>`, no auth. Trap: the server answers a success with a redirect to `/log/<id>` (the link) and a failed or empty upload with HTTP 200 and its page, so only a redirect counts as success. A SMAPI log holds local paths including the user's name and anyone with the link can read it, so Mortar shows the log and asks first. Only a loader with the `loader.LogShare` capability (SMAPI) offers it, since smapi.io's parser reads no other loader's log (`support.CanShare`).
  - **Save diagnostics** writes `mortar-diagnostics-<date>.zip` through the native save dialog: `build.json`, `settings.json` with identity cleared and every field whose name says token, secret, key or password removed, `profiles.json` (no notes), `queue.json` without `nxm://` keys, `doctor.txt`, `runs.json` (3 newest, no log text), the last 2,000 lines of the Mortar logs and crash log, the open profile's SMAPI log when it owns it, and `manifest.txt` saying what is in and stripped. The home folder is written `~` and the keyring is not read.

### Problems

Problems warn and never block. The checks are in `internal/problems` (one file per family, each with a `_test.go`); each records per-family timings on the cached `Result` and logs `problems: <profile> <family> <duration> (<count> packs)`. Rules that are not obvious from the code:

- **Minimum game version:** compared against the loader's game version or, where it knows none, the version the game's last run logged (Vintage Story's `Game Version: v…` line).
- **Broken, obsolete, abandoned:** from SMAPI's API for the game version, with a one-click replacement when its `compatibilitySummary` names a Nexus or GitHub target Mortar can install. A mod whose replacement is enabled too is **superseded** and loses its Broken and Compatibility rows. Abandoned is info-level and dismissible per profile.
- **Source flags** (`source_flags.go`): `Broken` rows with `Source` naming the site: Nexus pages whose cached status is not `published` (read from the page cache, never fetched) and, through `source.StandingChecker`, Modrinth `archived` (`GET /projects?ids=`, 100 per request), CurseForge Inactive (7), Abandoned (8), Deleted (9) or `isAvailable: false` (`POST /mods`, 500 per request), GitHub `archived: true` (`GET /repos/<owner>/<repo>`, at most 20 per pass, stopping on a rate limit). Each answer is cached a day under `cache/standing-<site>-<hash>.json`. Thunderstore deprecations are `DeprecatedPackage` rows with **Replace with** the package the deprecated one's own summary names.
- **Known broken** (`known_broken.go`): the game's `knownBroken` list, matched by mod id or Thunderstore "Namespace-Name" and version range. **Redundant:** shadowed content packs and [Same job](#same-job); a mod is listed once. **Runs:** enabled mods that logged errors in the newest stored run. `PluginClash` (`pluginclash.go`): a `[BepInPlugin]` GUID declared by more than one enabled package (read from compiled plugins through `internal/dotnet`; BepInEx loads only one), with **Keep newer**.
- **Paths too long** (`longpath.go`, Windows builds only): an entry with a file the game would read at a full path of 260 UTF-16 characters or more (MAX_PATH counts the NUL, so 259 is the longest a game opens without `\\?\` paths or a `longPathAware` manifest; `LongPathsEnabled` is not read, since it lifts the limit only for the latter). Each file is taken where the game reads it: a redirected profile's `mods/` in place, less dot folders (switched-off mods); a `profile` game's package layout (`PackageFileOwners`, so before the first sync too), with the folder a `loader.PlacesFolder` loader places (the folder loader's mods target) moved under its path role. Mortar's own file calls take long paths, so nothing fails while copying. Wine opens such a path (BepInEx matrix `edge.longpath`), so Linux never checks. The walk starts once the rest of the check is done and is kept per mods fingerprint: the window's loads (`ProblemsNoWait`) answer without it, holding the previous walk's rows meanwhile so none leave and return, and `problems:changed` (game, profile) brings the new ones; `Problems` (the pre-Play check, the command line, background badges) and the check's `health.json` point wait for it. The pre-Play check lists the entries as `longPaths`.
- **Nexus-listed requirements** come from batched page data (`nexussvc.Prime`). The game's loader is never reported; any other outside download is a note with only Dismiss. Trap: Nexus lists a page-wide outside requirement for every file of the page, sub-packs included, so it is only Optional for a file whose own manifest declares dependencies and names none like it.
- **Cleanup** (listed, not counted; `cleanup.go`; **Remove** drops the framework, [gui-design.md](gui-design.md#problems-tab)): frameworks no enabled mod needs but a switched-off mod still names; conservatively detected unused Content Patcher tilesheet packs (a pack that edits an existing sheet is a retexture and never a candidate); enabled mods made for a recolour the profile does not have enabled.
- **Content Patcher config suggestions** (`internal/framework/contentpatcher/settings.go`, `settings_recolour.go`, tests `settings_test.go`, `variant_suggestions_test.go`): an on/off `ConfigSchema` field whose value runs none of the pack's `HasMod` compatibility patches is suggested with the values that would; fields that list NPCs are never suggested; a variant picker (palette, recolour) is recognised from the pack's own mapping and suggests its automatic choice. **Set to** writes only that field into `config.json` and remembers the field and value so the reverse suggestion stays hidden until the value changes.

#### Content Patcher conflicts

Rules: `internal/framework/contentpatcher` (`contentpatcher.go`, `winner.go`, `conflict_evidence.go`; tests `contentpatcher_test.go`, `winner_test.go`, `conflict_evidence_test.go`, `contentpatcher_regression_test.go`). The invariants:

- **What counts:** two or more enabled packs that `Load` the same target (warning: only one wins; a Load without `Priority` is `Exclusive`), or that `EditImage`/`EditMap` the same target or `EditData` the same entry or field (info, dismissible per profile). `EditData` that only shares a target is not reported. Overlap is never reported between packs built to work together (one entry, or one names the other as a manifest dependency or in a `HasMod` condition).
- **Only edits that can both apply count:** a `HasMod` condition counts only when it holds for the enabled mods; a change whose config conditions do not match the pack's current settings (`config.json`, else schema `Default`) is not counted; edits needing different spouses, or disjoint literal `LocationName`, `LocationContext`, `Season`, `Weather`, `DayOfWeek` or `FarmType` values, never apply together. Image edits conflict only where an opaque 16x16 source cell lands; JSON equality is by parsed value, so formatting creates no conflict.
- **Cosmetic or harmless:** a conflict whose every overlap is harmless (both image edits, both text edits, a literal `LocationName`/`LocationContext`/`Weather` gate, a one- or two-tile area at a tokenized position) shows under **Cosmetic or harmless** and is never counted.
- **Evidence** is per pack; `Problems` leaves it out (it is most of the result's size) and `ConflictEvidence` returns one conflict's when **Why?** is expanded.
- **Fixes:** per pack the narrowest on/off field every clashing edit needs is offered as **Set the field to its other value**; a field that would leave the pack nothing active, or that gates a fifth or more of its patches without being named for the target, is never offered.
- **Conflict winner:** "Make <mod> win" records the loser's UniqueID in the winner entry's `loadAfter` and adds it to the winner's installed `manifest.json` as an optional dependency, so SMAPI loads the winner later; the profile's `manifest.json` is its own copy, so the store is untouched, and the dependency is rewritten after an update. Load-against-Load conflicts still need one mod disabled.

#### Same job

Redundant lists enabled C# mods that change the same game members (`internal/dotnet`, `contentpatcher/footprint.go`, `internal/problems/samejob.go`, tests alongside; assembly reads cached by file size and mtime in `cache/problems-assemblies.json`). A mod's footprint is the `StardewValley` properties and fields its `EntryDll` assigns, read from the compiled IL, plus its Harmony-replaced methods from the startup report; input-only members (`mouseClickPolling`, `lastClick`, `FacingDirection`) are dropped. Members are weighted ln(N/df); a pair is flagged when the shared weight reaches 0.45 of the larger mod's total and some shared member is written by 12 mods at most, unless one depends on the other, they share an author or download, or another enabled mod depends on either. A smaller mod is also listed as covered by a larger one when the larger changes 0.8 of its footprint by weight, the smaller footprint weighs at least 10, and every shared member is written by 12 mods at most; without those guards large mods cover one-member mods incidentally.

#### Asset map

Every asset an enabled mod changes (`contentpatcher/assetmap.go`, `internal/problems/assetmap.go`), with each mod's Action and Priority and the winner; mods are ranked in SMAPI load order (`internal/loadorder`), not profile order. Edits apply by priority, then load order, then patch order ([Content Patcher's EditData docs](https://github.com/Pathoschild/StardewMods/blob/develop/ContentPatcher/docs/author-guide/action-editdata.md), Priority). Trap: for Loads the last loaded wins on a tie although the Load docs say "first" (`PatchManager.ApplyPatchesToAsset` replaces its pick with every later candidate that is not strictly lower); two Exclusive loads apply neither. A losing mod offers **Make win** only when it ties the winner's priority and no other mod in the group already loads after it through its dependencies.

#### Problem scan caches

- A check reuses each patch's shape index and a pack's reachable dynamic tokens. The tilesheet map-file scan is saved in `cache/problems-map-scans.json` (gzip). Problems reads the newest run's id from the run index rather than its log.
- A one-time zip-name repair walks the store and profiles; `names-repaired` in the data folder marks a clean pass. Every launch points a mod record whose folder is gone at the one folder differing only by U+FFFD standing for real characters, so switching that mod off keeps working.

#### Generic Mod Config Menu

Menus a mod registers with GMCM or GMCM Options come from mortar-smapi-bridge, which runs inside the game: it writes each menu to `<profile>/gmcm/<UniqueID>.json` (index `_index.json`). Edits made through `mortar mods menu` wait in `<profile>/gmcm-pending/<UniqueID>.json` until the next launch, when the bridge applies them through the setters registered with GMCM, then the mod's save callback, and writes `<UniqueID>.result.json` (applied or skipped). The bridge finds the profile by walking up from its folder to the first holding `profile.json`. The config editor lists the menu as an **In-game menu** file; widgets the bridge cannot set (colour, image, custom drawing) are read-only. `Store.SetGmcmOption` (`internal/profile/gmcm.go`) checks a change against the capture, writes or drops the pending edit and records a history event; the pending files are part of the config capture history keeps, so Undo puts them back.

#### Other per-entry settings

- **Update channel:** an entry's `updateChannel` is empty (main files only), `optional` (also newer OPTIONAL files on the same Nexus page) or `beta` (also prerelease versions); it filters offers where pins and skipped versions do. GitHub reads `beta` as prereleases (`github.Select`); CurseForge and Modrinth read the three as release, release and beta, and release, beta and alpha files (`source.Stability`, which `InstalledFile.Channel` carries to `UpdateChecker.Latest`).
- **Config presets:** a mod's `config.json` can be saved by name under `<data>/config-presets/<game>/<local id>/<name>.json` and applied to any profile's copy as one history event. A profile's `groups` enable or disable together in one history event; after each problem check the counts are appended to `health.json` beside `profile.json` (newest 200 points).

## Nexus Mods

Sources: the API acceptable-use policy (help.nexusmods.com article 114), the SSO demo `Nexus-Mods/sso-integration-demo`, the `Nexus-Mods/node-nexus-api` client, and Vortex's (`Nexus-Mods/Vortex`) `NXMUrl.ts`. Client `internal/nexus` (REST v1, GraphQL v2), service `internal/nexussvc`; endpoint shapes and caching are in their tests.

- **Sign-in:** Settings takes a personal API key, kept in the OS keyring and never sent to a server of ours. `GET /v1/users/validate.json` gives the account's `user_id` and `is_premium`. Every request carries a truthful `Application-Name` and `Application-Version`.
- **Browser sign-in:** build flags pick the flow: `-X github.com/Rethunk-Tech/mortar/internal/nexussso.ClientID=<id>` selects OAuth PKCE (wins over a slug), only `-X .../internal/nexussso.Slug=<slug>` selects legacy SSO (dial `wss://sso.nexusmods.com`, send `{id, token, protocol: 2}`, open `https://www.nexusmods.com/sso?id=<uuid>&application=<slug>`, read the key off the socket), neither hides sign-in. OAuth uses S256, scopes `public openid profile` and one fixed loopback redirect `http://127.0.0.1:51762/oauth/callback` (`nexussso.RedirectURI`; Nexus registers a non-dynamic callback, so a taken port fails the sign-in); tokens live in the keyring as `nexus-oauth`, every call carries `Authorization: Bearer` (`nexussvc.Authed`) and a pasted key is refused. The API-key path is isolated in `nexussvc/apikey.go`, `nexus/auth.go` and the key box (each marked `remove with the API-key path once OAuth ships`). Registration facts: [nexus-application.md](nexus-application.md).
- **Browse:** search uses the public v2 GraphQL endpoint (`POST https://api.nexusmods.com/v2/graphql`), which needs no key. Trap: a category list is an AND in Nexus's filter, so included categories become one OR branch each, every branch also excluding the excluded ones; category names come from the game's category list, which Nexus serves only to a signed-in account. GitHub search is `search/repositories` with the game's topic (`topic:stardew-valley-mod`; Lethal Company `lethal-company-mod`).
- **Downloads need the user ([AGENTS.md](../AGENTS.md)):** update checks (including the background check every four hours, which only notifies) are allowed, but a Nexus file is never downloaded or installed without a user action, and a queue restored from a previous session is held paused at startup when it holds a Nexus file. A Nexus collection link previews and imports like a share link.
- **Update path:** a Nexus mod's update comes from SMAPI's API through the mod's `UpdateKeys` (`Nexus:<id>`), asked in batches ([Update checks](#mod-data)), and the Nexus file lists then decide the file. Trap: Mortar never searches Nexus once per installed mod (`problems` skips `nexus` and `github` sources in its per-source update search): that would spend hundreds of the hourly quota to repeat SMAPI's answer. Page data for many mods is one GraphQL `legacyModsByDomain` request per 50 mods (`nexus.Client.ModsByDomain`; Nexus caps a query's complexity at 10,000 and a mod with its requirements costs ~160), cached by `nexussvc.PrimeDetails` in `cache/nexus/page-v2-<domain>-<id>.json` (`Partial`: no file list, changelog or description until `Details` replaces it).
- **Manual downloads:** per-game `offerNewDownloads` offers new archives landing in the user Downloads folder or Mortar's download folder, one toast per batch; nothing installs on its own (`internal/dlwatch`, `internal/folderwatch`, `archivesvc.NewDownloads`). A Nexus file name `<name>-<modId>-<version>-<timestamp>.<ext>` supplies the mod id, otherwise `dlwatch.Identify` peeks `manifest.json` in a zip.
- **Pictures:** a mod's `picture_url` and `endorsement_count` (`GET /v1/games/<domain>/mods/<id>.json`) are fetched once when installed; pictures are cached under `cache/modpic` (pruned at startup by mtime to 64 MiB) and served at `/mod-picture/` for the Browse sources' picture hosts only, images up to 8 MiB.
- **Rate limits** (a free account): `x-rl-daily-limit: 20000`, `x-rl-hourly-limit: 2000`, with `-remaining` and `-reset` headers; the client reads them on every response and pauses before running out.
- **Mod page details** (`nexussvc.Details`): the page, `files.json`, `changelogs.json`, requirements and the category name (`GET /v1/games/<domain>.json`, cached 30 days) live in `<datadir>/cache/nexus/details-v4-<domain>-<mod id>.json`, never in `profile.json`; signed out, rate-limited or offline, the cached copy is served however old. `available` false marks **Hidden on Nexus**, `status` other than `published` **Removed from Nexus**; those pages are not offered as updates. Changelog notes containing `breaking`, `incompatible`, `requires`, `now needs`, `new save`, `start a new`, `not save compatible` or `remove before updating` mark the update row with a warning ([gui-design.md](gui-design.md#download-queue)).
- **Endorse and track:** only on the user's click, signed in: `POST /v1/games/<domain>/mods/<id>/endorse.json` and `abstain.json` with `{version}`; `POST`/`DELETE /v1/user/tracked_mods.json` with `{domain_name, mod_id}`.
- **Files:** `GET /v1/games/<domain>/mods/<id>/files.json` lists every file with `file_id`, `file_name`, `version`, `mod_version`, `category_name` (`MAIN`, `OPTIONAL`, `UPDATE`, `MISCELLANEOUS`, `OLD_VERSION`, `ARCHIVED`, or null), `size_kb`, `is_primary`. An update takes the `MAIN` file matching SMAPI's `suggestedUpdate`, else the `is_primary` one, and never an `OPTIONAL` file unless the profile already uses it. A file whose GraphQL v2 `modFiles { fileId scannedV2 }` is `QUARANTINED` is omitted, and a request for it fails the queue item.
- **Download links:** `GET /v1/games/<domain>/mods/<id>/files/<file id>/download_link.json`. Premium accounts get links directly; they expire, so Mortar asks just before downloading and again on a restart. A free account gets HTTP 403 ("...this is for premium users only") and needs the `key` and `expires` from the `nxm://` link of the site's Mod Manager Download, one click per mod. Each answer lists several CDN mirrors (`name`, `short_name`, `URI`); Settings › Downloads **Preferred download server** picks one.

### `nxm://` links

`nxm://<domain>/mods/<mod id>/files/<file id>?key=<key>&expires=<unix>&user_id=<id>`; Mortar takes this form only for a Nexus domain a catalog game maps to (`internal/nxm/link.go` `Parse`, `link_test.go`).

- **Registration:** only one app can own the scheme, and Wails' NSIS macro would delete and rewrite its key at install time without asking (`build/windows/nsis/wails_tools.nsh`), taking it from Vortex or Mod Organizer 2. So `nxm` is not in `build/config.yml`: Mortar registers it at runtime after the user agrees (Windows `HKCU\Software\Classes\nxm`; Linux a user-level `tech.rethunk.Mortar.desktop` with `x-scheme-handler/nxm` and `xdg-mime default`), records the previous handler in `settings.json` (`nxmPreviousHandlers`, `nxmPreviousName`) and restores it when turned off or when uninstall runs `mortar.exe --release-links`. Other games' links can be forwarded to the recorded handler (`internal/nxm/forward.go`).
- **Bursts:** each `nxm://` launch is a second instance whose arguments the running one queues at once and handles in order; a link that arrives again before its own `expires` is taken once (in memory only).
- **Browser limit:** Chromium browsers launch at most one external protocol per user gesture (`g_accept_requests` in `chrome/browser/external_protocol/external_protocol_handler.cc`), so Nexus Slow Download countdowns that end with no click in between are blocked (`Not allowed to launch 'nxm://…' because a user gesture is required.` in the tab's console).

### Browser extension host

The extension lives in its own repo (<https://github.com/Rethunk-Tech/mortar-browser-extension>, MV3 for Chromium and Firefox; UI in [gui-design.md](gui-design.md#browser-extension)). It avoids the gesture gate: on `www.nexusmods.com` it reads each `nxm://` anchor and sends it with `sendNativeMessage` to the host `tech.rethunk.mortar`, which is Mortar itself (`internal/nativehost`: Chromium passes the extension origin as the first argument, Firefox the manifest path and extension id). That process starts `mortar <link>`, so the link takes the same second-instance path.

- **Protocol:** every extension message carries `protocol` and every reply carries Mortar's (`nativehost.Protocol`, 3). Mortar answers `MinProtocol`..`MaxProtocol` (3..3; a message without one counts as 0) and refuses others with `protocolError` `extensionTooOld` or `extensionTooNew`, recorded in `extension-contact.json` as `mismatch`. A change to a message's shape bumps both sides. Message and reply shapes: `internal/nativehost/nativehost.go`, `nativehost_test.go`.
- **Data requests** are read-only, for Nexus pages only, and start no download: `installed` returns `modIds` (and `brokenIds`, from the cached SMAPI compatibility list) for the last-open profile of the game the Nexus domain maps to; `mod` returns that profile's entry and the other profiles'. The page's game is the Nexus domain, not a hard-coded Stardew id; every reply carries `games` so the extension maps a page's key to the Mortar game id and opens `mortar://<game id>/mod/<id>`. The extension follows the Download link of Nexus's requirements dialog only when it points at the page's own mod, because Mortar resolves requirements itself.
- **Project requests** (`installedProjects`, source `curseforge` or `vsmoddb`, `sourceGameKey` the game's source key; none just lists `games`) return `projects` (`{id, name, slug}`; slug is the CurseForge slug or Mod DB alias, cached in `cache/extension-project-pages.json` after a background site lookup, so empty on the first reply) for that game's open profile: a CurseForge entry's project id, a Mod DB entry's asset id (the id its pages are addressed by). The extension hands CurseForge `curseforge://install` and Mod DB `vintagestorymodinstall://` clicks over as `link`, which `source.IsLink` accepts like `nxm://`.
- **Host manifest:** on Linux, turning nxm handling on (and every start while on) writes the host manifest into `NativeMessagingHosts/` of each installed Chromium browser under `$XDG_CONFIG_HOME` (Chrome, Chromium, Brave, Edge, Vivaldi) and `~/.mozilla/native-messaging-hosts/`; turning it off removes them (`internal/nxm/nativehost_linux.go`). A Flatpak build writes none. The unpacked extension's id is fixed by the `key` in its manifest.

### Download queue

An import or a profile's missing files run one queue (`internal/queue`: `queue.go`, `work.go`, `resume.go`, `merge.go`, `overlay.go` and tests), persisted in `<datadir>/queue.json` without `nxm://` keys. **No re-hosting:** mod files and Nexus data stay on the user's machine; a share link holds IDs only. Rules a change must keep:

- Items store as `nexus-<mod id>-<file id>`; the entry records source kind `nexus` with mod id, file id, version, picture URL and endorsement count, fetched once at install. Source kinds (`profile.Kind*`): `local`, `nexus`, `github`, `thunderstore`, `modrinth`, `curseforge`, `itch`, `vsmoddb`, plus `smapi` and `mortar` for bundled entries; a `github` source holds `repo`, `tag`, `asset` (share links read them as `<owner>/<repo>@<tag>/<asset>`).
- **`latest`:** installs started from a save's missing mods, a missing dependency or a Problems fix follow Nexus `file_updates` to the newest listed file, because the file they name came from the dataset or a save and may be old. Share imports leave it off to reproduce the shared files.
- **Which file an update downloads** (`nexus.Supersedes`, `internal/nexus/choose.go`, `update_selection_test.go`): a page can hold several downloads (a main file and optional packs) and its version is the main file's, so the page's version never decides. In order: the author's `file_updates` chain; a newer file of the same download (display name or archive stem); the one current file of the entry's category at the new version; for a MAIN entry on a page with exactly one current MAIN file, that file. When the installed file is the newest of its download the mod has no update, however high the page's number; when none supersedes it but a current file of another download exists the update is marked `pickFile` and nothing queues it. A queued update that resolves to a file the profile already holds ends `skipped` (`queue.skipHeld`).
- **Update to CurseForge:** a mod whose newest version SMAPI reports from a `CurseForge:<id>` update key is resolved through the CurseForge driver (`problems.curseforgeSwitches`): the newest stable file becomes an update of source `curseforge`, marked `switch` with `fromSource` when installed elsewhere; a project that forbids downloads outside CurseForge shows as `notDistributable`.
- Premium accounts download without clicks. A free account's head item waits for its click (**Open download page**, **Skip**) and a matching `nxm://` link is routed to it. A Nexus file the game's store already holds installs from the store with no download and no click, unless the profile has an entry from the same mod page, whose Install together choice needs the archive. A reached rate limit, Nexus's or GitHub's, pauses the whole queue until its reset.
- **Large downloads and free space** (`internal/queue/size.go`, `size_test.go`): just before the first byte, `guardSize` takes the size the source gave up front (Nexus `size_kb`, Thunderstore, Modrinth, CurseForge and itch.io sizes from the resolve step, a GitHub asset's `size`). Free space is checked first: the archive (less any partial already on disk) plus twice its size for the extraction plus 512 MB must fit, on the downloads folder's volume and on the data folder's (one sum when the downloads folder is inside it). A download that does not fit fails with `NoSpaceError` (`errorKind` `disk`) before any bytes, with no way to override; `Deps.FreeBytes` is the test seam. A download over `LargeDownloadBytes` (2048 MB, a constant) then parks in `StateConfirmLarge` until `ConfirmLarge` (Continue anyway, sets `largeOk`, which survives a restart) or `Cancel`. An item with no size up front downloads without either check and keeps the after-the-fact `DiskFullError`. The Nexus check runs after the store lookup, so an item installed from the store never asks.
- **Resume** (`github.Download`, the one path every queue download takes: Nexus, Thunderstore, Modrinth, CurseForge, itch.io, Vintage Story Mod DB and GitHub; SMAPI, MelonLoader and component downloads use it too): a retry, restart or unpause sends `Range` from the partial's size, with `If-Range` (the strong `ETag`, else `Last-Modified`) while the address is unchanged. It accepts 206 only when `Content-Range` starts at the offset and its total equals the recorded size; it starts over on 200, on a changed validator, a changed total, or a partial nothing vouches for (no sidecar, no size, no validator), at most three times. A new address (another Thunderstore CDN, a fresh Nexus link after a dead one) resumes the same partial when the total matches, since its validators differ; the final size, `X-Checksum-Sha256`, `Content-MD5`, Nexus MD5 and package digest checks then decide, and a mismatch deletes the file. A network error, a stall or a pause keeps the partial; a failed check, Cancel and Skip delete it. Loader pack fetches (`host.Direct`, small one-shot files) do not resume.
- **Queue states** besides the final ones: `paused` is a user pause of one item (`PauseItem`, `ResumeItem`; `queue pause-item|resume-item ID`). It cancels the transfer, keeps the partial and survives a restart; the rest of the queue goes on and a paused item holds no download slot. `paused` with `autoResume` is an item that yielded its slot to **Download now** (`Top`, `queue top ID`): it starts again by itself, in queue order, when a slot is free, and also after a restart (a Nexus one waits for the queue to be resumed). `Top` moves the item to the front behind its pending dependencies (`Item.needs`, the package ids it requires), which move and unpause with it; when every slot (`min(Parallel, 3)`) is busy it pauses the last running downloads that are not among them. `Move` swaps an unfinished item with its neighbour. Order is the order of `queue.json`'s `items`. `HoldForPlay` (from `launchsvc.OnState`, when a launching or running game resolves `pauseDownloadsWhilePlaying` true for its profile) pauses running downloads the same way and starts none until the game exits; installs go on. `github.SpeedLimit` (`downloadSpeedLimit`, MB/s) feeds one token bucket (`throttle.go`) that every download shares, read on each chunk. Failed and paused items report `partial`, the bytes on disk, so the window says "Resume" instead of "Retry".

## GitHub releases

`internal/github` reads `/repos/<owner>/<repo>/releases` without sign-in. Answers are cached on disk for an hour and served stale when GitHub is unreachable. The unauthenticated limit is 60 calls an hour per IP; a reached limit shows its retry time. SMAPI's own release lookup uses the same client.

- **Trust** (`internal/github/verify.go`): a GitHub-sourced install counts as verified only when SMAPI's update API (`includeExtendedMetadata: true`) maps the manifest's `UniqueID` to the same repo. A known mismatch parks the item in `needs-confirm` (Install anyway or Skip); an unknown answer installs and marks it "could not verify"; nothing here blocks.
- **Asset picker** (`internal/github/pick.go`, `pick_test.go`): for a release with several archives the first rule that leaves one wins (the asset shaped like the one the user last chose, kept in `github-choices.json`; else installable assets; else zips one of the game's loaders recognises); several left park the item in `needs-choice`.
- **GitHub vs Nexus for updates:** Update review uses GitHub when the mod's update key is `GitHub:<owner>/<repo>` and SMAPI's suggested update URL is on github.com; otherwise Nexus. A free Nexus account must click for every file, so a Nexus update carries a GitHub fallback repo (`GitHubFallback`) and, when the item would wait for that click, the queue downloads a GitHub release at the same version with exactly one archive; the staged archive must contain the updated mod's UniqueID (`FallbackID`), else the item goes back to Nexus.
- When an update check finds a manifest older than the download it came in (the installed file is already the suggested version), Mortar sets that manifest's `Version` to the suggested version in the profile's copy and the store item, so SMAPI stops offering an installed update; a mod from another file of the same entry is never rewritten.

## Sharing

- **Form:** Discord makes only `http://`, `https://` and `discord://` links clickable (Discord community posts 14574789338135 and 25441082215447), so a link is `https://mortar.rethunk.tech/<game id>/p#<payload>`, handed to the app as `mortar://<game id>/p/<payload>`. Each playable game's share page is built from `web/src/pages/[game]/p/index.astro`, all running `web/public/share/app.js`. Browsers never send the part after `#`, so no profile data reaches any server. The app accepts either form, or a bare payload.
- **Payload** (`internal/share/share.go`, `share_test.go`): compact JSON `[3, "<profile name>", "<game id>", {"<source id>": "<that source's game key>"}, [<entry>, ...], "<game version>"]`, Brotli quality 11, base64url without padding (`github.com/andybalholm/brotli`, MIT; the standard library has none). The leading number is the format version (only 3 is read); the game version is optional. The link holds no `UniqueID`s, which barely compress. About 240 mods fit a 2,000-character Discord message. `web/test/testdata/go-link.txt` is the link the app's encoder made, read by both the Go and site tests.
  - **Entry** = object naming its source, so a link names the exact file: `{"s":"nexus","mod":<id>,"file":<id>}`, `{"s":"github","repo":"<owner>/<repo>","tag":"<tag>","asset":"<asset>"}`, `{"s":"thunderstore","ns":"<namespace>","name":"<name>","version":"<version>"}`, `{"s":"curseforge","mod":<project id>,"file":<file id>}`, `{"s":"vsmoddb","name":"<modid>-<assetid>","file":<release id>,"version":"<version>"}`, `{"s":"itch","name":"<user>/<game>"}`, `{"s":"patreon","name":"<post id>"}`. The format version is unchanged for new sources: an older Mortar rejects an unknown source as a bad entry.
  - **Optional extras:** `disabled`, `fomod`, `note`, `tags`, `files` (a split archive's per-file `note` and `tags`), `overlay` (`from`, `to`, `off`), `imp` (implicit entry), `pin`/`pinr`, `grp`; for the share page `kb` (store item size, two significant digits) and `min` (newest `MinimumGameVersion`). Past the cap `kb` and `min` go first, then the extras except `imp`. A share with no `imp` entry may predate install reasons, so the receiver infers them (a listed package another listed package requires is implicit; members of a cycle nothing outside requires stay explicit); profile codes, `.r2z` files and modpacks are inferred the same way.
  - **What is shared:** only enabled entries with a source; local archives and switched-off entries are listed at Share as left out. Every entry cut from one store item is one ref keyed by `Entry.StoreKey()`, carrying the switched-off entries' ids in `disabled`. SMAPI's bundled mods and the bridge are never shared, listed or imported. CurseForge downloads with the receiver's own key (without one the preview lists it unavailable, `sharesvc.ReasonCurseForgeKey`); itch.io and Patreon entries travel as the page alone; optional files install after their main file (`Request.Overlay`). Nexus thumbnail URLs are too long for the share page's 8 KB, so it shows pictures only where public, keyless URLs follow from the link.
- **Import** (`internal/sharesvc`, `preview.go`, `preview_test.go`): the preview resolves every entry and creates nothing (a Nexus file that is gone or `ARCHIVED` is replaced by the `MAIN` file with the same version, else the primary file, marked "different file"); nothing downloads before the user's click on **New profile from link** or **Add to the selected profile**. The Share dialog suggests the file over 240 mods or the 8 KB payload cap.
- **`.mortar` file:** a zip holding `profile.json` (same format version and entries as a link, the game and its source keys, name, notes, description and the shared mods' ids `ids`, which bound the config files it may carry), `configs/<format>/<local id>/<relative path>.json` for each enabled mod's `.json` files except `manifest.json`, and `loader/<path in the profile>` for text config files (`.cfg`, `.json`, `.toml`, `.ini`, `.yml`, `.yaml`, `.txt`, valid UTF-8) under the config folders of the loader the profile runs (`loader.WithConfig`), leaving out the companion's state file. Files over 1 MiB, with unusual names or past the totals are skipped and listed at Save. The description (at most 280 characters) travels only in this file; colour and icon travel in neither. The profile's favourite star travels only in this file too, and a mod's star (a per-game setting) in neither.
  - `share.Apply` writes config files once their mods are installed: only under a folder an installed mod of that import already has, re-validated at write time, never over mods the profile already had; waiting ones are kept in `<datadir>/pending-configs.json`, independently of queue rows.
  - **Problem choices** (`problems` in `profile.json`; File and LAN only): `dismissed` tokens (kept in `settings.Dismissed["~mortar/cp/<game>/<profile>"]`) and `wins` (`Component.LoadAfter`), caps 1,000 of each with tokens at most 300 bytes; a file past them is refused whole. The receiver only adds (`sharesvc.applySharedChoices`, `choices.go`) and skips a win when the profile decided the pair the other way.
- **Routing:** `mortar://` is in `protocols:` in `build/config.yml` and `.mortar` in `fileAssociations:`; on Linux `nxm.System.RegisterLinks` writes `~/.local/share/mime/packages/mortar.xml` and the `xdg-mime` defaults. A link reaches the app as `events.Common.ApplicationLaunchedWithUrl` on a cold start (fired when the only argument contains `://`, `Rethunk-AI/wails` `v3/pkg/application/application_linux.go:73-83`) or in `SecondInstanceData.Args` when running (`sharesvc.Receive`); it opens the Import dialog filled in, never importing by itself. `mortar://<game>/mod/<id>` (a positive decimal Nexus mod id with no leading zeros) selects the Nexus mod on the Mods tab (`route.go`, `route_test.go`).
- **Trust boundaries:** a link's encoded payload is capped at 8 KB and its decompressed form at 64 KB before parsing; a `.mortar` file at 32 MiB, 5,000 entries, 1 MiB per config and 32 MiB of configs, and any entry outside its layout fails the whole file; the clipboard is read only when the user presses Paste. Extraction limits: [Trust boundaries](#trust-boundaries).
- **LAN sharing** (`internal/lan`): with Settings › General **Share profiles on the local network** on, Mortar advertises `_mortar._tcp` (hashicorp/mdns) and serves HTTP on `lanPort`; sends are refused while sharing is off and incoming shares are rate-limited per peer (10 s). A send is a `.mortar` payload (at most 32 MiB). To a paired computer every option applies and archives added from disk travel as store items; to an unpaired one config files are dropped (they can hold keys) and local archives left out. Handshake protocol 5. UI: [gui-design.md](gui-design.md#profile-management).
  - **Pairing** makes two of the user's own computers trust each other, independent of any store account: a single-use code (8 characters, valid 5 minutes) shown on one and typed on the other, leaving a 32-byte key in `<data>/lan/peers.json` (0600). Exchange (`POST /pair/begin`, `/pair/finish`): X25519 from both sides, then HMAC proofs over the transcript and the X25519 secret keyed by a PBKDF2 stretch of the code (200,000 rounds), so a passive observer cannot test code guesses; the long-term key is HKDF of the X25519 secret, never of the code. A host locks a peer for 10 minutes after 5 wrong codes and burns the code after 15. Threat model: top of `internal/lan/pairing.go`.
  - **Share handshake** (`protocol.go`, `service.go`, `paired_import_test.go`): `GET /hello` returns the receiver's id and a one-minute nonce bound to that peer; `POST /share` carries the payload, the sender's port and id and, when paired, an HMAC-SHA256 proof under the pairing key over the nonce plus SHA-256 of the payload (the key is never sent). A paired share's response carries a 5-minute Bearer token scoped to the store keys of every entry, with a proof under the same key so the sender never grants a token an unpaired computer made up.
  - **Store transfer** (`transfer.go`): the receiver `GET`s `/store/<game>/<key>` with that token and the sender streams a tar of each granted store folder (10,000 entries and 2 GiB caps). Invariant: the receiver installs through `Store.AddDir` only when the hash of what arrived (`store.HashDir`) equals the one the sender vouched for, and refuses an entry with no vouched hash; the vouched hash is an HMAC over game, entry key and hash under the pairing key (`entryDigests`), so what an eavesdropper serves on the unauthenticated transfer address cannot pass for what the sender holds. Sending between one's own machines is copying, so a paired receiver gets the files whatever the source or licence.
- **Windows firewall:** the per-user installer adds no firewall rule. Settings › General **Fix** relaunches Mortar elevated (`--firewall-allow`), which writes the rules through `INetFwPolicy2` (`internal/lan/firewall_windows.go` `AllowFirewall`): it removes every inbound block rule for the executable (Windows names the ones it creates after the file description, not `Mortar`) and writes a rule for every network profile so Windows never prompts (default: allow on Domain and Private, block on Public). When every connected network is Public and the allow-any-address setting is off, Mortar does not listen and LAN use returns a Permission error (`publicBlocksListening`, `errPublicNetwork`).
- **Nexus collection draft** (`sharesvc.ExportCollection`, `collection_export.go`, `collection_export_test.go`): read-only (no Nexus write); one `collection.zip` holding `collection.json` in Vortex's `ICollection` shape ([`ICollection.ts`](https://github.com/Nexus-Mods/Vortex/blob/master/src/renderer/src/extensions/collections/types/ICollection.ts)), using the importer's Go types so `parseChoices` reads an export back. Nexus takes a collection as a 7z, and no 7z-writing Go library is in go.mod (`bodgit/sevenzip` is read-only), so the export is a zip and the toast gives a one-line repack to 7z.

## Sync folder

`internal/syncsvc` keeps each profile's state in step between computers through a folder that another tool (Syncthing, Dropbox, a NAS) carries. It carries the profile's `.mortar` export (never mod files, so every computer downloads each mod from its source). The folder is the `syncFolder` setting (empty is off); `main.go` runs the service with a five-second quiet period.

- **Layout:** `<folder>/<game>/<remote id>.mortar` is the payload and `<remote id>.sync.json` the version file `{name, machine, machineName, vector}`; the vector maps a machine id to the newest revision that machine wrote. The payload is written first and the version file last, so a computer that sees a version finds the payload it names. Local state `<data>/sync-state.json` holds this machine's random id and, per local profile, its remote id, the vector last written or applied and the profile's `updated` time then.
- **Offers** (`syncsvc.go`, `property_test.go`): a version file whose vector holds a revision this machine lacks becomes an **offer**, never merged. `Resolve(game, remote, "theirs")` makes the profile match the payload through the share service's replace and adopts the remote vector; `"mine"` keeps the local profile and writes a revision on top of both vectors. A profile changed on both sides is flagged `Conflict`.

## Release

Build and publish mechanics live in `Taskfile`/`build/` and [HUMANS.md](../HUMANS.md#release) (workflow, how `wails3` is built from the fork, the update key); facts that settle questions:

- **Linux artifacts:** AppImage (`wails3 task linux:create:appimage`; AppRun sources `build/linux/appimage/glibc-check.sh`, because the bundled WebKitGTK and GTK 4 need host glibc 2.38 or newer: an older host gets a dialog pointing to the Flatpak); nfpm `.deb`/`.rpm`/Arch (`wails3 task linux:nfpm`) from a binary linked with `-X main.packaged=deb`; a Flatpak bundle (`wails3 task linux:flatpak`, built with `--runtime-repo=https://dl.flathub.org/repo/flathub.flatpakrepo` so the bundle can fetch its runtime; the GNOME Platform and SDK version is the manifest's `runtime-version`); the packaged ELF (`bin/mortar-aur-linux-amd64`/`-arm64`) for the AUR `mortar-bin` PKGBUILD (`build/linux/aur/`) (the nfpm packages carry `share/metainfo/tech.rethunk.Mortar.metainfo.xml`); and the AppImage's unpackaged binary as portable `bin/mortar-linux-amd64`/`-arm64`, which updates itself and writes its own desktop entry and nxm handler. amd64 and arm64 both ship; Stardew Valley has no native ARM Linux build and runs through Box64 or FEX there. The package remove script (`build/linux/nfpm/preremove.sh`, skipped on upgrade) runs `mortar quit`, `--release-links` and `uninstall-cleanup` as the user who ran the package manager through sudo or pkexec (per-user state is out of root's reach otherwise).
  - **arm64:** CI runs it only on `v*` tags (`ubuntu-24.04-arm`); local arm64 deb/rpm/Arch are `wails3 task linux:build:arm64`; the AppImage stays CI-native because linuxdeploy-aarch64 needs qemu plus a full runtime.
- **Flatpak sandbox:** finish-args (`build/linux/flatpak/tech.rethunk.Mortar.yml`, copied into the Flathub manifest by `build/linux/flathub/render.sh`) expose the game libraries and launcher data Mortar manages; other paths are invisible until `flatpak override --user --filesystem=<path> tech.rethunk.Mortar`. The sandbox cannot see the host's Steam or processes, so Mortar goes through `flatpak-spawn --host` (`internal/sandbox`, finish-arg `--talk-name=org.freedesktop.Flatpak`); every launch runs on the host, so the game never inherits the sandbox. Launch at login uses the Background portal and shortcuts the DynamicLauncher portal (`internal/portal`). Add to Steam is refused in the Flatpak (host Steam cannot start `/app/bin/mortar`).
- **Windows:** a per-user NSIS installer is the only scope (`build/windows/nsis/wails_tools.nsh` `WAILS_INSTALL_SCOPE`), installing to `$LOCALAPPDATA\Programs\Mortar` without admin (a machine-wide build would register a second copy beside it); the updater's Windows asset is the bare `mortar-windows-amd64.exe`. The installer and uninstaller close a running Mortar first: `mortar quit` asks the app at `$INSTDIR` over its control channel (`app.quit`: replies with its pid, or refuses when downloads or the game run unless `--force`) and waits until the pid has exited, failing after ten seconds. The signed manifest lists both Linux AppImages plus the Windows exe so the updater matches `runtime.GOARCH`.
- **Self-update:** `internal/updatesvc` drives Wails' updater (`app.Updater`) with the `endpoint` provider reading the signed manifest at `https://github.com/Rethunk-Tech/mortar/releases/latest/download/manifest.json`; signing key `main.go` `updateKey` (the private half never enters the repository). Wails' GitHub provider is not used because it verifies no signature, only an optional checksum asset.
  - A production AppImage, portable Linux binary or Windows build checks in the background (after startup, then every four hours), verifies a newer signed release and leaves it staged; quitting applies it. A release is installed only when its manifest entry carries a signature. Asset URLs name the release tag (`releases/download/v<version>/…`), so a release published mid-update cannot swap the file under it.
  - **Off:** a build without the `production` tag (`wails3 dev`), a server build, a version containing `dev`, or a packaged build (`-X main.packaged=…` from nfpm, Flatpak, AUR). The bare Linux binaries are listed in the manifest under platform `linux-portable` (`updatesvc.PortablePlatform`; `release:manifest` rewrites their inferred `linux`, which the per-file signatures do not cover), so each flavour replaces itself with its own kind of file.
  - **Test:** `wails3 task test:updater` (Linux) serves a manifest signed by `wails3 updater manifest` over two server-mode builds of `internal/updatesvc/testdata/fixture` (0.1.1, 0.1.2) and asserts the binary becomes 0.1.2 and relaunches, while a tampered artifact, a wrong-key signature, an unsigned entry and a downgrade manifest are refused, and that under a fake `$APPDIR` the file `$APPIMAGE` names is replaced. The build tag `updatetest` (never in releases) lets `MORTAR_UPDATE_MANIFEST_URL` replace the manifest URL.
  - **Windows swap** (`applied_windows.go`: the old exe is renamed `.old.<n>` because a running exe cannot be deleted) is not in the automated test; check it in the Windows VM with `-tags updatetest`: **Restart now** replaces `%LOCALAPPDATA%\Programs\Mortar\mortar.exe` and relaunches, the new process removes the `.old.<n>` copy (`RemoveOldExecutables`) and `DisplayVersion` under `HKCU\…\Uninstall\Rethunk.TechMortar` takes the new version.
- **What's new:** `<datadir>/last-run-version` records the previous run's version; when the running version is newer, Mortar fetches that release's GitHub notes once and shows them; offline skips silently and leaves the file so the next start tries again.
- **Wails behaviour Mortar relies on** (upstream, except `OnUpdateApplied`, which only the `Rethunk-AI/wails` branch `mortar/v3-next` carries): a self-contained AppImage (`v3/internal/commands/appimage.go`): each WebKit helper directory moves to `usr/lib/<name>` in the AppDir and the bundled library's compiled-in path becomes `././<name>/`, NUL-padded to the same length, with AppRun running the app from `$APPDIR/usr/lib` and the user's folder in `OWD` (`sharesvc.LaunchDir`), so the relative path resolves inside and outside WebKit's bubblewrap sandbox; the file search covers only `/usr/lib`, `/usr/lib64`, `/usr/libexec`, so other projects' AppDirs under `/usr/local` are never bundled. And the updater (`v3/pkg/updater`): staging goes beside the target and a cross-filesystem rename falls back to a copy (`/tmp` is tmpfs on Fedora); inside an AppImage it replaces and relaunches `$APPIMAGE`, not the read-only mount; `Config.OnUpdateApplied` lets Mortar rewrite `DisplayVersion` on Windows.
- **Linux desktop integration:** packaged installs (nfpm, AUR, Flatpak) own the system desktop entry `tech.rethunk.Mortar.desktop` (`Exec=mortar %u`, `MimeType` for `mortar://`, `application/x-mortar`, `nxm://`), the MIME XML and hicolor icons; a packaged binary (`-X main.packaged=` / `-X …/internal/nxm.packaged=`, `deb` or `flatpak`) writes no user-level desktop entry, icons or MIME XML at startup. Nothing installs an AppImage's embedded `.desktop` file, so an AppImage writes its own with `Exec=` set to `$APPIMAGE` (desktop files do not expand variables and the mount vanishes on exit), rewritten at startup when its target no longer exists (`Refresh` in `internal/nxm/handler_linux.go`). Application id and single-instance id are both `tech.rethunk.Mortar`, so Wails' D-Bus name sits under the app id, which a Flatpak may own without a finish-arg; a portable copy appends a hash of its data folder.
- **Download page:** `web/src/pages/download/index.astro` and the landing page link `https://github.com/Rethunk-Tech/mortar/releases/latest/download/<asset>` for `mortar-linux-x86_64.AppImage`, `mortar-linux-aarch64.AppImage`, `mortar-windows-amd64.exe`, `mortar-amd64-installer.exe`. `bun run site:downloads` (`scripts/site-downloads.ts`) resolves every release link on the site against the latest releases and fails on a missing or mismatched asset; CI runs it when `web/` changes and `release.yml` after publishing.
