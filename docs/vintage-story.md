# Vintage Story

Catalog id `vintage-story`. Sold outside any store app by Anego Studios; native Windows and Linux builds of one .NET program. Paths and settings the catalog holds (`internal/components/components.json`) are not repeated here.

## Installs

- **Windows:** default folder `%APPDATA%\Vintagestory` (`Vintagestory.exe`) ([wiki](https://wiki.vintagestory.at/index.php/Vintagestory_folder)); the `standalone` store finds it.
- **Linux, manual:** the tarball (`vs_client_linux-x64_<version>.tar.gz`) holds `vintagestory/` with `Vintagestory` (no `.exe`) and `run.sh`; its install script copies it to `~/.local/share/vintagestory` (`~/ApplicationData/vintagestory` before 1.19.2). `run.sh` points fontconfig at the game's `fonts.conf` and sets the working folder, so a native start goes through it (`linuxStart`). A .NET runtime installed by Microsoft's script lives in `~/.dotnet`, which the desktop leaves out of `DOTNET_ROOT`; Mortar sets it when unset and that runtime exists.
- **Linux, Flatpak:** `at.vintagestory.VintageStory` (Flathub or `flatpak.vintagestory.at`) unpacks the same tarball as extra data, at `<flatpak>/app/at.vintagestory.VintageStory/current/active/files/extra/vintagestory`; the `flatpak` store finds it. It bundles its .NET runtime, starts with `flatpak run at.vintagestory.VintageStory`, and keeps data under `~/.var/app/at.vintagestory.VintageStory/config`.
- **Linux, Lutris:** the `vintage-story` game on lutris.net (installer `vintage-story-website-download`) unpacks the same tarball into a Lutris game folder; the `lutris` store finds it by its `vintage-story` slug.
- **AUR:** `/opt/vintagestory`; not in the catalog (a path template cannot start with a token), so the player chooses the folder.

## Data and mods

- The data folder is .NET's ApplicationData plus `VintagestoryData`: `%APPDATA%\VintagestoryData`, `$XDG_CONFIG_HOME/VintagestoryData` ([wiki](https://wiki.vintagestory.at/VintagestoryData_folder)). Mods go in `VintagestoryData/Mods`; the install's own `Mods` holds the base game's modules (`VSSurvivalMod.dll`, `do_not_add_mods_here.txt`).
- A mod is a zip whose root holds `modinfo.json` (`modid`, `version`, `dependencies`), a folder holding one, or a bare `.cs` or `.dll`. The `mods` target's `modRoot` is `modinfo.json`: an archive is laid out as one folder named after its store item, a bare file stays loose.
- **Saves** are `Saves/<name>.vcdbs` (SQLite) with `-shm` and `-wal` companions; a restore deletes companions the restored copy lacks, since SQLite replays a leftover `-wal` over the restored file. Each world's one `gamedata` row is a protobuf `SaveGame` ([vs-proto](https://github.com/bluelightning32/vs-proto) schema: `WorldName` 13, `TotalSecondsPlayed` 14, `LastSavedGameVersion` 21, `PlayStyle` 29, `SavegameIdentifier` 34); Saves reads it read-only and immutable for name, play style (`surviveandbuild`, `exploration`, `wildernesssurvival`, `homosapiens`, `creativebuilding`, the codes `vssurvivalmod` tests), play time and version.
- **Game-made copies** beside `Saves`: `/genbackup` writes `Backups/<world>-<yyyy-MM-dd_HH-mm-ss>.vcdbs`; the Modify World dialog's Create a backup writes `BackupSaves` with a `-bkp-` infix (wiki folder list, string in `VintagestoryLib.dll`). The catalog's `saveCopies` and `saveCopyFolders` list both on Saves.
- **Minimap:** `Maps/<SavegameIdentifier>.db`. The catalog's `saveLinked` (`Maps/{uuid}.db`) backs it up with `Saves/` and restores it with a world; restoring one of the game's own copies leaves it.
- **Logs:** `Logs/client-main.log` (rewritten each start) and `client-crash.log`; also `client-debug.log`, `client-chat.log`, `client-audit.log` and the `server-*.log` set (names from `VintagestoryLib.dll`). Lines read `d.M.yyyy HH:mm:ss [Level] message`; levels `Notification`, `Event`, `Debug`, `VerboseDebug`, `Warning`, `Error`, `Fatal`. The mod loader's failures carry the mod id in brackets (`internal/loader/vslog`, from logs users pasted into GitHub issues): `[modid] Could not resolve some dependencies:` followed by `[modid]     dep@version - Missing` (or `- Dependency '<file>' (dep) has dependency errors itself`), `[modid] An exception was thrown when trying to start the mod:` and `... to load assembly:`. They become Problems and Problems-in-this-run rows and feed the crash hint; the game keeps one log for every profile, so the Problems page reads it only for the profile that ran last.
- **Mod settings** are `ModConfig/<name>.json`. Each profile keeps its own copy in `<profile>/ModConfig` (seeded from the game's folder on first launch), swapped in per launch like separate saves (`savesiso`, journalled, recovered after a crash). The Config page matches a file to a mod when its name holds the mod id from `modinfo.json`; the rest list under Other.
- **Mods in a world:** a world's `ModData` holds `BlockIDs` and `ItemIDs` (id to code), and a mod's codes carry its mod id as domain (`primitivesurvival:fishbasket`; the game's own are bare or `creative`/`survival`). A mod that only generates the world, or one that failed to load, leaves no codes. Saves reads those domains as `modinfo:<id>` and offers missing ones from the Mod DB; a mod of code alone leaves no trace, so the world stays marked as not recording its full mod list.
- The game unzips each mod into `Cache/unpack` and recreates a missing folder there; the catalog lists it under `caches`, and the `cacheClearing` setting clears it once after a profile's mod set changes.
- Screenshots go to `Pictures/Vintagestory` in the user's home on both systems (wiki).
- The game takes `--addModPath` and `--dataPath`; Mortar uses neither, since the folder deployer fills and empties the Mods folder per launch.

## Sources

- **Vintage Story Mod DB** (`vsmoddb`, `internal/source/vsmoddb`): public API `https://mods.vintagestory.at/api`, no key. `/mods` lists mods (`text`, `orderby` `downloads`, `follows`, `lastreleased`, `asset.created`, `tagids[]`) with a `limit` and no offset; `/mod/<modid>` lists releases newest first, test builds (`-rc`, `-pre`, `-dev`) included. A mod's page is `/show/mod/<assetid>` or `/<urlalias>` and the API does not answer to the assetid, so Mortar's id is `<modid>-<assetid>`. Downloads take the newest stable release unless one is named; the release id is the entry's file id. Release files carry no hash and no dependency list, so after a Mod DB install Mortar reads each mod's `modinfo.json` `dependencies` and queues every required mod id missing from the profile (the game's own `game`, `survival`, `creative` excepted).
- **Install links:** the site's 1-click button opens `vintagestorymodinstall://<modid>@<version>`, registered by the game's installer for `Vintagestory -i`. Mortar claims the scheme only when the player turns it on, reads the Mod DB ids so the entry matches one added from Browse, and installs that release.
- **Nexus** domain `vintagestory` (game id 3576); **GitHub** topic `vintagestory-mod`.

## Settings

The folder loader reads every per-game setting as for The Sims 4, except `skipIntro` and `graphicsApi` (no catalog entry), `gameSettingsMode` (no `requiredSettings`), `defaultLaunchMethod` (no store relay: every copy starts directly), and `enableRequirements` and `missingRequirements` (a Mod DB install queues the mods it requires).
