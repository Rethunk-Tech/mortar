## Ready to build

### Update version binding

A freshness gap in what the signing pipeline signs ([security](security.md)). It needs the signing step, so it is not a client-only change.

- **Update version binding.** Wails' updater verifies an Ed25519 signature over the artifact digest only (`Rethunk-AI/wails/v3/pkg/updater/verify.go:137`, `:175`); `Verification` carries no version or platform. Whoever controls `releases/latest/download/manifest.json` can serve an older signed build, or another platform's, under a higher version number. `TestUpdaterE2EDowngradeIgnored` covers only a lower version number.
  - **Decided shape:** the release step signs `version|platform|digest` instead of the digest (`wails3 task release:manifest`, `docs/release.md`), the fork's verifier rebuilds that message from the release it checked, and `updatesvc.Check` (`internal/updatesvc/service.go:187`) keeps refusing a release without a signature. Mortar and the fork change together, and older builds must still read the new manifest, so the manifest carries both signatures for one release cycle.
  - **Done when:** an e2e test installs nothing when a validly signed older artifact is relabelled with a higher version.

### Game sandbox (Linux, opt-in)

A malicious mod is code in the game process, so it can read the player's `~/.ssh`, browser profiles and Mortar's own data folder (store keys, tokens). Built so far, off by default until the Lethal Company (Proton) proof passes (maintainer, 2026-11-07): `internal/sandbox` builds the bubblewrap argv, `game.sandboxed` applies it to a direct start, `launchsvc.sandboxSpec` supplies the profile, saves and mod roots. The run record keeps the writable folders (`Run.Sandbox`), and the Console shows them under the run's problems with any denial found in its logs (`launchsvc.SandboxReport`, `sandbox.Denials`, `console/SandboxNote.tsx`). Reuses what the self-test harness learned (`scripts/launch-guard.sh`): bwrap works unprivileged here, nested namespaces work, and a socket stays connectable through a read-only bind.

- **Setting:** `sandboxLaunch`, a per-game bool with per-profile override, default off (`settings/registry.go`, row on the Play page after `skipPlayCheck`). It earns a setting because no existing one covers confinement, and it changes the launch method: on, Mortar starts the game directly (the same trade as `defaultLaunchMethod` direct, which the description names: no Steam overlay or playtime). Windows and macOS ignore it. With bwrap missing, or Mortar running as the Flatpak, the launch fails with that reason; it never starts the game unsandboxed.
- **What it wraps, per launch method:**
  - _Direct native_ (Stardew, SMAPI; any `linux` build): the game process and everything it spawns. Full confinement.
  - _Proton direct_ (Mortar's `proton waitforexitandrun`, which is what Steam games become when the setting is on): wraps the `proton` script, so Wine, the game and pressure-vessel's container sit inside it. Pressure-vessel makes its own namespaces inside bwrap; unverified, see Acceptance.
  - _Wine and other launchers_ (Bottles, Heroic, Lutris `launcher-prefix`): direct starts through `launcherCommand` fallback are wrapped like Proton direct, with the prefix bound read-write. A relay (`bottles-cli`, `heroic://`, `lutris:rungame`) starts the game under that launcher's own process tree, which Mortar cannot wrap, so the setting forces the direct fallback for those games and refuses if the plan needs a relay.
  - _Steam-launched_ (`steam -applaunch`, native or Flatpak Steam): the game is a child of the Steam client, not of Mortar, so Mortar cannot wrap it, and wrapping the Steam client would not confine the game from its own files. Honest result: a game left on the Steam launch method is not sandboxed. With the setting on Mortar does not use that method.
  - _Flatpak Steam / Mortar as a Flatpak:_ Flatpak Steam's games run in Steam's flatpak; bwrap inside it needs `--talk-name=org.freedesktop.Flatpak`, so it is not supported and is refused. A Flatpak game already has its own sandbox.
- **Remaining gaps, stated in the setting's help:** network stays open (multiplayer, the bridge's loopback channel, mod downloads from the game), so a mod can still send out what it can read, which is now only the game's own folders; the host PID namespace is kept (Mortar finds and stops the game by process), so a mod can see other processes of the same user; the session D-Bus is reached only through a filtered proxy (see D-Bus below); environment variables whose names look like credentials are removed (`sandbox.Credentials`), not others.
- **D-Bus and process cap:** the first sandbox left `DISPLAY` and the X11 socket but stripped `DBUS_SESSION_BUS_ADDRESS` and emptied `XDG_RUNTIME_DIR`, so libdbus autolaunched `dbus-launch`, which under no_new_privs spawned more of itself (about 150,000 in two minutes, the terminal scope's task limit held for hours). Now `sandbox.Argv` always sets `DBUS_SESSION_BUS_ADDRESS`: with `xdg-dbus-proxy` installed, `game.sandboxed` starts `sandbox.StartProxy` (`--filter`, talk to `com.feralinteractive.GameMode`, `org.freedesktop.ScreenSaver`, `org.freedesktop.portal.*` only), binds its socket to `$XDG_RUNTIME_DIR/bus` and points the address there; the proxy ends with the game (`OnExit`, a failed start, or Mortar dying closes its sync pipe). Without it the address is `disabled:`, which libdbus and GDBus read as no bus and never autolaunch, and the run's console says so. The system bus is always off (`/run/dbus` emptied, `DBUS_SYSTEM_BUS_ADDRESS=disabled:`): logind, NetworkManager and polkit-gated calls are not game needs. The Steam overlay is not reachable anyway (Steam is not the parent). Every sandboxed start also runs in `systemd-run --user --scope -p TasksMax=4096` (`sandbox.TaskCap`; Proton games peak at a few hundred threads), so a future fork storm stays in the game's scope; without a systemd user manager the game starts uncapped and the console says so. Tests: `TestArgvAlwaysSetsASessionBusAddress`, `TestProxyArgvFiltersToTheNamesGamesUse`, `TestTaskCapWrapsInATransientUserScope`.
- **Mounts:** the root is read-only (system libraries, `/etc`, `/run/udev` for joysticks, `/sys`), `/dev` is bound whole (GPU `dri`, `input`, `hidraw`, `uinput` for Steam Input, audio), `/tmp` is empty except `/tmp/.X11-unix`, and `/home`, `/root`, `/mnt`, `/media`, `/run/media`, the real home and `XDG_RUNTIME_DIR` are emptied, then these come back: the display, PipeWire and Pulse sockets, `XAUTHORITY`.
- **Folders per loader:**

  | Need                          | Mode | Source                                                                                                                                                                                                                                |
  | ----------------------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | Game install                  | rw   | `inst.Dir` (BepInEx `BepInEx/` logs and config, MelonLoader `Mods`, `UserData`, `Logs`, SMAPI's beside-exe files, folder loaders' placed files)                                                                                       |
  | Proton prefix                 | rw   | `STEAM_COMPAT_DATA_PATH` (the Steam `compatdata/<appid>` or `<data>/prefixes/<game>`); Windows saves and registry live here                                                                                                           |
  | Proton build and runtime      | ro   | the `proton` folder, `steamapps/common`, `compatibilitytools.d`, `ubuntu12_32`/`64`, `linux32`/`64` of the Steam root (`sandbox.SteamRO`); not `config/`, `userdata`, login files or other games' `compatdata`                        |
  | Profile                       | rw   | `profiles/<game>/<id>/` (SMAPI's `mods/`, BepInEx config swapped in, `startup/`, `runs/`, `saves/`); no other profile and nothing else of the data folder                                                                             |
  | Saves played                  | rw   | `playedSavesDir`: SMAPI `~/.config/StardewValley` for a native build, else inside the prefix                                                                                                                                          |
  | Mod roots outside the install | rw   | `planRoots` (Sims 4 `Mods`, a Documents path role)                                                                                                                                                                                    |
  | .NET runtime Mortar installed | ro   | `DOTNET_ROOT` for SMAPI                                                                                                                                                                                                               |
  | Shader caches                 | rw   | `<profile>/sandbox-cache` through `MESA_SHADER_CACHE_DIR`, `DXVK_STATE_CACHE_PATH`, `__GL_SHADER_DISK_CACHE_PATH`; the player's own caches are not shared, so a mod cannot poison them, at the cost of a cold first start per profile |

  Unverified: whether Proton needs `config/` or `steam.pipe` from the Steam root (the first Lethal Company run answers it), and whether `~/.steam/sdk64/steamclient.so` is needed for a native Steamworks game (Stardew).
- **Overlays and input:** the Steam overlay is already off for a direct start, so nothing is lost beyond what the setting's help says. Controllers work through `/dev/input`, `hidraw` and `/run/udev`. Launch prefixes (`mangohud`, `gamescope`, `gamemoderun`) run inside the sandbox, so their binaries must be on the read-only root; `~/.config/MangoHud` is not carried (the prefix runs with defaults), and gamemode needs the session bus, which is not passed. Mortar's own bridge, console and overlay page use loopback, which is open.
- **What the player sees:** the game starts as usual. The Console shows "This run was sandboxed: the game could write N folders" for a sandboxed run, the folders in its tooltip. When the loader or Unity log of that run holds a refusal (`UnauthorizedAccess`, `Permission denied`, `EROFS`, `EACCES`) for a path in a folder the sandbox empties, or a missing path under the home folder (also Wine's `Z:\home\...` spelling), outside the writable set, a warning lists the paths and says to turn the setting off for the game or profile. The scan is by path only, so it names no mod and is a hint: a mod that looks for a missing file under the home folder is listed too. Each denied path offers **Allow <folder>** (the path if it is a folder, else its nearest existing folder; none for the home folder or a place the sandbox empties whole), which appends to `sandboxExtraFolders` where the open profile reads it. That setting (per game, per-profile override, empty by default, a colon-separated list on Linux) binds each folder read-write; an entry that is relative, missing, `/` or the home folder refuses the launch with its reason (`sandbox.ExtraFolders`). The note lives in the Console, not the Problems tab, because those rows are per mod. Render case: `console-sandboxed-run`.
- **Out of scope until asked:** seccomp filters, `xdg-dbus-proxy` for an allow-listed session bus, a network namespace with a loopback-only bridge, Windows (AppContainer) and macOS.
- **Acceptance:** (1) `go test ./internal/sandbox ./internal/game` passes on the argv: home hidden before binds, strict rw, no `--unshare-net`/`--unshare-pid`, credentials removed; (2) a launch prefix that reads `$HOME/.ssh` and the real home's canary file from inside the sandbox finds neither, while the game's own folders write; (3) Stardew with SMAPI loads every enabled mod and saves to the profile or Saves folder, and the game folder hashes as the plain regress requires; (4) Lethal Company under Proton loads BepInEx and its plugins and writes a save into the prefix; (5) a gamepad and audio work in a manual run (human-only); (6) the launch fails with the bwrap reason when bwrap is absent; (7) an extra folder is writable in the next sandboxed run and a bad one refuses the launch; (8) the setting rows and their Lingui strings are present, off for every game after an upgrade.
