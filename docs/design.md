## Ready to build

### Game sandbox (Linux, opt-in)

A malicious mod is code in the game process, so it can read the player's `~/.ssh`, browser profiles and Mortar's own data folder (store keys, tokens). The sandbox is opt-in (the maintainer's decision of 2026-11-07).

- **Mechanism:** `internal/sandbox` builds the bubblewrap argv and mounts (`sandbox.Argv`, `sandbox.go:70`), strips credential-looking environment variables (`sandbox.Credentials`, `sandbox.go:138`), keeps only the Steam parts Proton reads read-only (`sandbox.SteamRO`, `sandbox.go:155`), runs a filtered session bus (`sandbox.ProxyArgv`, `dbus.go:35`; `sandbox.StartProxy`, `dbus.go:81`), caps the process count (`sandbox.TaskCap`, `dbus.go:120`), and reads `sandboxExtraFolders` with the refusals for keys and sign-ins (`sandbox.ExtraFolders`, `folders.go:12`; `sandbox.Allowable`, `folders.go:38`; `sandbox.holdsSecrets`, `folders.go:60`). `game.sandboxed` applies it to a direct start, and fails the launch instead of starting unsandboxed when bwrap is missing or Mortar is the Flatpak (`internal/game/start.go:296`, `sandbox.ErrNoBwrap` at `sandbox.go:18`); `launchsvc.sandboxSpec` supplies the profile, saves, cache and extra folders (`internal/launchsvc/sandbox.go:18`), and the setting forces a direct start even where the store would relay (`internal/launchsvc/service.go:1102`). The run keeps the folders it could write (`Run.Sandbox`, `internal/launchsvc/runs.go:63`); `launchsvc.SandboxReport` reads them back with each denial and the folder it may allow (`internal/launchsvc/sandbox.go:99`, `sandbox.Denials` at `denial.go:20`), and the Console shows them (`frontend/src/console/SandboxNote.tsx`, render case `console-sandboxed-run`, `frontend/e2e/stateCases.ts:340`). The settings are `sandboxLaunch` and `sandboxExtraFolders` (`internal/settings/registry.go:271`), rows on the Play page (`frontend/src/settings/GameSettingsPage.tsx:84`) with their strings (`frontend/src/settings/prefCopyGame.ts:130`); the registry rows and `settings.Defaults()` are kept in step by `TestRegistryDefaultsMatchDefaults` (`internal/settings/registry_test.go:112`). Tests: `internal/sandbox/sandbox_test.go` (home hidden before binds, strict rw, no `--unshare-net`/`--unshare-pid`, credentials removed, session bus, proxy filter, task cap, extra folders, denials), `internal/launchsvc/sandbox_spec_test.go`.
- **Out of scope until asked:** seccomp filters, a network namespace with a loopback-only bridge, Windows (AppContainer) and macOS.

### Companion split (after the 0.6.0 tag)

The BepInEx companion keeps its channel and query, perf (needs Harmony's patch registry), the startup patcher, intro skip, console, configsync and log-source tags (always on). The stream overlays leave the bridges. Lethal Company's DevLaunch intro flags stay beside the companion's.

- **Companion (mortar-bepinex-bridge):** one runtime-detected DLL for every Mono game. Game rows stay in `Games/<Game>/` files, picked by `Application.productName`; no `#if`, no per-game zips once retired. `status` gains a `features` list (missing means the 0.5.x set). Before it: fix the stale TODO.md and README.md paths and HUMANS.md's Nexus ids; drop IL2CPP's LogTag link; move `IntroSkip.Find` and `Overlay.Probe` to a neutral helper; log the "alive after scene" line from `Plugin`, since bisect reads it (`internal/launchsvc/bisect.go:35`).
- **Overlays:** `mortar-mods/bepinex5/lethal-company/mortar-lc-streamoverlay` (Lethal Company only, MonoMod, Thunderstore) and `mortar-mods/smapi/stardew-valley/mortar-sdv-streamoverlay` (out of `mortar-smapi-bridge`). Both read `startup/overlay.json` and serve `/state` byte-identical to today's. Valheim's overlay is dropped.
- **Mortar:** a game's loader names its overlay component beside the companion (`GameLoader.Overlay`), the catalog accepts the `overlay` kind (the generator too), and a game that names none keeps the overlay settings hidden. Every profile holds the overlay as a second hidden `mortar` bundle beside the companion: `Source.Component` says which (`bridge`, `overlay`, empty reading as the bridge), `applyBundledTo` replaces only its own component, `bridgeFolder` finds the bridge entry alone, and the overlay joins while the overlay setting is on and leaves when it is off (the settings save syncs it, and a profile upgraded with the setting on keeps it in the same sync). A companion release before 0.6.0 serves the overlay itself and binds its port, so no overlay bundle joins its profile. `IsOwnListing` matches the overlay packages, and what a running companion can do is read from its `status` `features` (missing means the 0.5.x set). The `"bridge"` entry stays at 0.5.x for old Mortars, which install only that name.
- **Traps** (anchors from 2026-11-06; re-check each): the overlay reuses about 40 lines of bridge internals (`BridgeServer.TryAdmit`, `ReadLine`, `UnauthTimeoutMs`, `Protocol.TokenMatches`, `Files.ReadText`, `Json.Quote`, `Plugin.FindObject`), which the mortar-mods overlay re-implements with the same token check and unauthenticated timeout, and Valheim's console uses `Overlay.Probe` (`GameConsole.cs`), so Probe moves first. Catalog: a game-level `minVersion` hides the whole game, so it cannot gate one component; duplicates are per game and name; old Mortars look up only the companion name `bridge` (`game/service.go`, `browse/installed.go`). Keep byte-identical: `bridge-<ver>-<sha12>` store keys with source `mortar`, the `overlayEnabled`/`overlayPort`/`overlayToken` settings, the request files `startup/overlay.json`, `skip-intro`, `.measure-launch`, `hidden-log-sources`, and `ArmOverlay` with the `overlay.json` format. Bisect's "Bridge plugin alive after scene" line (`bisect.go`, `scripts/selftest.test.ts`) is logged only while `IntroRunner` runs; logged from `Plugin`, it appears on unarmed launches too. Add `features` to `status` (old Mortars ignore unknown keys), never a new command (the allowlist in `bridge.go`; old companions answer "unknown command"). One DLL rewrites the bridge's AGENTS.md and `CoreBuildTests.cs`, its per-game loops in `verify.sh` and `package.sh`, the per-game Nexus and CurseForge jobs in `ci.yml` (CurseForge rejects byte-identical files; `ci.yml` already works around it) and `packages/*.txt`. Stardew's overlay is in-process in mortar-smapi-bridge (`OverlayServer.cs`). The overlay mods follow mortar-mods' rules: Thunderstore team Mortar, GUID `tech.rethunk.mortar.<ModName>`, MonoMod hooks only.

- **macOS support** (darwin/arm64 and amd64), until the maintainer owns or borrows a Mac. The Linux-testable parts are under Ready to build.
  - **Scope:** the catalog's `darwin` path templates and the macOS asset picker exist. go-safefs already has a darwin `Clone` (`clonefile`), so profile copies need no new code. Lethal Company and most BepInEx games ship no macOS build, so the first targets are native-macOS games (check each game's macOS depot before enabling) and, for Windows-only games, a CrossOver or Whisky prefix.
  - **Wails v3:** `wails3 build GOOS=darwin` on the pinned fork ([stack](architecture.md#stack)), on a Mac only (cgo and the macOS SDK). Add `build/darwin/` (Taskfile, `Info.plist`, `icons.icns`, as `build/windows/` and `build/linux/` do) and `darwin: ./build/darwin/Taskfile.yml` under `includes` in `Taskfile.yml`. Check the fork's WKWebView paths first: frameless title bar, `BackgroundTypeSolid`, drag regions, the tray (`tray_other.go`), `nxm://` registration (`Info.plist` `CFBundleURLTypes`, replacing `internal/nxm` runtime registration), single-instance.
  - **Game discovery:** go-gamelocator's Unix Steam locator (`//go:build !windows`) lists only Linux roots. Add `~/Library/Application Support/Steam` (r2modman's darwin game-directory resolver) and `GOOS=darwin go vet ./...` in the module's crosscompile gate, and read `steamapps/libraryfolders.vdf` as the Linux path does. The install folder holds `<Game>.app` (marker `Contents/MacOS/<exe>` or `Contents/Resources/Data`), so the catalog's `marker` needs a `darwinMarker` like `LinuxMarker` (`internal/game/install.go`, `internal/gamestore/standalone.go`). Gale has no macOS code; r2modman is the only precedent: it launches Steam with `steam_osx -applaunch <id>` (its darwin Steam runner) and a `macos_proxy` launch wrapper (its launch utilities).
  - **Loaders:** BepInEx on macOS starts through the pack's `run_bepinex` script (Doorstop's `libdoorstop.dylib`, injected by the dynamic loader), set as the Steam launch option `"<profile>/run_bepinex" %command%` (r2modman's BepInEx game instructions). `internal/loader/bepinex5` places the Windows `winhttp.dll` pair and needs a darwin branch beside `contributeLinux` in `driver.go` (and thunderpack's). Steam strips dyld injection for hardened binaries, so test a hardened game early. SMAPI's installer swaps the launcher on macOS as on Linux ([games](games.md#smapi)), but `internal/loader/smapi/install.go` hardcodes the Linux names and the bundle layout (`Stardew Valley.app/Contents/MacOS/StardewValley`) differs. MelonLoader ships no macOS build: leave it off, as the driver already refuses Linux.
  - **Packaging:** a `.app` in a `.dmg`, universal or two arch builds; codesign (hardened runtime) and notarise (`notarytool`) with an Apple Developer ID certificate (paid account, a maintainer decision); self-update through `wails3 updater manifest` with a `darwin` artifact in `Taskfile.yml`; a Homebrew cask `Casks/mortar.rb` in Rethunk-Tech/homebrew-tap. Gatekeeper blocks an unnotarised app, so do not ship unsigned.
  - **Testing:** no macOS runners in workflows (billable minutes), so CI stays Linux and Windows; manual testing needs a lender with a Mac, or a one-off macOS VM or hosted runner the maintainer approves. The pure-Go parts (Steam roots, markers, loader branches) are unit-tested on Linux with a `Platform: "darwin"` view, as `internal/loader/thunderpack/thunderpack_test.go` does for Windows.
