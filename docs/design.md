## Queued for v1

Decided 2026-10-07 (NOMAD), from the audit of how Mortar was described to CurseForge.

- **Archives: tar and stream formats** beside zip, RAR and 7z in `internal/archive/archive.go` (magic-byte dispatch): tar, tar.gz, tar.xz, tar.zst, tar.bz2 and bare gz, xz, zst and lzma, under the same entry, size, path and bomb guards.
- **Per-frame time per mod.** The Stardew and BepInEx bridges time each mod's update and tick handlers per frame (average, p95, peak ms, share of frame), with an idle baseline (no mods vs all), shown in Performance. Today in-game numbers are SMAPI's own `performance` event timings, and BepInEx has only `perf start` on a measured launch.
- **Memory budget.** Measure peak RSS of the Go process and the WebView across browse, a large install, a Content Patcher check and a launch on the 811-mod Stardew profile; set `debug.SetMemoryLimit` for the Go side and add a regress check that fails over budget. The target is under 1 GB for both processes together; record the measured numbers here or in architecture.md.
- **Antivirus scan of extracted mods.** Every mod is scanned after extraction and before it enters the store (`internal/store/store.go` `AddArchive` :304, `AddArchiveKey` :317, `AddHashedDir` :333; one hook every path goes through, LAN receives included).
  - **Windows:** AMSI. `AmsiInitialize`, `AmsiOpenSession`, then `AmsiScanBuffer` per file, which reaches the antivirus registered as the AMSI provider (Defender or a third party).
  - **Linux:** clamd over its socket when one is reachable, otherwise skipped.
  - **Settings › General › Antivirus:** the user picks the scanner.
    - **Automatic** (default): AMSI on Windows, clamd on Linux. It names the product found (Windows Security Center `AntiVirusProduct` / the clamd version) or "No antivirus found".
    - **clamd socket:** a path, so Linux users can point at a non-default socket.
    - **Custom command:** an executable and arguments with a `{path}` placeholder. Exit 0 means clean, any other code a detection, and stdout supplies the detection name. Covers scanners with a CLI but no AMSI provider.
    - **Off:** no scanning, with a one-line note that the mod sites' own scans still apply.
    - **Placement:** it is app-wide, not per game: it guards Mortar's own store.
  - **On a detection:** the install is refused, the extracted files are deleted, and the user sees the scanner's detection name and the flagged file. **Install anyway** behind a confirm covers false positives (SMAPI and BepInEx DLLs often trip heuristics); the override is recorded in history.
  - **Errors:** a scanner error or timeout is not a detection. The mod installs and a notice names the error.
  - **Done when:** an EICAR test file in a zip is refused on Windows (Defender in the VM) and with clamd on Linux, and the override installs it.
- **Profiles for any game, and shared-state games (The Sims 4 first).** Design draft 2026-10-07, for NOMAD's go-ahead; nothing below is built. Facts marked (unverified) could not be confirmed from a primary source and need one check before code.
  - **Why it fits today's model.** A game is a catalog entry (`internal/components/components.go:112` `GameInfo`) plus a loader driver; `Validate` requires one (`components.go:357`). Everything a loader gives (launch args, load order, logs, performance, asset map) is optional capability on that driver, and the UI already hides a section the loader lacks (`frontend/src/game/sidebarTabs.ts` `sidebarGroups` caps, `tabUnavailable`). Three folder-level mechanisms already exist and are what Sims 4 needs: content targets with per-extension depth caps (`components.go:199` `TargetDef.MaxDepth`, enforced by `internal/installer/installer.go:112-126`), the journaled folder swap behind "keep this profile's saves separate" (`internal/savesiso/savesiso.go:73` `Apply`, `:125` `Purge`, `:174` `Recover`; wired at `internal/launchsvc/pipeline.go:122` `swapSaves`, recovered at `:264` `RecoverGameDeploys`), and path templates with a `{documents}` token resolved inside the Wine or Proton prefix (`components.go` `PathTemplate`, `internal/runtime/runtime.go:147,282`).
  - **The Sims 4 facts.**
    - **User-data folder:** `Documents\Electronic Arts\The Sims 4` holds `Mods`, `Saves`, `Tray`, `Options.ini`, `localthumbcache.package` and the `cache` and `cachestr` folders. Every launch uses it, whichever store started the game. EA's guide says the game always uses the location Windows gives Documents, so the only supported redirect is a symbolic link or junction (`MKLINK /J`), never moving Documents and never pointing the link into the install (EA Help, "Choosing where Sims 4 data is stored", https://forums.ea.com/kb/the-sims-helpers-blog-en/pc-choosing-where-sims-4-data-is-stored/12598500; reached through search, the page itself returned 403 to a fetch).
    - **No user-data argument found:** the command-line arguments in circulation are `-w` and `-f` (windowed, fullscreen), set in the EA app's Advanced Launch Options, Steam's launch options, or a shortcut to `Game\Bin\TS4_x64.exe` (https://forums.ea.com/discussions/-/-/11790557, search snippet). No `-userDataDir`-style option appears in any source I could reach (unverified: the EA forum pages blocked a direct fetch), and EA's own "link it" guidance implies there is none. Design as if there is none.
    - **Mods depth:** `.package` files are read up to 5 folders below `Mods` (the stock `Mods\Resource.cfg` says so), `.ts4script` files at most 1 folder below (https://thesimsresource.helpscoutdocs.com/article/37-the-sims-4-resource-cfg-file; https://forums.ea.com/discussions/the-sims-4-mods-and-custom-content-en/re-sub-folders/9164016; community pages disagree between 5 and 6 for packages, so enforce 5). `Resource.cfg` must sit in `Mods` itself; a swapped `Mods` folder therefore has to carry one.
    - **Enable settings:** Game Options > Other holds "Enable Custom Content and Mods" and "Script Mods Allowed". Every major patch unticks the script option and the game disables the Mods folder until the player re-enables it (itch.io tutorial https://itch.io/blog/769252/tutorial-how-to-install-mods-in-sims-4; EA forum threads on removed custom content). The values live in `Options.ini` (key names unverified; read a real file before writing any).
    - **Stores and Steam:** Steam app id 1222670 (`steamcommunity.com/app/1222670`). A Steam copy still starts through the EA app; the executable is `Game\Bin\TS4_x64.exe`. Mortar's Steam start is `steam -applaunch <appid>` (`internal/game/start.go:149`); the EA app is not a store driver yet (design.md, Later: EA App).
    - **Linux under Proton:** the prefix of a Steam copy is `~/.local/share/Steam/steamapps/compatdata/1222670/pfx`, so the folder is `.../pfx/drive_c/users/steamuser/Documents/Electronic Arts/The Sims 4` (ProtonDB-era community reports; `{documents}` already resolves to that for a Proton install, `runtime.go:282`). Rated gold on ProtonDB; EA's launcher is the usual pain.
    - **Cache files:** after changing mods, players delete `localthumbcache.package`, the `.cache`, `.jpeg` and `.dat` files in `cache`, and everything in `cachestr`; the game rebuilds them (EA forum threads, e.g. https://forums.ea.com/discussions/the-sims-4-technical-issues-pc-en/help-my-entire-game-of-sims-4-is-gone-after-update/11692323/replies/11692338).
  - **Generic games, decided shape.** Keep "a game is a catalog entry plus a loader" and add a registered loader driver `generic` (`internal/loader`, beside `smapi` and `bepinex5`) that contributes no arguments, always reports installed, and declares none of the optional capabilities. It touches none of the 45 `PrimaryLoader` and `LoaderOf` call sites, and the catalog entry lists `{"id": "generic"}` so `Validate` stands. A new deploy method `swap` (`components.go:192` beside `redirect` and `profile`) says the profile holds the mod folder and the launch swaps it into the game's user-data folder; there is no install-side placement, so `deploy.place` (`internal/deploy/place.go`) is not used. Catalog data for Sims 4: marker `Game/Bin/TS4_x64.exe` (a sub-folder marker; `ValidInstall` joins it to the install, `internal/game/catalog_only.go`), a `Documents`-rooted `modsFolder` path role beside `saves` (`internal/game/capabilities.go` roles), targets `mods` (`{profileMods}`, `maxDepth` `.package` 5, `.ts4script` 1) and `tray`, Steam store `1222670`, CurseForge source.
  - **Isolation options and the pick.**
    - **A. Swap only `Mods` per profile (recommended).** At Play, `savesiso.Apply` (generalised: it already is "set the shared folder aside, link the profile's in its place, copy where links are refused") swaps `Documents\...\Mods` for the profile's folder; Purge restores it on exit; the journal sits beside the saves journal (`<install>-mods`, as `savesJournal` does, `pipeline.go:117`). Smallest blast radius: `Options.ini`, graphics, `Saves` and `Tray` stay shared. Junctions need no admin on Windows; symlinks work inside a Proton prefix. Downside: saves made with one profile's script mods load with another's only with warnings, which is what the existing "separate saves" switch is for.
    - **B. Also `Saves` and `Tray` per profile (opt-in per profile).** Reuse `SeparateSaves` (`profile/profilestate.go:25`) for `Saves` and add a `tray` role the same way; each is one more `savesiso` swap and journal. Default off.
    - **C. Swap the whole `The Sims 4` folder.** One link, perfect isolation including `Options.ini`, but it hides the player's settings and keybinds in every profile, makes the first run of each profile a fresh install, and risks the `localthumbcache.package` and account state; rejected as the default, kept as an advanced profile setting only if NOMAD wants it.
    - **D. Launch argument.** None found; ruled out until one is verified.
    - **Crash and kill recovery:** every swap journals before the first rename and `Recover` at the next start puts the player's folder back (`pipeline.go:264` and `LeftoverJournals` at `:312`); this is the property to test hardest, because here the shared folder is the player's real saves path.
    - **Game updates:** a patch rewrites `Options.ini` (script option off) and may add files to `Mods` (`Resource.cfg`); it never needs the swap. A `Prelaunch` step (`loader.Prelaunch`, `pipeline.go:177`) re-ticks the two enable flags in `Options.ini` for the launch and puts the previous values back after, so a patch's unticking is not mistaken for a broken profile. Cache clearing runs on the first launch after the profile's mod set changes (compare a hash of the file list kept in the profile), never on every launch.
  - **Sources and installs.** CurseForge is the main Sims 4 host (`www.curseforge.com/sims4`, classes Mods, Build/Buy, Create a Sim, Rooms/Lots, Sims/Households, Pets, Worlds, Save Files, Translations, from the site). The numeric CurseForge game id and class ids are not published on the pages (unverified; read `GET /v1/games` and `/v1/categories?gameId=` once with the build's key, then fill `GameSource.GameID` and `Key` as Stardew's `669` and `4643` are, `components.source.json`). Nexus: a Sims 4 section could not be confirmed from here (network unreachable). The Sims Resource and Mod The Sims have no public API and stay link-only (page open, drag the archive in). Mapping: the `plain` installer (`internal/installer/plain.go`) puts `.package` and `.ts4script` into `mods` (depth validated by the target), `.trayitem`, `.blueprint`, `.bpi`, `.hhi`, `.sgi`, `.householdbinary`, `.room` and `.roomtemplate` into `tray`; an archive's own `Resource.cfg` is dropped.
  - **UI that has no loader behind it.** Hidden through the existing capability flags: loader picker, Load order, Console, Performance, startup and the asset map; Problems keeps duplicates only. Mods list rows need an identity without a manifest.
  - **Traps.**
    - Mod identity: SMAPI and Thunderstore mods carry ids from manifests, Sims files have none; a profile entry needs a synthetic id (`file:<name>` per archive component) and the mod list, drift check and share links all read `Entry.Mods` ids.
    - Update checks need CurseForge file ids or fingerprints; there is no manifest version.
    - `Resource.cfg` missing from a profile's `Mods` silently loads nothing deeper than the root.
    - The shared folder must be set aside by rename on the same volume (`savesiso` already requires it, `heldSuffix`).
    - Never run the swap while the game or the EA launcher runs (`GameProcesses`, `catalog_only.go`); the EA app can stay open after the game exits and re-create `Options.ini`.
    - A Windows build under Wine as a non-Steam EA app install has its own prefix; `{documents}` must come from that install's runtime, never the Steam one.
  - **Acceptance criteria.**
    - A sandbox profile pair with different `.package` and `.ts4script` sets plays with each set only, the player's own `Mods` returns intact after a normal exit, after the game is killed, and after Mortar is killed during the swap (journal recovery at next start).
    - A `.ts4script` six folders deep is refused at install with the depth message; a `.package` at depth 5 is accepted.
    - With "Script Mods Allowed" off in `Options.ini`, Play turns it on for the run and restores it after.
    - `localthumbcache.package` is cleared once after a mod-set change and not otherwise.
    - A game with no loader capabilities shows no Load order, Console or Performance entries; the gate, sidebar tests and `Validate` tests cover the `generic` loader.
    - Stardew, Lethal Company and Valheim behave exactly as before (existing tests unchanged).
  - **Open questions for NOMAD.**
    1. Isolation default: Mods only (option A, recommended), or also Saves and Tray per profile by default (B)?
    2. Is the whole-folder swap (C) wanted at all, as an advanced setting?
    3. Is the EA app store driver (design.md, Later) in this item or later? Steam-only first covers the Linux/Proton path and most Steam owners, but leaves EA app buyers out.
    4. Hand-curated Sims 4 only, or a user-addable "any game" definition (marker, folders, store id) from the start?
    5. Sources for v1: CurseForge only (recommended), or find and wire a Nexus Sims 4 section too?
    6. Mod identity for files without manifests: one component per archive (recommended) or one per `.package` file?
    7. May Mortar edit `Options.ini` (the two enable flags, restored after the run), or must it only warn the player to tick them?
    8. Update checks for CurseForge-installed files: fingerprint match (heavy) or file-id match recorded at install (light, recommended)?

Not in the first release; re-weigh only when asked:

- Translucent window, desktop showing through; on Windows it needs Acrylic measured with the frameless window. The see-through window looked wrong, so v1 is solid. The `Rethunk-AI/wails` fork's GTK4 `setTransparent()` fix (upstream wailsapp/wails#6197) makes it possible: stock GTK4 leaves `setTransparent()` empty (`wailsapp/wails` `v3/pkg/application/linux_cgo.go:1418`), and the fix registers a display-wide CSS provider that clears the window background. Any fading or `backdrop-filter` full-window layer turns WebKitGTK's translucent window opaque; a static tint does not. Stacked alphas compound toward opaque, so images and overlays each need their own alpha. Frosted glass needs `ext-background-effect-v1`, below.
- Frosted glass on Linux, built when the desktop runs GNOME 51. CSS cannot do it: `backdrop-filter` sees only the webview's pixels, and a full-window filter layer turns WebKitGTK's translucent window opaque. The compositor blurs behind the window through the Wayland protocol `ext-background-effect-v1` (Mutter from GNOME 51, KWin from Plasma 6.7; GTK 4.23.3 speaks it). Shape: in the `Rethunk-AI/wails` fork, beside `setTransparent()` in `v3/pkg/application/linux_cgo.go`, bind `ext_background_effect_manager_v1` on Wayland, and when it advertises blur, set the toplevel `wl_surface`'s blur region to the whole window, updated on resize; a no-op elsewhere, and only while the translucent window is on. Accept when the desktop behind the window shows blurred on GNOME 51 and is unchanged on GNOME 50. Offer it upstream with the GTK4 transparency PR. Windows already blurs through Acrylic.

- Decided against: deduplicating identical files across store items. Measured, not worth it (2026-10-05, a 1.6 GB store of 724 items, 50,257 files): files identical across items hold 76 MB, 4.7% of the store, under the 5% bar, and writable files barely change that; counting copies inside one item too it is 99 MB, 6.1%.
- Decided against: speeding up Play. Measured, not worth it (2026-10-05, the 811-mod Stardew profile, direct launch in a sandbox copy): Play to the game process takes 93 to 120 ms wall and 60 to 130 ms of Mortar CPU (deploy and journal included), and the warm pre-Play checks take 74 to 260 ms. A run changes the problems fingerprint, and the recheck that follows runs when the game exits, so the next Play finds it done.
- Decided against: trimming idle memory. Measured, not worth it (2026-10-05, the same profile after a full problem check): the parsed Content Patcher packs (about 80 MB) are already released two minutes after the last check, and after 30 minutes idle the heap holds 45 MB in use (RSS 192 MB). The largest retained part is the store listing for drift checks, at 13 MB, under the 50 MB bar.
- Decided against: cutting the details panel's open further. Measured, not worth it (2026-10-06, the 811-mod Stardew profile in a headless Chromium selftest, long main-thread tasks in the 400 ms after the click): the panel narrowed the card grid and remounted all 36 visible cards into new lanes, 103 to 109 ms warm. The cards now sit in one grid keyed by mod id (`ModCards.tsx` `GridWindow`), so a new column count moves them by CSS and mounts none: 79 to 81 ms warm, 0 cards added. What is left is the panel's own mount and the relayout of the narrowed grid.
- Decided against: cutting a Problems check after a change further. Measured, not worth it (2026-10-05, the 811-mod Stardew profile in a sandbox copy): an unchanged profile is served from the findings memo (`internal/framework/contentpatcher/memo.go`), 0.03 s of Content Patcher, and the window's request after a restart takes 0.3 s wall, the rest being requirements 0.1 s, the broken-mod lookup 0.04 s and the drift walk 0.06 s. After a change only the conflict targets and packs the change touches are recomputed (`internal/framework/contentpatcher/parts.go`): Content Patcher re-checks a one-pack edit in 0.15 s in a running Mortar and 0.44 s after a restart, and a pack enabled or removed in about 0.2 s. What is left is spread thin: statting every pack's files so an edit in place shows (0.045 s CPU, on every core), saving the memos and caches (0.04 s), and the targets the change really touches. Reusing the pack stamps for the tilesheet pass's map stats would save under 0.01 s.
- Decided against: collapsing the deploy, installer, metadata-provider and framework registries into direct calls. Measured, not taken (2026-10-06): it would remove about 210 lines, and `AGENTS.md` keeps them as registries so a game normally needs no code.
