### Folder games: files a mod writes during play

**Decided 2026-10-10 00:49Z (NOMAD): write back per profile.** Leaving such files shared and never setting a leftover aside was considered and not taken (see Later). Not built; picked up cold from this section.

Why. A script mod such as MC Command Center rewrites a settings file its archive shipped inside Mods. Today the first launch leaves the rewritten file behind (purge removes a placed file only while its hash is the recorded one, `internal/deploy/place.go:225` `undoOps`), the second launch of the same profile sets that leftover aside as the player's own and places the archive's bytes, so the game never sees its saved settings and the session's changes are discarded when the leftover is put back, and a profile without the mod sees the orphan file; a file a mod creates during play stays shared and visible to every profile. `internal/launchsvc/sims4_trace_test.go` `TestAModsSettingsFileAcrossLaunches` asserts all three rows as they are today.

**Shape.** The shared folder is a launch's scratch space; the profile owns what a launch changes in the files it placed.

- **Changed placed file.** A placed file whose hash differs from the recorded one and that displaced nothing is, at purge, copied over the profile's copy of it and then removed from the shared folder. A file that displaced one of the player's is written back the same way before it is removed and the player's file returns. The profile's copy is the plan's `Src`: `profile.SyncPackages` (`internal/profile/deploy.go:95`) lays every package file out under `<profile>/Mods` and the folder loader plans those copies (`internal/loader/folder/folder.go:45` `Contribute`), so `deploy` needs no profile knowledge to write back. The store item stays immutable.
- **Created file.** A file created during play inside a folder an entry owns (the mod's own folder below Mods, such as `mc/`) is adopted: copied into the profile at the same relative path and removed from the shared folder. A file at the Mods root or in a folder no entry owns stays shared as the player's own, `Resource.cfg` included.
- **Next launch.** `SyncPackages` keeps a changed or adopted profile copy and the launch places it, so the game sees its saved bytes; another profile never sees the file.

**What changes, by function** (A builds these; every line number is today's):

1. `internal/deploy/deploy.go:29` `Plan` and `:49` `Manifest`: add `Owned []Owned`, each `{Dir, Into string}`, an absolute shared folder an entry owns and the absolute profile folder it maps to. `Placed` (`:36`) gains no field: its `Src` is the profile copy.
2. `internal/deploy/place.go:20-60` `Plan` (the method): copy `Owned` from the view into the plan; `Apply` (`:89`) copies `Owned` into the manifest it persists, so recovery has it.
3. `internal/loader/folder/folder.go:45` `Contribute`: for each entry folder the walk covers, add an owned pair, shared `<mods role>/<entry folder>` to profile `<profile>/Mods/<entry folder>`. `launchplan.Plan` (`internal/launchplan`) gains the list; `internal/launchsvc/pipeline.go:267` `deployProfile` and `:281` `planRoots` resolve the shared side with `game.PathFor` and pass it in `deploy.View`.
4. `internal/deploy/place.go:225` `undoOps` and `:203` `Purge`: the write-back and adoption steps below, inside `undoOps` for operations and in a new `adopt` step in `Purge` after `undoOps` and before the folder removal.
5. `internal/deploy/oplog.go`: `step` (`:20-26`) gains `W *int` (an operation's bytes are in the profile) and `A string` (an adopted file's relative path, written before its removal); `replay` (`:77`) applies `W` as "written back" so recovery does not repeat the copy.
6. `internal/deploy/place.go:268` `Recover`: replays the log, then runs the same `Purge`; nothing else.

The store file seeds a changed path only when the profile copy is missing. An adopted file is recorded with its own hash so it is neither removed as stale nor overwritten.
8. `internal/profile/foldergame.go:72` `placeFolderLocked` (update): a changed or adopted copy of a file the new archive still ships, or inside a folder the entry still owns, is kept; a changed copy of a file the new archive no longer ships is set aside under `old-files/<key>` (`internal/profile/oldfiles.go:25`, `internal/profile/update.go:368`). `:170` `rollBackFolderLocked` leaves changed copies as they are.
9. `internal/profile/ops.go:439` `removeFrom` and `:88` `removeEntryFolders`: uninstall sets the entry's changed and adopted copies aside in `old-files/<key>` before it deletes the entry's files. A deleted profile is already held whole by `internal/profile/trash.go:52` `Delete`.
10. `internal/profile/backup.go:109` `BackupDirs` and the `.mortar` export (`internal/share/file.go`): carry the changed and adopted copies as `changed/<path>` entries; restore writes them back. Share links (`internal/share/share.go`) and a LAN send (`internal/lan/protocol.go` `transferItems`) carry none: ids and store items only.
11. Docs: the Purge and Journal safety bullets in `docs/architecture.md` and the Folder games bullet gain the rule; this section is then pruned to what remains unbuilt.

**Order inside Purge and Recover** (`Recover` replays `deploy.json` then `deploy.log`, then runs these exactly; a log line is one JSON object per line, `p` placed, `u` undone, `m` folder made, new `w` written back, new `a` adopted):

1. For operation i, last to first: remove `<Dst>.mortar-tmp`. Hash `Dst`.
2. Displaced backup present: if `Dst` exists and its hash differs from the recorded one, copy `Dst` to `<Src>.mortar-tmp`, sync, rename over `Src`, append `w i`. Then remove `Dst`, return the displaced file, append `u i`.
3. Nothing displaced, hash equal to the recorded one: remove `Dst`, append `u i` (as today).
4. Nothing displaced, hash differs: copy `Dst` over `Src` through its temp file and rename, append `w i`, remove `Dst`, append `u i`. If `Src` cannot be written (the profile folder is gone), leave `Dst` shared and append nothing: no bytes are ever removed without a copy.
5. Recovery after a crash between steps: `Dst` present and `Src` equal to it (a `w` line or not) means remove `Dst`; `Dst` present and differing means repeat the copy; `Dst` absent means nothing to do. A temp file is removed in step 1 whatever else is known.
6. After all operations, for each `Owned` pair: list the shared folder; each regular file that is not an operation's `Dst` is copied into the profile folder at the same relative path through a temp file and rename, append `a <relative path>`, remove the shared file. Folders left empty are removed deepest first, as `Created` already is. A file over the cap (below) is left and reported.
7. Then the existing folder removal and journal removal (`place.go:203-223`).

**Size and time.** Adoption is capped at 64 MiB per file and 512 MiB per launch; a created file over a cap stays shared and raises a Problems row naming it (A owns `internal/problems`), so a multi-gigabyte cache or world file a mod writes is never copied on every exit. The caps are a starting choice to revisit with a measurement. Changed files need no extra hashing, since `undoOps` already hashes each placed destination. Adoption adds a directory walk of the owned folders. Against the 3,001-file profile (place about 1.5 s, purge about 75 ms with `MORTAR_SCALE=1 go test ./internal/loader/folder/ -run TestPlaceAndPurgeAThreeThousandFileProfile -v`) the unchanged case adds the walk only; each changed file adds one copy. The timing test must stay under 2 s to place and 1 s to purge.

**Traps.**
- Hard-linked destinations are never written through (`datadir.CopyFile` renames over).
- A game that deletes a placed file leaves the profile's copy as it was.
- A file a mod renames is an adoption plus an unchanged original.
- Windows holds a file open while the game runs, so write-back happens only after exit.
- Case-insensitive folders fold paths as `Plan` does (`fsx.FoldCase`).
- A profile deleted between apply and recover loses nothing: recovery leaves the shared file.
- The profile's copy path is inside the journal-independent profile folder; never write back to a store item.
- Two entries that ship the same path: the winner's copy (`packageFiles`, `internal/profile/deploy.go:26`) is the one written back; adoption goes to the entry that owns the folder by longest prefix.
- Adopt only inside owned folders; a mod that writes to `Mods` root or to the saves folder is not adopted.

**Acceptance (exact tests).**
- `internal/launchsvc/sims4_trace_test.go` `TestAModsSettingsFileAcrossLaunches` is rewritten, same builder, to assert the three rows inverted:
  1. Launch 1: the game sees `default=1`; it writes `player=2` and creates `mc/mc_state.dat`. After purge the shared `mc/mc_settings.cfg` and `mc/mc_state.dat` are gone, the profile's `Mods/mc/mc_settings.cfg` holds `player=2` and the profile holds `Mods/mc/mc_state.dat`.
  2. Launch 2 of the same profile: the game sees `player=2` and `mc_state.dat`; it writes `player=3`; after purge the profile holds `player=3` and the shared folder holds neither file.
  3. Launch of profile B without the mod: the game sees neither `mc_settings.cfg` nor `mc_state.dat`, and the shared Mods folder is as the player left it.
  4. A file the mod writes at the Mods root and the player's own `Resource.cfg` and `player.package` stay byte-identical in the shared folder through all three launches.
- `internal/deploy` kill-between-steps tables (`crash_test.go`) gain a changed-file and an adopted-file case: after a crash at each step above, `Recover` ends with the bytes in the profile's copy and not in the shared folder, and never in neither.
- `internal/profile`: `SyncPackages` keeps a changed copy and an adopted file and reseeds a missing one; an update keeps `player=3` for a still-shipped file, sets aside a dropped one under `old-files/<key>`; uninstall sets the copies aside; backup then restore round-trips them.
- `TestPurgeLeavesAFileThatIsNoLongerOurs` becomes `TestPurgeWritesBackAFileThatIsNoLongerOurs` (the rule changes from "left" to "written back, then removed from the shared folder"); `TestPurgeRemovesARewrittenPlacedFileAndReturnsTheDisplacedOne` also asserts the rewritten bytes are in the profile copy.

### Patreon source: research and open choice

The source and its window are built ([architecture.md](architecture.md#games-and-the-catalog) Patreon). The research stays here so it is not repeated: Patreon's public API v2 gives a patron identity and memberships only (scopes `identity`, `identity.memberships`; `campaigns.posts` serves a creator's own campaign), the documented post resource has no attachment field, rate limits are 100 requests per 2 seconds per client and a 30 minute block after 2,000 4xx answers in 10 minutes, and the terms limit patrons to private, authorised use and bar sharing a creation with anyone who has not purchased it. The operator skipped the live probe, so the shape stands on that documentation.
